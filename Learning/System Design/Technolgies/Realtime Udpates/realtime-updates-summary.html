★ Interview Insight
Every real-time problem splits into these two distinct hops. Solve them separately and communicate that separation clearly — most candidates blur them together.
Networking Layers (What Matters)
Layer 3 — Network

IP

Routing and addressing. Breaks data into packets. No guarantees — packets can be lost, duplicated, or reordered.

Think of it as: the postal system — delivers envelopes but doesn't guarantee arrival.

Layer 4 — Transport

TCP vs UDP

TCP — Connection-oriented. Reliable, ordered delivery. Needs 3-way handshake before data flows. State on both sides.

UDP — Connectionless. Spray and pray. Fast, no guarantees. Good for gaming/video.

Layer 7 — Application

HTTP, WS, SSE, WebRTC

What you actually code against. Sits on top of TCP. Each protocol makes different trade-offs on connection lifecycle and directionality.

Think of it as: the language you speak once the phone call is connected.

TCP Handshake — Why Latency Exists
SYN → client initiates ← SYN-ACK server agrees ACK → connection established // now HTTP can flow

Each round-trip = latency. This is why persistent connections matter — you amortize setup cost over many messages.

Load Balancer Choice Matters
L4 Load Balancer

e.g. AWS NLB

Routes at TCP level (IP + port). Acts as if client has a direct TCP connection to a single backend. Maintains persistent connections.

✓ PROS
  • Native WebSocket support
  • Fast, minimal inspection
  • Sticky connections
✗ CONS
  • No content-based routing
  • Less flexible
★ Use for WebSockets
L4 is the right choice when you need stateful persistent connections. WebSocket servers behind L4 = same TCP connection throughout.
L7 Load Balancer

e.g. AWS ALB

Terminates incoming connections, creates new ones to backend. Understands HTTP — can route on URL, headers, cookies.

✓ PROS
  • URL/header-based routing
  • SSL termination
  • Great for HTTP polling/SSE
✗ CONS
  • Spotty WebSocket support
  • More CPU intensive
★ Use for Long Polling / SSE
L7 handles HTTP-based real-time well. Just ensure your LB timeout > polling interval (e.g. LB at 60s, long-poll at 15-30s).

Long Polling

The Easy Near-Realtime

Client sends HTTP request → Server holds it open until data arrives → Server responds → Client immediately re-requests.

async function longPoll() { while (true) { const res = await fetch('/api/updates'); processData(await res.json()); // immediately fires next request } }
★ High-Freq Latency Trap
2 updates 10ms apart = update #2 can be 290ms late (90ms finish + 100ms re-request + 100ms response). Use SSE if frequency is high.

Real-world: Stripe/payment status polling before success page.

SSE — Server-Sent Events

The Efficient One-Way Street

Uses Transfer-Encoding: chunked — server keeps connection open and streams chunks. Browser's EventSource handles reconnection automatically.

// Client const es = new EventSource('/api/updates'); es.onmessage = (e) => updateUI(JSON.parse(e.data)); // Server (Express) res.setHeader('Content-Type', 'text/event-stream'); res.write(`data: ${JSON.stringify(data)}\n\n`);
★ Proxy Gotcha
Many proxies buffer streaming responses — effectively blocking your stream silently. Hard to debug! Confirm your infra supports chunked transfer.

Real-world: ChatGPT/Claude streaming tokens to browser.

WebSockets

The Full-Duplex Champion

HTTP "upgrade" handshake converts TCP connection to WS protocol. Both sides send messages freely. No headers per message = low overhead.

// Client const ws = new WebSocket('ws://api.example.com/ws'); ws.onmessage = (e) => handle(JSON.parse(e.data)); ws.onclose = () => setTimeout(reconnect, 1000);
✓ PROS
  • True bidirectional
  • Lowest overhead
  • Wide browser support
✗ CONS
  • Stateful = complex scaling
  • Deployment churn kills connections
  • Needs L4 LB ideally
★ Architecture Tip
Terminate WebSockets in a dedicated WS service early in infra. Rest of system stays stateless. WS service changes rarely = fewer connection disruptions.
WebRTC

The Peer-to-Peer Solution

Clients find each other via Signaling Server, exchange ICE candidates, then connect directly. STUN handles NAT traversal; TURN relays when direct fails.

Signaling Server → find peers → STUN → public addr → Direct P2P or TURN relay

Real-world: Zoom, Google Meet, Canva cursor presence sharing.

★ Rare in Interviews
Use only when the question clearly involves audio/video OR scale demands P2P offload. Signaling server itself needs SSE/WS — it's real-time updates all the way down!

Hop 2 — Server-Side Trigger Mechanisms
Approach 1

Pull via Polling

Client polls server → server reads from DB → DB written to by update source. Decoupled by the DB.

Update Source → DB ← Server ← Client
✓
  • Simplest possible
  • State only in DB
✗
  • High latency
  • DB hammered on idle

⚠️ 1M clients × poll/10s = 100k TPS read volume. Easy to forget.

Approach 2

Push via Consistent Hashing

Hash user ID → deterministic server assignment. Each user's persistent connection always lands on the same server. Zookeeper/etcd tracks server registry.

user_id % N → server_n
// consistent hash ring when N changes
// only affected segment reconnects
✓
  • Predictable routing
  • Minimal churn on scale
✗
  • Zookeeper coordination needed
  • Complex scaling events
★ Use When
Connections carry expensive per-user state (e.g. Google Docs: document loaded + ops applied). Worth the coordination overhead.
Approach 3

Push via Pub/Sub

Update source publishes to topic → Pub/Sub (Redis/Kafka) broadcasts → Endpoint servers subscribed forward to connected clients.

UpdateServer → Redis PubSub → EndpointServer → Client
✓
  • Stateless endpoint servers
  • Any server can serve any client
  • <10ms extra latency
✗
  • Redis = SPOF if not clustered
  • Many-to-many connections
★ Default Choice
Best balance for most systems. Use "least connections" LB strategy. Scale with Redis Cluster (shard subscriptions by key).
Consistent Hashing vs Pub/Sub — When to Choose

Use Consistent Hashing when…

  • Connection carries heavy per-user state
  • Rebuilding state on reconnect is expensive
  • E.g. Google Docs — document + ops history loaded per connection

Use Pub/Sub when…

  • Passing small messages, little server-side state
  • Need to broadcast to many subscribers
  • E.g. Chat app, live feed, Uber driver location
Common Interview Deep Dives
Deep Dive 1

Connection Failures & Reconnection

WebSockets don't always signal when they break ("zombie connections"). Use heartbeat/ping-pong to detect stale connections.

Track sequence numbers or last-event-ID per user. On reconnect, replay missed messages. Redis Streams is a popular option for this buffer.

SSE has built-in last-event-id reconnect in EventSource API. WebSockets need manual implementation.

Deep Dive 2

Celebrity / Fan-Out Problem

Elon Musk tweets → 100M users need that update. Naive fan-out = system crash.

Solution: Hierarchical aggregation. Cache update once, distribute through regional layers. Broadcast nodes aggregate writes for last N seconds before pushing to clients.

Write Processors → Root Processor → Broadcast Nodes → Clients
Deep Dive 3

Message Ordering Across Servers

Two messages sent 10ms apart can arrive out of order across distributed servers.

Simple answer: Route all messages for an entity through a single server/partition — total order becomes trivial.

Advanced: Vector clocks / logical timestamps for distributed ordering — but this is infra-level, not typical product design questions.

Deep Dive 4

WebSocket Deployment Challenges

Server restarts sever all connections. Two strategies:

Preferred: Gracefully close connections → clients reconnect to new instance. Simple, resilient.

Advanced: Zero-downtime handoff — new server takes over connections. Complex, rarely worth it.

★ Isolate WS service — changes less often = fewer restarts = less churn.

★ Interview Strategy
Interview Playbook
1
Start with polling — "I'll use simple polling here to keep things simple. We can upgrade to SSE/WebSockets if we find latency is an issue." Preserve mental energy for harder parts.
2
Name both hops explicitly — "There are two separate concerns: how the client receives updates, and how the server learns about them." Interviewers love structured thinking.
3
Don't default to WebSockets — Most candidates over-engineer. If you don't need bidirectional high-frequency, SSE is simpler, lower infra overhead, and still impressive to mention.
4
Mention load balancer implications — "We'd use an L4 LB here since WebSockets need sticky connections." This signals depth most candidates lack.
5
Manage statefulness at senior/staff level — Talk about minimizing state spread. "The WS service handles connection state; everything downstream stays stateless."
