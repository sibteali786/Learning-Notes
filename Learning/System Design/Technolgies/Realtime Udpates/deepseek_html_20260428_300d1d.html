Real-time Updates Architecture

Two‑hop model · low‑latency streaming · from TCP limitations to production ready patterns

01

Why real‑time?  — The core challenge

📌 Traditional HTTP request‑response closes connection after each response → servers cannot proactively push updates.
Even with TCP keep‑alive, the request‑reply pattern forces clients to poll. Real‑time apps require persistent, event‑driven communication with sub‑second latency.

🔵 Hop 1 (Server → Client)
How does the server push events down to browsers/apps?
WebSockets, SSE, Long Polling, WebRTC
→→→
🔴 Hop 2 (Source → Server)
How do updates (message, location, edit) reach the backend?
Polling DB · Consistent hashing · Pub/Sub (Kafka/Redis)
🤔 Why doesn’t plain TCP solve this?
Raw TCP is low‑level, lacks native browser API, doesn’t handle reconnection, authentication, or HTTP‑friendly firewalls. WebSockets/SSE build on top of TCP to provide proper messaging semantics, origin‑based security, and automatic reconnection — exactly what modern web needs.

🛡️ Failure handling, reconnection & celebrity problem

🔄 Reconnection & data loss

💡 Client stores lastSeqNum, reconnects using Last-Event-ID. Server replays missed messages from Redis stream or Kafka log.
Heartbeat mechanism (ping/pong) detects dead connections.

📌 Example: WhatsApp resume from last message ID.

⭐ Celebrity fan‑out problem

A single tweet from a global star → millions of followers must receive update simultaneously.
Solution: write‑once, fan‑out using hierarchical cache (CDN edge + regional fan‑out). Avoid writing to 10M feeds individually.

In practice: Twitter fan‑out at write time with list caching / hybrid model.
📦 Message ordering across partitions: Use Kafka with consistent partition key (ex: user_id), or vector clocks for distributed ordering. For most product designs, single partition per conversation is enough.
06

🌍 Real‑world complete architectures

🚗 Uber – live driver tracking
  • 🔹 Client → Server: HTTP POST (ride request)
  • 🔹 Server → Client (driver app): WebSocket (location every 2 sec)
  • 🔹 Propagation: Kafka Pub/Sub (positions → fleet service)
📈 Robinhood – stock ticker
  • 🔹 Client → Server: HTTP (order placement)
  • 🔹 Server → Client: SSE (price stream) – one‑way efficient
  • 🔹 Propagation: Redis Pub/Sub + cache
✍️ Google Docs – collaborative editing

WebSockets + consistent hashing (document state pinned to specific server). Operational transformation (OT) or CRDTs resolve concurrent edits. Also uses WebRTC for cursor sharing in some peer‑to‑peer cases.

07

📋 Interview cheat sheet – choose the right tool

💬 Chat / messaging
→ WebSockets + Pub/Sub (Kafka topic per user)
📊 Live dashboard
→ SSE + Redis Pub/Sub (server‑sent events)
📹 Video call
→ WebRTC + STUN/TURN
💰 Payment status
→ Long polling (infrequent completion)
📄 Collaborative doc
→ WebSockets + consistent hashing + CRDT
🚀 MVP / lean startup
→ Simple polling (save complexity, optimize later)
💡 “Start simple. Only add WebSockets when you truly need low‑latency bidirectional flow.”
📌 Key takeaway
Real‑time systems = two independent problems (client push + source propagation).
Pub/Sub + WebSockets is the most common production stack.
