Why we need it ^863Q7sKI

- Its more performant than HTTP based JSON requsts since its uses binary encoding instead of JSON.
- It uses Protocol Buffers instead of JSON ^LrJfGXHP

Protocol Buffers are a compact binary data format with a strict schema that you define upfront, which makes messages smaller on the wire and faster to parse than JSON. The biggest difference is schema and encoding. JSON is human readable and flexible but verbose, while Protobuf is typed, versionable, and binary. REST is not a format at all but an API style that usually uses HTTP and often JSON. ^IZmAeKj6

Server-Sent Events (SSE): Real-Time Push Communication ^viJbZyma

Intuition  ^fN5IUrhJ

- Unidirectional HTTP based connection
- Only server can send messages to client
- Kinda like long polling where we have no idea when it will end.
- Allows to send multiple responses to client in a single setting / connection ^Njq3rAbD

How it works ^pER0VNKB

- Client sends GET with `text/event-stream` causes server to start uni-directional server sent events.
- Server responds with `content-type` as `text/event-stream`
 ^VvzkPZWv

Limitations ^Wt58cEIa

Where to Use it ^vWf71gv8

- We can't keep an SSE connection open for too long because the server (or the load balancer, or a middle box proxy) will close down the connection.
- SSE standard defines that Event Source Object reconnects with ID of last message it sent to client when it gets closed.
- Offcourse server is expected to keep track of prior messages when its closing so it can send those missed messages when server gets closed. ^qhGlIGT2

You'll find SSE useful in system design interviews in situations where you want clients to get notifications or events as soon as they happen ^Zz15q9LW

WebSockets: Real-Time Bidirectional Communication ^rhkJeML4

Intuition ^Qyf3HAPG

- Websocket is a binary protocol
- Different from HTTP
- Client and Server both can send data to each other i.e Bi-Directional Connection
- Statefull since client and server are both aware of each other's presence
Connection is persisitent. ^aJYQkDBR

Why we need it  ^iUMmu5tu

- Http/1.0 oly allows one request and response i.e one file send, Thus need to open and close connection again n again.
- Http/1.1 allows multiple files but closes on last file is received. ^qRTccqey

How it works ^vo3hBZTj

- Create a handshake first using underlying HTTP/1.1 with `upgrade` header.
- Then server sends back `101` or `Switching Protocols` (To binary) .
- Web-sockets detach from HTTP to binary protocol after-wards.
- Since we used HTTP so we can still utilize HTTP session information like cookies, headers etc.
- Client / Server can send data to each other ^enEo0C8E

Limitations ^xzwYr0dt

Gotcha ^ndgEzx0e

WebSockets don't dictate an application protocol, you effectively have a channel where you can send binary packets to the server from the client and vice versa. This means you'll need some way of defining what it is your client and server are exchanging. For many WebSocket applications, simple serialized JSON messages are a great option! This also gives you a chance to define the API of your service for your design: ^WGHoZfX2

Where to use it ^OgQk9gU4

- when you need high-frequency, persistent, bi-directional communication between client and server. Think real-time applications, games, and other use-cases where you need to send and receive messages as soon as they happen.
- For applications where either you just need to be able to send requests and receive responses, or situations where you can make due with the push notifications provided by SSE, WebSockets are overkill. ^aATFQkpZ
