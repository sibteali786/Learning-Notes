Index Optimization Patterns ^rpAsbCcJ

- B-trees for general-purpose querying 
- hash indexes for exact matches
- geospatial indexes for location data
- inverted indexes for text search. ^OBIa1HW4

Composite Indexes ^HOENRh3S

Instead of creating separate indexes for each column, we create a single index that combines multiple columns in a specific order.  ^CupAP0jE

- Consider a typical social media feed query ^U4UGgmkb

SELECT * FROM posts 
WHERE user_id = 123 
AND created_at > '2024-01-01'
ORDER BY created_at DESC; ^rhQVEF6k

- We could create two indexes for this ^6awPYmem

CREATE INDEX idx_user ON posts(user_id);
CREATE INDEX idx_time ON posts(created_at); ^RG0cECW6

But this isn't optimal. The database would need to:

    - Use one index to find all posts by user 123
    - Use another index to find all posts after January 1st
    - Intersect these results
    - Sort the final result set by created_at ^7K7asnbY

- Instead a composite keys gives us everything in one shot ^KLql6aNW

CREATE INDEX idx_user_time ON posts(user_id, created_at); ^vxvDxOv6

How it works  ^hcDNdEvv

When we create a composite index, we're really creating a B-tree where each node's key is a concatenation of our indexed columns. For our (user_id, created_at) index, each key in the B-tree is effectively a tuple of both values. The B-tree maintains these keys in sorted order based on user_id first, then created_at. Conceptually, the keys might look like: ^4K81Xg4s

(1, 2024-01-01)
(1, 2024-01-02)
(1, 2024-01-03)
(2, 2024-01-01)
(2, 2024-01-02)
(3, 2024-01-01) ^PdcuqLZj

- Now when we query, the database can traverse the B-Tree to find
entry for user_id = 123
- Then scans sequentially through index entries for that user until it finds
entries beyond our date rang. 
- Becuase entries are already sorted by created_at within each user_id group
we get both our filtering and sorting for free.  ^sNg7llYQ

The Order Matters ^cIZoog74

- In case of composite keys the order matters alot.
- We should order columns for composite index from high selective to low selective
Selectivity = how much a column narrows down your results.
Table: 1 million orders

user_id = 5        → returns 50 rows      ← HIGH selectivity
status = 'active'  → returns 600,000 rows ← LOW selectivity

Why does this matter for leading column?
Say your index is (status, user_id) — bad order:
Step 1: WHERE status = 'active'  → still 600,000 rows to scan
Step 2: WHERE user_id = 5        → now 50 rows
You did most of the work after the index gave you 600k rows. Index barely helped.

Now flip it — (user_id, status) — good order:
Step 1: WHERE user_id = 5        → immediately 50 rows
Step 2: WHERE status = 'active'  → filter within 50 rows
Index jumped straight to 50 rows. Done.

One line rule:

Put the column that eliminates the most rows first. Why scan 600k when you can scan 50
 ^pSiY511d

Covering Indexes ^15WkNmBv

- Includes all the columns needed by our query - not only we re filtering or sorting on. ^ptpgzLIl

Intuition ^njapvH37

- Think about showing a social media feed with post timestamps and like counts.   
- With a regular index on (user_id, created_at), the database first finds matching posts in the index, then has to fetch each post's full data page just to get the like count. 
- That's a lot of extra disk reads just to display a number. ^laoKWufW

- By including `likes` column directly into our index, we can skip expensive page lookups
entirely. Databse can return everything straight from index.  ^stMowPbK

Example ^ZBKDz4If

CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    user_id INT,
    title TEXT,
    content TEXT,
    likes INT,
    created_at TIMESTAMP
);

-- Regular index
CREATE INDEX idx_user_time ON posts(user_id, created_at);

-- Covering index includes likes column
CREATE INDEX idx_user_time_likes ON posts(user_id, created_at) INCLUDE (likes); ^sq7cz91A

Trade-off ^E5JvFIMK

- The trade-off is, of course, size - covering indexes are larger because they store extra columns. 
- But for frequently-run queries that only need a few columns, the performance boost from avoiding table lookups often justifies the storage cost. 
- This is particularly true in social feeds, leaderboards, and other read-heavy features where query speed is critical. ^8HHRlCcX
