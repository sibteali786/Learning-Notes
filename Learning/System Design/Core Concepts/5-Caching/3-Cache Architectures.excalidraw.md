Cache Architectures ^iUxq6Hip

- The way we read from and write to the cache changes performance, consistency and complexity. ^8XxRW2W3

Cache-Aside (Lazy Loading) ^ohPmF80Y

- Most common caching pattern and also the default one.

How it works:

    Application checks the cache.
    If the data is there, return it.
    If not, fetch from the database, store it in the cache, and return it.

- Only caches data when needed, which keeps cache lean. 
- Downside cache miss causes extra latency. ^SyMagnt9

Write Through Cache ^dnZ5kb5A

- application only writes to cache.
- Cache then synchronously writes to the database before returning to application.
- Write operations has two parts
    1. Write to cache
    2. Write to database

Limitations and Issues

- This introduces problems like writing complex write logic ourselves for redis/ mecached as they do not support it natively to synchronise with database.

- Also Cause Dual-Write problem i.e 
What if Cache write works but database write fails ? introduces in-consistency if not dealt properly using retry-logic or failure handling.
- Pollute cache with data that may never be needed ever again. ^HWIWdWsw

Use this when reads must always return fresh data and your system can tolerate slightly slower writes. ^4VffuHnn

Write-Behind (Write-Back) Caching ^23SkNcCn

- Application only writes to cache which in turn asynchronously writes it to database ( in batches in background ) 

Example
In write-behind, the cache says success first and plans to write to the database later. Same example.


    App writes to cache

    Cache immediately returns success

    Cache will flush to database a few seconds later


Now if the cache crashes before that flush, the new email was only sitting in cache memory and never reached the database. The client already heard success, so that is real data loss.
A simple mental model is this.


    Write-through means save to cache and database now

    Write-behind means save to cache now and database later

 ^LhslmQYC

Use this when you need high write throughput and eventual consistency is acceptable. Common in analytics and metrics pipelines. ^LQzGAXUW

Read Through ^zto8ZtlA

- Similar to cache aside except cache acts as a smart proxy.
- Application never talks to database.
- If cache miss: cache itself reads from database and then writes to cache and returns to application server.


- Almost similar to write through but in terms of reading.
- In both cases cache acts as intermediary that handles database operations.
- Read through manages reads and write-through manages writes.

Limitations
- Adds a complexity to handle cache trying to acccess database in case of cache miss.

When Used

- If we think closely CDNs are read-through caches.
- When a CDN gets a cache miss, it fetches from your origin server, caches the result, and returns it. But for application-level caching with Redis, cache-aside is far more common.

- Very few reasons to propose it unless we bring CDNs or similar infrastructure. ^pjM7PrVT

Write-through writes to both cache and database, but they're separate systems without a distributed transaction. The database write could succeed while the cache write fails (or vice versa), leaving them inconsistent. Write-through reduces the window of inconsistency compared to cache-aside, but it doesn't eliminate it entirely without a distributed transaction mechanism. ^KkNxhufl
