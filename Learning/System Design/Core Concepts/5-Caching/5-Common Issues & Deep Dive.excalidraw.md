Cache Stampeded ( Thundering Herd )  ^0DgQ5ksQ

Common Caching Problems ^PVogQSLU

- Consider a home feed with 60s ttl where 100k requests are made / second
- when item expires all requests hit cache: Cache Miss so they hit database ? 
- This overwhelms database and can causes cascading failure.

How to avoid ?
Request coalescing (single flight):
- Only first request to database should work while later ones can wait and act once response from database comes.
                                OR
Cache warming:
- Refresh item from database few moments before it expires making sure it cache miss never happens.
but it works only with TTL based expiration or planned expiration, if we invalidate cache on writes instead then stampede. 
 ^ay7Pqiko

Cache Consistency ^LaSQgFDb

- most common problem in system design interviews.

Happens when
-  Cache and database return different values for same data.
- Like a user updates its profile picture in database but cache has still the older value.
- users would still get old value from cache while database has updated value.
- This would happen until cache eventually refreshes.
Here is Cache Inconsistency


No Perfect solution, we chose strategy based on fresh the data must be.
Cache invalidation on writes: 
- Delete the cache entry after updating the database so it gets repopulated with fresh data.

Short TTLs for stale tolerance: 
- Let slightly stale data live temporarily if eventual consistency is acceptable.

Accept eventual consistency: 
- For feeds, metrics, and analytics, a short delay is usually fine. Its fine if user sees old values for a while. ^sKCo0Jyy

Hot Keys  ^3PENr4QT

- specific item in cache is receiving huge amount of traffic ( like trending music, popular news, trending celebrity profile )
- Even if cache hit rate is high, a single hot key can overload one cache node or one redis shard and becomes a bottleneck.

How to handle it ? 
Replicate Hot keys:
- Store same value on multiple cache nodes and load balance across them.

Add a local fallback cache: 
- use in process-cache to store extreemely hot values. 


Apply Rate Limiting: 
- slow down abusive traffic patterns on specific keys ^x2awEN1g

In Process ^mK4hrbW2

When to bring up caching ^lBYKERJc

- Ready Heavy workloads: 
We're serving 10M daily active users, each making 20 requests/day. Thats 200M reads hitting database.
Even with indexes we are looking at 2--50ms per query.
cache drops that to under 2ms, takes most load off the database. ^teEz9WaQ

Only bring caching when we identify these problems ^XLIt61cA

- Expensive queries: 
"Computing a user's personalized feed requires joining posts, followers, and likes across multiple tables. That query takes 200ms. We can cache the computed feed for 60 seconds and serve it in 1ms from Redis."

- High database CPU: 
"Our database CPU is hitting 80% during peak hours just serving reads. The same queries run over and over. Caching the hot queries will cut database load by 70-80%."

- Latency requirements: 
"We need sub-10ms response times for the API. Database queries are taking 30-50ms. We have to cache." ^wmncWoHN
