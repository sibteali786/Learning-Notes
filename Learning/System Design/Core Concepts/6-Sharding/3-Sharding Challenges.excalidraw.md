Challenges of Sharding ^yUqfSWAd

Hot Spots and Load Imbalance ^KP1EOsin

- Even with good shard keys still some shards can end up handling more traffic than others.
This is called Hot Spot.

- It negates or nullifies the main benefit of sharding i.e to get rid of bottleneck.

Example of this

- Celebrity profile search problem. If we sharded by user_id then Messi's profile would be the most one to be visited thus it shard would become hot spot creating load imbalance among shards.

Hash Bash or Consistent Hash Based sharding wont help here since this problem is not related to distribution but some keys are more active than others.

- Time based sharding creates another kind of hot spot i.e most recent writes go to most recent shard.
- That shard handles all the write traffic while older shards sit mostly idle handling only reads of historical data. ^AVCtUonF

How to handle it ?  ^HcW8jypL

 - Isolate hot keys to a dedicated shard ( using directory based sharding ). Place messi in a dedicated shard if its causing huge traffic.
Directory based sharding in specific cases is valid solution but its not a good starting point until moments call for it.

- Compound Shard keys: we can shard keys like hash(user_id + N or created_at) where N is number of shards this would distribute user's data across shards.

- Some databases support automatically splitting a shard when it gets too large or too hot. For example, MongoDB's balancer will split and migrate range-based chunks (including when using a hashed shard key) to maintain balance. By contrast, Vitess supports online resharding, but it is operator-driven (initiated and managed by operators), not automatic. ^WNSNxMNW

Cross-Shard Operations ^OTJIKm8l

- When data lives on multiple machines and we query data that needs to visit more than one shard.
- We have to wait for all of them to respond, aggregate result and return.
- 
- This problem can arise in cases where our queries do not align with our shard keys.
- like for user_id shard key if we query "Top 10 popular posts globally" now we've to check
every shard because posts are scattered across all shards.
- You send the query to all 64 shards, wait for all 64 responses, merge the results, and then return the top 10. That's 64x the network calls and latency.

unfortuntely cross shard queries can not be eliminated entirely but can be improved. ^TmuW620p

Ways to mitigate ^hXpZ3jMQ

- Cache the results: First cache miss for "Top 10 popular posts" would be costly. then we can 
cache results for some time like 5 min, next few thousands reqs wont hit all N number of shards.
This works especially well for queries that don't need real-time accuracy (ie. eventual consistency is acceptable). Leaderboards, trending content, and aggregate stats are perfect candidates.


- Denormalize or Duplicate data, if we are visiting two shards frequently we can place same data on both, this improves read but would cost heavily for writes since when writing we will have to repeat for all shards sharing same data.

- Accept the hit for rare queries: Sometimes a query genuinely needs to hit all shards and that's okay as long as it's infrequent. An admin dashboard that shows "total users across all shards" can afford to be slow if it's only loaded a few times a day. ^sT12FZrR

In interviews, cross-shard operations are often a signal that something in your design needs rethinking. If you find yourself saying "we'll query all shards and aggregate the results" for a common use case, pause and consider: Can I denormalize to avoid this? Can I cache it? Can I precompute it with a background job? Interviewers expect you to minimize cross-shard queries, not just accept them as inevitable. ^Umq9NppW

Maintaining Consistency ^caxLdjQ5

Consistency in Sharded Systems

The Problem: Wrap two writes in one DB transaction → easy on a single DB. But what if User A is on shard 1 and User B on shard 2? No single transaction spans both. You need to coordinate independently.

    💡 e.g. transferring $100 between two users on different shards — deduct from A, credit to B. What if the credit fails after the deduct succeeds?

Solutions (best to worst):

    Design away the problem ✅ — co-locate related data under the same shard key (e.g., all of a user's data under user_id). Transactions stay single-shard.
    Saga pattern — break multi-shard ops into steps, each with a compensating action.

        Deduct A (shard 1) → Credit B (shard 2) → fail? → Refund A

    Accept eventual consistency — for non-critical data (e.g., follower counts), brief cross-shard inconsistency is fine. Shards converge eventually.
    Two-phase commit (2PC) ❌ — coordinator asks all shards to prepare, then commit. Correct but slow & fragile. Coordinator failure = system stuck. Avoided in production.

Key takeaway: Constantly needing distributed transactions → wrong shard key or wrong shard boundaries. ^sePcuOAU

Sharding in Modern Databases ^xDr4Jcc3

Key takeaway: you almost never implement sharding from scratch — pick a DB, pick a partition key, and the system handles rebalancing and routing. The only real decision is which DB fits your consistency and query model. ^91i6BYOb
