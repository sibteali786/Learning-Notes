How to Shard Your Data ^BcenZM6j

There are two things to decide when we are sharding our data. ^4OPxr5OS

What to shard by  ^X8lQhrDP

- The field / column we use to split data. Defines how data is grouped. ^xdPN4CiW

Choosing our Shard key ^QbtOnOh5

- IF we say in an interview we are sharding by [field], we should know 
    - what field to use as our shard key
    - why ^SlcG0P1o

Good Shard key ^X3fv6aAl

- High Cardinality: 
should have many unique values.
sharding by boolean field means we can have at max two shards which 
defeats the purpose.
sharding by user id when we have millions of users gives us plenty of room 
to distribute data. ^l7dzAMA0

Cardinality asks how many different labels a field can produce. More labels usually means more room to spread load. ^cVpWwNXs

Examples
A few examples make it easier.


    is_premium has low cardinality because it only has two values. true or false.

    country has medium cardinality because there may be around 200 possible values.

    user_id has high cardinality because every user can have a different value. That could mean millions of unique values. ^kKt4dBPx

- Even Distribution:
Values should spread evenly across shards.
if we shard by country maybe 90% of users are in the US, making that shard
massively larger than other.
User_id usually distributes well why ? uniqueness
Creation timestamps can work if new records don't all pile onto the most recent shard. ^Z6MdOdS1

- Aligns with queries
Most common queries should ideally hit just one shard.
if we shard by user_id queries like get user profile or get user orders hit a 
single shard.
Queries that span all shards become expensive. ^Lf4QwpmY

Examples ^DAjEkThn

For example, some good shard keys would be:
🟢 user_id for user-centric app: High cardinality (millions of users), even distribution, and most queries are scoped to a single user anyway ("show me this user's data"). Perfect fit.
🟢 order_id for an e-commerce orders table: High cardinality (millions of orders), queries are usually scoped to a specific order ("get order details", "update order status"), and orders distribute evenly over time.
Whereas bad ones could be:
🔴 is_premium (boolean): Only two possible values means only two shards. One shard gets all premium users, the other gets free users. If most users are free, that shard is overloaded.
🔴 created_at for a growing table: All new writes go to the most recent shard. That shard becomes a hot spot for writes while older shards handle almost no traffic. ^jCEDi7TK

Sharding Strategies ^mlwDdwMZ

- We have our shard key now its time to distribute that data across shard key. ^qUoGNF8a

Range based sharding ^Cq0ml9Ko

- most straightforward, just groups records by continous range of values.
- pick shard key like user_id and assign value ranges to shards

For example, if we were to shard by user_id, we might assign the first 1 million users to shard 1, the next 1 million users to shard 2, and so on. ^sILzLnot

Shard 1 → User IDs 1–1M
Shard 2 → User IDs 1M–2M
Shard 3 → User IDs 2M–3M ^uUaOlQPy

Advantage
- simplicity of implementation
- support for efficient range quries.
Example
need all orders between user_ids 500k and 600k, we only hit one shard. ^TZ3OuBi7

Most real-world access patterns don't distribute evenly across ranges. If you shard orders by created_at, almost all your traffic hits the most recent shard because users care about recent orders. New writes only go to the latest shard. Old shards sit mostly idle. ^uhnMm6OU

When does it works best ?  ^lvNznyzK

Range-based sharding works best when different users naturally query different ranges. Multi-tenant systems, for example, are a good fit. These are systems where each company gets a range of IDs. Think of a SaaS application where each client has a range of user IDs. Company A's users only query Company A's range, and Company B's users only query Company B's range. This distributes the load across shards. ^MsaFq4Xh

Hash Based Sharding ^7RMtHvIB

- uses a function distribute records across shards.
- we take shard key like user_id and hash it, modulo result to total shards and assign key to relevant shard.  ^ZEjYZSXW

shard = hash(user_id) % 4

User 42  → hash(42) % 4 = Shard 2
User 99  → hash(99) % 4 = Shard 3
User 123 → hash(123) % 4 = Shard 1 ^gi4zGHek

Example if we had 4 shards, we would route users like this ^fyf8OgdE

Advantage ^C6YVgMIy

- even distribution because hash function turns similar inputs into outputs that
look unrelated. Thus 100, 101, 102 should end up in different shards. ^EObYTt9P

Disadvantage ^vW7ukC9W

- Your instincts might have already pinched you that what would happen if number
of shards are to be increase ? modulo operation would change from %4 to %5.
- This means every record now maps to different shard that may lead to uneven
distribution if data is not moved. ^CVltVaKG

- Its solved using Consistent Hashing which minimises data movement when we add 
or remove shards. ^Ra55HdJj

In short Hash Bash sharding works great as long as we have plan for resharding. ^GxGDmKSG

Generally speaking, this is the default and most common sharding strategy. It's also what your interviewer will likely assume you're using unless you explicitly state otherwise. ^93j1d9E6

Directory Based Sharding ^vgBcDrQG

- Use a lookup table to decide where each record lives.
- Instead of using a formula we store shard assignments in mapping table or service. ^qjnuvxga

user_to_shard
---------------
User 15   → Shard 1
User 87   → Shard 4
User 204  → Shard 2 ^IuF6foHY

Advantages ^NgBIofyg

- It has flexibility, like if a user generates much traffic move them to a dedicated shard.
- If need to rebalance load just update mapping.
- Complex sharding logic can be implemented here which otherwise wont be possible in case
of hash bash sharding. ^h9dAJnbj

Downside ^TLMhvofi

- Latency -> every single request goes for lookup.
- Before we query user data we need to know which shard to loop for ( lookup table )
- If directory goes down everything halts even if shards are healthy ( single point of 
failure ). ^pwtR0TX2

Directory-based sharding makes sense when you need maximum flexibility and can afford the extra lookup cost.  ^UkEaVbc8

Realistically, while directory-based sharding is a valid solution for dynamic use cases, it is rarely the answer in a system design interview. It introduces a single point of failure and adds latency to every request, which will prompt your interviewer to ask a number of follow-up questions that could derail the conversation. ^L2SCRCTl
