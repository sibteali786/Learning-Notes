Database Modelling Options ^eD0ujX3r

- Default choice should always be Relational Databases in an interview
- Unless there is a specific reason not to. ^Llb0VvMp

Relational Databases (SQL) ^V4aIGr42

- Organise data into tables with fixed schema.
- Rows represent entities and column represent attributes
- Enforce relationship through FK ( Foreign Keys ) and provide ACID ( Atomicity, Consistency, Isolation and Durability )  ^0oaeUaiB

Gotchas ^5kYYH2u9

- Great at handling complex queries using JOINs but be careful as it can become 
performance trap.
- Make sure queries are performant enough or if we need denormalised views, caching or pre-computed results.
- Can't scale enpugh -> well no, things like read replicas, sharding, connection pooling and caching  ^OZxVNDna

- Strong Consistency is key -> Bank transactions -> SQLs ACID gurantees this ^kfK7iDfw

Right For Job ^Iem05MZT

Document Databases ^LHru4nir

- Stores data as JSON-like docs with flexible schemas
- Its more about nesting and embedding relations rather than normalising across tables ^zi2hMOpn

Good For  ^xC8OdbB3

- Rapidly evolving app where we don't know all fields upfront. ^LqRf9ld1

Example:
{
  "_id": "507f1f77bcf86cd799439011",
  "username": "john_doe",
  "email": "john@example.com",
  "posts": [
    {
      "content": "Hello, world!",
      "created_at": "2024-01-01T10:00:00Z"
    },
    {
      "content": "My first post",
      "created_at": "2024-01-01T10:05:00Z"
    }
  ],
  "created_at": "2024-01-01T10:00:00Z"
} ^Sx24lGMx

- here posts lie inside the user document
- eliminates joins but updating a post requires finding and modifying relevant user document ^w0WfpguM

System design interviews intentionally scope functional requirements to a clear, concise set. This means you're unlikely to have "evolving schemas" in the first place, which removes the main reason to choose document databases. Only consider them if your interviewer explicitly mentions rapidly changing data structures. ^N94zoC9O

When to Chose over SQL ^JvHQXeAP

- Schema changes frequently
- have deeply nested data that require JOINs in SQL
- when different records have vast different strcutures

Example: 
A user profile system where some users have extensive work histories while others have minimal data fits this pattern ^atHEmySA

- We denormalize more aggressively, embedding related data within documents to avoid expensive lookups across collections. 
- This trades storage space and update complexity for read performance. ^hFlsPywe

Data modeling impact:  ^IJPT7sAI

Key-Value Stores ^AQJPSRJX

- Provides simple lookups where we can fetch values by exact keys used to store them
- Extremely fast but limited queries ability.  ^OQhonNjP

When to Chose  ^5wdgTaFV

- For Caching 
- Session Storage
- feature flags
- scenario where need to lookup data by single identifier ( KEY )
- high write scenarios where we need maximum performance. ^1nnJBhNR

"Over SQL" is misleading here. In practice, you'll often use both together. SQL as your source of truth with a key-value cache (like Redis) in front for hot data. This gives you fast access without sacrificing durability or complex queries. ^dfmmVWUq

Data Modelling Impact ^5Lo6XMIU

- Our schema becomes very flat. 
- we'll denormalize heavily and duplicate data across multiple keys to support different access patterns
- since we can't join or query across relationships. This is great for reads but terrible for consistency when data changes. ^pYuMBcPI

Redis, DynamoDB, Memcached ^2xfEamar

Wide Column Databases ^HXN7XVeO

- organize data into column families
- where rows can have different sets of columns.
- optimized for write heavy workloads and time-series data ^gWKF2r1Z

Good For  ^75AFnUo7

- Enormus write volumes
- time series data
- Analytics worloads
where we primarily append data and run aggregations
- Telemetry, Event logging or IOT sensor data ^KEPiIHBe

- We'll design around query patterns even more than with SQL
- often duplicating data across different column families to support various access patterns. 
- Time becomes a first-class citizen in your modeling. ^sTRLNnBh

Data modeling impact: ^HTPxHqr4

Example to understand it ^Ui3C4Cy1

Wide column means each row can have its own set of columns, so rows do not all share the same shape. Picture a posts_by_user table in Cassandra where the row key is user_id. The row for user 123 has columns named by post timestamp that point to each post, maybe three columns if they wrote three posts. The row for user 456 might have only one column if they wrote once. Reads are fast because you fetch a single row and scan the newest columns for that user. Writes are fast because you just add a new column to that row. ^uwFPZJ9y

Cassanrda, HBase ^fxYa085d

MongoDB, Firestore, and CouchDB. ^4fOW7RiU

Graph Databases ^IYbdrUqv

- store data as Nodes and Edges 
- Optimised for traversing relationship entities ^ScvLzc9T

When to chose over SQL ^7mxmd9lv

- Almost never in interviews
- classic exmples are social networks and reccomendation engines but even facebook models their social graph with SQL ^ztWAa3JL

Neo4J, Amazon Neptune ^hPF4zKpo

Graph databases are a common mistake in interviews. They sound sophisticated but add unnecessary complexity. Even "graph-heavy" companies like LinkedIn and Twitter use SQL for their core relationship data. Other databases can handle the primary query patterns without the operational complexity that comes with specialized graph systems. ^bzsQAiPE
