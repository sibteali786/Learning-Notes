🎯 1. The Problem Statement

Reads are the easy half of scaling — replicas, caches, CDNs solve most of it. Writes are what interviewers actually probe, because most candidates aren't ready for that half of the conversation.

Running example: Chirp

A Twitter-like app. Users post short updates; others like/comment/view. Starting point: 1 app server → 1 Postgres DB. A modest Postgres instance handles ~10,000 writes/sec. Fine at small scale — but Chirp is growing: new country launch, a celebrity joins, a post goes viral.

Why it breaks
App servers are stateless → just add more behind a load balancer, done. The database is not stateless — it's the single bottleneck for the whole product. When it saturates, posts time out and likes fail to register — right when the app matters most.

🧱 2. Four Core Strategies (in interview order)

You rarely use all four — usually 2–3 combined. Go through them in this order: hardware/DB choice → sharding → queues/load shedding → batching/aggregation (only in extreme cases).

① Vertical Scaling & Database Choice

Use What You Have Start here

Before touching architecture: move Postgres to a bigger box (more CPU/RAM/faster disks). Skipping straight to sharding is a common candidate mistake — it signals over-engineering.

Do the math first. Modern hardware is underestimated — 200-CPU boxes with 10 Gbps networking are common. Check whether your actual required write-throughput fits on one beefy machine.

Pick the Right DB

Postgres: updates a B-tree per insert → random disk seeks → slower writes, fast/rich reads.

Cassandra: appends to a log → sequential I/O → tens of thousands of writes/sec per node, scales linearly into millions across a cluster. Trade-off: reads are slower (scans/merges multiple files).

Good fit example: Chirp "view events" (append-only, never updated) → Cassandra sweet spot. Same logic applies to time-series DBs (InfluxDB) and column stores (ClickHouse).

Caveat
Most interview rubrics are built assuming you eventually need non-vertical scaling. Make the case for a bigger box, then move on — don't stop there.

② Sharding (Horizontal Scaling)

10 servers handling a slice each ≈ 10× the throughput of one — you pay ~10× the infra cost for ~linear capacity gain.

Two questions sharding forces you to answer
1. Which shard does a piece of data go on?  ·  2. How does the app know which shard to talk to?

Picking a Partition Key — the part interviewers actually grade

Bad Partition by Country

China shard gets hammered (huge population), New Zealand shard sits idle. Uneven load defeats the purpose of sharding entirely.

Good Partition by User ID / Post ID

Pick a key with high cardinality and even distribution — usually the primary identifier of the entity being written.

Related concept — Vertical Partitioning
Sharding splits rows across servers. Vertical partitioning splits columns of the same logical entity across specialized databases, because different fields have different access patterns.

Chirp post table example: a naive design jams text, media URLs, like counts, and comment counts into one row → hammered from every direction (creation, likes, views, analytics all collide).
FieldMoves toWhy
Post text/contentPostgresWrite once, read many — B-tree indexes shine here
Like/comment countersRedisHigh-frequency in-memory increments
View/engagement eventsCassandra / column storeAppend-only stream, optimized for sequential writes

③ Queues & Load Shedding — handling bursty traffic

Real write traffic isn't steady — Black Friday, Super Bowl spikes. Auto-scaling doesn't save you here: spinning up new boxes takes minutes, and database scaling usually means downtime — the opposite of what a live traffic surge needs.

Option A — Buffer (Queue)

Put Kafka/SQS between app server and DB. App accepts the write, drops it on the queue, responds "got it" immediately. Workers drain the queue into the DB async (seconds–minutes later).

Trade-off Client only knows the write was accepted, not committed — may need a way to check status. If write rate > drain rate, the queue grows unboundedly. Queues absorb short bursts — they are not a patch for a DB that can't handle steady-state load.

Option B — Load Shedding (drop writes)

Deliberately drop the least valuable writes so the system keeps serving important ones.

Real example: Uber/Strava location pings every few seconds — dropping one stale update is harmless since a fresher one lands in seconds. A release valve that trades a slightly worse UX for a few minutes over total system collapse.

④ Batching & Hierarchical Aggregation — extreme cases only

Every write has fixed overhead (network round trip, transaction setup, index updates). Databases process batches far more efficiently than individual writes — group writes together for a free throughput win.

App-layer batching

Buffer writes in memory briefly, flush as one batch. Risk Crash mid-batch = data loss. Only safe if loss is tolerable or the source is replayable (e.g. Kafka).

New batching layer

Like batcher example: reads a window of like events, sums per post (+1+1+1 → +5, +15), forwards one write instead of 100. A chirp with 100 likes/min → 1 DB write instead of 100 (100× reduction). Only helps if a key gets multiple events per window — 1 like/hour on a 1-min window gives zero benefit.

DB-layer flush tuning

Tune how often the DB flushes memory → disk. Same safety trade-off as app-layer batching: in-memory writes die with the server.

Real example — viral Chirp thread (1M concurrent viewers)

Naive design: every viewer writes to one central service, which fans out to every other viewer → 1M-to-1 fan-in and 1-to-1M fan-out simultaneously. Ugly, but eventual consistency is fine here (everyone sees "roughly" the same feed).

Fix — Hierarchical Aggregation: assign viewers to broadcast nodes via consistent hashing (now writing to M nodes instead of N viewers). On the way in, a layer of write processors (hashed by comment ID) aggregate likes over a window and forward batches to the root, which merges them. Aggregating in + disaggregating out = dramatically less load per node, at the cost of a little extra latency from the hops.

🔍 3. The Two Deep Dives Interviewers Always Push

A. Resharding — scaling shards without downtime

Scenario
Chirp's post table has run on 8 shards for years. Busiest shard hits 80% CPU → need to double capacity to 16 shards, with zero downtime.
❌ Naive approach
Take everything offline → rehash → copy to new shards → bring back up. Hours of downtime — unacceptable in production.
1
Stand up the new 16-shard cluster alongside the old 8-shard one.
2
Dual writes — every chirp/like/view goes to both the old shard and its new home. This is the key step that prevents data loss.
3
In the background, copy historical data into the new cluster.
4
Reads keep going to the old cluster until you're confident the new one is fully caught up.
5
Flip reads over to the new cluster, then decommission the old shards.

B. Hot Keys — one key overwhelms one shard

Scenario
You've sharded well, load is spread evenly — then one celebrity chirp gets 100,000 likes/sec. One shard is on fire; the other 99 are idle.
ApproachHow it worksVerdict
Fixed key splittingSplit every key into K subkeys upfront (post1_likes_0 … post1_likes_K-1) spread across K shards.Costly always-on Multiplies dataset size by K, and every read must fan out to K subkeys and sum them — even for keys that were never hot.
Dynamic splittingMost keys stay single-shard. Writers detect a key going hot and start spreading its writes across subkeys on the fly.Efficient Read amplification (K reads) only paid on keys that actually need it. Harder: readers & writers must agree which keys are currently split.

Simple fix

Readers always check all subkeys for every key — effectively reduces to fixed splitting, but simpler to reason about.

Fancier fix

Writers announce splits as they happen (a coordination record readers consult). Lower steady-state cost, more moving parts. Most production systems in practice just check all subkeys on read.

Important limit
Both hot-key fixes only work for aggregatable data (likes, views, counts). They don't work for atomic data like a user profile — but atomic data rarely sees this kind of write pressure anyway.

🎤 4. How to Bring This Up in an Interview

Don't wait to be asked
Identify the bottleneck yourself. Right after your HLD + non-functional requirements, run back-of-envelope math on write throughput. If numbers are tame, don't over-engineer. If you're looking at millions of writes/sec, you raise scaling — not the interviewer.
1
Hardware & database choice — cheapest lever, shows judgment
2
Sharding + partition key selection — the "real" scaling lever
3
Queues / load shedding — for bursty traffic, when sharding alone isn't enough
4
Batching / hierarchical aggregation — only for the most extreme, high fan-in/out cases
Watch out
Every strategy has a trade-off — say it out loud. Queues → async + eventual consistency. Partitioning → can compromise reads. Introducing a heavy strategy to solve a problem that doesn't exist yet reads as over-engineering to the interviewer, not sophistication.

🧠 5. Glossary (so nothing is assumed)

TermPlain definition
Vertical scalingMaking one machine bigger (more CPU/RAM/disk) instead of adding more machines.
Horizontal scaling / ShardingSplitting data across many independent database instances ("shards"), each owning a slice of the data.
Partition keyThe field on a row that gets hashed to decide which shard the row lives on. Picking this well is the crux of good sharding.
Vertical partitioningSplitting columns of one logical entity across different specialized databases, as opposed to sharding which splits rows.
B-tree (Postgres)A balanced tree index structure updated on every insert — supports fast reads, but writes require random disk seeks.
Log-structured append (Cassandra)New writes are appended sequentially to a log rather than updating an index in place — much faster writes, slower reads (multiple files to merge).
Load sheddingDeliberately dropping the least valuable writes/requests during overload so the system keeps functioning for what matters.
BatchingGrouping multiple writes into one operation to amortize per-write overhead (network round trip, transaction setup, index updates).
Hierarchical aggregationUsing intermediate layers of nodes to aggregate writes on the way in and fan out reads on the way out, instead of one node handling all N clients directly.
Consistent hashingA hashing scheme where adding/removing nodes only remaps a small fraction of keys, instead of reshuffling everything (used here to assign viewers to broadcast nodes).
ReshardingIncreasing the number of shards in a live system without downtime, typically via a dual-write migration.
Dual writesDuring a migration, writing every update to both the old and new system so neither falls out of sync until cutover.
Hot keyA single key/partition that receives disproportionate traffic, overwhelming its shard while others sit idle.
Read amplificationThe cost increase on reads caused by a fix applied on the write side (e.g. needing K reads to reconstruct one value after key-splitting).
