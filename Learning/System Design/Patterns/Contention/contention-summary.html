🎯 1. The Problem — Two People, One Ticket

Contention = multiple processes competing for the same resource at the exact same instant. Two shoppers racing for the last flash-sale item, two fans hitting "buy" on the last concert ticket.

Running example: TicketMaster, last GA ticket

Naive flow: app server asks DB "how many left?" → gets 1 → checks it's >0 in app code → sends a second query to decrement. The decision happens in the app server, not atomically in the database.

Root cause — every fix targets this
Read → Modify → Write is the shape where contention lives. Any second request can slip into the gap between read and write and act on stale data. Every solution below is just a different way of making that gap safe: either collapse read+write into one atomic step (compare-and-set), or hold the data still while deciding (locking).

🧰 2. The Toolkit — In the Order You'd Reach For Them

Complexity escalates left → right. Start simple, escalate only when you actually need to — reaching for a lock when a WHERE clause would do reads as over-engineering to interviewers.

① Conditional Write — decision is a simple predicate on the row itself (counter, status flag, claim)
② Pessimistic Lock — app logic needed between read & write, collisions are common
③ Optimistic Concurrency Control — app logic needed, collisions are rare
④ Serializable Isolation — invariant spans multiple rows that never collide directly (write skew)
⑤ Distributed Lock — the hold needs to outlive a single transaction

① Conditional Writes — the tool that solves most interview contention

The fix

Stop checking in app code — let the database check as part of the write itself, via a WHERE clause:

UPDATE tickets
SET count = count - 1
WHERE count > 0;

Why it's contention-safe

Every SQL database takes an exclusive row lock automatically on any write, held until commit — this is built into ACID's Isolation guarantee. Other writers to that row simply wait their turn. (Postgres does it via single-threaded execution; DynamoDB via optimistic checks — different mechanisms, same single-writer effect.)

Bob's write runs against the row Alice already changed, not the row he originally read — his WHERE clause matches nothing, so it silently affects 0 rows.

Gotcha — "0 rows changed" ≠ failure
A conditional UPDATE that matches nothing still reports success — it just changed 0 rows. If you wrap a decrement + an INSERT (new ticket row) in one transaction, the transaction won't auto-rollback just because the decrement affected 0 rows. Fix: make the INSERT depend on the UPDATE's affected-row-count, or chain the insert off the row the update actually returned.
Gotcha — guard the thing people are actually fighting over
A WHERE clause on count > 0 guarantees a seat was left — it says nothing about which seat. If tickets are assigned seats (A15, A16...), Alice and Bob can both pass the counter check and both write a row for A15. Fix: point the conditional write at the specific contended resource (the seat row), not a proxy for it (the counter).
What this generalizes to
Decrementing inventory, flipping status available→sold, claiming an unassigned task, accepting a bid only if it's higher than current. Same shape exists outside SQL: DynamoDB conditional expressions, Redis SET NX.

② Pessimistic Locking — when the decision needs real app logic

Some decisions can't be expressed in a single WHERE clause — e.g. "find 4 adjacent open seats for a group." The decision depends on reading many rows at once, so it can't collapse into one atomic write.

Example — group of 4 wanting to sit together

Two groups both read the seat map, both land on A15–A18, both try to claim before either commits → lost update again, this time across a set of rows instead of one.

The fix — SELECT ... FOR UPDATE

Assume the conflict will happen and block up front. Every row the query returns is explicitly locked; a second group running the same query simply waits, and by the time it's their turn A15–A18 are already gone from the result set.

Other real examples
Routing a support ticket to the least-busy agent (read all agents' queue depths, pick one, lock it before anyone else grabs the same agent).
Rule of thumb
If the logic ever simplifies back down to a single WHERE-clause predicate, drop the lock and go back to a conditional write — no reason to pay the locking penalty you don't need.

③ Optimistic Concurrency Control (OCC)

Opposite bet from pessimistic locking: assume conflicts are rare, let everyone proceed, detect collisions only at commit time.

Mechanism — version numbers

Read the row, note its version (e.g. 42). On write: WHERE version = 42, and bump it to 43 in the same statement. If someone else wrote first, your WHERE clause matches nothing → 0 rows changed → you know you lost the race → retry or fail gracefully.

Same shape appears outside SQL: HTTP ETags + If-Match headers, CRDT revisions, DynamoDB's version attribute.

OCC vs Pessimistic — pick by collision rate

High collision rate → pessimistic locking (OCC's losers all retry from scratch and pile up).
Low collision rate (most e-commerce traffic) → OCC, since you happily eat the occasional retry without paying an upfront locking cost.

What NOT to use as your version — and why
CandidateRisk
Dedicated monotonic version columnSafest — increments by exactly 1 on every write. Default choice.
Last-updated timestampSafe only if clock resolution is fine enough that two rapid writes can never land on the identical value.
A business value already on the row (e.g. current highest bid)Safe only if it strictly moves one direction. Otherwise exposed to the ABA problem (value goes A→B→A, equality check sees no change — see Deep Dives).

🔀 3. Write Skew & Isolation Levels — the sneaky case

So far every conflict guarded the same row being written. Write skew is different: neither transaction writes to the same row — the conflict is hidden in what each one read.

Example — on-call schedule, "at least 1 engineer on call at all times"

Alice and Bob are both on call. Both get sick and check the schedule simultaneously. Alice reads "Bob is still on call" → decides it's safe to step down. Bob reads "Alice is still on call" → decides the same. Both commit. Nobody is on call. No single row was double-written, so a row-level lock or version check catches nothing.

Why this is easy to miss
Nothing flags that those reads are what the decision depends on. This is called write skew, and the only reliable way to catch it automatically is having the database track read/write dependencies — i.e. isolation levels.
Isolation LevelGuaranteeCatches write skew?
Read UncommittedCan see other transactions' uncommitted changes — dangerous, rarely usedNo
Read Committed (Postgres default)Only ever sees committed dataNo
Repeatable Read (MySQL default)Data you've already read stays stable for the transaction's lifeNo — common misconception! Only catches two writes on the same row.
SerializableOutcome identical to running all transactions one at a timeYes — but expensive: DB must track every read/write to detect conflicts, and aborts throw away work that must be redone.
The holy grail fix — materialize the invariant onto one row
Instead of paying for serializable isolation, restructure the problem so the conflict lands on a single row: keep an on_call_count on the team row, decrement it as part of stepping down, or take a FOR UPDATE lock on the team row before anyone leaves. Both transactions now touch the same row — back to tools you already have.

🔐 4. Distributed Locks — holds that outlive a transaction

Everything above lives inside a single DB transaction; a lock only lasts as long as that transaction. But some holds need to survive longer.

Example — holding a seat for checkout

Picking seat A15 needs to hold that seat for ~10 minutes while the buyer enters payment details. A FOR UPDATE lock can't hold that long — it would pin the DB connection for the full 10 minutes and stall every other transaction needing that row.

The idea
Instead of holding the lock as an open transaction, hold it as data — a record of who has the seat and when the hold expires. Any server can read that record with no open transaction required. Same concept as pessimistic locking, just with a lifetime beyond one transaction.

Option 1 — Redis fast, most popular

SET key value NX EX 600 — NX = set only if key doesn't exist (same safety as a conditional write); EX = TTL auto-releases the lock.

Caveat TTL expiry isn't perfectly precise — GC pauses/slow networks can cause a rare double-grant at the boundary. Harmless here since the actual purchase still goes through a conditional write. If a double-grant would corrupt data, add a fencing token (a number that climbs with every grant, checked by the resource before accepting a write).

Option 2 — Lease row in your existing DB simple, slower

New column/table: who holds the lock + expiry. Acquiring is just another conditional write (claim WHERE reservation is empty or expired) — essentially free to build. Downside: this row can become a hotspot under heavy load (10k–100k concurrent claimants) since a single DB row can't match Redis's throughput.

Option 3 — Zookeeper / etcd heavy machinery

Consensus-backed coordination, survives partitions/node failures, self-cleans on crash. Only reach for this when a double-grant is truly unacceptable and your database isn't a viable home — brings a whole new system to operate.

🧭 5. Decision Matrix

Q1: Is the check a predicate on the row being written (counter, status, claim)?
Yes → Conditional write. Done.
Q2: Decision needs app logic between read and write — how often do writes collide?
Often → Pessimistic lock (FOR UPDATE). Rarely → OCC with a version column.
Q3: Does the invariant span multiple rows that never directly collide?
→ That's write skew. Use Serializable isolation, or better: materialize the invariant onto a single row you can lock/guard normally.
Q4: Does the hold need to outlive a single transaction (e.g. a 10-min checkout window)?
→ Distributed lock. Pick its home by expected throughput and how bad a double-grant would be (Redis → DB lease row → Zookeeper/etcd, in that order of escalation).
Common mistake to avoid
Hearing "concurrency" and reflexively reaching for a heavy pessimistic or distributed lock. A single modern Postgres instance absorbs far more contention via a simple conditional write than most candidates assume. Start simple, escalate only when you hit a real limit.
Where this pattern ends
Once a single atomic operation has to span multiple databases (e.g. a transfer between accounts on different shards), you've left contention-land and entered distributed transactions — sagas, outbox pattern, etc. (covered separately in the multi-step processes pattern).

🔍 6. Deep Dives Interviewers Push On

A. Preventing Deadlocks with Pessimistic Locking

Example — simultaneous transfers

Alice sends Bob $100 while Bob sends Alice $50. Transaction A locks Alice's row, then wants Bob's. Transaction B has already locked Bob's row, then wants Alice's. Each holds what the other needs → deadlock.

❌ Tempting but wrong fix
A lock-wait timeout just repeats the problem — the retried transaction can grab locks in the same order again and deadlock again.
✅ Real fix — deterministic lock ordering
Always sort the rows you need to lock by a deterministic key (e.g. user ID) and acquire them in that order every time. Both transfers now try to lock the lower ID first — one simply waits, no cycle can form.
Bonus point to mention
Every major database detects deadlocks automatically and resolves them by killing one transaction with a catchable error you can retry. Still best practice to order locks and avoid the deadlock in the first place.

B. The ABA Problem with OCC

A value changes A → B → A between your read and your write. Within one round trip it looks unchanged — but it wasn't.

Example — Yelp review count as a naive "version"

You read a review count of 100 (using it as your OCC version). Between your read and write, someone deletes a review (99), then a new one lands (100 again). Your check "WHERE count = 100" passes — but you've just silently overwritten someone else's intervening change.

Fix
Never reuse a business value as your OCC version unless it's guaranteed monotonic in one direction. Use a dedicated version column that increments by exactly 1 on every write.

C. Scale — everyone wants the same resource at once

Example — Taylor Swift surprise show, viral collectible drop

The instinctive reflex is "shard it" — but sharding splits different rows across DBs; here everyone wants the same row, so there's nothing to split. Read replicas take load off reads, but all writes still contend for the single primary row.

1
Push back on the question first: do all these requests actually need to contend for the exact same thing? A drop of 10 different collectibles could become 10 separate rows — dividing contention by 10.
2
Ask if strict consistency is even required — can a follower count be eventually consistent / batched instead of exact-to-the-second?
3
If you genuinely need strong consistency on one hot row: put a queue in front of the database. Requests line up serially; a single worker drains and applies updates one at a time — contention disappears entirely.
The trade-off to name out loud
Queueing caps throughput to whatever speed that single worker can sustain. You can have accurate contention handling or high throughput on a hot row — not both simultaneously.

🧠 7. Glossary

TermPlain definition
ContentionMultiple processes competing to read/modify the same resource at nearly the same instant.
Lost updateTwo writers both read a stale value and both write, with the second write silently overwriting/duplicating the first's effect.
Conditional write (compare-and-set)A write that only applies if a condition on the current row state still holds, checked atomically inside the database via a WHERE clause (or DynamoDB conditional expression, Redis SET NX).
Row-level lockingA database's automatic exclusive lock on any row being written, held until commit — the mechanism that makes conditional writes safe.
Pessimistic locking (SELECT FOR UPDATE)Assume a conflict will happen; explicitly lock rows up front so no one else can act on them until you're done.
Optimistic Concurrency Control (OCC)Assume conflicts are rare; let everyone proceed, detect a conflict only at write time via a version check, and retry on failure.
Version numberA value on a row (ideally a dedicated monotonic counter) checked-and-bumped atomically on write, used by OCC to detect if the row changed since it was read.
ABA problemA value changes A→B→A between read and write; a simple equality check on the value sees no change even though one occurred — defeats naive OCC "versions."
Write skewTwo transactions each write to a different row, but each one's write invalidates the assumption the other one's decision was based on — an invariant spanning multiple rows breaks even though no single row was double-written.
Isolation levelA SQL setting controlling how much of another in-flight transaction's work is visible to you; ranges from Read Uncommitted (weakest) to Serializable (strongest, only level guaranteed to catch write skew).
Serializable isolationStrongest isolation level — guarantees the outcome is as if all transactions ran one at a time. Expensive: requires tracking all reads/writes and re-running aborted transactions.
Distributed lockA lock represented as a data record (with an expiry) rather than an open DB transaction, so it can safely outlive a single transaction's lifetime.
Fencing tokenA monotonically increasing number attached to each lock grant, used by the protected resource to reject stale/late writers even if a lock was briefly double-granted.
DeadlockTwo transactions each hold a lock the other needs, and each is waiting on the other — neither can proceed. Prevented by acquiring locks in a consistent, deterministic order.
