🎯 1. The Problem — Why This Is Hard

Real-time updates show up everywhere: Google Docs collaborative typing, Uber "your driver is ready," live comments on a stream. Candidates bungle this not because they're bad engineers, but because it touches networking concepts (WebSockets, pub/sub) most people never build from scratch.

The Two Hops framework
Break the problem into two independent sub-problems with completely different trade-offs:
  • Hop 1: How do updates get from server → client? (a networking/protocol question)
  • Hop 2: How does the update reach the specific server that's holding the connection to the right client? (a routing question — the server that generates the data often isn't the server the client is connected to)
Why Hop 2 exists — Uber example

A rider requests a driver. The rider's app is connected to Server A; the matched driver's location update might be produced by Server B. The backend has to figure out how to route "driver found" from B to A. This is a natural partition — the two hops are solved with entirely different tools.

Start here — Polling is the default
Simple, stateless, works with any infra. Most interview problems don't need sub-second updates — a stock price refreshing every 3s or a dashboard every 5s is usually fine. Ask your interviewer how real-time "real-time" needs to be before reaching for anything fancier.

Long Polling — a clever hack, with a latency catch

Instead of instantly replying "no updates," the server holds the request open until data is available or it times out. Cuts down wasted round trips — but introduces state (something you usually want to minimize) and a subtle latency problem:

SSE (Server-Sent Events)

How it works

HTTP responses don't have to arrive as one packet — a chunked encoding response type lets the browser keep the connection open and receive multiple events over time. Client side: EventSource API with a callback per event.

Server sets Content-Type: text/event-stream (and often chunked encoding), marks the response uncacheable, then keeps writing new events down the same open response.

Why it's often the best pick

Works out of the box with existing HTTP infra (just make sure your load balancer/API gateway doesn't kill long-lived connections). Unlike long polling, no callback-and-wait problem — multiple events can stream down one response. Great default for high-frequency, one-directional (server→client) pushes.

WebSockets

What it actually is
An abstraction over a raw TCP channel — bytes flow either direction, no request/response pairing required. You get TCP's guarantees (ordering, delivery ack) and build your own protocol on top (e.g. client sends subscribe, server pushes ticker_update).

Infra implications

Connections can stay open for hours, unlike SSE's periodic reconnects. Best practice: terminate WebSockets early in your infra (one dedicated service) so not every backend service needs to hold stateful connections.

Load balancer choice

Use a Layer 4 load balancer — WebSockets are a bare TCP connection, so Layer 7 features (inspecting/routing HTTP packets) don't apply. Layer 7 LBs that support WebSockets exist and are fine too; interviewers rarely grade hard on this specific choice.

When to reach for it
Bidirectional + low-latency requirements. If it's server→client only, prefer SSE — it's simpler infra.

WebRTC — narrow, esoteric, mostly skip it

Peer-to-peer connections between clients — surprisingly involves a lot of backend setup:

1
Signaling server — tells each peer who else is connectable. Can be regionalized if you never want cross-region peers. Called only during the initial handshake, so latency isn't critical here.
2
STUN — clients normally don't listen for inbound traffic (security). STUN helps open a publicly addressable port on each client.
3
Signaling server shares those public addresses between peers → clients connect directly to each other.
4
TURN (fallback) — if peer-to-peer can't be established (e.g. behind a corporate firewall), traffic is relayed through a central server — the least desirable mode, since it reintroduces the server-in-the-middle cost WebRTC was trying to avoid.
When to actually use it
Only when a server-in-the-middle's added latency/bandwidth cost is prohibitive — video calling (Google Meet) or multiplayer gaming. For nearly everything else, WebSockets are simpler (server control, no STUN/TURN, no malicious-peer risk).

Hop 1 Decision Flow

Q1: Am I truly latency-sensitive?
No (5s is fine) → Polling. Careful: a lot of production systems that "feel" real-time are actually just polling under the hood.
Q2: Is communication frequent AND bidirectional?
No (mostly server→client) → SSE (~75% of real-time use cases land here).
Q3: Do I have audio/video requirements?
Yes → WebRTC. No, but frequent + bidirectional → WebSockets (treat as last resort, not first instinct).

🧭 3. Hop 2 — Routing the Update to the Right Server

Now that the client can receive pushes, the harder question: the update was generated somewhere else in your backend — how does it find the exact server holding that client's connection?

Option A — Server-Side Polling uncommon / stopgap

The client-facing server (already connected via SSE/WebSocket) itself polls the DB for changes at its own frequency — lower latency than client polling since it's inside the data center, but still introduces latency and requires storage for updates to land in. Usually a hack when there's no time to build the full solution — interviewers expect near-zero latency, not "polling but faster."

Option B — Consistent Hashing stateful services

Mechanism

Hash a user ID onto a ring of server positions; each server owns an arc of the ring. Removing/adding a node only reshuffles the neighboring arc's users — not everyone — avoiding a load spike concentrated on one server.

Implementation pieces

Ring state store: an ordered list of servers + agreed hash function — Zookeeper (via lightweight Z-nodes) is a good fit for propagating this.
Client routing: either (a) a lightweight lookup service hashes the user and redirects them to the right server, or (b) Redis-style: client connects to any node, that node says "yes, that's me" or redirects to the correct owner.

Operational deep dives interviewers push on
  • During scaling, servers must know about both the old and new ring layout until the transition finishes.
  • Thundering herd risk: don't dump all reassigned users on the new server at once — drain connections gradually with back-pressure/feedback on uptake rate.
Trade-off to name explicitly
Consistent hashing opens a lot of deep-dive surface area (ring management, drain/thundering herd, Zookeeper dependency). If real-time delivery isn't the core focus of the problem, this complexity may not be worth it.

Option C — Pub/Sub default when services aren't already stateful

1
Client connects to any endpoint server (plain load balancer, no ring bookkeeping needed).
2
That server subscribes to a topic (e.g. the user's ID) on the pub/sub backend.
3
When an update happens elsewhere, the producing server publishes to that topic.
4
The pub/sub system pushes it to whichever endpoint server(s) are subscribed; that server forwards it down the local WebSocket/SSE connection it already holds.

Hop 2 Decision Flow

Q1: Am I latency-sensitive?
Rarely "no" if you're even considering real-time — if it is, server-side polling might suffice.
Q2: Are my services already stateful?
Yes (e.g. collaborative editor where co-editors must share a server for CRDT/OT broadcasting) → Consistent hashing.
No → Pub/Sub is the simpler default — no ring registry, no Zookeeper, connect anywhere.

🎤 5. Interview Tips

Default posture
Start with polling. Escalate only when you've justified why polling's latency isn't acceptable. Then walk Hop 1 and Hop 2 as separate decisions — don't conflate "which protocol" with "which routing strategy," they solve different problems.
What interviewers actually want
Most engineers — even good ones — haven't built this from scratch because a platform team usually owns it. The bar is knowing the menu of options and justifying your pick with a clear trade-off, not reciting a "correct" architecture from memory.

🧠 6. Glossary

TermPlain definition
Long pollingServer holds an HTTP request open until data is ready or a timeout hits, instead of replying immediately with "nothing new."
SSE (Server-Sent Events)A chunked HTTP response the browser keeps open, letting the server stream multiple discrete events down one connection. One-directional (server→client).
WebSocketA bidirectional abstraction over a raw TCP connection — no request/response pairing required, you define your own message protocol on top.
WebRTCA peer-to-peer connection protocol between clients, set up via a signaling server plus STUN/TURN; used for audio/video/gaming.
STUNA server that helps a client discover/open a publicly reachable address/port so peers can connect directly (bypasses the fact that clients don't normally listen for inbound traffic).
TURNA fallback relay server used when direct peer-to-peer (STUN) connection fails — routes all traffic through a central server, the least desirable WebRTC mode.
Consistent hashingA hashing scheme that places servers on a ring so adding/removing a node only remaps its neighboring arc of users, not the whole population.
Thundering herdA spike of simultaneous reconnections/load caused by disconnecting too many clients from a server at once — mitigated by gradual connection draining.
Pub/SubA messaging pattern where publishers send to a topic/channel and any subscribed servers receive it — decouples "who has the data" from "who holds the client connection."
Celebrity problemWhen one entity (a huge chat room, a viral post) attracts disproportionate traffic — can overload a single server if using consistent hashing to co-locate all related users.
Layer 4 vs Layer 7 load balancerL4 routes based on raw TCP/IP info (works for stateful WebSocket connections); L7 inspects HTTP-level content to route (less applicable once a connection is a bare TCP/WebSocket stream).
