01 The Problem — Why Reads Dominate
The Imbalance

Loading an Instagram feed = 100+ read ops (photo metadata, user info, likes, comment previews) vs. maybe 1 post/day per user (1 write). This pattern repeats everywhere: 1 tweet → thousands of reads, 1 Amazon product upload → hundreds of browses, YouTube serves billions of views/day on millions of uploads.

Interview note
This is often physics, not a software bug — CPU cores, memory, disk I/O are all physically bounded. More code won't fix a hardware ceiling.

03 Step 1 — Optimize Within Your Database
Indexing

O(n) → O(log n)

Index = sorted lookup table pointing to rows, like a book index. Without it: full table scan (read every row). With it: jump straight to matches.

1M row scan → ~20 index lookups.

B-tree = general queries. Hash = exact matches. Specialized = full-text/geo.

Confidently over-index
"Too many indexes slow writes" fear is overblown on modern hardware. Under-indexing kills more apps than over-indexing. Index columns you query/join/sort on.
Hardware Upgrades

Boring but Effective

  • SSD vs spinning disk: 10-100x faster random I/O
  • More RAM → more dataset cached in memory
  • Faster CPU/more cores → more concurrent queries

Mention it, but rarely what interviewer wants — sidesteps the actual question.

Denormalization

Trade Storage for Speed

Normalized data = split across tables, needs joins (expensive at scale). Denormalized = redundant data in one table, single-query reads.

-- Normalized: needs 3-way join SELECT u.name, o.order_date, p.price FROM users u JOIN orders o ... -- Denormalized: single table SELECT user_name, order_date, price FROM order_summary WHERE order_id = 12345;
Check read/write ratio first
Duplicated data (e.g. user name) means updates touch multiple places. Worth it only when reads vastly outnumber writes.

Materialized views: precompute expensive aggregations (e.g. avg rating) via background job instead of on every page load.

04 Step 2 — Scale Your Database Horizontally
Numbers to know
Rough rule of thumb: horizontal scaling (or caching) needed beyond 50,000–100,000 read requests/sec (assuming proper indexing already in place). Rough estimate — fine to justify decisions in interview.
Read Replicas

Leader-Follower Replication

Primary (leader) handles writes, secondaries (followers) handle reads. Distributes read load; bonus: promote a replica if primary fails (redundancy).

Sync
  • Strong consistency
Sync
  • Higher write latency
Async
  • Lower latency
Async
  • Replication lag — stale reads
Common question
Users may not see their own writes if reading from a lagging replica. Know the sync vs. async trade-off cold.
Database Sharding

Split the Dataset Itself

Replicas don't shrink dataset size. Sharding splits data across DBs so each query hits a smaller, faster dataset — and spreads read load.

  • Functional sharding — split by domain (users DB, products DB)
  • Geographic sharding — US data in US DBs, EU in EU DBs; faster local reads
Mostly a write-scaling tool
Sharding adds real operational complexity. For read scaling specifically, caching is usually more effective and easier to implement — reach for it first.
05 Step 3 — Add External Caching Layers
Why Caching Works

Most apps have skewed access patterns — millions read the same viral tweet, thousands view the same popular product. You're repeatedly querying identical, rarely-changing data. Caches serve pre-computed results from RAM: sub-millisecond vs tens of ms for even well-optimized DB queries.

Application-Level Caching

Redis / Memcached

Sits between app and DB. Hit → sub-ms response. Miss → query DB, populate cache. Popular data naturally stays warm; cold data falls back to DB.

Invalidation strategies:

  • TTL — simplest, tolerates some staleness
  • Write-through — update/delete cache on write; consistent, adds write latency
  • Write-behind — async invalidation queue; faster writes, brief stale window
  • Tagged — invalidate by tag (e.g. "user:123:posts"); powerful, needs tag tracking
  • Versioned keys — bump version on update, old keys naturally orphaned
TTL from requirements
"Search results ≤30s stale" → 30s TTL directly. "Profile tolerates 5min" → 5min TTL. Most production systems combine short TTL (5-15min) as safety net + active invalidation for critical data.
CDN & Edge Caching

Cache at the Edge, Globally

Modern CDNs cache dynamic content too (API responses, query results), not just static assets.

Numbers to know
Tokyo user hitting Tokyo edge vs. Virginia origin: 200ms → under 10ms. CDN caching can cut origin load by 90%+ for read-heavy apps.

Only cache shared data — product pages, public posts, search results. Never cache user-specific data (preferences, private messages) — zero hit-rate benefit, only one user ever requests it.

06 When to Use in Interviews
Core advice
Look at each external API request; for high-volume ones, plan optimization proactively. E.g. while sketching API design: "This profile endpoint gets hit every profile view — millions of users means billions of reads/day. I'll address that in the deep dive."
ScenarioStrategy
Bitly / URL Shortener Extreme ratio — shortened once, accessed millions of times. Cache short→long mapping aggressively in Redis with no expiration (URLs immutable). Add CDN for global traffic. DB only hit on cache miss for unpopular links.
Ticketmaster Event pages hammered at ticket drop. Cache event/venue/seating info aggressively — but never cache seat availability (would oversell). Read replicas for browsing, write master reserved for actual purchases.
News Feed (FB/LinkedIn/Twitter) Pre-compute feeds for active users, cache recent posts from followed users, smart pagination. Insight: users mostly read first few items — aggressive caching of recent content pays off massively.
YouTube / Video Platforms Metadata (titles, thumbnails, descriptions) cached aggressively — rarely changes. View counts can be eventually consistent (update every few minutes, not per-view). CDN extensively for thumbnails.
When NOT to Use
  • Write-heavy systems — Uber location tracking (updates every few seconds); ratio might be 2:1 or 1:1. Focus on write scaling first.
  • Small scale — "design for 1000 users" → well-indexed single DB handles thousands of QPS fine. Solve the actual problem, not the imagined one.
  • Strongly consistent systems — financial transactions, inventory. Still usable but needs aggressive invalidation + short TTLs.
  • Real-time collaborative — Google Docs needs real-time updates more than read scaling; caching actively hurts when every keystroke must be instantly visible.
Remember

Read scaling reduces database load, not just latency. If DB handles load fine but you need lower latency, that's a different problem (edge computing, service mesh optimization) — don't conflate the two.

07 Common Deep Dives
Deep Dive 1

Queries Slow as Dataset Grows

10K users → snappy. 10M users → simple lookup takes 30s, CPU pegged at 100% on basic queries. Cause: no index → full table scan on every query (2GB scan @ 200 bytes/row × 10M rows just to find one user). Joins compound this — billions of row comparisons for a simple lookup.

-- Before: Seq Scan (cost=0.00..412,000.00) EXPLAIN SELECT * FROM users WHERE email = 'x@y.com'; CREATE INDEX idx_users_email ON users(email); -- After: Index Scan (cost=0.43..8.45)

Compound queries: column order in index matters. Index on (status, created_at) helps queries filtering by status alone or both — not created_at alone.

Deep Dive 2

Millions of Concurrent Reads, Same Key

Celebrity posts → cache servers normally at 50K req/s suddenly hit 500K req/s for one key. Traditional caching assumes load spreads across keys — breaks when everyone wants the same one.

Fix 1 — Request Coalescing:

class CoalescingCache: def get(key): if key in inflight: return await inflight[key] # else fetch once, share result with all waiters

Reduces backend load from "infinite" to exactly N (one per app server), even with millions of simultaneous requesters.

Fix 2 — Cache Key Fanout:

Store identical copies under N keys (feed:x:1, feed:x:2...). Clients randomly pick one — spreads 500K req/s across 10 keys → 50K each. Trade-off: extra memory, more complex invalidation (must clear all copies).

Deep Dive 3

Cache Stampede on Expiry

100K req/s all served from a cache entry with 1hr TTL. Entry expires → all 100K requests miss simultaneously, all hit DB at once — DB sized for ~1K req/s gets 100K identical queries. Self-inflicted DDoS.

Distributed Locks
  • First request rebuilds, rest wait
Downside
  • Fragile — failed/slow rebuild = mass timeouts
Better: probabilistic early refresh
Chance of background refresh grows as entry ages (e.g. 1% at min 50, 5% at min 55, 20% at min 59 of a 60min TTL). Spreads refreshes over last 10-15min instead of one stampede at expiry. Most-critical data: continuous background refresh before expiry (never goes stale, costs extra infra + wasted work).
Deep Dive 4

Cache Invalidation, Immediate Visibility

Naive delete-on-write has real problems: which caches to clear (app/CDN/browser)? What if invalidation fails? Race: read slips in between delete and new write, re-caches stale data.

Better — Cache Versioning:

Version number stored in DB, incremented on write (in same transaction). Cache key includes version: event:123:v42 → event:123:v43. Old versions never deleted, just become unreachable — no race conditions (DB forces new version atomically), no invalidation broadcasts needed.

Trade-offs
  • 2 lookups/request (version + data)
  • Old versions accumulate — needs TTL cleanup
  • Doesn't help computed data (feeds, search)

For computed/aggregated data:

Deleted items cache — small, fast cache of recently deleted/hidden/changed IDs. Filter these out of stale feed cache while background job properly rebuilds the larger structure. Good for moderation/privacy changes.

CDN invalidation is hardest — hundreds of edge locations, propagation takes time. Critical updates: prevent CDN caching entirely via headers, trading perf for consistency.

08 Interview Strategy
Interview Playbook
1
Follow the progression — optimize (indexing, denormalization) → horizontal scale (replicas/sharding) → caching. Don't skip straight to distributed caching.
2
Index confidently — call out exactly which columns you'll index and why, while outlining schema. Under-indexing is the more common failure.
3
Justify decisions with rough numbers — "beyond 50-100K reads/sec we'd need to scale horizontally" is enough; you don't need exact figures.
4
Tie TTL to non-functional requirements — "results can be 30s stale" directly gives you the TTL. Don't pick arbitrary cache durations.
5
Flag hot endpoints proactively — pause at high-traffic endpoints during API design and note you'll address scaling in the deep dive.
6
Know when NOT to cache — write-heavy systems, small scale, strongly-consistent, or real-time collaborative apps. Shows judgment, not just pattern memorization.
