## Text Elements
GraphQL ^8D80grjP

- Emerged from Facebook in 2012 to solve over fetching or under fetching issue fro mobile applications.
- With Rest We can either Under Fetch or Over Fetch ( one endpoint returns everything ) causing the payload to be much larger than it has to be. ^eBGA3FuI

GraphQL consolidates resource endpoints into a single endpoint that accepts queries describing exactly what data we want. ^npYFUXKT

How GraphQL Works  ^8qqzV3ql

- Using same ticket-master scenario as in REST instead of separate endpoints for events, tickets and venues we have a single GraphQL endpoint ^Stc68BNM

query {
  event(id: "123") {
    name
    date
    venue {
      name
      address
    }
    tickets {
      section
      price
      available
    }
  }
} ^ymCdDqzK

When to Use GraphQL ^7Suiu7tl

- When the interviewer mentions diverse clients with different data needs.
- Like mobile apps needs different data than web App
OR
- Like avoid over fetching or under fetching

- Also a good choice when frontend needs to iterate quickly without backend changes.
- Because in REST adding a new field requires changing in backend and API deployment.
While in GraphQL we can add any new field in frontend as long as its defined in schema. ^rpZgEmdx

But this brings complexity as well like Query Parsing, Schema Validation and also complex caching strategies.

There its advised to use REST unless there is specific problem that calls for GraphQL. ^4GvCONKU

GraphQL Schema Design ^SS1sDnvC

- Instead of resource endpoints here we design a schema that defines our data types and their realtionships.
- Like for ticket master example  ^yCEPQwQ3

type Event {
  id: ID!
  name: String!
  date: DateTime!
  venue: Venue!
  tickets: [Ticket!]!
}

type Venue {
  id: ID!
  name: String!
  address: String!
}

type Query {
  event(id: ID!): Event
  events(limit: Int, after: String): [Event!]!
} ^0IGuuJ2E

- We define the realtionships directly in the schema. Like an Event has a venue so client can traverse  the relationship in a single query. ^Wr6cNmM2

Problem  ^6LScyZdK

- This flexibility introduces a problem called N+1
- When a client queries events with their venues, we might execute one query for events but for each venue of each event we will execute N queries

- for 100 events its 101 database queries since an event belongs to 1 venue, so 1 query to get 100 events and then 100 venue lookups which is 101 ^Oc28NU0t

Solution ^vnqXWn1t

- Batching / Dataloader patterns that group related queries together, BUT at cost of complexity we do not have with REST ^GKYVFSW4

Advice ^kceNu2AT

In interviews, mention GraphQL when you see clear over-fetching or under-fetching problems, but don't default to it. Most interviewers appreciate that you know about GraphQL, but they usually prefer to see you solve the core architectural challenges with simpler tools first. ^eH76I7Qr
