Common API Patterns ^acY6nZYt

Pagination ^1MiLVHvy

Why we need it ? 
In real word fetching all events would or can contain gigabytes of data
so its disaster to design such an endpoint.

Pagination helps us to break large results into manageable chunks ^X5CjNOdy

It has two types ^sd4CeUHk

Offset-Based Pagination ^T3vL8ZQ4

- Specify how many records to skip and how many to return
/events?offset=20&limit=10
- It would fetch records from 21 to 30 ^nWdvyJBe

Problem: 
For large datasets if someone adds a new event while we are pagianting through we might see duplicate results or miss records as data shifts  delete an entry at 25. ^uxBpgq6T

Cursor-based Pagination ^r62d2GpN

- It uses pointer to a specific record instead of counting from beginning 
- The pointer is usually named "Cursor"
- We send cursor in query params or sometimes in request body as well to receive data based on cursor
Example

/events?limit=10
response like  ^hk4doPgI

{
  "events": [...],
  "next_cursor": "cmd9atj3p000007ky19w1dpy2"
} ^F3tCs4E3

Next request would be /events?cursor=cmd9atj3p000007ky19w1dpy2&limit=10 ^eyauBDYS

Problem
- Complex to implement completely like Jump to Page 5 ? This would require fetching most or all ids aka cursors list and then compute page size on runtime divide into pages and with each page user clicks retreive that nextCursor to be sent to server to return results   ^GSQvq8Lf

For interviews, offset-based pagination is usually fine unless you're dealing with real-time data or the interviewer specifically asks about high-volume scenarios ^SaE0YOg4

Versioning Strategies ^4r7PHzjt

Apis evolve over time and small changes are added somtimes for testing a feature, sometimes adding new feature with a fallback that is a strategy to handle new feature without breaking existing clients ^UUINLozk

Url Versioning ^6vsXmvND

- Including version number in the path: /v1/events or /v2/events
- explicit and easy to understand
- Simple to implement
- easy re route to different code paths based on version number. ^5WJE3Fty

Header Versioning ^yCvSmOug

- Version in an HTTP header instead: `Accept-Version: v2` or `Api-Version:2`
- Keeps Url clean while conveying the idea of versioning safely with HTTP standards ^TOs9bYRk

For interviews:  ^5Frp4B4a

Url versioning is usually the safer choice bcuase its more widely understood and easier to explain quickly. Unless intervoewer explicitly asks about header versioning so better stick with URL versioning ^3yRFc6fO

Security Considerations ^lXBnASzy

- Demonstration of designing secure systems shows that we know and care how production ready systems work.
- It does not mean we go full Security Engineerbut showing basics would set us Apart ^ScRWEuc8

Authentication and Authorization ^UpH98vJv

Question: If we designed an Api : Who is making request and are they allowed to do what they are asking. ^Av2LyKal

Authentication: Verifies identity: proves the user is who they claim to be.

Authorisation: verifies permissions: checking if that authenticated user is allowed to perform the specific action they are requesting ^vM2DDsPn

Api Keys  ^4YiSsekp

For our Ticketmaster example, authentication might verify that the request comes from user "john@example.com", while authorization checks if John is allowed to cancel the specific booking he's trying to cancel (he should only be able to cancel his own bookings, not everyone's). ^XX084QBg

- long randomly generated strings that act like passwords for apps.
- Client making request includes api key in their request in authorisation header, server looks up key in database and verifies.

Perfect for Server to Server communication like two microservcies communicating.
Never a good choice for client facing APIs since it never expires and also does not have user context unlike Jwt. ^grlOGk3a

GET /events
Authorization: Bearer sk_live_abc123... ^QxN6M3NI

JWT ( JSON Web Tokens ) ^iQF99qgU

- Encode User info direclty in token rather than storing session into database
- Removes database lookup dependency 
-JWTs work particularly well for distributed systems because any service that knows your signing secret can validate tokens independently. ^qt5aaa0K

// JWT payload
{
  "user_id": "123",
  "email": "john@example.com",
  "role": "customer",
  "exp": 1640995200
} ^qcub5dNm

Use APi keys for internal service to service communication and JWT for user sessions in web and mobile since JWT can carry user info, context making ideal for user facing apps ( no database lookups ) ^KVw6M0gs

Role Based Access Control ( RBAC ) ^AF5onX5t

- Real system have different types of users with different permissions.
Like in Ticketmaster customer can book tickets, view their bookings , venue managers can create events and view sales report.  ^oheUwEXt

Roles:
- customer: can book tickets, view own bookings
- venue_manager: can create events, view sales for their venues
- admin: can access everything

User: john@example.com → Role: customer
User: manager@venue.com → Role: venue_manager ^5IL1OYuu

In an interview you'd just mention which endpoints can be accessed by which roles, though more times than not this distinction is not relevant. ^eyv1U0LM

GET /bookings/{id}
1. Is the user authenticated? (valid JWT token)
2. Is the user authorized? (owns this booking OR is admin) ^w23aGwQu

Rate Limiting and Throttling ^Mzv60eFo

- Prevents abuse by restricting how many requests a client can make in a given time period
- Protects your system from both malicious attacks and accidental overuse ^emlb8d0s

Common Strategies include 
- Per-user limits: 1000 requests/hour per authenticated user.
- Per-Ip limits: 100 request/hour for unauthenticated requests.
- Endpoint-specific limits: 10 bookings attempts/minute to prevent ticket scalping. ^3TMXeuFS

Usually implemented using Api Gateway or middleware in our application
when limits are exceeded return 429 Too Many Requests status code ^ddKvd5iH

In interviews, mentioning rate limiting shows you understand production concerns, but don't spend time designing the specific algorithms unless asked. A simple "we'll implement rate limiting to prevent abuse" is usually sufficient. ^3x0XBy3c
