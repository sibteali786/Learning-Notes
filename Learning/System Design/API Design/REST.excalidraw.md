Resource Modelling ^otuAqD6R

- Identify the resources
- Resource are usually core entities  ^X6qFN87u

Take Ticketmaster as an example. Your core entities might be events, venues, tickets, and bookings. These naturally map to REST resources: ^MPVCghnq

GET /events                    # Get all events
GET /events/{id}               # Get a specific event
GET /venues/{id}               # Get a specific venue
GET /events/{id}/tickets       # Get available tickets for an event
POST /events/{id}/bookings     # Create a new booking for an event
GET /bookings/{id}             # Get a specific booking ^liRGl463

- Rest resources should represent things not actions, like instead of thinking what users can do ( like book or purchase ) think about what exists in our system like event, venues, tickets etc ^2UqsBJyO

Resources should always be plural nouns, i.e., bookings, events, tickets, etc. ^mePKVcN7

Handling Realtionships between Resources ^IpAyow9j

- We can either nest resources when there is a clear parent child relationship.
like /events/{id}/tickets

- We can also keep resources flat and use query params for filtering
like /tickets?event_id=123  ^IrfeiEYD

Question is how to chose in between ? ^vhRzrVoS

- Key difference is whether realtionship is required or optional 

- Use Path parameters ( or nested resources ) when the value is required like /events/{id}/tickets where we always need to specify which event's tickets we want.

- Use Query params when the filter is optional - like /tickets?event_id=123&section=VIP where we might want all tickets, or tickets filtered by event or by both event and section  ^lxr0tZYw

In interviews, this distinction helps you make the right choice quickly. If the relationship is always required for the query to make sense, use a path parameter. If it's an optional filter among many possible filters, use a query parameter. The interviewer cares more about whether you can identify the right resources than perfect URL structure, but showing this understanding demonstrates good API design intuition. ^BrKQwuRS

Advice ^7X4VR6In

HTTP Methods ^ygbeiwpg

- Get ( retrieve data without changing anything )
- POST ( create new resource , its not Idempotent ) 
- Put ( replaces an entire resource with what we send ) -> Should be idempotent 
- PATCH ( updates part of a resource, like just updating email address )
- DELETE ( removes a resource ) -> Should be Idempotent ^6R4stW9d

GET, PUT, and DELETE are idempotent because calling them multiple times doesn't change the final result. POST is not idempotent, which matters when networks fail and clients retry requests. ^EV7iFKZT

Passing Data to APIs ^qfBiaxK6

- Api endpoints need to tell the server what to do that is which resource to fetch, which data to update in database or how to filter results. ^kxRYoI2r

Three options to pass data to your APIs ^9SIuKFn4

1. Path Parameters ^7MHPbRZ2

Identify which resource we are working with like when we want to get event details we put event id in the path. 
/events/123

Use path Parameters when the value is required to identify resource - without it request does not makes sense.
like without 123 we do not know which event we are talking about ^JAXocikL

2. Query Parameters ^llwBczdK

- Filter, sort or modify , how we retrieve a resource.
- When searching for events in specific city or date range we use query params. 
like /events?city=NYC&date=2024-01-01
- Works well with pagination too
like /events?page=2&limit=20 ^E7wMlkEx

3. Request Body ^RfzQE99i

- Contains actual data we are sending to create or update a resource.
- When a user books tickets, you POST to /events/{id}/bookings with the booking details in the request body. ^cePHLoSU

Each type of inputs serves a different role in APIs contract ^HmP1FG8V

- Path parameters are structural, they determine which endpoint you're hitting. 
- Query parameters are modifiers, they change how the endpoint behaves.
- Request body is payload, it's the data you're actually working with. ^1gaLAqAD

Returning Data ^I6DO515n

An API response is made up of two parts:

- The status code, which indicates whether the request was successful or not.

- The response body, which contains the data you're returning to the client (typically JSON) ^zZLEj1Zs

Don't overthink this in interviews - interviewers care more about whether you understand the difference between client errors (4xx) and server errors (5xx) than memorizing every status code. Even using X's to obscure the status code is typically totally fine. ^KIQZGI0C
