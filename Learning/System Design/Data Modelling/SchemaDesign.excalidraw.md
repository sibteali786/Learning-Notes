Start with Requirements ^FCpKVL0x

- Gather requirements about the system itself. It has 3 key factors ^Asfnk8Rj

Data Volume ^JFbldTvP

- determine where data lives
Sometimes all data stays in one place, others its spread across different zones or even each entity is stored spearetly for some reasons ^zbB3JipC

Access Patterns ^YEkBaw6I

- How will our data be queried 
like
- A news feed that loads " recent posts by followed users " suggests denormalised data or performant indexes
OR 
An analytics dashboard that aggregates data across time period might need different table structures entirely ^dHcyKSlZ

Consistency Requirements ^3FLux1L1

- how tightly coupled our data can be.
like 
- Financial transactions need strong consistency, keeps related data in same database with ACID gurantees.
- A user's feed can handle eventual consistency ( its okay if a like shows up few seconds later, which can allow us to distribute data across different systems with maybe different schemas optimized for different access patterns ^sCemlcm6

In interviews, explicitly tie your schema choices back to these factors. For example, "Since we need to load feeds quickly and likes can be eventually consistent, I'll denormalize like counts into the posts table." That shows you're reasoning instead of memorizing patterns. ^7XxoQwzD

Eventual Consistency
A consistency model where, given enough time without new updates, all replicas will eventually return the same value. Prioritizes availability over immediate consistency. ^Rs4WKkwd

Entities, Keys and Relationships ^HIX9CFhn

- For a social media app, you might have users, posts, comments, and likes. Each entity needs a primary key to identify individual records. ^SIOzSQGZ

users: id (PK), username, email
posts: id (PK), user_id (FK → users.id), content, created_at
comments: id (PK), post_id (FK → posts.id), user_id (FK → users.id), content
likes: user_id (FK → users.id), post_id (FK → posts.id) ^OPcLmhYS

- This shows the core relationships: each post belongs to one user (posts.user_id), each comment belongs to one post and one user, and likes connect users to posts. ^lfaesqTq

In interviews, just pick an obvious primary key and explain why. "post_id will be our primary key so we can uniquely identify each post and reference it from comments and likes." ^T1jLYENv

After entities we define relationships between them ^SfsCrYL9

- One-to-many (1:N): a user has many posts, a post has many comments.

- Many-to-many (N:M): users like many posts, posts are liked by many users.

- One-to-one (1:1): rare in practice, often a sign that two tables should just be merged. ^TrlcietS

- These are enforced through Foreign Keys: they help ensure referential integrity - meaning they prevent orphaned records like a post referencing a user that does not exists or comments poiting to deleted posts ^8jjOwNp8

- They come at a cost since with each insert / update database has to validate it.
- Thus thye might be dropped at large scale for write performance
- Integrity than is dealt at application level. ^QocGPWeL

Constraints ^YPTEN5bf

- NOT NULL, UNIQUE or CHECK
- enforce correctness at database level ( emails must be unique,  price must be positive )
- Add write overhead.  ^4Ylzs8jc

- Keeping our schema ground in the problem domain is good so we ap entities to real life data 
when modelling twitter , Users, Tweets and follows are logical entities.
- We should have abstract entities and relationships, we should correctly identify primary and
 foreign keys so we can have correct realtionships defined.  ^fdItBdSF

Indexing for Access Patterns ^S9ifEC3C

- Indexes are data structures that help database find records quickly without scanning 
- These are likes table of content of a book ^cHSdcP3O

Your indexes should directly support your most important queries. For a social media app:

- Index on posts.user_id to quickly find all posts by a user
- Index on posts.created_at to load recent posts chronologically
- Composite index on (user_id, created_at) to efficiently load a user's recent posts
 ^uQ65HAIk

In interviews, connect your indexes directly to your API endpoints. "The GET /users/{id}/posts endpoint needs an index on posts.user_id" shows you're thinking about real query performance. ^aigJHI40

Normalisation Vs Denormalisation ^FBw8WAFr

- Storing data in exactly one place
User data lives only in the users table not duplicated across other tables  ^FRsiAS6t

- Update should happen only in one place and conveyed to other accordingly ^8ytvIMGg

- In the denormalized version if user changes their username, we also have to 
update every single post they've ever made otherwise it introduces inconsistency ^cbJOZ6Gp

- Start with normalization first and only denormalise when needed.
- Avoid repeating data in schema as it introduces consistency problems ^Na3zzxYd

Exceptions for denormalisation ^lZGsROD2

- Analytics and reporting systems where you're aggregating data that changes infrequently
- Event logs and audit trails where you're capturing a snapshot of data at a point in time
- Heavily read-optimized systems like search engines where consistency is less critical than speed ^yousvryR

Even if you need denormalized quick access for performance, you can just put a cache in front that has a denormalized representation of the data. Your source of truth stays clean and normalized, but your cache can have pre-computed joins, aggregations, or whatever structure makes reads fast. ^1WnpvvcW

Scaling and Sharding ^FXGzuswO

- When data grows large for single database, we shard it across multiple machines
- Key is to chose a partition strategy that keeps related data together ^nh1pkI6D

Shard by the primary key access pattern ^zu7FNBaw

- If mostly we query "posts by users" sharding by user_id would keep all user posts on same database, avoiding expensive cross shard queries ^zRUejcUZ

Be careful with time-range sharding. While it sounds appealing for "recent posts" queries, all current writes hit the same shard (the latest time range), creating a hot shard. This is usually an anti-pattern for write-heavy systems. Time range partitiong works for use cases where every nw entry is not going get stored in a single shard making it HOT Shard. It can be painful in social media feed whee each new post goes to same partition making it HOT shard ^dCQV6enS

Avoid cross shard queries ^xnkHG3hZ

- whenever possible.
- If your timeline feature needs to show posts from multiple users a user follows, and you've sharded by user_id, you'll have to query multiple shards and merge results. This is expensive and complex.
 ^8N2x6mvI

Start by outlining your core entities early in the interview. Then, when introducing a database component during the high-level design:

    Determine the type of database you'll use
    List the columns needed to fulfill the functional requirements for each entity
    Specify primary and foreign keys for each relationship
    Determine which columns need indexes (if any)
    Determine whether you need to denormalize for performance
    Consider whether sharding is necessary. If yes, choose a shard key that matches your main access pattern.
 ^pjLHapGy

Conclusion ^g9AZla8V
