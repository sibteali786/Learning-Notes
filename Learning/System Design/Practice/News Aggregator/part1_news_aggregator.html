📰 News Aggregator (Google News) — Requirements → HLD

Hello Interview walkthrough, part 1 — the setup before we start deep-diving

100M DAU · spikes to 500M <200ms feed latency Availability > Consistency

🧭 Understanding the Problem

Google News aggregates articles from thousands of publishers into a scrollable feed — it never hosts content itself, only links out.

✅ Functional Requirements

  • View aggregated feed from thousands of publishers worldwide
  • Infinitely scroll the feed
  • Click article → redirect to publisher's site
  • Personalized feed (out of scope — later added as bonus deep dive)
  • Save articles / share on social (out of scope)

⚖️ Non-Functional Requirements

  • Availability > Consistency (CAP theorem) — stale news beats no news
  • Scale to 100M DAU, spikes to 500M
  • Feed loads in < 200ms
  • Privacy, monitoring, publisher-API resilience (out of scope)

🧱 Defining the Core Entities

Start broad — relationships and purpose matter more than every column at this stage.

Article — id, title, summary, thumbnailUrl, publishDate, publisherId, region, mediaUrls Publisher — id, name, url, feedUrl, region User — id, region (from IP or explicit)

🔌 API / System Interface

GET /feed?page={page}&limit={limit}®ion={region} → Article[]
Offset pagination is a starting placeholder — it breaks under scroll + new content, so it gets replaced with cursor-based pagination in Deep Dive #1 (see Part 2). No endpoint is needed to "read" an article — the browser simply navigates to article.url when clicked.

🏗️ High-Level Design (v1)

Requirement 1 — Aggregated feed from thousands of publishers

Why this is two problems, not one: collecting content from publishers and serving it to users are separate concerns. We start with collection.

Data Collection Service — polls publisher RSS feeds/APIs every 3–6 hrs based on each publisher's update frequency Publishers — thousands of sources worldwide via RSS/APIs Database — stores articles, publishers, metadata Object Storage — stores article thumbnails

🙋 You asked: what is an RSS feed?
A publisher-provided, machine-readable list of recent articles — usually XML — with each article's title, link, and publish time. Your Data Collection Service sends an HTTP request to the feed URL and gets back structured data, letting your system discover new articles without scraping web pages.

Requirement 2 — Infinite scroll

How: client calls /feed?page=1&limit=20, then page=2, etc. Feed Service computes the offset (page-1)*limit and the database runs a query with OFFSET and LIMIT. Simple foundation, but has real performance/consistency limitations addressed later.

Requirement 3 — Click article → redirect to publisher

Why it's easy: the browser handles it — when a user clicks, it redirects to the url field stored on the Article. Aggregators like this never host content themselves. (In the real product, this click would also be tracked for analytics/recommendations — out of scope here.)

v1 satisfies the functional requirements but is naive: every feed request hits the DB directly, and offset pagination breaks under scroll + new content. Both become the first two deep dives. → Continue to Part 2: Deep Dives → Final Design
