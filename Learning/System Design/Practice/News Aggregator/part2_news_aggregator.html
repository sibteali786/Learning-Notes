1️⃣ How can we improve pagination consistency and efficiency?

Why this matters: with thousands of publishers posting 50–100 articles/hour during peak periods, offset pagination causes "pagination drift" — a user scrolling for 10 minutes can see duplicate articles or miss new ones, because the offsets shift as new content is inserted above.
GoodTimestamp-Based Cursors
Approach (how)

Return a cursor = the timestamp of the last article in the response. Next request: WHERE published_at < cursor_timestamp ORDER BY published_at DESC LIMIT 20. Since we're always querying relative to a fixed point in time (not a shifting offset), new articles published above don't affect older pagination. An index on published_at keeps this efficient.

Challenges

Breaks when multiple articles share an identical timestamp — common when publishers batch-import or auto-timestamp articles. Querying "before X" can silently skip articles stamped at exactly X, creating gaps that worsen during high-volume periods.

GreatComposite Cursor (timestamp + article_id)
Approach (how)

Combine timestamp and article ID into one cursor, e.g. 2024-01-15T10:30:00Z_article123. Query: WHERE (published_at, article_id) < (cursor_timestamp, cursor_id) ORDER BY published_at DESC, article_id DESC LIMIT 20 using SQL tuple comparison. A composite index on (published_at, article_id) keeps it fast at scale, and the article ID breaks any timestamp ties, giving total ordering.

Challenges

Slightly more complex cursor encoding/decoding logic in the app layer; marginally more complex queries (though DBs handle tuple comparisons efficiently); a bit more storage for the wider composite index — negligible against the consistency gained.

GreatMonotonically Increasing Article IDs
Approach (how)

Design IDs to increase monotonically from the start — time-ordered UUIDs (ULIDs) or DB auto-increment — instead of random UUIDs. Since articles are collected chronologically, newer articles always get higher IDs. Pagination collapses to WHERE article_id < cursor_id ORDER BY article_id DESC LIMIT 20 — a single cursor value, no composite logic, no timestamp handling, just a simple index on article_id.

Challenges

Must be planned upfront — migrating an existing random-UUID system to monotonic IDs is a real data migration. In distributed systems, ID generation must be coordinated across instances to preserve ordering (ULID generation or a centralized ID service handles this).

2️⃣ How do we achieve low latency (< 200ms) feed requests?

Why this matters: 100M DAU refreshing 5–10x/day = 500M–1B feed requests daily. Querying millions of articles and filtering by region on every request, even indexed, blows past the 200ms budget.
GoodRedis Cache with TTL
Approach (how)

Cache recent articles per region in Redis sorted sets (feed:US, feed:UK...) with a TTL (e.g. 30 min) on the whole feed key (not per-article — sorted sets don't support per-member TTL). Cache-aside pattern: on miss, query DB, populate cache, return; subsequent requests hit cache until expiry.

Challenges

Cache misses still trigger expensive DB queries that can violate latency requirements. The 30-min TTL means users may not see new articles for up to 30 minutes — violates freshness for a news platform. On expiry, every user requesting that region hits the DB simultaneously (thundering herd), degrading performance for minutes while the cache repopulates. Response times become inconsistent (fast on hit, slow on miss/refresh).

GreatReal-time Cached Feeds with CDC
Approach (how)

Data Collection Service stores a new article in the DB → this triggers a CDC (Change Data Capture) event. Feed Generation Workers consume that event, determine which regional feeds it belongs to, and add it via ZADD feed:US <timestamp> <article_id> — score = timestamp, so ordering is automatic. No TTL needed; instead cap growth with ZREMRANGEBYRANK feed:US 0 -2001 right after each ZADD, keeping only the newest ~2,000 per region. Reads become pure ZREVRANGE feed:US 0 19 calls, completing well under 5ms because sorted sets are skip-list backed — O(log N + M) for N=2,000, M=20.

Challenges

Added complexity in the ingestion/generation pipeline — need CDC infra, message queues, and worker processes, all requiring monitoring. Storage costs rise slightly from duplicating article data into caches (bounded by the size limit). Must handle cache corruption or worker failures with robust rebuild/error-handling logic. Despite this, it's the pattern major news/social platforms actually use because it balances performance and freshness best.

🙋 Where do Feed Generation Workers fit in — they weren't in the v1 HLD?
Correct — v1 kept caching simple. This deep dive is exactly where they're introduced: a CDC stream sits between the DB and these workers. The Data Collection Service fetches & saves articles; workers react afterward to place articles into ready-to-read Redis feeds. This decouples ingestion from cache-serving, so a slow scrape never blocks a fast read.
🙋 Is Redis access really under 1ms, and is ZREVRANGE 5ms end-to-end?
Redis itself: ~0.1–1ms in-region — "<200ms" in the article is the full request budget (network + app + serialization), not Redis alone. Same idea for "ZREVRANGE completes under 5ms" — that's the isolated command time, not the full round trip to the client. The speed comes from sorted sets' O(log N + M) range reads.
🙋 Do we have documented replication lag numbers for Redis/DB read replicas?
No — don't state a fixed number. Lag depends on write volume, network distance, replica load, and failures. Route correctness-sensitive reads to the primary; route feed reads (tolerant of slight staleness) to replicas.

3️⃣ How do we ensure articles appear in feeds within 30 minutes of publication?

Why this matters: polling every 3–6 hours means breaking news is already stale by the time it's discovered — users have seen it elsewhere first. A modern feed needs to surface major stories within minutes.
GoodIncreased RSS Polling Frequency (tiered)
Approach (how)

Tiered polling by publisher priority: high-priority (CNN, BBC, Reuters — historically frequent, breaking-heavy) polled every 5–10 min; medium every 30 min; low (weekly magazines, niche) every 2–3 hrs. Separate worker processes per tier; high-priority workers run continuous loops sleeping only 5–10 min between cycles, comparing article GUIDs/timestamps against the DB and using ETags/Last-Modified headers to skip unchanged feeds.

Challenges

With 10,000+ publishers, high-priority polling every 5–10 min means 100,000+ HTTP requests/hour (vs. 2,000–3,000 today) — higher cost and risk of overwhelming/blocking smaller publishers' servers. Still fundamentally reactive: even 5-min polling adds up to 5 min + processing delay. Critically, not all publishers have RSS feeds — many newer sites have limited or none.

GoodIntelligent Web Scraping
Approach (how)

For publishers without (good) RSS, run crawlers over homepages/category pages looking for article links (classes like "article-headline", "story-link"), extracting URL/title/timestamp. A fingerprint DB (URL hash or content checksum) identifies genuinely new content; full content gets extracted and normalized into the standard Article format, feeding the same pipeline as RSS. Same tiered scheduling idea — high-traffic sites scraped every 10–15 min, smaller sites hourly.

Challenges

High maintenance overhead — sites change HTML structure and break extraction logic. Slower and less reliable than RSS parsing, plus legal concerns for sites that prohibit scraping. Used strategically as a fallback, not the primary method.

GreatPublisher Webhooks with Fallback Polling
Approach (how)

Flip pull→push: build POST /webhooks/article-published that publishers call the moment they publish, with metadata or full content. A high-availability endpoint absorbs spikes when multiple publishers notify simultaneously; validates payloads, extracts data, queues into the same standard ingestion pipeline; webhook auth via shared secrets/API keys prevents spam. Content from webhook-enabled publishers can appear in feeds within ~30 seconds of publication. RSS polling and scraping remain as fallback for publishers who don't support webhooks — a hybrid system.

Challenges

Requires coordination/buy-in from publishers — can't be implemented unilaterally like polling or scraping. Smaller publishers may lack the technical resources or be reluctant to add external integration dependencies. Good candidate for a back-and-forth with the interviewer: can I black box ingestion? Do publishers maintain RSS? Given our scale, would publishers implement webhooks for us?

🙋 What does "ingestion" and the "ingestion pipeline" mean here?
Ingestion = bringing outside data into the system to process/store — interviewers let you "black box" it so you can focus on serving. The referenced ingestion pipeline is the same flow used after RSS polling or scraping — the webhook just supplies the raw data at the front:
webhook payload→ validate→ normalize to Article→ store thumbnail (S3)→ save to DB→ CDC event→ Feed Generation Workers update Redis

Final strategy = hybrid: RSS for cooperative publishers, scraping for no-RSS publishers, webhooks for premium/high-volume partnerships.

4️⃣ How do we handle media content (images/videos) efficiently?

Why this matters: since we link out to publishers rather than hosting articles, we only need thumbnails — but at 100M+ DAU even thumbnail delivery must be fast and cheap. We keep our own copies because publisher image URLs can be slow, change, or go down.
BadDatabase Blob Storage
Approach (how)

Download and resize the primary image (e.g. 300x200) at collection time, store the binary directly in the database alongside article metadata.

Challenges

Even 20–50KB thumbnails multiplied by millions of articles bloat the DB — slow queries, huge backups, memory consumed by image bytes instead of query performance. Doesn't scale past a few thousand articles. Rule of thumb: databases store structured data; large binary blobs belong in object storage.

GoodS3 Storage with Direct Links
Approach (how)

Store thumbnails in S3, reference the URL in the article's metadata. During collection: download original → generate thumbnail (300x200) → upload to S3 → store URL. Thumbnails load directly from S3 to the browser, off-loading the app servers. This is what's in the v1 HLD.

Challenges

Global users far from the S3 region see high latency. S3 egress costs add up across millions of daily thumbnail views. No adaptation for screen density (retina vs. standard) or slow networks.

GreatS3 + CloudFront CDN with Multiple Sizes
Approach (how)

Same S3 storage, but served through CloudFront for global edge distribution. Generate multiple sizes (150x100 mobile, 300x200 desktop, 600x400 retina) and use srcset or client logic to pick the right version per device/density. CDN edge caching gets sub-200ms loads worldwide.

Challenges

Higher storage cost for multiple variants — minor compared to the performance gain. CDN caching cuts S3 requests by 90%+, lowering overall cost while improving UX.

5️⃣ How do we handle traffic spikes during breaking news?

Why this matters: elections, disasters, celebrity news can spike normal 100M DAU traffic to (an intentionally aggressive, interview-style estimate of) 10M concurrent users within minutes — everyone wants the latest update at once.

Key advantage: news is naturally region-partitionable — Americans want US news, Europeans want EU news. So instead of one massive global system, we build several smaller regional systems, each assumed to handle 10M concurrent users at peak, and scale each component to that number.

Feed Service (application layer)
How

A single server handles roughly 10,000–100,000 concurrent connections — nowhere near 10M. Solution: horizontal scaling — many stateless Feed Service instances behind load balancers, with cloud auto-scaling triggered by CPU/memory thresholds. Because the service is stateless, instances spin up/down in seconds, paying only for capacity during the spike.

Database layer
How

A single DB instance can't handle 10M concurrent reads — I/O, network, and CPU all bottleneck regardless of hardware upgrades. The existing cache (from Deep Dive #2) already absorbs essentially all read traffic, so the scaling challenge shifts entirely from the database to the cache layer.

Cache layer (Redis)
How

A single Redis instance serves ~100k requests/sec. Math: 10M concurrent ÷ 100k req/s per instance ≈ 100 Redis instances needed (fewer in practice — not every region is equally popular, so scale per-region on demand). Since each region only holds ~2,000 recent articles, no complex sharding is needed — this is purely a read-throughput problem, solved with master + read replicas: writes (new articles, cache updates) go to master; reads are load-balanced (round-robin / least-connections) across replicas; Redis Sentinel auto-promotes a replica if the master fails. (If not using Redis: same idea via consistent hashing + replicas per shard.)

Challenges / trade-offs

More infrastructure to provision and monitor per region; replicas must be spun up ahead of predictable spikes (or fast enough during unpredictable ones) and scaled back down after, to control cost.

          ┌── Replica 1 ──▶ reads
Master ───┼── Replica 2 ──▶ reads
 (writes) ├── Replica N ──▶ reads
          └── Sentinel: auto-promotes a replica if master fails
Regional clusters give sub-50ms cache responses from the nearest cluster; a spike in one region doesn't affect others; each region scales independently based on local demand — during breaking news, affected regions add replicas while others stay at baseline.
🙋 Do we have a documented replication lag number for Redis/DB read replicas?
No — don't quote a fixed number. It depends on write volume, network distance, replica load, and failure conditions. In an interview: state that lag is usually low in normal operation but replicas can be stale, so route correctness-sensitive reads to primary and use replicas for feeds where slight staleness is fine.

6️⃣ Bonus: How can we support category-based feeds (Sports, Politics, Tech...)?

Why this matters: real platforms organize into 25+ categories with hundreds of articles/day each. At 100M DAU that's up to 10M category-specific requests during peak (e.g. Sports during a big game) — the existing regional-only cache can't filter this granularly without hammering the database.
BadDatabase Query Filtering with a Category Column
Approach (how)

Add a category column to Article, extracted during ingestion from RSS <category> tags, webpage structure, or keyword matching. Feed Service queries WHERE region='US' AND category='sports' ORDER BY published_at DESC LIMIT 20 with a composite index on (region, category, published_at).

Challenges

50M peak requests = 50M DB operations; connection pools exhaust under concurrent load even with indexing. Caching is awkward — 25 categories × 10 regions = 250 cache-key combinations, each with its own invalidation pattern; misses still trigger expensive filtered queries.

GoodPre-computed Category Feeds in Redis
Approach (how)

Extend the existing Redis regional caching with per-category-per-region sorted sets: feed:sports:US, feed:politics:UK, etc. During ingestion, Feed Generation Workers categorize each article and update multiple sorted sets simultaneously (e.g. a US sports article goes into both feed:US and feed:sports:US). A request becomes ZREVRANGE feed:sports:US 0 19 — under 5ms.

Challenges

25 categories × 10 regions = 250+ sorted sets to maintain instead of 10 — significant memory growth (~1,000–2,000 articles each). Cache invalidation gets more complex since one article can belong to multiple sets, requiring coordinated cleanup; heavy publishing volume can make cache maintenance impact read performance.

GreatIn-Memory Filtering of the Regional Cache
Approach (how)

Store full article metadata (not just IDs) as JSON in the existing feed:US cache, including a category field, e.g.:

{
  "id": "123",
  "title": "NBA Finals Game 7 Results",
  "description": "Warriors defeat Celtics in thrilling finale",
  "url": "https://espn.com/nba/finals/game7",
  "category": "sports",
  "region": "US",
  "published_at": "2024-06-21T22:30:00Z"
}

A category request pulls the top ~1,000 from ZREVRANGE feed:US 0 999 (under 10ms) and filters in application memory for category === "sports" (1–2ms), then paginates. No new cache keys — the existing CDC pipeline just needs to include category in the cached payload.

Challenges

Requires enough article volume per category within the top 1,000 regional articles to return 20–50 relevant results — fine for well-represented categories, could be thinner for niche ones. Considered the pragmatic choice: "the best solution is often the most straightforward one."

7️⃣ Bonus: How do we generate personalized feeds based on user reading behavior?

Why this matters: a single regional feed is one-size-fits-all; users expect content prioritizing topics/publishers they engage with. (The actual scoring model is usually ML — abstracted away here; this isn't an MLE interview.)
BadReal-time Recommendation Scoring
Approach (how)

Maintain user profiles (reading history, topic preferences, behavior); on each feed request, score recent articles against the profile in real time using topic match, publisher preference, freshness, and collaborative filtering ("users who read A and B also engage with C").

Challenges

Scoring thousands of articles against 100M profiles is billions of calculations per hour — takes seconds, not the 200ms budget. Cost and latency degrade catastrophically exactly when traffic spikes (many users wanting personalization simultaneously).

GoodPre-computed User Feed Caches
Approach (how)

Pre-compute personalized feeds per active user in Redis, e.g. feed:user:12345. Background workers continuously update these as new articles arrive, scoring by relevance to that user's interests/behavior rather than pure recency, blending explicit preferences (subscribed topics, publishers) with implicit signals (clicks, reading time, shares). Active users get dedicated caches; inactive users fall back to category caches generated on demand.

Challenges

Memory explodes: 1,000 articles/user × 50M active users = 50 billion cache entries — 200–500x larger than category caching alone. Personalized feeds can go stale as interests shift, and may miss globally important breaking news that everyone should see.

GreatHybrid Personalization with Dynamic Feed Assembly
Approach (how)

Store a lightweight preference vector per user (just kilobytes), and assemble a personalized feed on-demand by mixing existing pre-computed category caches — e.g. a tech-interested user gets 60% feed:technology:US + 30% feed:business:US + 10% feed:trending:US, with the mixing ratio driven by their preference vector. During breaking news, the system temporarily boosts trending-content weight while retaining personal preferences. This reuses the category cache infrastructure from Deep Dive #6, cutting memory needs by ~100x versus per-user caches — a few hundred category caches instead of 100M user caches. ML can tune mixing ratios from engagement over time.

Challenges

Less personalization depth than a full recommendation engine. Assembly ratios need careful tuning — too narrow and users miss important global stories; too broad and it feels generic. Balances individual relevance against editorial/global importance while holding the sub-200ms budget.
