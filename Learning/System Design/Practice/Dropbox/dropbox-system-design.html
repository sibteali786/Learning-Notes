☁️ Designing Dropbox

System Design Interview Visual Summary

1. Requirements

✅ Functional (in scope)

  • Upload a file from any device
  • Download a file from any device
  • Share a file with other users, view shared files
  • Automatically sync files across devices
Out of scope: editing files, viewing without downloading, blob-storage internals

⚙️ Non-Functional

  • Availability > Consistency (eventual consistency is fine)
  • Support files up to 50GB
  • Secure & reliable — recoverable if lost/corrupted
  • Low latency upload / download / sync
Out of scope: storage quotas, versioning, virus scanning
Why availability > consistency: Unlike a stock-trading app (where a buy in Germany must replicate before a buy in the US), Dropbox is fine if a file uploaded in Germany takes a few extra seconds to appear for a user in the US.

2. Core Entities

📄 Filethe raw bytes
🏷️ FileMetadataname, size, mimeType, owner
👤 Userthe account holder

3. API Surface

POST/files — upload File + FileMetadata
GET/files/{fileId} — download File & FileMetadata
POST/files/{fileId}/share — share with User[]
GET/files/changes?since={timestamp} — poll ChangeEvent[] for sync
Auth (session token / JWT) always travels in headers, never the request body — prevents client tampering with identity.

4. High-Level Architecture

Key idea: File Service never touches file bytes — it only signs URLs. Uploads/downloads flow client ⇄ S3/CDN directly, keeping the backend out of the data path.

5. Feature Walkthroughs

① Upload

Client requests a presigned URL from File Service → uploads bytes straight to S3 → S3 fires a completion notification → metadata status flips to "uploaded".

② Download

File Service checks permissions → issues a CDN-signed URL → CDN serves from edge cache (fetching from S3 on first miss).

③ Share

Owner adds a user's email to the file's ACL → a row is written to the SharedFiles table (userId, fileId) → download requests check this table for authorization.

④ Sync (Local ⇄ Remote)

Local→Remote: OS file-watcher (FSEvents/FileSystemWatcher) detects change → queues upload → last-write-wins on conflict.
Remote→Local: Hybrid — WebSocket push for real-time change events, plus periodic GET /files/changes?since= polling as a reliability safety net.

6. Deep Dive — Large File Uploads (50GB)

Why a single POST fails

ProblemDetail
Timeouts50GB @ 100Mbps ≈ 1.1 hours — far past typical server/client timeouts
Payload limitsAPI Gateway caps requests at ~10MB
Network dropsAny interruption forces a full restart
UXNo progress feedback

Solution: Client-side chunking + S3 Multipart Upload

  • File split into 5–10MB chunks on the client (never the server — that defeats the purpose)
  • SHA-256 fingerprint per file and per chunk → enables dedup + resume
  • chunks[] array tracked in FileMetadata (uploaded / uploading / not-uploaded)
  • Backend calls S3 CreateMultipartUpload → presigned URL per part → client uploads in parallel → CompleteMultipartUpload assembles the object
{
  "id": "123", "name": "file.txt", "status": "uploading",
  "chunks": [
    {"id": "chunk1", "status": "uploaded"},
    {"id": "chunk2", "status": "uploading"},
    {"id": "chunk3", "status": "not-uploaded"}
  ]
}
Resumability in practice: User's laptop dies at 40GB. On reopening, client re-fingerprints the file, backend sees a matching in-progress upload, and only the remaining ~10GB of chunks are sent — not the whole file again.

Speed: chunking, CDC & compression

  • Parallel chunk upload maximizes available bandwidth
  • Content-Defined Chunking (rolling hash) instead of fixed-size chunks — a 1-byte edit near the start of a file only reshuffles nearby chunk boundaries, not every chunk after it, so delta sync stays cheap
  • Client-side compression (Zstandard/Brotli/Gzip) — big win for text, negligible for already-compressed media like JPEG/PNG/MP4
  • Always compress before encrypt — encrypted data is random and doesn't compress well

Security

  • In transit: HTTPS everywhere
  • At rest: S3 server-side encryption
  • Access control: SharedFiles table acts as the ACL
  • Signed URLs: short-lived (~5 min) bearer tokens for CDN/S3 access — limits blast radius if a link leaks, though anyone holding it before expiry can still use it

7. Interview Bar by Level

🟢 Mid-level (E4)

Define API + data model, land a working high-level design for upload/download/share. Not expected to independently know presigned URLs or chunking, but should reason to them when prompted.

🔵 Senior (E5)

Moves fast through the high-level design to spend real time on large-file upload deep dive; proactively discusses multipart upload and trade-offs.

🟣 Staff+ (E6+)

Breezes through the basics; drives depth on CDC, compression ordering, resumability internals, and security trade-offs from real experience. Interviewer intervenes only to focus, not to steer.
