PART 1 — Requirements → High-Level Design

~15 minutes of a 45-minute interview

🗺️ The Interview Roadmap

Follow this order for any user-facing product design interview:

1
Requirements — functional (features) + non-functional (qualities)
2
Core entities — what data is persisted/exchanged
3
APIs — client-facing endpoints that satisfy the functional requirements
4
High-level design — simplest architecture that satisfies functional requirements
5
Deep dives — go deeper to satisfy the non-functional requirements

Work backwards through the user flow to find the 3 core features:

⚖️ Non-Functional Requirements

The #1 mistake candidates make here
Just writing "scalability," "availability," "reliability" as bare words. Every system has those qualities — that's not interesting to an interviewer. The value is in identifying what makes THIS system unique, in context.

CAP Theorem — Consistency vs Availability

Mid-level answer "Prioritize consistency" — no double-booking, one seat can't go to two people.

Senior-level answer These aren't mutually exclusive across different parts of the system: strong consistency for booking, but high availability for search/viewing — it's fine if a just-added event doesn't show up for a couple seconds, it's not fine if two people both think a seat is free.

Read:Write Ratio

Far more people search/view than actually buy — roughly 100:1 (maybe even 1000:1) if the booking conversion rate is ~1%. This has real design consequences (caching, search infra) covered in the deep dives.

Query Access Pattern

Traffic is normally light and even — until a Taylor Swift tour or World Cup goes on sale, and you get tens to hundreds of millions of people hitting the same handful of events at once. Scalability here specifically means handling surges from popular events, not generic "the system should scale."

Explicitly Out of Scope

GDPR compliance, general fault tolerance, etc. — note these below the line rather than ignoring them silently. Then check in: "Here's what I'm prioritizing and what I've left out of scope — want me to reprioritize anything?"

Interview tip: checking in like this signals product thinking and focus — you know the full landscape but you're deliberately scoping.

🧱 Core Entities

Spend ~2 minutes here — just get the shape right, don't over-specify fields yet (they'll evolve naturally once you're in the HLD).

Event

The thing being sold — added by admins (out of scope here).

Venue

Where the event is hosted (stadium, arena).

Performer

Who's performing.

Ticket

One per seat per event — availability, purchaser, price all live here.

A 5th entity worth naming explicitly — Booking / Reservation
The transcript builds this implicitly rather than naming it up front: booking a ticket isn't just a status flip on the Ticket row, it's its own concept with a lifecycle (who reserved it, when, has payment been confirmed). In an interview it's worth calling this out as its own entity — Booking: id, ticketId, userId, status (reserved/confirmed/expired), reservedAt, paymentIntentId — even if, as the design evolves, its state ends up split between the Ticket row (for the final booked status + owning user) and the distributed lock in Redis (for the temporary 10-minute hold). Naming it early avoids conflating "a ticket" (the seat/inventory) with "a booking" (one user's claim on that seat, which can expire or fail).

🔌 API Design

For each functional requirement, derive an endpoint. Exchange the core entities as payloads.

View an Event

GET /event/{eventId}
→ { event, venue, performer, tickets[] }

Returns everything needed to render the page: event details + venue + performer (via joins) + the ticket list to draw the seat map.

Search for Events

GET /search?term={text}&location={lat,lng}&type={category}&dateRange={...}
→ PartialEvent[]

Returns partial events (name, description, performer) — just enough for search-result cards; clicking one hits the full GET /event/{id}.

Book a Ticket — Two-Phase Process

Why two phases
Just like TicketMaster or an airline booking flow in real life: pick a seat → it's held for you (e.g. 10 minutes) → you go to a payment page → confirm. A single "book" endpoint misses this — flagging the two-phase nature is a strong signal in an interview, but not disqualifying if you miss it initially (interviewer will nudge you). 
PUT /booking/reserve         body: { ticketId }
PUT /booking/confirm         body: { ticketId, paymentDetails }
Security detail worth stating out loud
No userId in the request body. Putting it there lets anyone forge a request "on behalf of" another user. User identity comes from the auth header (JWT / session token) instead — small detail, but it signals technical maturity.

Confirm hands off payment to Stripe (payment intents); Stripe processes asynchronously and calls back via a registered webhook rather than responding to your original request directly.

🏗️ High-Level Design

Architecture choice: microservices behind an API Gateway (routing + auth + rate limiting) — the default, safe choice for these interviews unless you have a strong reason otherwise.

① Viewing an Event

Client → API Gateway → Event CRUD Service → Postgres. Reads the event, joins venue + performer, includes the ticket list. Simple.

Postgres field sketch (evolves naturally as you design)
TableKey fields
Eventid, venueId (FK), performerId (FK), name, description, … , tickets (1-to-many)
Venueid, location, seat map, …
Performerid, …
Ticketid, eventId (FK), seat, price, status (available/reserved/booked)
SQL vs NoSQL — the senior-level framing
Postgres chosen here for ACID transactions on tickets + the relational joins (event↔venue↔performer). But the SQL-vs-NoSQL debate itself is largely outdated — most modern NoSQL DBs (e.g. DynamoDB) can offer ACID guarantees too. A senior candidate names the qualities they need (transactions, relationships) rather than picking a side in an old debate. Either family could work here.

② Searching for Events

Naive first pass, intentionally left rough to fix in deep dives:

SELECT * FROM events WHERE type IN (...) AND name LIKE '%term%'
Why this is bad
The wildcard LIKE forces a full table scan on every search. Call this out explicitly in the interview and say you'll come back to optimize it once the functional requirements are satisfied — that sequencing itself is a good signal.

③ Booking a Ticket (happy path first)

1
Reserve: PUT /booking/reserve {ticketId} → update the ticket row's status to reserved → return 200.
2
Confirm: client goes to payment page → PUT /booking/confirm {ticketId, paymentDetails} → Booking Service calls Stripe → Stripe processes async and calls back via webhook.
3
On successful payment: update ticket status → booked, attach userId. (Sending a confirmation email etc. — out of scope.)

⏱️ The Reservation Expiry Problem — 3 Evolving Solutions

The bug in the happy path
What if the user closes their laptop mid-payment, or the 10-minute window lapses? Status stays reserved forever — that seat is infinitely locked away from everyone else. This is the single most important thing interviewers watch for candidates to catch.
① Timestamp check Confusing data model
Add a reservedTimestamp column. Read query becomes WHERE status='available' OR (status='reserved' AND reservedTimestamp < now() - 10min). Works, but the row's status field lies about reality — two fields now need to stay conceptually consistent with each other, which is fragile and confusing.
② Cron job Passing for mid-level, not senior
A job runs every ~10 minutes, finds all reserved tickets past their timestamp, flips them back to available.
The problem: introduces a drift window Δ between when a ticket should free up and when the cron actually runs. If it should expire at 12:00 but cron runs at 12:09, that seat was wrongly locked for 19 minutes instead of 10 — bad for a high-surge system.
③ Distributed lock (Redis) — the senior-level answer Real-time, elegant
Drop the status/timestamp columns entirely for reservation purposes. On reserve: write ticketId → true into Redis with a TTL of 10 minutes — nothing touches Postgres at reserve time. On expiry, Redis auto-deletes the key — instantly, no polling delay.
To check availability: query Postgres for status='available' tickets, then cross-reference each against the Redis lock — anything currently locked gets excluded from what's shown to the client.
Why Redis specifically, not just an in-memory map in the Booking Service?
The Booking Service horizontally scales to multiple instances. They all need a single consistent view of which tickets are locked — an in-process map on one instance wouldn't be visible to the others. A shared external store (Redis) gives every instance the same view.
Deep-dive question interviewers love: what if the Redis lock goes down?
Bring up a new instance immediately — but any reservations made in roughly the last 10 minutes are lost, so several users could simultaneously reach the payment page for the same seat. Postgres's ACID guarantees on the final status write still prevent double-booking — whoever's confirm-purchase write lands first wins, the other gets an error. Consistency is preserved; a small window of users just get a bad experience. Worth explicitly flagging this trade-off to the interviewer/product team rather than silently assuming it away.

PART 2 — Deep Dives

Where senior/staff candidates earn their keep — go 1–3 levels deep, not everywhere

Interview tip: Process for choosing where to go deep — look back at your non-functional requirements and find what's still unmet. Here: low-latency search (never addressed) and scalability for popular-event surges (only partially addressed) are the two obvious gaps.

🔍 Deep Dive 1: Low-Latency Search

Why the current solution is slow
The LIKE '%term%' query forces a full table scan across every event row on every search.

Elasticsearch — the standard fix

Builds an inverted index: tokenize event text (name, description) into terms, map each term → the documents (events) containing it.

Worked example

"The Philadelphia Eagles are playing in a wild card matchup against the Broncos" tokenizes into terms like Philadelphia, Eagles, playoff, wildcard. A search for "playoff" instantly returns every event whose index contains that term — no table scan. Elasticsearch also supports geospatial queries (via quad-trees/geohashing) so location + term + date can all be combined efficiently.

Keeping Elasticsearch in sync with Postgres

Important caveat
Don't use Elasticsearch as your primary data store — weak durability guarantees and no real transaction support (learned the hard way from real production experience, per the source).
Sync methodHowTrade-off
Dual write in app codeOn event write, write to Postgres and Elasticsearch in the same code path.Simple, but you own the failure logic — what happens if the ES write fails after Postgres succeeds? Needs retry/rollback handling.
Change Data Capture (CDC)Changes to Postgres are emitted onto a stream; a consumer applies them to Elasticsearch.Decouples the two stores. Often abstracted as a black box in interviews — fine to note that abstraction explicitly. Elasticsearch has a write-rate ceiling (index updates per write), so high-volume domains would need batching/queueing — not needed here since events/venues/performers change rarely (an admin adds maybe thousands a day, at most).

Making popular searches (Taylor Swift) even faster — caching layers

Key precondition for caching
No personalized ranking/recommendations in this system — two users searching the same term get identical results. That's what makes caching safe and effective here.

Node/shard query cache

If using AWS OpenSearch (managed Elasticsearch), each shard can cache its top ~10K queries (LRU) — often just a config flag. Quick and easy.

Redis / Memcached

Cache a normalized search term → results. Requires explicit invalidation on relevant updates.

CDN (the pick made here)

Cache the search API response itself for a short TTL (30s–1min), geographically close to users — very fast, and infra you likely already have for static assets.

CDN caching's real limitation
Works great with few, coarse query parameters (city-level location). Breaks down with high-cardinality parameters like raw lat/lng — near-zero cache-hit overlap between users, so you're just wasting CDN space. Also stops working entirely the moment the system adds personalized recommendations, since then identical queries should return different results per user.

📈 Deep Dive 2: Real-Time Seat Map & Traffic Surges

Problem — a stale seat map

The client loads the seat map once via the view-event call. Seconds to minutes later, other users have booked seats — the client's view is now stale, and users click on seats that error out. Bad experience, worse at scale.

Making the map real-time

OptionFit
Long pollingSimplest Cheap, no extra infra, request held ~30s–1min in a loop. Great if users are on the page for a few minutes.
SSE (Server-Sent Events)Better for long sessions Persistent, server→client only push — exactly what's needed here (client never needs to push seat data back over this channel). Preferred over WebSockets since bidirectionality isn't required.
Interview tip: the choice between these should be justified by data — if analytics show users linger 5–30+ minutes on this page, the more sophisticated persistent-connection approach earns its complexity; for short visits, long polling suffices. (See the separate Real-Time Updates pattern reference for the full protocol decision tree.)

The real problem at extreme scale — the "instant sellout blackout"

Taylor Swift / Super Bowl / World Cup scenario

100,000–1,000,000 people hit the event page simultaneously, fighting over 10,000–100,000 seats. The seat map loads, then goes black within milliseconds as everything gets booked — a terrible experience even with real-time updates working correctly.

Solution — Virtual Waiting Queue

The core idea
Introduce a choke point in front of the backend to protect it and improve UX — instead of everyone hitting the event page at once, they enter a queue and get a "you're in line, we'll notify you" message.
1
Feature is opt-in/admin-enabled — only turned on for events expected to surge.
2
Queue implemented in Redis — a sorted set as a priority queue by arrival time (or randomized for fairness, so users geographically closer to your servers don't have an unfair head start).
3
Event-driven admission: as seats get booked (e.g. every time 100 book), pull the next batch of users off the queue.
4
Notify admitted users over the same SSE connection already established — they're let into the event page to actually book.
Why this deep dive is a great one to lead with
It demonstrates that the best answer isn't always the most technically complex one — a virtual queue is conceptually simple (a Redis sorted set + event-driven admission) but elegantly solves a genuinely hard UX and load problem. Signals maturity, not just technical vocabulary.

⚙️ General Scaling, Sharding & Caching

On back-of-envelope math — a deliberate choice
The source intentionally skips generic QPS/DAU/storage math right after non-functional requirements — doing math with no bearing on the design ("it's a lot, so it's a big system") teaches the interviewer nothing about you. Only calculate when the result will directly change a design decision — e.g. sizing whether Postgres needs sharding, done at the point in the design where that decision actually matters.

Compute scaling

API Gateway and each microservice sit behind managed load balancers (e.g. AWS-managed), scaling horizontally on CPU/memory automatically. This part of the conversation is usually the least interesting — call it out briefly and move on.

Database sharding — if the math says you need it

Natural shard key candidates: event ID (matches the majority of query patterns) or venue ID (if there's strong geographic correlation between users and nearby venues, letting you distribute shards geographically). No universally right answer — a trade-off discussion with the interviewer.

Reducing read load — cache aggressively

Given the ~100:1 read:write ratio, and that event/venue/performer records rarely change: cache them heavily in Redis (event ID → event+venue+performer). No eviction policy even strictly needed if the working set is small enough, or bound it to upcoming events only. Only ticket status stays uncached, since it's the genuinely dynamic piece.

Net effect

The view-event call becomes very fast: static metadata served from cache, only the dynamic ticket-availability portion hits the database/lock layer.

🏁 Wrap-up & How This Gets Graded

LevelBar to clear
Mid-levelComplete HLD satisfying the 3 functional requirements; the cron-job version of reservation expiry is a passing answer. Bonus if you reach the Redis lock. Expect the interviewer to prompt you toward scaling/search questions rather than you leading there yourself.
SeniorReach the Redis distributed lock unprompted; lead 1–3 deep dives yourself (search + surge handling is a strong pair); explicitly separate consistency needs (booking) from availability needs (search/view).
Staff / PrincipalSame technical depth as senior, plus demonstrated judgment: knowing when math matters, pushing back appropriately, framing trade-offs as product conversations (e.g. "is this UX degradation during a lock outage acceptable?") rather than purely technical choices.
Final self-check before ending the interview
Can you say "yes" to both: does this design satisfy every functional requirement? Does it satisfy every non-functional requirement? If yes to both, you're in good shape.

🧠 Glossary

TermPlain definition
Functional requirementA feature/capability of the system — phrased as "users should be able to ___."
Non-functional requirementA quality of the system (consistency, availability, latency, scale) — most valuable when tied to what's actually unique about this specific system, not generic buzzwords.
CAP theoremA distributed system can't simultaneously guarantee Consistency, Availability, and Partition tolerance — you pick which to prioritize under a network partition. Different subsystems can make different choices.
Two-phase bookingReserve (temporary hold) → Confirm (payment finalizes it) — mirrors real airline/ticket booking flows, avoids permanently locking a seat before payment is guaranteed.
Distributed lock (TTL-based)A lock represented as a key with an expiry in a shared store (e.g. Redis), visible to all instances of a horizontally-scaled service, auto-releasing without needing a background job.
Cron-job expiry drift (Δ)The gap between when a reservation *should* expire and when a periodic job actually notices and expires it — grows with the job's interval, a key weakness of the cron approach.
Inverted indexA search-index structure mapping each term to the set of documents containing it, enabling near-instant term lookups instead of scanning every document (used by Elasticsearch).
Change Data Capture (CDC)A pattern where changes to a primary datastore are emitted onto a stream, consumed by a worker to propagate the change elsewhere (e.g. into a search index) — decouples the write path from the sync logic.
Virtual waiting queueA choke point placed in front of a high-demand resource; users are queued (e.g. in a Redis sorted set) and admitted in controlled batches rather than all hitting the backend simultaneously.
Long pollingClient holds an HTTP request open; server responds when new data is ready or a timeout hits — cheap, no new infra, good for shorter sessions.
SSE (Server-Sent Events)A persistent, one-directional (server→client) HTTP connection for pushing updates — fits the seat-map use case since the client never needs to push data back over that channel.
Sharding keyThe field a database is partitioned on; choice should follow the dominant query pattern (e.g. event ID) or a distribution goal (e.g. venue ID for geographic locality).
"Math without a purpose"Back-of-envelope estimation done reflexively rather than to inform an actual design decision — the source explicitly advises against this as a box-checking exercise.
