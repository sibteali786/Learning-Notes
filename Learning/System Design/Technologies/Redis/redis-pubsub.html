The Problem It Solves

Normally, if service A wants to tell service B "something happened," A needs to know B exists and how to reach it. Pub/Sub removes that coupling.

Publisher
→
channel: "news.tech"
→
Subscriber A
Publisher
→
x
→
Subscriber B

Publishers send messages into a channel with zero awareness of who — if anyone — is listening. Subscribers listen to channels with zero awareness of who is publishing. Neither side needs the other's identity.

Uncommon Terms Explained

RESP (REdis Serialization Protocol)

The wire format Redis clients and servers speak. Every request and reply is encoded as simple typed lines — no JSON, no binary blobs. RESP2 is the classic version; RESP3 (opt-in via HELLO 3) adds richer types and, importantly for Pub/Sub, lets a subscribed client run any command instead of being restricted to a handful.

Array reply

A RESP reply type representing an ordered list of other replies. Every Pub/Sub push (a subscribe confirmation, an incoming message) is a 3-element array reply. In raw RESP it looks like *3 (array of 3) followed by each element.

Integer reply

A RESP reply that's just a number, prefixed with : on the wire. PUBLISH returns an integer reply — the count of clients that received the message.

Bulk string ($) vs Simple string (+)

In RESP, $9\r\nsubscribe\r\n is a bulk string (length-prefixed, binary-safe) — this is how channel names and message payloads are sent. A simple string uses + and is for short fixed replies like +OK.

Why this matters: when you see raw SUBSCRIBE traffic on the wire, you're reading RESP directly — no client library in between. Understanding it makes debugging with redis-cli --no-raw or a raw TCP dump actually readable.

Command Reference

since 2.0.0
SUBSCRIBE
SUBSCRIBE channel [channel ...]
@pubsub@slow O(N) — N = channels subscribed

Arguments: one or more channel names (required).

Behavior: enters the client into "subscribed" state. Once subscribed, a RESP2 client can only issue PING, PSUBSCRIBE, PUNSUBSCRIBE, QUIT, RESET, SSUBSCRIBE, SUBSCRIBE, SUNSUBSCRIBE, UNSUBSCRIBE. A RESP3 client (via HELLO 3) can run anything.

Return: no direct return value — instead, for each channel, one array-reply push arrives: ["subscribe", channel, count] where count is the total channels+patterns you're now subscribed to.

# subscribe to two channels
SUBSCRIBE channel11 ch:00
# pushes back:
1) "subscribe"  2) "channel11"  3) (integer) 1
1) "subscribe"  2) "ch:00"      3) (integer) 2
since 2.0.0
UNSUBSCRIBE
UNSUBSCRIBE [channel [channel ...]]
@pubsub@slow O(N) — N = channels to unsubscribe

Arguments: zero or more channel names (all optional). No arguments → unsubscribe from every channel.

Return: one array-reply push per channel: ["unsubscribe", channel, count]. When count hits 0, the client has fully exited Pub/Sub state and can run ordinary commands again.

UNSUBSCRIBE
1) "unsubscribe"  2) "second"  3) (integer) 1
1) "unsubscribe"  2) "first"   3) (integer) 0
redis-cli gotcha: inside redis-cli's subscribed mode you cannot type UNSUBSCRIBE interactively — the CLI won't accept any command while subscribed. You must Ctrl-C out.
since 2.0.0
PSUBSCRIBE
PSUBSCRIBE pattern [pattern ...]
@pubsub@slow O(N) — N = patterns to subscribe

Arguments: one or more glob-style patterns (required) — e.g. news.*, user.???.login.

Behavior: subscribes to every channel whose name matches the glob pattern, present or future. Same "subscribed state" restrictions as SUBSCRIBE apply.

Return: array-reply push per pattern: ["psubscribe", pattern, count].

PSUBSCRIBE news.*
# matches: news.art.figurative, news.music.jazz, news.tech...
since 2.0.0
PUNSUBSCRIBE
PUNSUBSCRIBE [pattern [pattern ...]]
@pubsub@slow O(N) — N = patterns to unsubscribe

Arguments: zero or more patterns. No arguments → unsubscribe from all patterns (channel subscriptions are untouched).

Return: array-reply push per pattern: ["punsubscribe", pattern, count].

PUNSUBSCRIBE news.*
# only affects the "news.*" pattern subscription, nothing else
since 2.0.0
PUBLISH
PUBLISH channel message
@pubsub@fast O(N+M) — N clients on channel, M patterns subscribed cluster-wide

Arguments: channel (the target), message (the payload) — both required.

Return: Integer reply — the number of clients the message was delivered to. In Redis Cluster, only clients connected to the same node as the publisher are counted.

PUBLISH second Hello
(integer) 1   # one subscriber received it

A client subscribed to both foo (exact) and f* (pattern) will receive a published message to foo twice — once as message, once as pmessage.

since 2.8.0
PUBSUB <subcommand>
PUBSUB CHANNELS [pattern] | PUBSUB NUMSUB [channel...] | PUBSUB NUMPAT
@pubsub@slow

Introspection commands — they don't subscribe you to anything, they just report the server's current Pub/Sub state.

SubcommandArgsReturns
PUBSUB CHANNELS [pattern]optional glob patternArray of active channel names (channels with ≥1 subscriber) matching the pattern, or all if omitted
PUBSUB NUMSUB [ch ...]zero or more channel namesArray alternating channel, subscriber-count pairs
PUBSUB NUMPATnoneInteger reply — total number of pattern subscriptions across all clients
PUBSUB CHANNELS news.*
1) "news.tech"
2) "news.jazz"

PUBSUB NUMSUB news.tech news.jazz
1) "news.tech"  2) (integer) 3
3) "news.jazz"  4) (integer) 1

PUBSUB NUMPAT
(integer) 2

Message Formats & Pattern Matching

Direct message

Delivered when a subscriber matched via SUBSCRIBE.

["message", channel, payload]

Pattern message

Delivered when a subscriber matched via PSUBSCRIBE.

["pmessage", pattern, channel, payload]
Subscription counter: in every subscribe/unsubscribe/psubscribe/punsubscribe push, the last element is the total count of channels and patterns you're still subscribed to. It only reaches Pub/Sub exit (0) once every channel and pattern is gone.

Sharded Pub/Sub (Redis 7.0+)

Regular Pub/Sub messages propagate to every node in a Redis Cluster — fine at small scale, wasteful at large scale. Sharded Pub/Sub restricts propagation to just the shard that owns the channel's hash slot.

Regular Pub/Sub

SUBSCRIBE / PUBLISH — message fans out across the entire cluster bus, to every node, every time.

Sharded Pub/Sub

SSUBSCRIBE / SPUBLISH / SUNSUBSCRIBE — channel is hashed to a slot; message stays within that shard (master + its replicas) only.

This lets you horizontally scale Pub/Sub throughput by adding shards, instead of every message hitting every node in the cluster.

Code Example — Python (redis-py)

Two processes: one subscribes and listens forever, the other publishes a message.

# subscriber.py — runs in a separate process/terminal
import redis

r = redis.Redis(host="localhost", port=6379)
pubsub = r.pubsub()
pubsub.subscribe("orders.new")

# blocks, yielding a dict for every message/subscribe confirmation
for msg in pubsub.listen():
    if msg["type"] == "message":
        print(f"New order: {msg['data']}")
# publisher.py
import redis

r = redis.Redis(host="localhost", port=6379)
n = r.publish("orders.new", "order#4521 placed")
print(f"delivered to {n} subscriber(s)")

pubsub.listen() internally wraps SUBSCRIBE + a blocking read loop that parses the raw RESP array-replies for you — this is the client library doing exactly what the wire-protocol example above shows manually.

Real-World Scenarios

Live chat / notifications

Each chat room = a channel. Every connected WebSocket server subscribes; any server can PUBLISH a new message and every other server (and its connected users) gets it instantly.

Cache invalidation

When a record changes, publish to cache.invalidate.<table>. Every app instance subscribed to that pattern drops its local cache entry — no polling needed.

Multiplayer game state

Game-room events (PSUBSCRIBE room.42.*) broadcast player moves to every client in that room with sub-millisecond fan-out.

Practical / Interview Tips

  • At-most-once delivery. If a subscriber is offline or crashes mid-message, that message is gone forever — Pub/Sub has zero persistence. If you need durability or replay, that's Redis Streams (XADD/XREAD), not Pub/Sub. Interviewers love asking "what happens if the subscriber disconnects?" — this is the answer.
  • No relation to keyspace / databases. Publishing on DB 10 is heard by a subscriber connected to DB 1 — channels are entirely separate from the key namespace. If you need isolation, prefix channel names yourself (e.g. prod:orders.new vs staging:orders.new).
  • A subscribed client is mostly "read-only." Under RESP2 it can't run arbitrary commands while subscribed — only the Pub/Sub-adjacent ones. Use a separate connection for publishing/other commands, or upgrade to RESP3 via HELLO 3.
  • Fan-out cost scales with subscribers + patterns. PUBLISH is O(N+M) — lots of pattern subscriptions across the cluster make every publish more expensive, even on unrelated channels.
  • Cluster mode: plain Pub/Sub messages propagate to every node in the cluster bus; Sharded Pub/Sub (SSUBSCRIBE/SPUBLISH) confines them to one shard — know when to reach for which.
