1. Hash Slots sharding mechanism

Redis Cluster splits the entire keyspace into 16,384 fixed slots. Every key is deterministically mapped to one slot: CRC16(key) % 16384. Each node owns a contiguous range of slots.

Node A
slots 0–5460
Node B
slots 5461–10922
Node C
slots 10923–16383
Analogy: think of it as a hotel with 16,384 room numbers, split across 3 wings (nodes). Reception (the hash function) always sends "John Smith" to the same room number every time — it doesn't care which wing owns that room, it just computes the number.
Example: key user:1001 hashes to slot 5678 → lives on Node B. Key user:1002 might hash to slot 200 → lives on Node A. They're unrelated keys, so nobody cares they're on different nodes.

Why fixed slots instead of "just hash to a node directly"? Because slots are the unit that moves during rebalancing — not individual keys, not whole nodes. Adding Node D just means migrating some slot ranges to it. This is why Redis doesn't need consistent hashing (rehashing all keys) — it's a coarser, pre-defined layer of indirection.

2. Client Routing — MOVED how requests find the right node

There is no proxy/router node. Clients compute the slot themselves and cache a slot→node map. If they guess wrong (stale cache, slot recently migrated), the node replies MOVED <slot> <ip:port> instead of forwarding the request — the client updates its map and retries.

client: hash(key)→slot 5678 → asks Node A (stale cache) → Node A: "MOVED 5678 B:6379" → client updates map, asks Node B → ✅ hit
Common interview trip-up: people assume any node can forward the request internally like a proxy. It can't — the client is responsible for redirecting itself. That's a deliberate design choice for low latency (no extra hop) at the cost of "dumb" nodes needing smart clients.

3. Replication & Failover high availability

Each master can have one or more replicas. Replication is asynchronous — the master ACKs your write before the replica has received it. If the master dies right after ACKing, that write can be lost when a replica is promoted.

This is the single most-tested fact about Redis in interviews: "Redis is not a strongly consistent system of record" — because of async replication. If asked "would you use Redis for payment balances?" the expected answer is generally no, or only with extreme caution (e.g. WAIT command, and even that has limits).
Example: Master B acks a SET cart:99 {...}. 4ms later, before B1 (its replica) receives the update, B's process crashes. Cluster promotes B1 → new master. That write is gone. Client thinks it succeeded.

Reads from replicas: a client can opt into reading from replicas (READONLY command in cluster mode) to spread load — but those reads can be stale by however far replication lag has drifted.

4. The Core Tradeoff why this matters in system design

PropertyWhat Redis Cluster gives you
AvailabilityHigh — replica auto-promotes on master failure
Partition toleranceYes — cluster keeps serving slots that aren't affected
ConsistencyWeak — async replication can lose acknowledged writes
Analogy: it's like a manager (master) who tells you "done!" the moment they've written a note themselves, without waiting to confirm their assistant (replica) copied it too. Usually fine, occasionally the note gets lost if the manager gets hit by a bus mid-sentence.

In interviews, this is the hook to talk about CAP theorem: Redis Cluster picks AP-leaning behavior (favors availability) over strict consistency, similar to how you'd frame Cassandra or DynamoDB vs. something like a single-leader SQL replica set configured for sync replication.

5. Hash Tags co-locating related keys

Multi-key operations (MGET, transactions, Lua scripts) only work if all keys are on the same node. By default that's basically random. Hash tags force co-location: only the substring inside {} is hashed.

KeysResult
{user:123}:posts and {user:123}:likes✅ same slot (only user:123 is hashed)
user:123:posts and user:123:likes❌ different slots likely → CROSSSLOT error on multi-key ops
Example use case: you want to run a transaction that updates a user's profile and their session count atomically. Tag both keys with {user:123} so Redis guarantees they land on the same node/slot.

6. What Cluster Deliberately Doesn't Do good interview signal to mention

  • No query fan-out/merge — a command touching keys on multiple nodes just errors, it doesn't get split and recombined for you.
  • No cross-shard transactions unless keys share a slot (via hash tags).
  • No strong consistency guarantee — see above.

Mentioning this unprompted signals you understand it's a sharding + availability tool, not a distributed database with a smart query planner — a distinction interviewers like to probe.

7. Rapid-Fire Interview Q&A

Q: Why 16,384 slots specifically?
A: Small enough that the slot bitmap fits in ~2KB (cheap to gossip between nodes), large enough to divide reasonably evenly across up to ~1000 nodes.
Q: How does a client know the slot map without asking every time?
A: It caches it locally and only refreshes on a MOVED response or at startup — same idea as a DNS cache with invalidation on stale hits.
Q: What happens if a master and all its replicas die simultaneously?
A: Those slots become unavailable — the cluster can't serve that keyspace range until manual intervention. Other nodes/slots keep working.
Q: How would you design a leaderboard system with Redis in an interview?
A: Sorted Set (ZSET) per leaderboard/shard key, cluster for horizontal scale if the leaderboard is huge, replicas for read scaling, and accept eventual/lossy consistency as a tradeoff for speed — flag it explicitly as a design decision.
Q: Redis Cluster vs Sentinel — when would you pick which?
A: Sentinel = HA only, single master holds all data (no sharding), simpler ops. Cluster = HA + horizontal scaling via sharding, more moving parts. Pick Sentinel if dataset fits one node and you just need failover; Cluster if you need to scale beyond one node's memory/throughput.
