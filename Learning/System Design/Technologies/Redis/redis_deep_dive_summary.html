🧠 Core Redis Model

Single-threaded

Only one command runs at a time, in the exact order received. No multi-core parallelism, but no confusing race conditions either — order is predictable.

In-memory

Data lives in RAM, not disk. This makes reads/writes sub-millisecond fast, but data can be lost if the process crashes (unless you configure persistence).

Data Structure Server

Values aren't just strings — they can be sorted sets, hashes, streams, geospatial indexes, bloom filters. It's like a distributed version of the data structures from a DS&A course.
Real-life analogy: Think of Redis like a single very fast cashier (single-threaded) working from a notebook they keep in their hands, not a filing cabinet (in-memory) — and that notebook has labeled sections for different types of lists, not just plain notes (data structure server).

⌨️ Commands & the Keyspace

SET user:1 "Ali"
GET user:1
INCR page_views          # atomic +1
XADD mystream * field val   # add to a stream
Commands are grouped by data type (e.g. Z* for sorted sets, X* for streams). You can't run INCR on a hash — each type has its own command family.
Why keys matter: Redis decides which node in a cluster owns a piece of data based on a hash of the key. So your choice of key design directly controls how evenly your data/traffic spreads across a cluster.

💾 Persistence: RDB, AOF, and fsync

These are the three terms from your snippet — here's what each means and how they relate:

RDB (snapshot)

A full point-in-time copy of the entire dataset, saved to disk periodically (e.g. every few minutes).
Analogy: Like taking a full photo of your desk every hour. If it crashes 10 minutes after the last photo, those 10 minutes of changes are gone.

AOF (Append Only File)

A log file that records every write command as it happens (like SET, INCR). On restart, Redis replays this log to rebuild the dataset.
Analogy: Like a diary where you write down every single change the moment it happens, instead of a periodic photo. More durable, but the file grows continuously.

fsync

The system call that forces data sitting in the OS's memory buffer to actually be written to physical disk.
Analogy: Writing something in your diary (AOF) vs. actually pressing it into a permanent notebook page. Until fsync happens, the data could still vanish if the machine loses power.
How they connect:
Write command runs
→
Appended to AOF log
→
fsync to disk (~every 1 sec by default)
→
Durable on disk
The tradeoff: with the default "fsync every 1 second" setting, Redis can lose up to ~1 second of the most recent acknowledged writes if it crashes right before an fsync happens. You can configure fsync to run on every single write (safer, slower) or less often (faster, riskier).

In practice (per the article): relying on a single Redis instance + disk recovery is fragile. Most production setups instead use a replica that continuously reads the AOF/log from the main node — much like Change Data Capture (CDC) in other databases.

🌐 Clustering & Sharding

What is a Cluster?

A cluster is a group of Redis nodes (servers) working together so that the total dataset and traffic can scale beyond what a single machine can handle. Each node owns a subset of the keyspace.

How sharding works

Redis divides the keyspace into 16,384 slots. Each key is hashed (CRC) to determine its slot, and each slot is owned by one node. Nodes gossip with each other so every node knows who owns what.

→ owned by →
Node C

Client routes request directly to Node C
Hot key problem: if one key gets a disproportionate share of traffic, that one node can get overwhelmed even though other nodes are idle — because that key always lives on the same node. Fix: append a random suffix to popular keys (e.g. product:123:0…product:123:9) to spread the same logical data across multiple nodes.

🛠️ Common System Design Use Cases

1. Cache

App checks Redis first → if miss, query DB → store result in Redis. Two big design questions interviewers ask: (a) hot key mitigation, (b) eviction policy (EXPIRE / TTL vs. LRU eviction when memory fills up).

2. Rate Limiter

Use INCR on a key per client; if the count is under the limit, allow the request; set an EXPIRE so the counter resets after the time window (e.g. 5 requests / 60 sec).

3. Leaderboard

Use a sorted set (ZADD) keyed by score (e.g. likes). ZRANGE lets you fetch top-N in O(log N) — like a self-maintaining heap.

4. Geospatial Index

GEOADD stores lat/long as a geohash inside a sorted set; GEOSEARCH finds nearby points within a radius — great for "find nearby stores."

📨 Streams, Consumer Groups & Workers

These three terms work together — here's each one explained separately, then how they connect.

What is a Stream?

A Redis Stream is an append-only, ordered log of entries — conceptually the same idea as a Kafka topic. Each entry gets an auto-generated ID (usually timestamp-based) and holds a small set of field-value pairs (like a mini JSON object).
Analogy: Think of a stream like a numbered list in a notebook where you can only ever add new lines at the bottom — never edit or delete old ones. Each line is one "event," e.g. {orderId: 55, status: "created"}.
XADD orders * orderId 55 status created

What is a Consumer Group?

A consumer group is a named "bookmark" (pointer) into a stream that tracks how far a group of workers has processed. It lets multiple workers cooperatively read from the same stream without processing the same item twice.
Analogy: Imagine several people reading the same numbered notebook, but there's a shared sticky note saying "we've processed up to line 42." Whoever is free next grabs line 43.

What is a Worker?

A worker is just a process/service instance that pulls unprocessed items from a consumer group and does the actual work (e.g. sending an email, processing a payment). Multiple workers can run in parallel, each claiming different stream entries.
Analogy: Workers are like employees picking up tasks from a shared inbox tray — each takes the next unclaimed item, does the job, and marks it done.

How they fit together (Async Job Queue example)

Producer: XADD job to stream
→
Consumer Group tracks position
→
Worker 1 claims item #43
Worker 2 claims item #44
Fault tolerance: a worker must "heartbeat" back to the consumer group while processing (saying "still working on this"). If a worker dies or stops heartbeating, the item is reclaimed and re-assigned to another worker.
Important caveat: this only guarantees at-least-once processing, not exactly-once. If a worker loses connection to Redis but is still connected to the actual downstream database, it might finish the job while another worker also gets assigned the same item — leading to duplicate processing in rare cases. Design your job handlers to be idempotent (safe to run twice) to protect against this.

📢 What is Pub/Sub?

Pub/Sub (Publish/Subscribe) is a messaging pattern where senders ("publishers") broadcast messages to a named channel/topic, and any servers listening ("subscribers") on that topic instantly receive it. Redis keeps no history — it just relays messages live.
Analogy: Like a radio station. A publisher "broadcasts" on a channel; only listeners currently tuned in ("subscribed") to that channel hear it. If you weren't listening when it aired, you missed it forever.
User 1 → Server A
Server A subscribes to topic "user1"
User 3 → Server C subscribes to topic "user3"
→
Server A publishes to "user3"
→
Redis routes it to Server C → delivered to User 3
Use case in system design: chat apps where User 1 is connected via WebSocket to Server A, but wants to message User 3 who's connected to a completely different server (Server C). Redis Pub/Sub acts as the "registry" so servers can find and message each other without needing a consistent hash ring.
Key limitation: Redis Pub/Sub is at-most-once delivery — if a subscriber isn't connected at the moment of publish, the message is lost forever (no replay, unlike Streams). Don't use it where guaranteed delivery matters.

🎓 Distributed Systems Fundamentals (Beginner Primer)

You're right that these Redis terms sit on top of general distributed systems concepts. Here are the core ideas you'll keep running into — explained from scratch:

Node

Just one machine/process in a system that has many machines working together. A "3-node cluster" = 3 separate servers cooperating.

Sharding (a.k.a. Partitioning)

Splitting one big dataset across multiple nodes so no single machine has to hold or serve all the data. Redis shards by hashing keys into slots (explained above).
Analogy: Instead of one giant library building, you split books across 10 branch libraries by first letter of the author's last name.

Replication

Keeping copies of the same data on multiple nodes (a "primary/main" and one or more "replicas/secondaries") so that if one node dies, another has the data. Also lets you scale reads by spreading them across replicas.

Consistent Hashing

A hashing technique used to decide which node owns which piece of data, designed so that when you add/remove a node, only a small fraction of keys need to move (instead of reshuffling everything).

Gossip Protocol

A way for nodes to share status information (who's alive, who owns what) by randomly "gossiping" with a few other nodes periodically, until the info spreads to everyone — like rumors spreading through a group.

Eventual Consistency

A system design tradeoff where, after a write, different nodes might briefly show different (stale) data — but they'll all converge to the same value eventually. Common in caches and replicas.

At-most-once vs At-least-once vs Exactly-once

Delivery guarantees for messages/jobs: at-most-once = might be lost, never duplicated (Pub/Sub). At-least-once = never lost, but might be duplicated (Streams). Exactly-once = the hardest to achieve — never lost, never duplicated.

Idempotency

A property of an operation where running it multiple times has the same effect as running it once. Critical when a system only guarantees "at-least-once" delivery, since duplicates can happen.

📖 Full Glossary (every term used above)

Redis
An in-memory, single-threaded data structure server used for caching, queues, leaderboards, rate limiting, pub/sub, and more.
Single-threaded
Only one operation executes at a time, in strict arrival order — simplifies reasoning but limits CPU parallelism.
In-memory
Data is stored in RAM rather than on disk, making access extremely fast but volatile without persistence.
Key / Value
The fundamental unit in Redis — every piece of data is stored under a unique key, mapped to some value/data structure.
Slot
One of 16,384 fixed buckets Redis divides its keyspace into; each key hashes to exactly one slot, and each slot is owned by one node.
Cluster
A group of Redis nodes working together, each owning a portion of the keyspace, to scale beyond one machine's capacity.
Node
A single server/process participating in a cluster.
Hot key
A single key receiving disproportionately high traffic, which can overload the one node that owns it.
Sharding
Splitting data across multiple nodes so no one node stores/serves everything.
Replica / Replication
A secondary copy of a node's data, kept in sync with the primary, used for durability and read scaling.
Gossip protocol
A peer-to-peer method where nodes periodically exchange status info with random peers until the whole cluster is informed.
RDB (Redis Database file)
A full snapshot of the dataset saved to disk at intervals.
AOF (Append Only File)
A log of every write command, replayed on restart to rebuild the dataset with less data loss than RDB.
fsync
The OS-level call that forces buffered data to be physically written to disk, making it durable against crashes.
TTL (Time To Live) / EXPIRE
A duration after which a key automatically becomes unreadable/deleted — used for cache expiration.
LRU (Least Recently Used)
An eviction policy where, once memory is full, the key that hasn't been accessed in the longest time gets removed first.
Rate limiter
A mechanism that caps how many requests a client/service can make in a given time window.
Sorted Set (ZSET)
A Redis data structure that keeps unique members ordered by a numeric score — ideal for leaderboards and rankings.
Geospatial Index
A Redis structure (built on sorted sets) storing lat/long points, queryable by radius/proximity.
Stream
An append-only, ordered log of timestamped entries — Redis's answer to a Kafka-like event log.
Consumer Group
A tracked position/pointer into a stream shared by multiple workers, ensuring each entry is only handed to one worker at a time.
Worker
A process instance that pulls and processes unclaimed items from a consumer group.
Heartbeat
A periodic "still alive / still working" signal a worker sends so its claimed item isn't reassigned prematurely.
Claiming / Reclaiming
The process where a consumer group assigns an item to a worker (claim), and reassigns it to a different worker if the original one stops heartbeating (reclaim).
At-least-once delivery
A guarantee that a message will be delivered/processed at least once, but possibly more than once (duplicates possible).
Exactly-once delivery
A (much harder) guarantee that a message is processed exactly one time — not guaranteed by Redis Streams alone.
Idempotent
An operation that produces the same result no matter how many times it's applied — important for safely handling duplicate deliveries.
Pub/Sub (Publish/Subscribe)
A messaging pattern where publishers send to named channels and only currently-subscribed listeners receive the message, with no history/replay.
At-most-once delivery
A guarantee that a message is delivered zero or one times — it may be lost, but is never duplicated (this is what Redis Pub/Sub provides).
Consistent hashing
A hashing scheme that minimizes data movement when nodes are added or removed from a cluster.
Eventual consistency
A guarantee that, absent new writes, all replicas will eventually converge to the same data — but may be briefly inconsistent.
CDC (Change Data Capture)
A technique where a system streams out every data change (insert/update/delete) so other systems (like a replica) can stay in sync.
