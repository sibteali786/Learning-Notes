PostgreSQL Deep Dive

Hello Interview — System Design in a Hurry · Key Technologies
Framing

Interviewer isn't grading you as a DBA. They want architectural judgment: when to pick Postgres, when to look elsewhere, and what trade-offs you're accepting. Two common failure modes: (1) diving into MVCC/WAL internals nobody asked for, (2) vague claims like "NoSQL scales better" with no reasoning behind them.

Motivating Example — Social Media Platform

Users: create posts · comment · follow · like posts/comments · DM each other.

  • DM thread creation needs atomicity (thread + participants + first message together)
  • Comments/follows need referential integrity (can't comment on a nonexistent post, follow a nonexistent user)
  • Like counts can be eventually consistent — a few seconds' delay is fine
  • Profile view needs fast fetch of posts + follower count + metadata
  • Users need to search posts and other users
  • As the platform grows → more data, more complex queries

Complex relationships + mixed consistency needs + search + growth = exactly the mix that makes Postgres worth exploring.

Read Performance

Basic Indexing (B-tree, default)

Good for: exact match, range queries, sorting (when ORDER BY matches index column order). Postgres auto-indexes the primary key; you add more yourself.

-- bread and butter index
CREATE INDEX idx_users_email ON users(email);

-- multi-column for common query patterns
CREATE INDEX idx_posts_user_date ON posts(user_id, created_at);
Interview trap: indexing every column. Each index slows writes (must be kept updated), costs disk space, and the planner may skip it anyway for a sequential scan.

Beyond Basic Indexes — replaces whole other systems

GINFull-Text Search — like a book's index: maps each word → every location it appears.

ALTER TABLE posts ADD COLUMN search_vector tsvector;
CREATE INDEX idx_posts_search ON posts USING GIN(search_vector);

SELECT * FROM posts
WHERE search_vector @@ to_tsquery('postgresql & database');

Supports stemming (find/finds/finding match), relevance ranking, multi-language, AND/OR/NOT.

Stick with Postgres search whenReach for Elasticsearch when you need
Simpler use cases, keeping architecture leanSophisticated relevancy scoring, faceted search, fuzzy/"search-as-you-type", distributed search at very large scale, advanced analytics

GINJSONB metadata — NoSQL-style flexible schema inside Postgres.

ALTER TABLE posts ADD COLUMN metadata JSONB;
CREATE INDEX idx_posts_metadata ON posts USING GIN(metadata);

SELECT * FROM posts
WHERE metadata @> '{"type": "video"}'
  AND metadata @> '{"hashtags": ["coding"]}';

-- find all posts that mention a specific user
SELECT * FROM posts WHERE metadata @> '{"mentions": ["user123"]}';

GiSTGeospatial via PostGIS extension — index location data like you'd index text.

CREATE EXTENSION postgis;
ALTER TABLE posts ADD COLUMN location geography(Point, 4326);
CREATE INDEX idx_posts_location ON posts USING GIST(location);

-- all posts within 5km of SF
SELECT * FROM posts
WHERE ST_DWithin(location, ST_MakePoint(-122.4194, 37.7749)::geography, 5000);

GiST is a general-purpose index framework; PostGIS uses it for bounding-box strategies so "within X km" queries skip row-by-row checks. Handles points/lines/polygons, multiple distance calcs, coordinate systems. Real example: Uber initially ran their entire ride-matching system on PostGIS before moving to custom infra at massive scale.

You can combine all three in one query — full-text + JSONB + geospatial — e.g. "video posts within 5km of SF mentioning 'food', tagged #restaurant." This is a strong interview signal: sophisticated functionality without adding a new system.

Query Optimization Essentials

Covering indexes — store the columns you need right in the index, so Postgres never touches the table:

CREATE INDEX idx_posts_user_include
ON posts(user_id) INCLUDE (title, created_at);

Trade-off: bigger index, slightly slower writes.

Partial indexes — index only the subset you actually query:

CREATE INDEX idx_active_users
ON users(email) WHERE status = 'active';

Great when most queries hit "active" rows and "inactive/deleted" rows are dead weight in the index.

Write Performance

What happens on a write (4 steps)

  1. Buffer Cache + WAL record [Memory] — data pages marked dirty, WAL record generated, both in memory
  2. WAL Flush [Disk] — at commit, WAL flushed to disk (sequential = fast). Transaction is now durable — crash-safe via WAL replay, even before data pages are written
  3. Background Writer [Memory→Disk] — dirty pages written to actual data files asynchronously, batched for efficiency
  4. Index Updates [Memory+Disk] — every index also needs a WAL entry; more indexes = slower writes
Key line for interviews: write throughput is bounded by WAL flush speed (disk I/O) — that's the one synchronous step gating commit confirmation. Buffer cache just batches the rest for later.

Throughput limits (single node, Read Committed default)

OperationRate
Simple inserts~5,000/sec/core
Updates w/ index mods~1,000–2,000/sec/core
Complex transactions (multi-table/index)hundreds/sec

What moves these numbers: hardware (WAL disk I/O), index count, synchronous replication (adds latency waiting on replica ack), transaction complexity, and connection count — Postgres forks an OS process per connection, so use a pooler like PgBouncer in front when running many app instances.

5k writes/sec isn't a hard ceiling on Postgres overall — it's the per-node number. Beyond that, you shard across nodes.

5 Write-Scaling Optimizations

#TechniqueNotes
1Vertical ScalingFaster NVMe (WAL), more RAM (buffer cache), more cores. Simple, but a weak standalone interview answer
2Batch ProcessingCombine many writes into one transaction. Risk: crash mid-batch loses the whole batch
3Write OffloadingNon-critical writes (analytics, activity logs, "last seen") → message queue (Kafka) → background workers → async DB / separate analytics DB
4Table PartitioningTime-based split across physical tables. Helps concurrency (different sessions write different partitions) and reads (scan only recent partitions)
5ShardingMost common interview answer. Shard on the column you query by most (e.g. user_id) to avoid cross-shard scatter-gather
-- 2. Batch insert instead of 1000 separate ones
INSERT INTO likes (post_id, user_id) VALUES (1,101),(1,102),...,(1,1000);
-- 4. Time-based partitioning
CREATE TABLE posts (
  id SERIAL, user_id INT, content TEXT, created_at TIMESTAMP
) PARTITION BY RANGE (created_at);

CREATE TABLE posts_2024_01 PARTITION OF posts
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

Common pattern: recent partitions on fast NVMe, older ones moved to cheap storage.

Sharding trade-offs: cross-shard queries, keeping schema consistent across shards, more DBs to manage. Postgres has no built-in sharding (unlike DynamoDB) — build it yourself or use a managed layer like Citus.

Replication

Two purposes: ① scale reads (spread queries across replicas) and ② high availability (survive node failure).

TypeBehaviorTrade-off
Asynchronous (default)Primary confirms write immediately, replicates in backgroundBest performance; risk of losing recent writes if primary fails before replicas catch up
SynchronousPrimary waits for ≥1 replica ack before confirmingStronger durability/consistency; adds write latency

Common hybrid: a few synchronous replicas for durability + more asynchronous ones purely for read scaling. Postgres lets you designate which replicas are synchronous.

Replication lag ("read-your-writes"): a user who just wrote data may not see it if their next read hits a replica that hasn't caught up.

Failover sequence: detect primary is down → promote a replica → update connection info → repoint applications. In interviews, it's enough to know this is possible and roughly how it works — managed services (RDS, Cloud SQL) automate it.

Data Consistency & Transactions

A transaction = a set of operations that all succeed or all fail together.

-- atomic money transfer
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
The trap: transactions alone don't protect you from concurrent transactions.
Auction example — two users bid at once, default Read Committed isolation:
  1. User A reads maxBid = $90
  2. User B reads maxBid = $90 (before A commits)
  3. A bids $100, updates maxBid → $100, commits
  4. B still thinks max is $90, bids $95 — the guard UPDATE ... WHERE maxBid < 100 updates 0 rows, but B's INSERT still goes through and commits
Result: an inconsistent $95 bid record exists after a $100 bid was already accepted. The read-then-write isn't atomic across transactions.

Fix 1 — Row-Level Locking

BEGIN;
SELECT maxBid FROM Auction WHERE id = 123 FOR UPDATE;
INSERT INTO bids (item_id, user_id, amount) VALUES (123, 456, 100);
UPDATE Auction SET maxBid = 100 WHERE id = 123;
COMMIT;

FOR UPDATE locks the row; other transactions trying to read it with FOR UPDATE wait. Say explicitly: "transactions + row-level locking on the auction row" — not just "we'll use transactions."

Fix 2 — Higher Isolation Level

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- same code as before
COMMIT;

Prevents all anomalies, but a conflicting transaction gets rolled back and must retry — your app needs retry logic.

Fix 3 — Optimistic Concurrency Control (OCC), app-level

SELECT maxBid, version FROM Auction WHERE id = 123;
-- returns maxBid=90, version=5

UPDATE Auction SET maxBid = 100, version = 6
WHERE id = 123 AND version = 5;
-- 0 rows updated → someone else got there first, retry

No native Postgres syntax — you add a version column yourself. Good when conflicts are rare (no locking overhead); bad when conflicts are frequent (wasted retries).

When to Use PostgreSQL (and When Not)

✅ Default choice — go here first

  • Complex relationships between data
  • Strong consistency requirements
  • Rich querying, structured + unstructured (JSONB) mix
  • Built-in full-text search / geospatial
  • Scales reads well via replication
  • Fits: e-commerce, financial systems, CMS, analytics (reasonable scale)

🚫 Consider alternatives when

  • Extreme write throughput (millions/sec) — WAL + index I/O bottlenecks even with sharding → Cassandra (event streaming), Redis (real-time counters)
  • Global multi-region active-active writes — single-primary architecture can't do true multi-writer without heavy conflict/latency cost → CockroachDB, Cassandra, DynamoDB global tables
  • Pure key-value access (no joins, no complex queries) — MVCC/WAL/planner overhead is wasted → Redis, DynamoDB, Cassandra
Scalability alone is not a good reason to avoid Postgres — it scales far with replication + partitioning + sharding, properly designed.
💡 Interview framing: Start with Postgres, then justify deviating — much stronger than starting niche and justifying against Postgres. Never just say "ACID compliant" — explain how you'll use transactions/locking/isolation level to meet the actual consistency requirement.

Appendix — SQL & ACID Fundamentals

Relational basics

Tables (relations) = rows + typed columns. Example:

CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  username VARCHAR(50) UNIQUE NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),   -- foreign key
  content TEXT NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

REFERENCES users(id) is a foreign key — Postgres enforces that every post belongs to a real user.

RelationshipExample
One-to-OneA user and their profile settings
One-to-ManyA user and their posts
Many-to-ManyUsers and the posts they like (needs a join table)
-- many-to-many join table
CREATE TABLE likes (
  user_id INTEGER REFERENCES users(id),
  post_id INTEGER REFERENCES posts(id),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, post_id)
);

Normalization = splitting data into related tables. Benefits: no duplicated data, easy integrity (username change updates everywhere), flexible schema. Denormalization (e.g. storing a like-count directly on posts instead of counting the likes table every time) trades consistency for read speed — worth raising explicitly in interviews.

ACID, explained through a bank transfer ($100: savings → checking)

AtomicityBoth updates happen or neither does. Crash mid-transfer → full rollback, money never vanishes.
ConsistencyDB enforces its own rules on every transaction (constraints, FKs). E.g. balance DECIMAL CHECK (balance >= 0) — a transaction that would go negative is rejected outright. NoSQL DBs typically push this check into app code instead.
IsolationConcurrent transactions don't corrupt each other — governed by isolation level (see table above).
DurabilityOnce committed, survives a crash — guaranteed via WAL. synchronous_commit = off trades this away for speed (unflushed writes can be lost in a power outage).
Don't conflate: ACID "Consistency" = the DB always follows its own constraints. CAP-theorem "Consistency" = every read returns the latest write. Same word, different meaning — mixing them up in an interview is a red flag.

When ACID actually matters: financial transactions (must-have), user authentication (must-have), social media likes (fine to relax), analytics data (often fine to relax for performance).

🗣️ Comment-section debate (worth knowing going in)

A recurring pushback: "Postgres can't handle social-media scale — use DynamoDB." Cited reasons: Aurora's 128TB storage ceiling, single-primary architecture blocking true multi-region active-active writes, and slow failover/rebuild. Counterpoints from other commenters:

  • Aurora replicas share the same storage volume — failover is typically ~15–60s, not "hours" to rebuild
  • Media/images belong in object storage (S3) regardless of DB choice, which makes the 128TB text-only ceiling far less scary
  • OpenAI scaled Postgres to 800M users on a single primary + 50 read replicas
  • Instagram, Facebook, Twitter, Pinterest all built their core platforms on sharded relational databases (Postgres/MySQL), not NoSQL
  • DynamoDB's genuine edge is global active-active multi-region writes with automatic sharding — that's the honest, narrow case for it, not "Postgres is bad"

Takeaway for interviews: know the real DynamoDB advantages (global tables, no storage ceiling, managed sharding) and argue for Postgres with reasoning — not folklore in either direction.

🎯 Quiz checkpoint from the article: "What is the primary bottleneck for write performance in a single PostgreSQL instance?" → Disk I/O for WAL writes (not CPU, network, or RAM).
