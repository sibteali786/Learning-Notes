1️⃣ Round Robin Partitioning (when no key is provided)

Q: How does round robin work when no key is given? How is broker chosen, then partition?

When a message has no key, Kafka doesn't hash anything — it just cycles through partitions. But there are two separate decisions happening:

Producer creates message (no key)
→
Producer client picks a partition (round robin / sticky)
→
Cluster metadata: which broker leads that partition?
→
Message sent to that broker

Step A — Partition is chosen first (client-side, not broker-side):

The producer already has a cached list from the cluster metadata: topic → [partition0, partition1, partition2, ...]. With no key, modern Kafka clients (2.4+) use the Sticky Partitioner: they stick to ONE partition until a batch fills up or lingers, THEN switch to the next partition. (Older clients did pure round robin, message by message — less efficient because batches got smaller.)

Step B — Broker is determined by lookup, not choice:

Each partition already has a fixed leader broker, decided when the topic was created / during rebalancing (by the Controller). The producer already knows this mapping from metadata it fetched earlier (Metadata API). So "choosing a broker" isn't really a decision per message — it's just "partition 2 → leader is Broker 3" lookup.

Example

Topic "logs" has 3 partitions, leaders:
  partition-0 → Broker A
  partition-1 → Broker B
  partition-2 → Broker C

No key provided. Sticky partitioner behavior:
  msg1, msg2, msg3  → batched onto partition-1 (sticky choice for this batch window)
  [batch full / linger.ms elapsed] → switch stickiness
  msg4, msg5        → batched onto partition-2
  ...

Each batch then routes to whichever broker leads that partition
  (partition-1's batch → Broker B, partition-2's batch → Broker C)
💡 Interview tip: If asked "how are partitions load-balanced with no key?" — mention the Sticky Partitioner explicitly. Saying "round robin" alone is technically outdated for Kafka ≥2.4 and shows deeper knowledge if you mention why sticky batching is more efficient (fewer, larger batches = higher throughput).

2️⃣ Retention Policies — How Many, and Which Kafka Uses

Q: How many retention policies are there, and which does Kafka use?

Kafka has three retention strategies, configured via cleanup.policy per topic. You can even combine two of them.

Policycleanup.policy valueWhat it deletesTypical use
Time-baseddelete (default) + retention.msWhole messages older than N ms (default 7 days)Event logs, click streams
Size-baseddelete + retention.bytesOldest messages once partition log exceeds size (default 1GB... unlimited unless set)Cap disk usage
Log CompactioncompactOlder messages sharing the same key — keeps only latest value per keyState/changelog topics (see next section)
✅ Default Kafka behavior = cleanup.policy=delete, using whichever of retention.ms (7 days) or retention.bytes (unbounded unless set) is hit first. Compaction is opt-in per topic — not the default.

You can also set cleanup.policy=compact,delete — compact by key AND still expire very old tombstones/records by time. Used for things like __consumer_offsets.

3️⃣ Log Compaction — Explained with a Real Kafka Example

Q: What is log compaction? Give an example relevant to the Kafka ecosystem.

Core idea: instead of deleting by age, compaction keeps only the most recent value for each key, deleting all older records with that same key. The log becomes a "latest state snapshot" rather than a full event history.

Before compaction:
(k1,v1)(k2,v1)(k1,v2)(k3,v1)(k1,v3)(k2,v2)
After compaction:
(k1,v3)(k3,v1)(k2,v2)

Order between different keys is preserved; only the older duplicates of the SAME key are dropped. This happens via a background compaction thread — not instantly.

Real Kafka-ecosystem example: __consumer_offsets

Kafka itself uses a compacted internal topic to store "which offset has consumer group X read up to on partition Y." Key = (group, topic, partition), Value = offset. You don't need the history of every offset commit ever made — you only need the latest one per group/partition. Compaction keeps this topic small forever instead of growing unboundedly.

Another common use: KTable / changelog topics (Kafka Streams)

If you're maintaining "current inventory count per productId" as a stream table, the changelog topic backing it is compacted by productId. Only the latest count per product needs to survive — old counts are noise.

Deleting a key entirely: write a message with that key and a null value — called a tombstone. After a grace period (delete.retention.ms), compaction removes the key completely.

💡 Interview tip: Mention compaction when your system needs "latest state per entity" rather than "full history of events" — e.g., user profile updates, current price per stock symbol, session state.

4️⃣ How Append-Only Logs Reduce Disk Seek Time

Q: How does log appending avoid/reduce disk I/O seek time?

First — a quick primer since this assumes some disk fundamentals:

Disk seek time = the mechanical delay for a spinning hard drive's read/write head to physically move to the correct location on disk before it can read/write. Random access (jumping around the disk) is slow (~ms range); sequential access (reading/writing one location right after another) is fast because the head barely moves.
❌ Random writes (e.g. B-tree/database updates in place)
Every write may touch a different, scattered disk location → head seeks constantly → slow, especially at scale.
✅ Kafka's append-only log
Every new message is written to the end of the file, sequentially. The disk head barely moves between writes — it's basically the same as streaming to disk.

Sequential disk I/O (even on spinning HDDs) can rival or beat random-access memory I/O in raw throughput — this is the whole reason Kafka can sustain very high write throughput on commodity hardware.

Kafka layers two more tricks on top of this:

TechniqueWhat it does
Page cache relianceKafka doesn't manage its own in-process cache — it leans on the OS page cache. Reads of recent data are often served straight from RAM, not disk at all.
Zero-copy transfer (sendfile)When sending data to consumers, Kafka uses the OS's sendfile() syscall to move bytes straight from page cache to network socket — skipping extra copies through user-space/application memory.
💡 Interview tip: If asked "why is Kafka fast?" — the 3-part answer is: (1) sequential append-only writes, (2) OS page cache reuse, (3) zero-copy reads via sendfile. This is a favorite deep-dive question.

5️⃣ Why Follower Replicas Live on a Different Broker

Q: Why does the follower replica exist on another broker? Can't they all be on the same broker?

Technically you could put a leader and its follower on the same broker — but it would defeat the entire purpose of replication. Here's why:

❌ Same broker for leader + follower
If that one broker/machine crashes (disk failure, power loss, OS crash), both the leader AND its "backup" die together. You've replicated the data but not the fault domain — zero actual protection gained.
✅ Different brokers (ideally different racks/AZs)
A broker going down only takes out one copy. The follower on another machine has the data and can be promoted to leader immediately — actual fault tolerance.

The whole point of "replication factor = 3" is to survive the failure of up to N-1 physical machines. Kafka's Controller specifically avoids placing replicas of the same partition on the same broker (and in well-configured clusters, tries to spread them across racks/availability zones too, via broker.rack).

✅ Analogy: it's like keeping a backup of important documents in a fireproof safe in a different building, not just a second folder in the same drawer — if the drawer burns, both copies burn with it.

6️⃣ How a Topic's Partitions Get Spread Across Many Brokers

Q: When we say "partitioned across many brokers," how do we identify which partition goes where?

This is a cluster-management decision, separate from the per-message partition-key decision you already know. Two different layers:

LayerDecidesWhen
Per-messageWhich partition number (0,1,2...) a message goes toEvery produce call — via key hash or sticky/round-robin
Per-topic (cluster admin)Which broker hosts partition 0, which hosts partition 1, etc.Topic creation time (and rebalanced later if brokers added/removed)

When you create a topic with e.g. 6 partitions and replication factor 3 on a 4-broker cluster, the Controller assigns each partition's leader + followers to brokers using a placement algorithm that aims to:

  • Spread partitions evenly across all brokers (so no broker is overloaded)
  • Never put two replicas of the same partition on the same broker (see section 5)
  • Spread replicas across racks/AZs if broker.rack is configured
Topic "orders" — 6 partitions, replication factor 3, cluster of 4 brokers (B1-B4)

partition-0: leader=B1, followers=[B2,B3]
partition-1: leader=B2, followers=[B3,B4]
partition-2: leader=B3, followers=[B4,B1]
partition-3: leader=B4, followers=[B1,B2]
partition-4: leader=B1, followers=[B3,B4]
partition-5: leader=B2, followers=[B4,B1]

Notice leadership is spread round-robin-ish across B1-B4 too — no single broker becomes a bottleneck for writes.

💡 Interview tip: "Scaling a topic" = adding more partitions (kafka-topics --alter --partitions N), which lets the Controller redistribute load across more brokers. Note: increasing partitions does NOT retroactively re-route already-produced messages with existing keys — it can change which partition future messages with the same key land on, since the modulo (hash % partitionCount) changes. Worth mentioning as a gotcha.

7️⃣ "Vary Independently" — What It Means

Q: What does "vary independently" mean in the compound-key context?

Context: to fix a hot partition (e.g. one ad ID getting flooded), you append something to the key. That "something" should vary independently of the thing causing the hotspot.

"Vary independently" = the extra attribute's value has no correlation with the hot dimension — it spreads evenly and unpredictably relative to it, so appending it actually breaks up the clustering instead of just re-creating it elsewhere.

Example: Ad Click Aggregator

Original key: adId → Nike's viral ad ID gets a hot partition.

✅ Good: append userId
Which user clicks a given ad has nothing to do with the ad itself — clicks come from millions of different, independently-distributed users. Key = adId:userId spreads clicks for the SAME ad across many partitions, evenly.
❌ Bad: append country
If the Nike ad is a US Super Bowl ad, 90% of clicks come from the US anyway — country is correlated with the hotspot, not independent of it. You'd just shift the hot partition to "adId:US" instead of fixing it.
✅ Rule of thumb: pick a dimension whose distribution doesn't change based on which value of the hot field you're looking at. Random number (1-10) is the simplest guaranteed-independent choice — at the cost of losing any meaningful grouping by that dimension.

8️⃣ Consumer Lag — What, How to Check, "Too High"?

Q: What does "lag" mean, how is it checked, and what counts as "too high"?

Lag = the gap between the latest offset written to a partition (the "log end offset") and the offset the consumer has last committed. It's literally "how many unprocessed messages are sitting behind this consumer." 
Lag = LogEndOffset(partition) − CommittedOffset(consumer group)

Example:
  Producer has written up to offset 10,000 on partition-3
  Consumer group "analytics" last committed offset 9,850
  Lag = 10,000 − 9,850 = 150 messages behind

How to check it

  • CLI: kafka-consumer-groups.sh --describe --group my-group --bootstrap-server localhost:9092 — prints LAG column per partition
  • JMX metrics: brokers/clients expose records-lag, records-lag-max which feed into Prometheus/Grafana dashboards in production
  • Managed platforms (Confluent Cloud, AWS MSK): built-in lag dashboards/alarms

What counts as "too high"?

There's no universal number — it's relative to your system's SLA. The real question to ask: "at current consumption rate, how long until this backlog is processed, and does that violate our freshness requirement?"

Estimated catch-up time = Lag ÷ Consumer throughput (msgs/sec)

Example: lag=150,000, consumer processes 1,000 msgs/sec
  → 150 seconds to catch up
  If your SLA requires data freshness under 30s → THIS is "too high"
  If your SLA tolerates minutes of staleness      → this is fine
💡 Interview tip: Don't just say "high lag is bad" — frame it in terms of your system's latency/freshness requirement, and mention it's usually paired with alerting thresholds (e.g. page on-call if lag growth rate stays positive for 5 minutes, meaning consumers can't keep up with producers at all).

9️⃣ "What If Kafka Goes Down?" — The Psycho Interviewer Scenario 😅

Q: What if the interviewer insists on hearing the "Kafka is down" scenario anyway?

You're right to gently push back first (shows you understand Kafka's HA design) — but if they insist, don't just say "it can't happen." Engage with what "down" could actually mean and design for it. That's what actually impresses.

Break "Kafka down" into the realistic sub-scenarios and answer each:

What "down" could really meanWhat actually happensMitigation
A single broker crashesPartitions it led fail over to a follower (handled by Controller + ISR, automatic)Already covered by replication factor ≥3 — mention this is the normal case, not a failure
Whole cluster/region unreachable (network partition, AZ outage)Producers can't reach brokers at allProducer-side: buffer + retry with backoff (bounded queue); beyond buffer capacity, must degrade gracefully
Producer's local buffer fills up because Kafka is unreachable too longYou must decide: drop, block, or fallbackFallback write path — e.g. write critical events to a local disk queue or a secondary store (S3, DB outbox table) and replay into Kafka once it recovers
Consumers can't reach KafkaProcessing simply pausesUsually acceptable if consumers are stateless — they just resume from last committed offset once Kafka is back; no data loss

Talking points to sound senior in this scenario

  • Client-side buffering: producer SDKs already buffer + retry (see section 10) — true full outages just mean this buffer eventually fills.
  • Circuit breaker / fallback store: for critical writes, fall back to a durable outbox (e.g., write to Postgres, have a background job publish to Kafka once it's healthy) — the "transactional outbox pattern."
  • Graceful degradation: define what your product does without real-time data — e.g. show stale cached feed instead of erroring, rather than pretending full availability is achievable.
  • Multi-region Kafka / MirrorMaker: for true DR against a full regional outage, some orgs replicate clusters cross-region — worth a one-line mention as "over-engineering unless requirements demand it."
✅ The winning move: acknowledge the premise is unrealistic in one sentence, then immediately pivot to "but here's how I'd design for partial/regional failure anyway" — you get credit for correcting them AND for depth.

🔟 Idempotent Producer — Why Duplicates Happen Without It

Q: Without idempotence, could we write the same message twice? Doesn't each message already get a unique offset?

Great instinct to question this — the key is understanding when the offset gets assigned relative to when the ack can be lost.

The offset is assigned by the broker, only after it durably appends the message to the partition log. The producer doesn't know the offset in advance — it finds out from the broker's response.

The failure window that causes duplicates

Producer sends msg
→
Broker appends it (offset 501 assigned)
→
Ack lost on the way back (network blip)
→
Producer times out, thinks it failed
→
Producer retries → broker appends AGAIN (offset 502)

The broker did its job correctly and gave a valid unique offset both times — 502 is a legitimate, real, unique offset. The problem isn't the offset mechanism; it's that the producer's retry logic can't tell "my write actually succeeded and only the ack was lost" apart from "my write genuinely never landed." Without idempotence, it just retries blindly → two copies of the same logical message, at two different offsets, both fully valid from Kafka's point of view.

How idempotent mode fixes it

Each producer instance gets a unique Producer ID (PID), and tags every message with a monotonically increasing sequence number per partition. The broker keeps track of the last (PID, sequence) it committed per partition — if a retry arrives with a sequence number it already has, the broker silently discards it as a duplicate instead of appending again, but still returns success to the producer.

enable.idempotence = true   // producer config
// automatically also sets:
acks = all
retries = Integer.MAX_VALUE  (safe to retry indefinitely now)
max.in.flight.requests.per.connection ≤ 5
💡 Interview tip: The precise phrase interviewers want to hear: "idempotence deduplicates at the broker using producer ID + per-partition sequence numbers, turning 'at-least-once' producer semantics into 'exactly-once' for the produce step specifically."

1️⃣1️⃣ Are We Sending to Only One Topic? What's sendBatch?

Q: In the KafkaJS producer.send() example, are we sending to only one topic? Show sendBatch too.

Correct — producer.send() takes one topic field, so all messages in that call go to the same topic (Kafka will still distribute them across that topic's partitions based on key/sticky logic).

// send() → single topic only, multiple messages
await producer.send({
  topic: 'my_topic',
  messages: [
    { key: 'key1', value: 'message1' },
    { key: 'key2', value: 'message2' },
    { key: 'key3', value: 'message3' },
  ],
});

sendBatch() lets you send to multiple different topics in one call — useful for reducing network round trips when a single logical event needs to fan out to several topics (e.g., an "order placed" event that both an "orders" topic and an "analytics" topic need).

await producer.sendBatch({
  topicMessages: [
    {
      topic: 'orders',
      messages: [
        { key: 'order-1', value: JSON.stringify({ id: 1, amount: 99 }) },
      ],
    },
    {
      topic: 'analytics-events',
      messages: [
        { key: 'order-1', value: JSON.stringify({ type: 'order_placed', orderId: 1 }) },
      ],
    },
    {
      topic: 'notifications',
      messages: [
        { key: 'user-42', value: JSON.stringify({ userId: 42, msg: 'Order confirmed!' }) },
      ],
    },
  ],
});
✅ Both are still just "one network request to the producer client," which internally batches per-broker based on which partitions/topics live where — sendBatch just lets you describe a multi-topic fan-out declaratively instead of calling send() three times.

1️⃣2️⃣ Choosing a Good Partition Key — Worked Example

Q: Walk through an example of a good partition key in practice.

Let's design the key for a ride-sharing trip-events system (driver location pings, trip start/end, etc.) — a classic system design interview scenario.

❌ Bad key: eventType (e.g. "location_ping", "trip_start")
Only ~5 distinct values ever exist. "location_ping" dominates 99% of traffic → massive hot partition, and you only ever use 5 partitions max no matter how many you create.
❌ Bad key: city
Better than eventType, but still skewed — NYC/SF will always dwarf smaller cities. A viral event in one city (New Year's Eve) creates a hot partition exactly when you need scale the most.
✅ Good key: driverId
Hundreds of thousands of drivers, roughly evenly active, no single driver dominates traffic. Also gives you a FREE correctness win: all events for the same driver stay in order (critical — you don't want a "trip_end" processed before its "trip_start").

Why driverId wins — checklist

Property you wantDoes driverId satisfy it?
High cardinality (many distinct values)✅ Hundreds of thousands of drivers
Even distribution (no single value dominates)✅ No driver produces disproportionately more events than another
Preserves needed ordering✅ Per-driver event order matters and is preserved (same key → same partition → in-order log)
Stable over time (doesn't spike unpredictably)✅ Unlike "city" during a local event surge
hash(driverId) % numPartitions → partition number

driverId = "drv_88213" → hash → % 12 partitions → partition 7
driverId = "drv_04471" → hash → % 12 partitions → partition 2

All events for drv_88213 (ping, ping, ping, trip_end)
always land on partition 7, always in the order produced.
💡 Interview tip: Always narrate your key choice out loud using this checklist (cardinality → distribution → ordering need → stability). Interviewers are grading your reasoning process, not just whether you land on the "correct" key. If two candidates pick driverId, the one who explains WHY via this framework scores higher.
