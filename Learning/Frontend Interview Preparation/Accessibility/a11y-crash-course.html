Accessibility Crash Course — ARIA Fundamentals

Before implementing the Tabs pattern. Focus: the mental model, not memorization.

1. The Two Governing Principles

Principle 1: A role is a promise

role="button" tells screen readers "treat this as a button" — but HTML/React gives you zero button behavior for free when you add a role manually. No Enter/Space activation, no focus styles, nothing. You owe the browser that behavior in JS.

<div role="button">Place Order</div>
<!-- promise made, not kept unless
     you wire up onKeyDown for Enter/Space -->

Principle 2: ARIA can cloak or enhance

Cloak = overrides what's announced (dangerous if wrong). Enhance = adds meaning HTML can't express (safe, additive).

<a role="menuitem">...</a>
<!-- CLOAK: screen reader no longer
     says "link", says "menu item" -->

<button aria-pressed="false">Mute</button>
<!-- ENHANCE: adds toggle state,
     doesn't hide that it's a button -->
Real-world scenario: You build a custom dropdown with a <div> instead of <select>, style it beautifully, but forget arrow-key navigation. Sighted mouse users never notice. A screen reader user tabs into it, hears "combobox," presses arrow keys expecting options to cycle — nothing happens. The role promised combobox behavior; the JS never delivered. This ships in production constantly because it's invisible in a visual QA pass.

2. The Golden Rule: "No ARIA is better than Bad ARIA"

✓ PREFER 
<button>Submit</button>

Native element. Keyboard, focus, role — all free, all correct.

✗ AVOID unless necessary 
<div role="button" tabindex="0"
     onKeyDown={...} onClick={...}>
  Submit
</div>

Only reach for this when the native element genuinely can't do the job.

3. ARIA's Three Categories

CategoryWhat it doesExample
RolesWhat is this element? (fixed for its lifetime)role="tab", role="tablist"
StatesChanges dynamically as user interactsaria-selected="true", aria-expanded="false"
PropertiesRelationships between elements, usually staticaria-controls="panel-1", aria-labelledby="tab-1"

Mental shortcut: Role = noun ("I am a tab"). State = adjective that changes ("I am currently selected"). Property = pointer to another element ("I control that panel over there").

4. Applying it: Tabs Pattern Anatomy

↑ visually: 3 buttons, 1 active. Structurally, ARIA needs to express: "these 3 buttons are a set," "this one is currently chosen," "this one controls that content block."

<div role="tablist" aria-label="Language tabs">
  <button role="tab"
          id="tab-html"
          aria-selected="true"
          aria-controls="panel-html">
    HTML
  </button>
  <button role="tab"
          id="tab-css"
          aria-selected="false"
          aria-controls="panel-css"
          tabindex="-1">
    CSS
  </button>
</div>

<div role="tabpanel"
     id="panel-html"
     aria-labelledby="tab-html">
  ... HTML content ...
</div>

Notice the bidirectional link: tab → aria-controls → panel's id. Panel → aria-labelledby → tab's id. This is how a screen reader announces "CSS tab, 2 of 3, selected" and "tabpanel, labelled CSS" when you land on the content.

5. Keyboard Behavior Contract

KeyExpected behavior
TabEnters tablist → lands on the active tab only (not the first one)
← →Moves focus between tabs, wraps at ends
Enter / SpaceActivates focused tab (only needed if not auto-activating on focus)
Tab (again)Leaves tablist entirely → goes to panel content, not the next tab

Key insight: only the active tab has tabindex="0"; all others get tabindex="-1". This is the "roving tabindex" pattern — it's how the tablist behaves as ONE stop in the page's tab order, while arrow keys handle movement within it. This trips up almost everyone the first time.

6. Quick Self-Check Before You Code

  1. Can I solve this with native HTML first? (native <button>, <details>, etc.)
  2. If not — have I identified all 3: role, states, properties?
  3. Does every role I add have matching JS behavior (the "promise")?
  4. Have I implemented roving tabindex, or am I letting Tab cycle through every tab individually? (wrong)
  5. Did I test with keyboard only — no mouse — end to end?
