Node.js Event Loop · Interview Gotcha

setImmediate() vs setTimeout(0)

Why the same two lines produce different output depending on where in the loop you currently are.

🔑
The Key Insight — It's About Loop Position, Not Timer Value

The question is never "which is faster?" It's: "where in the event loop are you RIGHT NOW when you schedule both?" — that determines which phase comes next, and therefore which runs first.

fs.readFile('file', () => { // You are inside poll phase right now setTimeout(() => console.log('timeout'), 0); setImmediate(() => console.log('immediate')); }); // Output: ALWAYS // → immediate (check phase, this iteration) // → timeout (timers phase, next iteration)
💡
timers phase already passed this iteration When you're inside a poll callback, the loop has already visited timers this cycle. setTimeout(0) must wait for the loop to complete and wrap back. check phase hasn't happened yet — so setImmediate goes first. Every. Single. Time.
Scenario 02
Outside I/O — Non-Deterministic
⏱ Case A — Slow startup / timer already ready

If Node took long enough to initialise, the 0ms setTimeout threshold has already passed by the time the loop starts.

timers
threshold passed → setTimeout runs ✅
↓
check
setImmediate runs
Output: timeout → immediate
⚡ Case B — Fast startup / timer not ready yet

If Node initialised very quickly, the 0ms threshold hasn't been reached when timers phase runs. Loop moves past it.

timers
threshold not met → skip
↓
check
setImmediate runs ✅
↓ wrap back
timers
now ready → setTimeout runs

// At top level — NOT inside any I/O callback setTimeout(() => console.log('timeout'), 0); setImmediate(() => console.log('immediate')); // Output: NON-DETERMINISTIC // Sometimes: timeout → immediate // Sometimes: immediate → timeout // Depends on OS scheduling + process startup time
⚠️
setTimeout(fn, 0) is a threshold — not a guarantee The spec says setTimeout fires "after at least N ms" — not "exactly at N ms". At the top level, whether 0ms has elapsed by the time the timers phase runs is a race against process startup time. You cannot rely on the order here.
Quick Reference
The Rules — Memorise These
Context setImmediate() setTimeout(0) Winner Why
Inside I/O callback check phase — this iteration timers phase — next iteration ✅ setImmediate — always Loop position: poll → check comes before ↺ timers
Top-level / outside I/O check phase timers phase 🎲 Non-deterministic Both at loop start — depends on startup elapsed time
Inside setTimeout callback check phase — this iteration timers phase — next iteration ✅ setImmediate — always Same as I/O — timers phase already ran this cycle
Inside setImmediate callback check phase — next iteration timers phase — next iteration 🎲 Non-deterministic Both deferred — same race as top-level
🎯
Interview one-liner answer "Inside an I/O callback, setImmediate always runs before setTimeout(0) because we're already past the timers phase — check comes next, and timers only fires on the next loop iteration. Outside I/O, the order is non-deterministic because it depends on whether Node's startup elapsed time has crossed the 0ms threshold."
