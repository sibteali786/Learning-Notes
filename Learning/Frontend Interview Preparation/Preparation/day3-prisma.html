Prisma Schema — Final
📐 schema.prisma
generator client {
  provider     = "prisma-client"
  output       = "../src/generated/prisma"
  moduleFormat = "cjs"   ← required for NestJS CommonJS compat
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

enum OrderStatus {
  PENDING
  SHIPPED
  BOOKED
}

model Order {
  id         String      @id @default(cuid())
  status     OrderStatus @default(PENDING)
  total      Decimal     @db.Decimal(10, 2)
  createdAt  DateTime    @default(now())
  orderItems OrderItem[]
}

model OrderItem {
  id          String  @id @default(cuid())
  productName String  @unique
  price       Decimal @db.Decimal(10, 2)
  quantity    Int
  orderId     String
  order       Order   @relation(fields: [orderId], references: [id])
}
What Prisma Generated — SQL Under the Hood
🗄️ migration.sql — Know What Prisma Does for You
Your Prisma SchemaSQL GeneratedWhy It Matters
enum OrderStatusCREATE TYPE "OrderStatus" AS ENUMNative Postgres enum — DB enforces valid values
@id @default(cuid())CONSTRAINT "Order_pkey" PRIMARY KEYUnique, URL-safe IDs without autoincrement
@db.Decimal(10,2)DECIMAL(10,2)Exact precision for money — never use Float for prices
@default(now())DEFAULT CURRENT_TIMESTAMPDB sets timestamp — not your app code

@relation(...)ADD CONSTRAINT ... FOREIGN KEY ... ON DELETE RESTRICTReal FK — can't delete Order with existing items
⚠️ ON DELETE RESTRICT — Interview Point

Prisma's default. Trying to delete an Order that has OrderItems → Postgres throws error. In real apps choose: CASCADE (delete items too) or SetNull (orphan items). Always a deliberate choice.

Module Scoping — The Key Architecture Decision
🏗️ Why PrismaModule Not Just AppModule
❌ Flat approach (docs example)
// Works only when everything
// is in AppModule — not scalable
@Module({
  providers: [
    PrismaService,
    UserService,   // all flat
    PostService,
  ]
})
✅ Feature module approach (our setup)
// PrismaModule exports PrismaService
@Module({
  providers: [PrismaService],
  exports: [PrismaService],  ← key
})
export class PrismaModule {}

// OrdersModule imports PrismaModule
@Module({
  imports: [PrismaModule],  ← gets access
  providers: [OrdersService, OrdersResolver],
})
The rule: NestJS modules are encapsulated by default. A service declared in AppModule is NOT automatically available in OrdersModule. You must explicitly export from the providing module and import in the consuming module.
Prisma Query Patterns Used
🔍 findMany with include — Replaces Field Resolver
// Gets all orders WITH their items in one DB query
const orders = await this.prismaService.order.findMany({
  include: {
    orderItems: true,   ← JOIN under the hood
  },
});

This is why we removed @ResolveField — items already come back on the order object. No need for a separate lookup.

✏️ Nested create — Order + Items in One Transaction
const order = await this.prismaService.order.create({
  data: {
    status: input.status as OrderStatus,
    total,
    orderItems: {
      create: newItems,   ← creates child records in same TX
    },
  },
  include: { orderItems: true },  ← return them too
});

Prisma wraps nested writes in a transaction automatically. If item creation fails, the order is rolled back. Production-safe by default.

Prisma → GraphQL Type Mapping Problem
🔄 The Type Mismatch Problem + Solution
Prisma ReturnsGraphQL Entity ExpectsFix
Decimal (Prisma type)numberNumber(order.total)
Date objectstringString(order.createdAt)
OrderStatus enum stringstring (old)Use registerEnumType + type as OrderStatus
✅ Reusable converter pattern you created
// Use Prisma.OrderGetPayload to get correct type with relations
type OrderWithItems = Prisma.OrderGetPayload<{
  include: { orderItems: true };
}>;

convertTypesFromPrismaToGraphql(orders: OrderWithItems[]): GraphQLOrder[] {
  return orders.map(order => ({
    ...order,
    total: Number(order.total),
    createdAt: String(order.createdAt),
    orderItems: order.orderItems.map(item => ({
      ...item,
      price: Number(item.price),
    })),
  }));
}
Every Bug & Mistake — With Explanations
🐛 Mistake 1 — Missing url in datasource block

Initial schema.prisma had datasource db { provider = "postgresql" } with no url. Prisma needs url = env("DATABASE_URL") to know where to connect. Without it, migration fails silently or uses wrong DB.

🐛 Mistake 2 — INT vs Int in Prisma schema

Used quantity INT and orderId INT — Prisma schema is case-sensitive. The correct type is Int (capital I, rest lowercase). INT causes a schema parse error.

🐛 Mistake 3 — orderId type mismatch with id

Defined orderId as Int but Order.id is String. Foreign key type must exactly match the referenced field type. Changed to orderId String.

🐛 Mistake 4 — Prisma v7 ESM vs NestJS CommonJS conflict

Prisma v7 ships as ESM by default. NestJS uses CommonJS. Without moduleFormat = "cjs" in the generator config, the generated client fails to import in NestJS. Fix: add moduleFormat = "cjs" to generator client block.

🐛 Mistake 5 — Using base Prisma Order type instead of OrderGetPayload

Imported Order from Prisma client and tried to access order.orderItems. The base Order type has no relations — it's just the table columns. Must use Prisma.OrderGetPayload<{ include: { orderItems: true } }> to get a type that includes the relation.

🐛 Mistake 6 — status typed as string instead of enum

Initially status on Order entity was typed as string. GraphQL accepted any string — no validation. Fixed by using registerEnumType(OrderStatus, { name: 'OrderStatus' }) and typing the field as OrderStatus. Now GraphQL rejects invalid values at the schema level.

Key Insights & Interview Points
💡 include replaces field resolvers for simple relations

When all data comes from Prisma with include, a @ResolveField is redundant — it adds an extra DB call for data already fetched. Use field resolvers only when the related data comes from a different service or data source.

💡 Prisma nested writes are transactional

When you use orderItems: { create: [...] } inside order.create(), Prisma wraps everything in a single DB transaction. If any item fails to create, the entire order is rolled back. You get ACID compliance for free.

💡 Never use Float for money in a DB

Floating point arithmetic is imprecise — 0.1 + 0.2 = 0.30000000000000004. Always use Decimal (Prisma) or NUMERIC (SQL) for prices, totals, or any financial value. @db.Decimal(10,2) = up to 10 digits, 2 decimal places.

💡 Prisma.ModelGetPayload is the correct type for relations

Base Prisma model types (e.g. Order) only include scalar fields. To get TypeScript types that include relations, use Prisma.OrderGetPayload<{ include: { orderItems: true } }>. This is Prisma's way of typing dynamic query results.

💡 PrismaModule with exports = production best practice

Rather than registering PrismaService in every feature module or flattening everything into AppModule, create a dedicated PrismaModule that exports PrismaService. Any feature module that needs DB access simply imports PrismaModule. Scales cleanly as the app grows.
