Key Patterns Learned
🔄 Dependency Injection (DI) Pattern
❌ WITHOUT DI
class OrdersResolver {
  service = new OrdersService()
  // tightly coupled
  // hard to test
  // can't swap implementation
}
✅ WITH DI
@Injectable()
class OrdersService { }

@Resolver(() => Order)
class OrdersResolver {
  constructor(
    private svc: OrdersService
  ) {} // NestJS injects it
}
How it works: NestJS reads TypeScript type metadata via reflect-metadata. It finds OrdersService registered in providers[], instantiates it once, and injects it wherever requested. You never call new manually.

🔗 Field Resolver + The N+1 Problem

A field resolver is needed when a parent type holds a reference ID but the client expects a full object.

@ResolveField('orderItems', () => [OrderItem])
orderItems(@Parent() order: Order) {
  const ids = order.orderItemIds;  // IDs from parent
  return this.orderService.findItemsByIds(ids);
}

Bugs Caught & Gotchas
🐛 Wrong @Query import package

Imported @Query from @nestjs/common instead of @nestjs/graphql. Always check the package — NestJS has similar decorator names across packages.

🐛 Array @Field missing explicit type

@Field() alone doesn't work for arrays. Must explicitly declare: @Field(() => [String]) or @Field(() => [OrderItem]). GraphQL needs to know the item type.

🐛 Class declaration order matters — TDZ

Used CreateOrderItemInput inside CreateOrderInput before declaring it. Classes are NOT hoisted — they sit in the Temporal Dead Zone like let/const. Decorators execute at load time so they see undefined. Always declare dependencies first.

🐛 Int vs Float for price

Used Int for price field. Int = whole numbers only. Price needs Float for decimals like 999.99.

🐛 GqlExecutionContext in Guards

In REST guards you'd use context.switchToHttp().getRequest(). In GraphQL this returns undefined. Must use GqlExecutionContext.create(context) to unwrap the GraphQL context.

Key Insights
💡 ValidationPipe is just metadata enforcement

@IsNotEmpty() and @Min() decorators do nothing by themselves — they only attach metadata. ValidationPipe reads and enforces that metadata. Without it, empty strings pass through silently.

💡 Field resolver is only needed when parent holds a reference ID

If you embed full objects in the parent directly, no field resolver needed. Field resolvers exist to resolve IDs → full objects, simulating a real DB join across separate tables.

💡 DTO = security boundary, not just validation

DTOs with whitelist: true strip fields the client sends that you didn't declare. This prevents mass-assignment attacks — clients can't inject unexpected fields into your service layer.

Production Tips for Inventeer
🚀 ValidationPipe — Always Use These Options
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,             // strip unknown fields (security)
  forbidNonWhitelisted: true,  // throw if unknown fields sent
  transform: true,             // auto-cast payload to DTO class
}));
whitelist Prevents mass-assignment attacks — client can't inject undeclared fields
transform Auto-converts plain JSON payload into typed DTO class instances
DI Scopes Use Scope.REQUEST for services that hold per-user state — prevents data leaking between requests
