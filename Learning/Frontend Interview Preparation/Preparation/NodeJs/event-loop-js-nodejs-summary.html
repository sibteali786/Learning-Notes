Section 01
What is the Event Loop?
🌐 Browser (Jake Archibald)

JavaScript runs on the main thread — the same thread as rendering, DOM updates, and user interaction. This gives a deterministic, race-condition-free order but means a long-running script blocks everything: animations freeze, clicks go unresponded.


The browser spawns separate threads for networking, crypto, input monitoring etc., but those threads must hand results back to the main thread. The event loop orchestrates that hand-off.

🟢 Node.js

Node uses a single JS thread too, but instead of a browser's main thread it communicates directly with the OS kernel. Most modern kernels are multi-threaded, so Node offloads I/O to them and gets notified via callbacks added to the poll queue.


Node uses libuv — a C library — to implement the event loop and all async behaviours. This gives it 6 named phases, each with its own queue.

💡
The shared core principle Both environments are single-threaded JS runtimes that use an event loop to handle async work without blocking. The difference is what they're managing: a browser manages pixels and user input; Node manages OS-level I/O and file system calls.
Section 02 · Browser Only
The Three Browser Queues

Jake identifies three distinct queues in the browser, each processed differently.

① Task Queue
setTimeout · setInterval · click events · fetch response
1 per loop tick
② rAF Queue
requestAnimationFrame callbacks
All until done · new ones deferred
③ Microtask Queue
Promise .then() · MutationObserver · queueMicrotask()
ALL including newly queued — drains completely
⚠️
The dangerous difference Tasks → only ONE runs before the loop continues. Microtasks → ALL run, including any microtasks queued while processing microtasks. A recursive Promise.resolve().then(loop) will starve the render loop exactly like a while(true).

🟢 poll — The Heart of Node.js

The poll phase is where Node spends most of its time. It has two jobs:

  1. Calculate how long to block waiting for I/O
  2. Process events in the poll queue

If the queue is empty and no setImmediate() is pending → Node blocks here waiting for new I/O. This is what makes Node efficient for servers.

🟡 setImmediate() vs setTimeout(0)

Outside an I/O callback → order is non-deterministic (depends on process startup time).


Inside an I/O callback (e.g. inside fs.readFile) → setImmediate() always runs first because check phase comes before the next timers phase.

// Inside I/O callback — always: immediate → timeout fs.readFile('file', () => { setTimeout(() => console.log('timeout'), 0); setImmediate(() => console.log('immediate')); }); // Output: immediate → timeout (always)
🔴 process.nextTick() — The Queue Jumper

Not technically a phase. Its queue drains after every operation, before the loop moves to the next phase — even before Promise microtasks.


Use case: guarantee a callback runs async (after current call stack) without waiting for I/O.

⚠️
Can starve I/O — recursive nextTick calls prevent the poll phase from ever running, blocking all file/network callbacks.

Section 05
Microtasks — The Most Misunderstood Part
Origin Story (from Jake's Talk)

Microtasks were invented for MutationObserver in the browser. The old system (mutation events) fired 200 events for inserting 100 spans. Microtasks batch those into a single callback fired after JS finishes — much more efficient. Promises then adopted the same queue.

Both Task Queue

One item processed per loop tick. Additional items queued during processing go to the end of the queue — processed in a future tick.

Browser rAF Queue

All current items run to completion. Items queued while processing rAF callbacks are deferred to the next frame.

Both Microtask Queue

All items drain completely — including items queued during processing. A recursive microtask loop blocks the render loop permanently.

⚠️
Microtasks run whenever the JS stack empties — not just between tasks They can fire mid-task, inside rAF callbacks, anywhere. This is what guarantees Promise callbacks always see a consistent, fully-initialised state.
⚡ Jake's Classic Quiz — Two Event Listeners

What's the log order when a user physically clicks vs when you call button.click() in JS?

button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('Microtask 1'));
  console.log('Listener 1');
});
button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('Microtask 2'));
  console.log('Listener 2');
});
👆 User clicks (physical)
Each listener runs in its own task.
Stack empties after Listener 1 → microtasks drain.

Listener 1 → Microtask 1 → Listener 2 → Microtask 2
💻 button.click() in JS
JS stack never empties between listeners (button.click() hasn't returned). Microtasks only drain after both listeners complete.

Listener 1 → Listener 2 → Microtask 1 → Microtask 2

⚠️ Real-world impact: automated tests clicking via JS may see different behaviour than a real user click. Also affects event.preventDefault() in async listeners.

Section 07 · Node.js Only
process.nextTick() — When and Why
Use Case 1 — Consistent Async API

Guarantee a callback is always called asynchronously, even if the error is detected synchronously. This prevents bugs where callers haven't finished setting up yet.

function apiCall(arg, callback) { if (typeof arg !== 'string') { return process.nextTick( callback, new TypeError('must be string') ); } // ... do real work } // callback fires AFTER apiCall returns // so caller is fully initialised
Use Case 2 — EventEmitter in Constructor

Emitting an event in a constructor fires before the caller can attach a listener. nextTick defers the emit until the constructor returns.

class MyEmitter extends EventEmitter { constructor() { super(); process.nextTick(() => { this.emit('ready'); }); } } const e = new MyEmitter(); e.on('ready', () => { console.log('works!'); // ✅ });
📌
Names are swapped — a historical quirk process.nextTick() fires more immediately than setImmediate(), even though the names imply the opposite. The Node.js team acknowledges this but can't change it without breaking npm. The recommendation: prefer setImmediate() when you just need to defer work.

Section 09 · Interview Focus
Top Interview Gotchas
🎯
setTimeout(fn, 0) is NOT immediate Browser uses ~4.7ms minimum. It's a macrotask — rendering and microtasks run before the next setTimeout fires.
🎯
Promise loop blocks like while(true) Microtasks drain fully — including newly queued ones. A recursive Promise loop starves rendering.
🎯
user click vs button.click() are different JS-triggered click keeps the stack non-empty between listeners — microtasks don't fire mid-dispatch.
🎯
process.nextTick beats Promise.then in Node Even though both are "microtask-like", nextTick has its own queue that drains first.
🎯
setImmediate vs setTimeout — non-deterministic at top level Inside an I/O callback → setImmediate always wins. Outside → unpredictable.
🎯
CSS changes batch until render steps Setting display 100 times in one task costs the same as setting it once — browser only reads final state.
