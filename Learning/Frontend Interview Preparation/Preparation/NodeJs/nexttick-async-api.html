Node.js · process.nextTick() · Use Case 1

Why defer errors when you could throw immediately?

It's not about delaying the error — it's about when the caller is ready to handle anything at all.

🔑
The Real Problem — Mixed Sync/Async Behaviour

The happy path (real work) is always async. If the error path is sync, your callback fires at two different times depending on which branch ran. Callers can't write predictable setup code around that.

Section 01 · The Bug
Without nextTick — Synchronous Error Path
📄 How you wrote it (source order)

Looks completely logical top-to-bottom...

function apiCall(arg, callback) { if (typeof arg !== 'string') { callback(new Error('bad arg')) return } } // 1. call apiCall apiCall(123, (err) => { errorHandled = true // looks like step 2 }) // 2. set up state let errorHandled = false // looks like step 3 console.log(errorHandled) // expect: true? false?
💥 What actually executes (runtime order)

Callback fires before caller finishes setup...

1
apiCall(123, callback) is called
jumps into function immediately
2
callback(new Error()) fires RIGHT NOW 🔴
synchronous — inside the if-block
3
errorHandled = true
runs inside callback — caller not ready yet
4
apiCall returns
callback already done by now
5
let errorHandled = false 😱
RESETS to false — callback already set it to true on step 3
6
console.log(errorHandled)
prints: false — even though callback ran ✓
💥 errorHandled = false — callback fired too early
🐛
The hidden bug

let errorHandled = false appears after apiCall() in source — but JS hoists the declaration and the assignment runs after apiCall() returns. Since the callback fired synchronously inside apiCall(), it ran before that assignment — then got overwritten back to false.

Section 02 · The Fix
With nextTick — Always Async
✅ Fixed with process.nextTick
function apiCall(arg, callback) { if (typeof arg !== 'string') { // schedule — don't fire immediately process.nextTick( callback, new Error('bad arg') ) return } } apiCall(123, (err) => { errorHandled = true // ✅ runs AFTER everything below }) let errorHandled = false // ✅ sets up correctly console.log(errorHandled) // → false (expected — callback hasn't fired yet) // → callback fires → errorHandled = true ✅
✅ Runtime order — now predictable
1
apiCall(123, callback) is called
2
process.nextTick schedules callback 🟣
does NOT fire now — queued for later
3
apiCall returns immediately
4
let errorHandled = false ✅
sets up correctly — callback hasn't run yet
5
console.log(errorHandled) → false ✅
expected — nothing has handled it yet
6
call stack empties
all sync code done — nextTick queue drains
7
callback fires 🟣
errorHandled = true — caller fully set up ✅
✅ errorHandled = true — at the right time
Section 03 · The Actual Rule
Why This Happens — Mixed Timing is the Root Cause
❌ Mixed timing (BAD)
Error path → sync callback
Happy path → async callback

Caller can't predict when their callback fires — setup code order matters in unexpected ways.
⚠️ Always sync (also BAD)
Both paths fire callback synchronously.

Blocks the event loop. Prevents caller from setting up listeners after the call.
✅ Always async (GOOD)
Both paths defer via nextTick.

Caller always finishes their setup first. Callback always fires after current call stack is done.
🎯
The contractor analogy

You give a contractor your phone number before you leave home. If they call you before you leave (sync), you're not ready — keys aren't in hand, car isn't started. If they call after (async via nextTick), you're fully set up and can actually deal with the problem.

The Rule to Remember
A function must be either always sync or always async —
never sometimes one, sometimes the other.
process.nextTick() on the error path isn't about delaying the error.
It's about making callback timing consistent and predictable for the caller — regardless of which branch ran.
