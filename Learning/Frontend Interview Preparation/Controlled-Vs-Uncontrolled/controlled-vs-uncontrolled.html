Controlled vs Uncontrolled Components

Reference: react.dev — Sharing State Between Components

1. The Core Idea in One Line

Uncontrolled = component owns its state (source of truth = useState inside it).
Controlled = parent owns the state (source of truth = props passed in); component just renders what it's told.

3. Why You'd Lift State Up (the Accordion Example)

Two independent Panels, each with their own isActive. Requirement changes: only one panel open at a time. Independent state can't coordinate — you must move it up.

1
Remove state from the children. Panel no longer has useState(false) — it receives isActive as a prop instead.
2
Move the state to the closest common parent — Accordion now holds activeIndex.
3
Pass down both the derived value (isActive={activeIndex === 0}) and an event handler (onShow={() => setActiveIndex(0)}) so children can request a change without owning the state themselves.
Real-world scenario (your Tabs case): Uncontrolled Tabs is fine for a standalone widget. But if a parent page needs to deep-link to a specific tab via URL (?tab=css), or fire analytics on every switch, the parent needs to own activeTab — that forces Tabs into controlled mode: <Tabs value={activeTab} onChange={setActiveTab} />.

4. Side-by-Side Comparison

AnalogyUncontrolled <input> — DOM tracks its own valueControlled <input value={x} onChange={...}>

5. Interview Tip

It's rarely all-or-nothing — per React docs: "each component usually has some mix of both local state and props." Many production components support both: uncontrolled by default (defaultValue prop) with an escape hatch to go controlled (value + onChange) — this is exactly what the Tabs challenge solution proposes, and how Radix/Headless UI/React Aria all do it.

Always clarify with your interviewer which one they want before you start coding — it changes your prop API from the first line.
