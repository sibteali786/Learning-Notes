⚛️ Vanilla JS vs React Hook

Same mechanism underneath — different lifecycle management

Vanilla JS

State storageLoose top-level variables (page, loading)
Sentinel lifecycleLives in HTML forever, never removed
Observer cleanupNever — page reload is the only "cleanup"
End of listNot handled — loops forever
Error handlingNone — fake fetch never fails
Re-render costN/A — direct DOM manipulation

React Hook

State storageuseState (items/loading/hasMore) + useRef (page/sentinel)
Sentinel lifecycleConditionally rendered — unmounts when hasMore=false
Observer cleanupuseEffect return fn calls disconnect() on unmount/dep change
End of listhasMore stops both fetches and observer re-attachment
Error handling.catch() + .finally() guarantee loading resets
Re-render costOnly items changes trigger re-render — page counter doesn't
Q: Why no root in the constructor?
root: null (default) watches the browser viewport — fine only if the scroll container IS the page. Our Feed div has its own overflowY: auto, so it's a separate scroll box. Missing this can cause the sentinel to misfire relative to the actual visible area.
✅ Fix: pass a containerRef for the scrolling div into root so intersection is measured against the real scroll box, not the page.
Q: What is pageRef for?
It's the pagination cursor ("which page to fetch next"). It's a ref, not state, because: (1) it needs to be read synchronously inside loadMore — state updates are async/batched; (2) bumping it shouldn't itself trigger a re-render — only items changing should update the UI.
Q: Where is the sentinel actually removed?
Not imperatively — it's conditionally rendered: {hasMore && <div ref={sentinelRef} />}. When hasMore becomes false, React unmounts it on the next render. The useEffect's cleanup (triggered by hasMore in the dependency array) disconnects the old observer at the same time — so nothing is left watching a sentinel that no longer exists.
