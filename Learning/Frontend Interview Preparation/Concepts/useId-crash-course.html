useId — When, Why, and Why Not the Alternatives

References: react.dev/reference/react/useId · GreatFrontEnd quiz

1. Unfamiliar Terms First

SSR (Server-Side Rendering) — the server runs your React components and produces finished HTML before sending it to the browser, instead of the browser building the page from scratch with JS.
Hydration — once that server-made HTML lands in the browser, React "wakes it up": attaches event handlers, wires up state, without re-building the DOM from scratch. For this to work correctly, the client must render the exact same output the server did — same elements, same ids, same everything.
Hydration mismatch — when client output differs from what the server sent (e.g. different generated ids). React throws a warning and may discard/redo that part of the tree — wasted work, visible flicker, sometimes broken interactivity.
Client-rendered — the browser does all the rendering work itself, from an empty HTML shell + JS bundle. No server HTML to match, so no hydration concerns — this is why useId issues mostly matter once SSR enters the picture.

2. What useId Actually Solves

The real problem isn't "how do I make a unique string" — Math.random() could technically do that. The real problem is: the server generates HTML first, the client re-renders separately to hydrate it, and both must produce identical ids — deterministically, regardless of render order, Suspense timing, or streaming chunk order.
Concrete failure without useId: server renders 3 components, a global counter assigns ids 1, 2, 3. On the client, due to streaming/Suspense, component 3 happens to hydrate before component 1 — counter now assigns 1, 2, 3 in a different order to different components. Client id ≠ server id for that DOM node → hydration mismatch → React discards and re-renders that subtree.

useId avoids this because the ID is derived from the component's position in the tree ("parent path"), not from render order or timing — so server and client always compute the same value for the same component, independent of when each one actually runs.

3. Why Not the Obvious Alternatives

ApproachSSR-safe?Stable across re-renders?Why it fails
Math.random()✗✗New value every call — server and client never match, and it changes every render even client-side.
Array index in .map()✗✗Not about SSR directly — the real issue is index isn't tied to the data. Reordering/inserting/filtering the list shifts indices, so id-to-element mapping silently breaks. (This is the same root problem as using index as a key.)
Module-level counter (let next = 0)✗✓ (within one session)Was the pre-React-18 workaround. Breaks because server/client can increment in different orders — same failure mode as above, just less obviously random.
crypto.randomUUID() / nanoid✗ (if called during render)✗Same as Math.random for render-time generation — different value per environment/render. Fine outside render, for data that needs to persist.
useId()✓✓Derived from tree position — deterministic on server and client regardless of timing.

4. Why useId Is NOT a List Key

✗ WRONG 
{items.map(item => {
  const id = useId(); // ✗ hook in a loop!
  return <li key={id}>...</li>
})}

Two separate violations: (1) hooks can't be called inside loops — breaks the Rules of Hooks; (2) even if it worked, the id identifies tree position, not the underlying data item.

✓ CORRECT 
{items.map(item => (
  <li key={item.id}>...</li>
))}

key must come from your data (DB id, slug) so React can track which item moved/was removed when the list reorders.

Concrete break scenario: if you used useId-per-render as a key, and the list gets reordered (drag-and-drop, sort, filter), the key is tied to position in the tree, not the item — so React thinks item content changed in place rather than "this item moved," and reconciliation does the wrong thing (wrong DOM node reused, state attached to the wrong row, stale inputs, etc). Keys must survive reordering; useId does not — it survives re-renders of the *same* component instance, but not changes to the *identity* of list membership.

5. Practical Usage Patterns

Single element

const id = useId();
<input id={id} />
<label htmlFor={id}>

Multiple related elements

const id = useId();
// call once, suffix per element
`${id}-firstName`
`${id}-lastName`

Multiple React roots

createRoot(el, {
  identifierPrefix: 'app-a-'
})

Prevents collisions when 2+ independent React apps share one page.

6. Your Tabs Case, Mapped to the Rule

You called useId() once at the top of Tabs (not inside the `.map()`), then concatenated it with value (data-derived, stable) for each tab/panel pair. That's exactly the correct pattern: one hook call per component instance, suffixes built from data for per-item uniqueness — SSR-safe, and never touching key.
