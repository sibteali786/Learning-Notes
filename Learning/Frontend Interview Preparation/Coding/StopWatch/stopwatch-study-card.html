Stopwatch — Study Card

Timestamp-anchored timing, ref-vs-state discipline, and the tick-boundary bug most solutions quietly ship. Comparing your build against the official reference.
Time source: Date.now() Your tick interval: 10ms Official tick interval: 1ms

Core principles

Drift-proof timingcore mechanic
Never accumulate with interval += tickMs — ticks aren't guaranteed to fire exactly on schedule (event loop, tab throttling). Anchor to a real timestamp instead: elapsed = accumulated + (Date.now() - startTimestamp). Self-correcting even if a tick fires late.
ref vs statedecision rule
Ask: does changing this need to update the screen on its own? Yes → useState (button label, running flag). No, it's just math bookkeeping another render will pick up → useRef (timestamps, accumulators).
Dummy re-render triggerpattern
forceTick(n => n+1) — a state variable whose value is meaningless, used purely so React recomputes derived values every interval. Always changes → never bailed out by Object.is.
Single source of trutharchitecture
Derive elapsedTime fresh every render from refs, rather than storing it as state you must remember to sync at every stop/reset call site. One formula, computed at render time, can't go stale.
Object.is bailoutgotcha
setState(sameValue) skips re-render silently. Don't rely on a boolean flip alone to guarantee a redraw if it might already be at that value — this is exactly why forceTick exists as a fallback.
Separation of concernsdesign
formatTime() returns plain numbers — pure data transform, testable in isolation. Omission logic (show hours only if >0) and styling live in JSX, the presentation layer.
A11y for rapid updatesaccessibility
aria-live="off" + a stable aria-label stop assistive tech from trying to announce a number changing 100×/sec. The Start/Stop label change gets announced for free via default button focus semantics — no extra ARIA needed there.

Your approach vs. the official solution

The bug the official solution has (and why it's invisible)

t=100ms last interval tick fires → lastTickTiming.current = 100
t=100.6 user clicks Stop — between ticks
stopInterval() → clears interval, nulls timerId. No final delta computed.
result the 0.6ms between last tick and actual click is silently dropped from totalDuration

This is the exact "two sources of truth" risk flagged earlier when choosing between storing elapsedTime directly as state vs. deriving it fresh from refs. The official solution accepted the risk and made it invisible by choosing a 1ms tick — smaller than what any display resolution (centiseconds) could ever show. Your anchor-based design has no such drift, at any tick interval, because accumulatedTime.current = elapsedTime captures the exact value at the exact click moment — never an interpolated tick value.

Complexity

O(1)
Time per tick — fixed number of arithmetic ops + one state update, regardless of how long the stopwatch has run.
O(1)
Space — fixed variable count. Would become O(n) only with an added feature like lap history.
