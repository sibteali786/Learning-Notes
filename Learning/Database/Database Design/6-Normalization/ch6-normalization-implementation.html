② What Is Normalization?

Definition

Normalization is the process of organizing a database to minimize redundancy and dependency while maximizing data integrity and consistency. It breaks the DB into smaller, more manageable tables — each representing a single entity or concept.

Primary goal: strengthen data integrity.

Normal Forms — Nested Dolls

Normal forms are hierarchical and sequential — each builds on the previous:

  • 1NF → no multivalued columns
  • 2NF → all columns depend on the full PK
  • 3NF → no transitive dependencies
  • BCNF → stricter 3NF (covers edge cases)
  • 4NF, 5NF, 6NF — beyond book scope (multivalued/join deps)

In practice: achieve BCNF = fully normalized.

Key Hierarchy: Superkey → Candidate Key → Primary Key

Superkey

A set of one or more columns that can uniquely identify a row. May contain unnecessary columns.

Candidate Key

A minimal superkey — a superkey with no unnecessary columns. A table can have multiple candidate keys.

Primary Key

One candidate key chosen as the definitive row identifier. Every table must have exactly one.

③ BCNF Rule 1 — Always Has a Primary Key

Rule

Every table in BCNF must have a primary key. Without one, you cannot uniquely identify rows, enforce referential integrity, or link tables reliably.

Check the E-R diagram from Ch5 — every entity has a PK. If any table is missing one, stop and assign a PK before proceeding.

④ BCNF Rule 2 — No Multivalued Columns (1NF)

What Is a Multivalued Column?

A column that holds multiple values in a single cell. Example: a course column in course_registration that stores a list like "Math, Physics, History" in one row.

Problems: difficult querying, data redundancy, inconsistency, update/deletion anomalies.

Who Decides if It's Multivalued?

The users of the application decide. A column is multivalued if users consider each stored item an indivisible unit of value.

✅ phone number → multivalued if multiple phones stored per row (each number is indivisible to users).
✅ email address storing one email per row → NOT multivalued (users don't care about username@domain split).

Fix Pattern

Redesign the column to hold only a single value per row. Usually this means moving the multivalued column into a separate table to prevent redundancy.

Example Fix: course_registration
-- BEFORE: multivalued column (violation)
course_registration
student_id | name    | course
-----------|---------|------------------
1          | Alice   | Math, Physics
2          | Bob     | History

-- AFTER: split into two tables
student
student_id | name
-----------|--------
1          | Alice
2          | Bob

course_registration
student_id | course
-----------|--------
1          | Math
1          | Physics
2          | History
✅ Sci-Fi Collective has no multivalued columns. All columns were designed to hold single values per row from the start.
⑤ BCNF Rule 3 — All Columns Dependent on Key Only (2NF + Functional Dependency)

What Is Functional Dependency?

Given a value of column A, if there is always a unique corresponding value of column B → A functionally determines B (B is functionally dependent on A).

Notation: A → B

Directional! employee_id → employee_name does NOT mean employee_name → employee_id (two employees could share a name).

BCNF Requirement

All columns must be functionally dependent on the primary key and only the primary key. If any column depends on something else, the table violates BCNF.

Fix: break the table into two (or more) tables — each containing only columns dependent on its key. Link via FK where needed.

Example: Bad product table
-- VIOLATION: supplier_contact depends on
-- supplier_name, NOT on product_id
product
product_id → product_name, supplier_name, category
supplier_name → supplier_contact  ← violation!
-- FIX: split into two tables
product(product_id PK, product_name, category,
         supplier_id FK)
supplier(supplier_id PK, supplier_name,
          supplier_contact)
Sci-Fi Collective: Normalizing the purchase Table

Problem Found in purchase

The purchase table had two functional dependencies:

purchase_id → total_price, purchase_time,
             payment_id, email
purchase_id + code → product_quantity,
                     product_price

product_quantity and product_price depend on both purchase_id AND product code — not on purchase_id alone. BCNF violation.

Trying to insert one receipt's multiple products → impossible (can't repeat the PK).

Fix: Move to purchase_product

Move product_quantity and product_price to the purchase_product junction table (composite PK: purchase_id + code).

Also add product_name to purchase_product — even though it exists in product table. Why?

Product prices and names can change over time. A receipt from 6 months ago must reflect the price and name at time of purchase, not today's values.

-- BEFORE: purchase table (violation)
purchase(purchase_id PK, total_price,
  purchase_time, email FK, payment_id FK,
  product_price, product_quantity) ← wrong!

-- AFTER: two clean tables
purchase(
  purchase_id PK,
  total_price,
  purchase_time,
  email FK → user,
  payment_id FK → payment_method
)

purchase_product(
  purchase_id PK+FK → purchase,
  code        PK+FK → product,
  product_price     ← snapshot at time of sale
  product_quantity,
  product_name      ← snapshot at time of sale
)
💡 Storing product_price and product_name in purchase_product is intentional denormalization for historical accuracy. A receipt must never change even if the product's current price does.
🔬 BCNF Edge Cases (advanced): (1) If a non-PK column depends on only part of a composite PK → violates 2NF. (2) If a non-PK column depends on another non-PK column that depends on PK → 3NF but not BCNF. (3) If a column depends on an alternate candidate key → still in BCNF. Rarely encountered in practice.
⑥ BCNF Rule 4 — No Transitive Dependency (3NF)

What Is Transitive Dependency?

When a non-key column depends on another non-key column, which itself depends on the PK. A chain: PK → col_A → col_B.

Problems: data redundancy, update anomalies (must update same value in every row), insertion/deletion anomalies.

Classic Example: employee Table

employee_id → department_id → department_name
-- department_name transitively depends on
-- employee_id via department_id

If you rename a department, you must update every single row for all employees in that department. Miss one → inconsistency.

Fix Pattern

Break the table into two tables — each containing columns directly dependent on its own key. Link via FK.

employee(employee_id PK, name, dept_id FK)
department(dept_id PK, department_name)

Sci-Fi Collective: The 3-Table Cycle Problem

After normalization, the purchase table had two FKs: email (→ user) and payment_id (→ payment_method).

But payment_method already has email as its own FK → user.

This creates a transitive chain:

purchase → user (direct via email FK)
purchase → payment_method → user (indirect)
= transitive dependency + cycle in E-R!

⚠️ Signal: If you have 3 tables connected in a cycle using 3 relationships, you likely have a transitive dependency.

Fix: Remove email from purchase

Remove the direct email FK from purchase. The user is still reachable via: purchase → payment_method → user.

Trade-off: Normalization is the correct move here, but it may slow down queries that need user info from purchase. This is revisited in Ch7 (Denormalization).

📐 Rule of thumb: If you need only N relationships to connect N tables, but you're using N+1 (forming a cycle) → investigate for transitive dependency. In theory, 3 tables need only 2 relationships.

⑧ Implementation — SQL Constraints Overview

What Are Constraints?

SQL rules applied to columns (or tables) to ensure data accuracy and reliability. They enforce data integrity and can be defined during or after table creation. When applied, developers must follow your design — the DB engine enforces it automatically.

NOT NULL

Column cannot accept NULL values. Applied to critical business data like usernames, emails, passwords.

PRIMARY KEY

Unique + NOT NULL on PK column(s). No duplicate rows, no NULL PKs. Can be composite.

FOREIGN KEY

Enforces referential integrity. Prevents orphan rows. Links child to parent table via PK reference.

UNIQUE

All values in a column (or column combo) must be distinct. For non-PK columns that must be unique.

DEFAULT

Sets a default value when none is provided. Handy for timestamps, numeric placeholders, optional fields.

CHECK

Validates data against a custom condition. Enforces ranges, formats, allowed value lists.

💡 Naming constraints is a best practice (not required). Named constraints: (1) communicate purpose clearly, (2) produce helpful error messages on violation, (3) avoid confusing auto-generated names that vary across RDBMSs, (4) are essential when you may need to restructure or migrate the DB. Exception: NOT NULL and DEFAULT are usually left unnamed as they're part of column definitions.
⑨ NOT NULL Constraint

When to Use

  • Columns with critical business data (username, email, password)
  • Legal/compliance columns (date of birth in financial apps)
  • Foreign keys in mandatory relationships (min cardinality = 1)
  • Columns used in aggregations/analytics

Note: PRIMARY KEY already implies NOT NULL — don't add it to PK columns.

Sci-Fi Collective: user Table

6 columns need NOT NULL: username, email (PK = implicit), password, first_name, last_name, last_login_time.

phone_number is optional → nullable.

-- MySQL, MariaDB, SQLite
CREATE TABLE user (
  email         VARCHAR(320) PRIMARY KEY,
  username      VARCHAR(30)  NOT NULL,
  password      VARCHAR(20)  NOT NULL,
  first_name    VARCHAR(50)  NOT NULL,
  last_name     VARCHAR(50)  NOT NULL,
  phone_number  VARCHAR(15),  -- nullable
  last_login_time TIMESTAMP  NOT NULL
);
⑩ PRIMARY KEY Constraint

What It Does

  • Prevents duplicate rows with same PK value
  • Guarantees no NULL in PK column
  • Implicit NOT NULL — no need to add separately

Composite Primary Key

When PK spans multiple columns (e.g., purchase_product), define it separately from column definitions using CONSTRAINT … PRIMARY KEY (col1, col2).

Each column in a composite PK must have NOT NULL explicitly.

-- Simple PK (inline)
CREATE TABLE user (
  email VARCHAR(320) PRIMARY KEY,
  ...
);

-- Named PK (best practice for migratable DBs)
CREATE TABLE user (
  email VARCHAR(320),
  ...,
  CONSTRAINT pk_user
    PRIMARY KEY (email)
);

-- Composite PK
CREATE TABLE purchase_product (
  purchase_id  INT          NOT NULL,
  code         CHAR(12)     NOT NULL,
  product_price DECIMAL(7,2) NOT NULL,
  product_quantity INT      NOT NULL,
  product_name VARCHAR(100) NOT NULL,
  CONSTRAINT pk_purchase_product
    PRIMARY KEY (purchase_id, code)
);
⑪ FOREIGN KEY Constraint & Referential Actions

What It Does

Enforces referential integrity — prevents inserting a FK value that doesn't exist in the parent table. The table with the FK = child table. The referenced table = parent table.

FK in a mandatory relationship (min cardinality = 1) must also be NOT NULL.

Syntax Options

Define inline during CREATE TABLE, or add afterward with ALTER TABLE ADD CONSTRAINT.

⚠️ SQLite does NOT support ALTER TABLE ADD CONSTRAINT — must define inline.

-- MySQL, MariaDB
CREATE TABLE review (
  review_id   INT          PRIMARY KEY,
  review_text TEXT         NOT NULL,
  review_time TIMESTAMP    NOT NULL,
  email       VARCHAR(320) NOT NULL,
  code        CHAR(12)     NOT NULL,
  CONSTRAINT fk_user_review
    FOREIGN KEY (email)
    REFERENCES user(email),
  CONSTRAINT fk_product_review
    FOREIGN KEY (code)
    REFERENCES product(code)
);
Referential Actions — What Happens When Parent Row Changes?
RESTRICT / NO ACTION Default. Block DELETE/UPDATE on parent if child rows exist. Maintains integrity by preventing orphan rows. default
CASCADE DELETE CASCADE: deleting parent row auto-deletes all child rows. UPDATE CASCADE: updating parent PK auto-updates all child FKs. Keeps link intact. most common
SET NULL Deleting parent row sets child FK to NULL (child row preserved). Use when relationship is non-essential or child data must be kept for records. ⚠️ Can create orphan rows / complicate queries. use with care
Sci-Fi Collective: payment_method with CASCADE
-- If user changes email or deletes account → cascade to payment_method
CREATE TABLE payment_method (
  payment_id  INT          PRIMARY KEY,
  name        VARCHAR(30)  NOT NULL,
  card_number CHAR(16)     NOT NULL,
  expiry_date CHAR(4)      NOT NULL,
  email       VARCHAR(320) NOT NULL,
  CONSTRAINT fk_payment_method_user
    FOREIGN KEY (email) REFERENCES user(email)
    ON DELETE CASCADE
    ON UPDATE CASCADE
);
⑫ UNIQUE Constraint

When to Use

When a non-PK column (or combination) must contain all distinct values — duplicates make no real-world sense.

Examples: Social Security Number, username, phone number, email in a non-PK context, (product_name + manufacturer) combo.

Sci-Fi Collective Cases

  • username in user → must be unique
  • phone_number in user → must be unique
  • (name, manufacturer) in product → combo must be unique
-- Single column UNIQUE
CREATE TABLE user (
  email         VARCHAR(320) PRIMARY KEY,
  username      VARCHAR(30)  NOT NULL,
  phone_number  VARCHAR(15),
  ...,
  CONSTRAINT unq_username
    UNIQUE(username),
  CONSTRAINT unq_phone_number
    UNIQUE(phone_number)
);

-- Multi-column UNIQUE (combo must be unique)
CREATE TABLE product (
  code         CHAR(12)     PRIMARY KEY,
  name         VARCHAR(100) NOT NULL,
  manufacturer VARCHAR(100) NOT NULL,
  ...,
  CONSTRAINT unq_name_manufacturer
    UNIQUE(name, manufacturer)
);
⑬ DEFAULT Constraint

When to Use

  • Timestamp columns (row creation/modification time)
  • Numeric columns used in aggregations
  • Optional columns that need a placeholder

⚠️ DEFAULT does not prevent NULL insertion — still add NOT NULL if NULLs are problematic.

UTC Time Zone Warning

CURRENT_TIMESTAMP behavior varies by RDBMS:

  • MySQL/MariaDB → stores UTC by default ✅
  • PostgreSQL → use TIMESTAMP WITH TIME ZONE to get UTC ✅
  • SQLite/SQL Server → check manual or ask AI assistant
-- MySQL/MariaDB/SQLite
CREATE TABLE purchase (
  purchase_id  INT            PRIMARY KEY,
  total_price  DECIMAL(13,2)  NOT NULL,
  purchase_time TIMESTAMP     NOT NULL
               DEFAULT CURRENT_TIMESTAMP,
  payment_id   INT            NOT NULL,
  CONSTRAINT fk_payment_method_purchase
    FOREIGN KEY (payment_id)
    REFERENCES payment_method(payment_id)
);

-- PostgreSQL (explicit UTC)
CREATE TABLE purchase (
  purchase_id  INT                       PRIMARY KEY,
  total_price  DECIMAL(13,2)              NOT NULL,
  purchase_time TIMESTAMP WITH TIME ZONE  NOT NULL
               DEFAULT CURRENT_TIMESTAMP,
  payment_id   INT                       NOT NULL,
  ...
);
⑭ CHECK Constraint

When to Use

  • Enforce data ranges (e.g., age 0–120)
  • Validate allowed values (e.g., US state names)
  • Enforce complex business logic that other constraints can't handle

Sci-Fi Collective: state column

Both user_address and billing_address have a state column. Valid values = exactly 50 US state names. Use CHECK … IN (…) to enforce this at DB level, taking the burden off front/backend devs.

Add via ALTER TABLE after creation (since the list is long).

-- MySQL, MariaDB, PostgreSQL, Oracle
CREATE TABLE user_address (
  email         VARCHAR(320) PRIMARY KEY,
  street_address VARCHAR(255),
  address_line_optional VARCHAR(100),
  city          CHAR(100)   NOT NULL,
  state         VARCHAR(20) NOT NULL,
  postal_code   CHAR(5)     NOT NULL
);

-- Add constraint after (50 values is long)
ALTER TABLE user_address
  ADD CONSTRAINT chk_state
  CHECK (state IN (
    'Alabama', 'Alaska', 'Arizona', 'Arkansas',
    'California', ..., 'Wyoming'
  ));

⑯ Interview / Practical Tips
🎯BCNF = the practical target for full normalization. It subsumes 1NF, 2NF, and 3NF. Achieve BCNF on all tables → done.
🔗Functional dependency is directional. employee_id → name does NOT imply name → employee_id. Always check both directions.
🔄3-table cycle = red flag. If 3 tables are connected in a cycle via 3 relationships, investigate for transitive dependency. Theory says 3 tables only need 2 relationships.
🧾Snapshot pattern: Store product_price and product_name in purchase_product even though they exist in product. Receipts must be immutable — prices and names change over time.
🏷️Always name constraints (except NOT NULL and DEFAULT). Named constraints = readable schema + helpful error messages + portable across RDBMSs.
⚡CASCADE is your best friend for user account management — if a user deletes their account, CASCADE deletes their payment methods, addresses, reviews, and purchases automatically.
⚠️SET NULL is a last resort — creates orphan rows and complicates queries expecting non-null FKs. Use only when child data must survive parent deletion for recordkeeping.
🕐Always use TIMESTAMP WITH TIME ZONE in PostgreSQL for UTC timestamps. MySQL/MariaDB store UTC by default, but always verify with your specific RDBMS manual.
🔒Constraints shift data integrity responsibility from application code to the DB engine. Even if a developer bypasses the API and writes directly to the DB, constraints still hold.
⑰ Chapter Recap

Normalization Summary

Breaking DB into smaller tables each representing one entity/concept. Target: BCNF. Process: check each table against 4 rules, identify violations, revise design.

4 BCNF Requirements

  • Has a primary key
  • No multivalued columns
  • All columns dependent on key only
  • No transitive dependency

Sci-Fi Changes Made

  • Moved product_price, product_quantity → purchase_product
  • Added product_name to purchase_product (snapshot)
  • Removed email FK from purchase (transitive dep)

Constraints Summary

  • NOT NULL + PRIMARY KEY = data presence & uniqueness
  • FOREIGN KEY = referential integrity (+ CASCADE/SET NULL)
  • UNIQUE = non-PK uniqueness
  • DEFAULT = auto-fill on insert
  • CHECK = custom validation rules

Naming Best Practice

Name all constraints that might need to be referenced, restructured, or migrated: PKs, FKs, UNIQUEs, CHECKs. Leave NOT NULL and DEFAULT unnamed (inline is fine).
