② What Is an E-R Diagram?

Definition

Entity-Relationship (E-R) diagrams are graphical representations of entities and their relationships. They describe data structure (schema) — not data itself. A table with 10M rows is still one box.

Components

Boxes = entities (tables)
Lines = relationships between entities
Crow's Foot symbols = cardinality (min/max instances)

Notation Used

Information Engineering / Crow's Foot notation — industry standard. Other types: Chen notation (historic), UML, IDEF1X. This book uses Crow's Foot exclusively.

Purpose

Not just visual — it's a contract between designers, devs, and stakeholders. Complex apps may need multiple E-R diagrams. The Sci-Fi Collective store needs just one.

④ Cardinality — Direction & Representation

Definition

Cardinality describes the number of instances of one entity that can be associated with a single instance of another entity via a relationship.

Every relationship has two directional relationships. Each direction is read separately:

e.g., user ↔ account:
→ "A user has zero, one, or more accounts."
→ "An account belongs to one and only one user."

Min & Max Cardinality

Inner symbol (closer to center of line) = min cardinality — minimum instances of B that one instance of A must associate with.

Outer symbol (near entity B) = max cardinality — maximum instances of B that one A can associate with.

Symbols are placed near the entity being described on the relationship line.

📐 Chen vs Crow's Foot notation: Chen notation has historic significance (uses mathematical symbols like 1, M, N). Crow's Foot is simpler, more popular among professionals, and is used throughout this book.
⑤ One-to-One Relationships — "A Perfect Match"

Definition

Each record in entity A relates to at most one record in entity B, and vice versa. One-to-one refers primarily to the max cardinalities of both directions being 1. Min cardinalities can be 0 or 1.

Implementation Problem — The Chicken-and-Egg Issue

If both min cardinalities are 1, you can't insert data into either table first — foreign key constraints block you both ways. Solution: relax one min cardinality from 1 to 0.

Example: department ↔ manager. Can't insert a department without a manager ID and vice versa.
Fix: "A department has zero or one manager."

Where Does the Foreign Key Go?

In a 1:1 relationship, place the FK on the side with min cardinality = 0 (the optional side). That side's table is "table B" — it holds the FK pointing to table A.

Rule: If the directional relationship from A → B has min cardinality = 0, place FK in B.

⑥ One-to-Many Relationships — "A Love Triangle"

Definition

The most common cardinality type. One directional relationship has max cardinality = 1, the other = many. One-to-many refers primarily to max cardinalities.

FK Rule: Always on the Many Side

The foreign key is placed on the many side — the entity the crow's foot (→) points to. This is because many rows on the "many" side can map to one row on the "one" side via the FK.

If FK were on the "one" side, you'd need extra rows for each additional record on the "many" side — impossible with a primary key.

Min Cardinality on Many Side

When both min cardinalities are 1, relax the many side min to 0 to enable data entry (same chicken-and-egg problem as 1:1).

Example: A user can make zero purchases (browsing without buying) → min = 0 from user to purchase.

Sci-Fi Collective: One-to-Many Relationships

user ↔ review

A user can write zero to many reviews. A review is written by one and only one user. FK: email in review table (many side).

user ↔ purchase

A user can make zero to many purchases (can browse without buying). A purchase is made by one and only one user. FK: email in purchase table.

user ↔ payment_method

A user can maintain zero to many payment methods. A payment method belongs to one and only one user. FK: email in payment_method.

payment_method ↔ purchase ★ new

A payment method can be used in zero to many purchases. A purchase uses one and only one payment method. FK: payment_id in purchase.

⚠️ Two paths now exist from payment_method to user — direct, and via purchase. This can cause redundancy anomalies → addressed in Chapter 6 (Normalization).
⑦ Many-to-Many Relationships — "The More, the Merrier"

Definition

Both directional relationships have max cardinality = many. Must be resolved with a junction (bridge) table that splits the M:M into two 1:M relationships.

Why NOT Just Insert FKs in Both Tables?

If author wrote 3 books → same author info must repeat 3 times in the author table (with different book_id FKs). But duplicate PKs are impossible. Same problem in reverse for books with multiple authors. → Data redundancy + impossible to implement.

Junction Table Pattern

Create a new entity containing only the PKs of both involved entities. These two PKs together form a composite primary key. Convert the M:M into two 1:M relationships — crow's feet always point TO the junction table.

Composite PK: Two or more columns that together uniquely identify each row. Use when no single column guarantees uniqueness.

⑧ Cardinality Yoga — When to Relax Min Cardinality to Zero

In 1:1 Relationships

  • If one entity is typically created before the other, set the min cardinality of the second to 0.
  • Allows the first entity to exist without an immediate counterpart.
  • Example: user can exist without user_address initially.

In 1:M Relationships

  • Relax the cardinality on the many side to allow the "one" entity to exist without corresponding "many" entries.
  • Example: A customer (user) can exist without any purchases.
  • The word "can" in requirements usually signals optional → min = 0.

In M:M Relationships

  • Often set to 0 on both sides if either entity can exist without the other.
  • May keep one side as 1 if strict business rules require it.
  • Example: A product doesn't need to appear in any purchase. But a purchase must have at least 1 product.
📌 These are rules of thumb, not absolute laws. Always verify with business requirements. The key question: "Can this entity exist without the other entity?" If yes → min = 0.
⑨ Strong & Weak Entities

Definitions

Strong entity: Can exist independently. Has its own sufficient PK to uniquely identify instances.

Weak entity: Cannot exist without a related strong entity. Cannot be uniquely identified by its own attributes alone — depends on the strong entity's PK.

Weak Entity PK Structure

A weak entity uses a composite PK = its own attribute(s) [partial keys] + the PK of the strong entity.

Partial keys: Attributes that distinguish different instances of the weak entity for the same strong entity instance.

Example: ticket entity uses movie_id (from movie) + seat/showing info as composite PK.

Decision Rule: To Convert or Not?

Ask: "Will converting to weak entity simplify the design or improve data accuracy?"

If yes → convert. If no → keep as strong entity.

Composite PKs require wider indexes → slower index lookups. Only convert when there's a real benefit.

Sci-Fi Collective Decisions

review — Stay Strong ❌ don't convert

Could be weak (depends on user + product), but converting forces a composite PK. No benefit — just adds index overhead and slower queries. Keep review_id INT as simple PK.

purchase_product — Already Weak ✅

All junction tables are weak entities by nature. Its composite PK (purchase_id + code) consists of the PKs of its two strong entities (purchase + product). No choice here.

user_address — Convert to Weak ✅

Currently uses address_id as PK + email as FK. Since it's in a 1:1 with user and email alone uniquely identifies each address, converting to weak (email as sole PK, FK removed) simplifies the design — eliminates one FK constraint.

billing_address — Weak Entity ✅

Same pattern as user_address. The billing address depends on payment_method. payment_id becomes its PK. Strong entity = payment_method.

✅ In Crow's Foot notation, weak entities are not represented differently from strong entities visually (unlike Chen notation where weak entities use double rectangles). The distinction is only in PK structure.

⑫ Interview / Practical Tips
🎯Always start with plain-English sentences (Subject → Verb → Object) before drawing any lines. Two nouns connected by verbs in one sentence = likely related entities.
🔗M:M always needs a junction table in relational DBs. Never try to put FKs directly in both tables — duplicate PKs make it impossible.
🧪Test every relationship against sample data. Also validate with stakeholders — the payment_method → purchase link was discovered only during stakeholder review.
🃏Skip attributes in draft diagrams. Add them only after entity relationships are confirmed — reduces noise during iteration.
🔑FK placement rule: 1:1 → side with min=0; 1:M → many side (crow's foot); M:M → junction table holds both FKs as composite PK.
⚡Composite PKs require wider indexes = slower lookups. Only convert to weak entity (composite PK) when it genuinely simplifies design — don't do it just because you can.
📐Crow's Foot is read both directions: "A user can make zero or many purchases; a purchase is made by one and only one user."
🔄Strong ↔ Weak is always convertible. If both options are viable, choose whichever makes the E-R diagram simpler and the database more efficient (fewer constraints, simpler PKs).
🏗️All junction tables (M:M resolvers) are weak entities by nature — their composite PK is made of borrowed PKs from the two strong entities they connect.
⑬ Chapter Recap (Book Summary)

3-Step Relationship Process

1. Establish relationships (connect entities with lines)
2. Identify cardinality of each relationship
3. Identify potential weak entities and decide whether to convert

1:1 Summary

Both max cardinalities = 1 (two bars). FK can go on either side — guided by which min = 0. Rarest type in practice.

1:M Summary

Max cardinalities = 1 and many. Many represented by crow's foot. FK always on many side. Most common type.

M:M Summary

Both max = many. Requires junction table between entities. Junction table holds composite PK (PKs of both entities). Two 1:M relationships replace the M:M. Junction = weak entity.

Strong & Weak Summary

Weak entity can't exist or be uniquely identified without its strong entity. Uses composite PK (own partial key + strong entity's PK). In Crow's Foot, no visual difference — only PK structure differs.
