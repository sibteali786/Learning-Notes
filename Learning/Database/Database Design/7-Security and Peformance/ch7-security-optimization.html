② Security — Integrity

What Is Integrity?

Maintaining the accuracy, completeness, and trustworthiness of data. Reviewing integrity means checking that every column, table, and relationship is designed and implemented properly following the principles from Ch4–Ch6:

  • Every column has the correct data type
  • Every table has a primary key
  • Foreign keys maintain relationships between tables
  • Constraints are based on requirements analysis

Why Integrity Matters for Security

Missing FK constraints allow orphan records — rows in a child table referencing nonexistent parent rows. These make the database complex to manage and create gaps attackers can exploit.

Database design involves multiple iterations — FK constraints are easy to forget. Always review before going to production.

Example: Missing FK on book table
-- WRONG: no FK constraint on book.author_id
CREATE TABLE book (
  book_id   INT          PRIMARY KEY,
  title     VARCHAR(200) NOT NULL,
  author_id INT          NOT NULL
  -- ← nothing prevents orphan records!
);

-- CORRECT: FK enforces referential integrity
CREATE TABLE book (
  book_id   INT          PRIMARY KEY,
  title     VARCHAR(200) NOT NULL,
  author_id INT          NOT NULL,
  CONSTRAINT fk_author_id
    FOREIGN KEY (author_id)
    REFERENCES author(author_id)
);
⚠️ E-R diagrams don't show FK constraints — it's easy to forget them during SQL implementation. Always cross-check your CREATE TABLE statements against the E-R diagram.
③ Security — Confidentiality: Access Control

What Is Confidentiality?

Protecting information from unauthorized access. Ensures data is accessed only by authorized people and processes. Two approaches: Access Control + Encryption.

MAC — Mandatory Access Control

Like a strict school with rigid rules. A central authority assigns sensitivity classifications to tables/rows (e.g., public, sensitive, confidential). Users get clearance levels. If your clearance doesn't match the data's classification → access denied. No exceptions.

Sensitivity classifications must be configured manually. Very strict — suitable for highly regulated environments.

RBAC — Role-Based Access Control

More flexible and user-friendly. Permissions are assigned to roles, users are assigned to roles. Like VIP vs bar vs general access in a club. Used by most web applications.

Steps: (1) Create role → (2) Grant permissions to role → (3) Create user → (4) Assign role to user.

⚠️ MySQL 8.0+: must also run ALTER USER … DEFAULT ROLE … to enable role by default.

Sci-Fi Collective RBAC — 3 Roles
USER roleSELECT on product. INSERT on purchase, purchase_product, review. (View + buy products, submit reviews)
ANALYST roleSELECT on all 4 tables. (View-only for statistical analysis)
ADMIN roleSELECT + INSERT + UPDATE + DELETE on all 4 tables. (Full control)
-- MySQL/MariaDB — USER role example
CREATE ROLE standard_user; -- not 'user' (reserved)
GRANT SELECT ON db.product TO standard_user;
GRANT INSERT ON db.purchase TO standard_user;
GRANT INSERT ON db.purchase_product TO standard_user;
GRANT INSERT ON db.review TO standard_user;

CREATE USER 'morpheus'@'%' IDENTIFIED BY 'password';
GRANT standard_user TO 'morpheus'@'%';

-- ANALYST (MySQL 8.0+ needs DEFAULT ROLE)
CREATE ROLE analyst;
GRANT SELECT ON db.product TO analyst;
-- ... GRANT SELECT on all 4 tables ...
CREATE USER 'smith'@'%' IDENTIFIED BY 'password';
GRANT analyst TO 'smith'@'%';
ALTER USER 'smith'@'%' DEFAULT ROLE analyst;
💡 Use 'username'@'%' to allow connections from any host. Replace % with a specific IP for tighter security in production.
📌 Access control is performed by both database designers and administrators throughout the software development lifecycle. It's worthy of its own book — this chapter covers the fundamentals for designers.
④ Security — Confidentiality: Encryption

One-Way Encryption (Hashing)

Irreversible. Input → fixed-size hash string. Cannot recover original data from hash. Used for passwords — people reuse passwords everywhere, so plain-text storage is catastrophic if DB is breached.

Salting: concatenate password + random salt before hashing. Defeats brute-force and rainbow-table attacks.

Auth flow: login → hash(input + salt) → compare to stored hash → match = authenticated.

Algorithms: bcrypt, PBKDF2, SHA-512

Symmetric Encryption (Reversible)

Reversible. Same key used for encryption + decryption. Used for sensitive data that needs to be reused in original form (e.g., credit card numbers).

Key security is critical — if attacker gets the key, all encrypted data is exposed. Never store the key in the same DB as the encrypted data. Store via: environment variables, key management service (KMS), hardware security module (HSM).

Algorithms: AES-128/192/256, Triple DES (3DES), Blowfish

⚠️ Never use symmetric encryption for passwords — use one-way hashing instead.

Sci-Fi Collective: Schema Changes for Encryption

password column → CHAR(60)

bcrypt outputs 40-byte binary. Base64-encoded → 60-byte ASCII string. Change from VARCHAR(20) to CHAR(60).

ALTER TABLE user
  MODIFY COLUMN password CHAR(60);

card_number + expiry_date → CHAR(45)

AES-256 with IV (16-byte block + 16-byte IV = 32-byte input). Base64-encoded output ≈ 45-byte ASCII string. Both columns updated to CHAR(45).

ALTER TABLE payment_method
  MODIFY COLUMN card_number  CHAR(45),
  MODIFY COLUMN expiry_date  CHAR(45);
🔐 AES-256 detail: Operates on 16-byte blocks. Uses an Initialization Vector (IV) — a non-secret 16-byte binary sequence — as extra input to enhance security. When IV is used, plain text + IV = 32 bytes input. Shorter inputs (like expiry_date) are padded to 16 bytes. Base64 encoding converts binary → ASCII for storage in CHAR columns.
⑤ Storage Considerations — Beyond Normalization
💰 Storage cost dropped from ~$250/MB in the 1970s to ~$0.00001/MB today. But storage optimization is still valuable for scalable apps with millions of users or exponential growth. Beyond normalization: check for redundant tables and categorical data columns.

Problem: Redundant Tables

user_address and billing_address had nearly identical columns — only the PK differed. A user and their payment method likely share the same address, so storing it twice is wasteful.

Question to ask: "Are there any redundant or almost-redundant tables?"

Fix: Consolidate into address Table

Create a single address table. Both user and payment_method point to it via FK (address_id).

PK choice: A composite PK from all columns is bad — drags performance and forces all columns into parent tables. Use a surrogate key (address_id INT AUTO_INCREMENT) + UNIQUE constraint on all non-key columns to prevent duplicate addresses.

Min Cardinality Relaxation

Relationship from user → address: min = 0. Users register without providing address. address_id in user table starts as NULL by default (no NOT NULL).

Relationship from payment_method → address: min = 1. Payment method must always have an address. address_id in payment_method uses NOT NULL.

-- New address table with surrogate PK
CREATE TABLE IF NOT EXISTS address (
  address_id             INT AUTO_INCREMENT  PRIMARY KEY,
  street_address         VARCHAR(255) NOT NULL,
  address_line_optional  VARCHAR(100),
  city                   VARCHAR(100) NOT NULL,
  state                  VARCHAR(20)  NOT NULL,
  postal_code            CHAR(5)     NOT NULL,
  CONSTRAINT unique_address_constraint
    UNIQUE (street_address, address_line_optional,
            postal_code, city, state)
);

-- payment_method: address_id NOT NULL (mandatory)
ALTER TABLE payment_method
  ADD COLUMN address_id INT NOT NULL;
ALTER TABLE payment_method
  ADD CONSTRAINT fk_address_payment_method
  FOREIGN KEY (address_id)
  REFERENCES address(address_id);

-- user: address_id NULL (optional, min=0)
ALTER TABLE user
  ADD COLUMN address_id INT NULL;
ALTER TABLE user
  ADD CONSTRAINT fk_address_user
  FOREIGN KEY (address_id)
  REFERENCES address(address_id);
⚠️ NULL FK = optional relationship. A NULL address_id in user means "no address yet." Be extra cautious with NULL handling in JOIN queries on these tables.
Categorical Data — state column Redundancy

Problem: Repetitive Categorical Data

With millions of users and only 50 US states + DC = 51 distinct values, the state column in address stores the same strings millions of times. Massive redundancy.

Question to ask: "Is there a column with a lot of redundant data from a small fixed set of values?"

Fix: Extract to state Table

Move state into a new state table. PK = state abbreviation (CHAR(2) — all abbreviations are same length = good PK). Link to address via 1:M relationship.

Relax min cardinality from state → address to 0 (to enable data entry — same pattern as Ch5).

Real-world benefit: updating a state name requires changing only 1 row in state, not millions in address.

⑥ Indexing — Making Data Retrieval Fast

What Is an Index?

Additional data structures that provide fast access to rows based on values in one or more columns. Implemented with B-trees — self-balancing tree that maintains sorted data, supports search/insert/delete in O(log n) time.

When an index is created: DB scans the table, records indexed column values + pointers to rows → stored in B-tree structure for fast future lookups.

Standard Index — When to Use

  • Columns used in ORDER BY (sorting)
  • Columns used in WHERE (exact-match filtering)
  • Foreign key columns (NOT auto-indexed)
  • Frequently queried non-PK columns

Note: Primary keys are auto-indexed. Don't create manual indexes on PKs.

Full-Text Index — When to Use

  • Keyword searching (partial word match)
  • Fuzzy searching (typos/misspellings)
  • Natural language queries on text columns

Tokenizes each word/term → stores each token in a lookup table. Much faster than LIKE '%keyword%'.

⚠️ Syntax varies significantly across RDBMSs — always check the manual or ask an AI assistant.

Standard Index Examples (movie table)
-- Index single column (sorting/search)
CREATE INDEX idx_rating ON movie (rating);

-- Index single column (date)
CREATE INDEX idx_date ON movie (date);

-- Composite index (sort by both cols together)
CREATE INDEX idx_combo ON movie (rating, date);
Full-Text Index — MySQL vs PostgreSQL
-- MySQL / MariaDB
CREATE FULLTEXT INDEX ft_idx_title
  ON movie (title);

SELECT * FROM movie
  WHERE MATCH(title) AGAINST('exciting'
  IN NATURAL LANGUAGE MODE);

-- PostgreSQL (different approach)
ALTER TABLE movie
  ADD COLUMN tsv_title TSVECTOR;
UPDATE movie
  SET tsv_title = to_tsvector('english', title);
CREATE INDEX gin_idx_title
  ON movie USING gin(tsv_title);
Sci-Fi Collective: 3 Indexing Decisions

product.name — Full-Text

Users search products by name keyword. LIKE '%text%' is too slow at scale. Use full-text index for keyword + partial matching.

CREATE FULLTEXT INDEX
  ft_idx_name
  ON product (name);

review.code — Standard

Users frequently check reviews for a specific product (exact code match). FK columns are NOT auto-indexed → manual index needed.

CREATE INDEX idx_code
  ON review (code);

payment_method.email — Standard

Users frequently select a payment method by their email (exact match). FK column → not auto-indexed → manual standard index needed.

CREATE INDEX idx_email
  ON payment_method (email);
🤝 Collaboration is key. DB designers must work closely with backend engineers to identify indexing opportunities. Backend devs contribute: query knowledge, performance bottlenecks, application logic. DB designers contribute: schema structure, optimal index design, query execution plans. Also use empirical data from query performance metrics and logs once in production.
⑦ Denormalization — Intentional Redundancy for Performance

What Is Denormalization?

A last-resort optimization technique that intentionally introduces redundancy to improve query performance for frequent, expensive multi-table joins.

You deliberately violate BCNF to make the DB faster. Rare, but sometimes the right call.

2-Step Process

1. Identify queries that are executed frequently and require joining more than two tables.

2. Duplicate some columns across the involved tables to reduce the number of joins required.

The Risks — Handle With Care

  • Compromises data integrity if not managed meticulously
  • Redundant data means multiple tables need updates on any change
  • INSERT/UPDATE/DELETE heavy workloads can negate performance gains
  • Controversial — requires team buy-in and thorough documentation

Music App Example — 3-Table Join Problem

Tables: artist → album → song (1:M each). Frequent query: "Top songs for artist X." Requires joining all 3 tables even though album contributes no output data.

Fix: Add artist_id FK directly to song. Now artist joins directly to song — skipping album. Introduces transitive dependency in song table → BCNF violation → deliberate denormalization.

-- BEFORE: 3-table join (slow)
SELECT artist.artist_name, song.song_title
FROM artist
INNER JOIN album ON artist.artist_id = album.artist_id
INNER JOIN song  ON album.album_id = song.album_id
WHERE artist.artist_name = 'Nebula Nova'
ORDER BY album.album_id, song.song_id LIMIT 5;

-- AFTER: 2-table join (fast, denormalized)
SELECT artist.artist_name, song.song_title
FROM artist
INNER JOIN song ON artist.artist_id = song.artist_id
WHERE artist.artist_name = 'Nebula Nova'
ORDER BY song.song_id LIMIT 5;
Sci-Fi Collective: Restoring user → purchase Direct Link

The Problem (from Ch6 normalization)

In Ch6, we removed email FK from purchase to eliminate transitive dependency. Now the path from purchase to user goes: purchase → payment_method → user (3 tables).

But in an online store, users frequently check their orders/receipts. This query runs constantly:

SELECT * FROM purchase
INNER JOIN payment_method
  ON purchase.payment_method_id =
     payment_method.payment_method_id
INNER JOIN user
  ON purchase.user_id = user.user_id
WHERE user.email = 'cat@humor.com';

payment_method contributes no output data but must be joined to link user → purchase. Expensive at scale.

The Fix: Restore email FK in purchase

Add email back to purchase → reintroduces transitive dependency (purchase_id → payment_id → email). Deliberate BCNF violation.

Cost-benefit analysis passed because:

  • Sci-Fi Collective doesn't allow email changes → no update anomaly risk
  • Purchases require existing accounts → no insertion anomaly risk
  • High-frequency query → performance gain is real and significant
  • No deletion anomalies expected
✅ This is a perfect denormalization scenario — real performance gain with minimal integrity risk due to specific business rules (no email changes allowed).
📋 Denormalization checklist before proceeding: (1) Is the query executed frequently? (2) Does it join 3+ tables? (3) Does the middle table contribute no output? (4) Are INSERT/UPDATE/DELETE anomalies manageable given business rules? (5) Have you done a thorough cost-benefit analysis? (6) Have you documented the decision and got team buy-in?

⑩ Interview / Practical Tips
🔒Never store passwords in plain text. Always use one-way hashing (bcrypt/SHA-512). Update your schema column to accommodate the hash size — bcrypt = CHAR(60).
🔑Symmetric key storage is critical. Never store the encryption key in the same DB as the encrypted data. Use env variables, KMS, or HSM.
👥Always use RBAC, not individual permissions. Role name can't be a SQL reserved word — use standard_user not user. On MySQL 8.0+, explicitly set DEFAULT ROLE after assigning.
🗃️Nearly-identical tables = merge them. Two tables differing only by PK can often be consolidated with a surrogate PK + UNIQUE constraint on all non-key columns.
📊Categorical columns with few distinct values = separate table. 51 US states stored millions of times = wasted space. Extract to a reference table, link via FK.
⚡FK columns are NOT auto-indexed. Always manually create indexes on FK columns used in frequent WHERE or JOIN conditions.
🔍LIKE '%keyword%' = table scan. Use full-text indexes for keyword/partial/fuzzy searching. Syntax varies by RDBMS — check the manual.
⚠️Denormalization = last resort. Only after normalization + storage optimization + indexing have failed to meet performance requirements. Document the decision, get team buy-in, and monitor after implementing.
📈Heavy INSERT/UPDATE/DELETE can negate denormalization gains. If your bottleneck is write-heavy, denormalization may hurt. Re-evaluate when workload patterns change.
🤝Index placement requires backend collaboration. DB designers don't know all query patterns. Work with backend devs + use production query logs to find real bottlenecks.
⑪ Chapter Recap

Security Summary

  • Integrity: verify all FKs and constraints are implemented, not just designed
  • RBAC: assign permissions to roles, assign roles to users
  • One-way encryption for passwords (bcrypt → CHAR(60))
  • Symmetric encryption for reusable sensitive data (AES-256 → CHAR(45))

Storage Summary

  • Check for nearly-identical tables → consolidate with surrogate key + UNIQUE
  • Check for high-redundancy categorical columns → extract to reference table
  • NULL FK = optional relationship (be careful with JOIN queries)

Indexing Summary

  • Standard index: ORDER BY, WHERE exact match, FK columns
  • Full-text index: keyword, partial, fuzzy text search
  • PKs auto-indexed; FKs are NOT
  • Collaborate with backend devs + use query logs

Denormalization Summary

  • Deliberate BCNF violation for performance
  • Use only for frequent queries joining 3+ tables
  • Must weigh anomaly risk against performance gain
  • Document thoroughly, get team buy-in, monitor post-deployment
