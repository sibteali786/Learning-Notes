🏊 Connection Pooling — Node.js + Postgres

Reusing TCP database connections instead of opening/closing one per request
Source: hnasr/javascript_playground — postgresnode-pool

The Problem

Establishing a database connection means a full TCP three-way handshake plus the Postgres protocol handshake (auth, session setup) — genuinely expensive. Tearing one down has its own cost too (releasing file descriptors, etc).

The naive REST pattern does this on every single request: connect → query → close. Stateless, sure — but paying full connection setup/teardown cost per request is wasteful, especially under load or against a remote (cloud) database.

❌ The Old Way — Connect Per Request

// old.js
const app = require("express")();
const {Client} = require("pg");

app.get("/all", async (req, res) => {
  const fromDate = new Date();

  const client = new Client({
    "host": "husseinmac.local",
    "port": 5432,
    "user":"postgres",
    "password" : "postgres",
    "database" : "husseindb"
  })

  // connect — full TCP + protocol handshake, every request
  await client.connect();
  // ⚠️ select * with no WHERE/LIMIT — never do this in production
  const results = await client.query("select * from employees")
  console.table(results.rows)
  // end — tear down the connection, every request
  client.end();

  const toDate = new Date();
  const elapsed = toDate.getTime() - fromDate.getTime();
  res.send({"rows": results.rows, "elapsed": elapsed, "method": "old"})
})

app.listen(9000, () => console.log("Listening on port 9000"))
⚠️ Every hit to /all pays the full connect + handshake + query + teardown cost from scratch. Also note the unbounded SELECT * — flagged in the video as a second, separate anti-pattern worth fixing (add proper paging).

✅ The Pool Way — Reuse a Shared Set of Connections

// pool.js
const app = require("express")();
const {Pool} = require("pg");

// created ONCE, at server startup — not per request
const pool = new Pool({
  "host": "husseinmac.local",
  "port": 5432,
  "user":"postgres",
  "password" : "postgres",
  "database" : "husseindb",
  "max": 20,                     // max simultaneous connections in the pool
  "connectionTimeoutMillis" : 0,  // 0 = wait forever for a free connection
  "idleTimeoutMillis": 0          // 0 = never destroy an idle connection
})

app.get("/employees", async (req, res) => {
  const fromDate = new Date();

  // pool picks an available connection for you — no connect()/end()
  const results = await pool.query("select employeeid eid,firstname,ssn from employees")
  console.table(results.rows)

  const toDate = new Date();
  const elapsed = toDate.getTime() - fromDate.getTime();
  res.send({"rows": results.rows, "elapsed": elapsed, "method": "pool"})
})

app.listen(2015, () => console.log("Listening on port 2015"))
✅ Key change: Pool is created once, outside the route handler. Each request just calls pool.query(...) — the pool internally borrows a warm, already-connected client, runs the query, and returns the connection to the pool (not destroyed) for the next request to reuse.

How the Pool Config Options Work

OptionMeaningDefault
maxMax number of simultaneous connections the pool will ever open10
connectionTimeoutMillisHow long a request waits for a free connection if all max are busy. 0 = wait forever0
idleTimeoutMillisHow long an unused connection stays open before being destroyed (frees memory/file descriptors). 0 = never destroy10,000 ms
🔑 If all 20 connections are busy, a new request queues up and waits (governed by connectionTimeoutMillis) — it does not open a 21st connection. This caps how hard your app can hammer the database, which protects the database server itself.

Measured Benchmark — 1,000 Requests Each

// all.js — a combined server exposing both /old and /pool endpoints
const app = require("express")();
const {Pool} = require("pg");
const {Client} = require("pg");

let oldCount = 0, oldSum = 0, poolCount = 0, poolSum = 0;

const pool = new Pool({ /* ...same config, max: 10 */ })

app.get("/old", async (req, res) => {
  const fromDate = new Date(); oldCount++;
  const client = new Client({ /* connection config */ })
  await client.connect();
  const results = await client.query("select * from employees")
  client.end();
  const elapsed = new Date().getTime() - fromDate.getTime();
  oldSum += elapsed;
  res.send({rows: results.rows, elapsed, avg: Math.round(oldSum/oldCount), method: "old"})
})

app.get("/pool", async (req, res) => {
  const fromDate = new Date(); poolCount++;
  const results = await pool.query("select * from employees")
  const elapsed = new Date().getTime() - fromDate.getTime();
  poolSum += elapsed;
  res.send({rows: results.rows, elapsed, avg: Math.round(poolSum/poolCount), method: "pool"})
})

Key Distinctions

Client (old.js)Pool (pool.js)
Connection lifecycleOpened & closed every requestOpened once, reused across requests
Handshake cost paidEvery requestOnly when the pool grows a new connection
Concurrency controlUnbounded — one connection per in-flight requestCapped by max; extra requests queue
Good for transactions (multi-statement, atomic)?N/A — always dedicatedUse pool.connect() to get a dedicated client, run statements, then release() it — pool.query() alone doesn't guarantee the same connection across calls
Typical useAvoid in productionStandard pattern for any web backend hitting Postgres

Real-World Scenarios

☁️ Serverless / Cloud DB Backends
Against a remote managed Postgres (RDS, Supabase, etc.), network latency makes each fresh handshake far costlier than the local 40ms→19ms example — pooling matters even more there. (Note: serverless functions bring their own pooling headaches — e.g. PgBouncer — since each cold invocation can spawn a new pool.)
🏦 High-Traffic APIs
Any backend fielding many concurrent requests (checkout APIs, dashboards) benefits from capping simultaneous DB connections via max — it protects the database from being overwhelmed by connection storms during traffic spikes.

Trade-offs

⚠️ Per-Request Client

  • Simple mental model — fully stateless, no shared resource
  • Pays full connect/handshake/teardown cost every time
  • No cap on concurrent DB connections — risk of overwhelming the database under load

✅ Pool

  • ~2× faster in this benchmark by reusing warm connections
  • Caps concurrent connections (max) — protects the database
  • Node's single-threaded, non-blocking event loop manages many pooled connections concurrently without blocking
  • Slightly more setup complexity; pool lives for the app's lifetime, so its config (max, timeouts) needs sizing to the database's actual connection limit

Practical Tips

  • Always create the Pool once, at module/server scope — never inside a request handler (that would defeat the whole point).
  • For a sequence of statements that must run atomically (a transaction), use pool.connect() to check out a dedicated client, run your statements on it, then call client.release() — plain pool.query() calls may each land on a different underlying connection.
  • Size max against your actual Postgres max_connections setting and how many app instances you run — too high a pool size across many instances can itself exhaust the database's connection limit.
  • The video's other flagged issue — SELECT * FROM employees with no WHERE/paging — is a separate anti-pattern from pooling; combine pooling with proper query scoping (see the earlier OFFSET/keyset pagination notes) for a production-ready backend.
