Hash Indexes

How they work, why they're fast, why they're rare in production — from DDIA (Kleppmann) + system-design interview framing

🎯 The Problem Why

Scanning a whole table to find one row is slow. An index is a side structure that trades write overhead / extra storage for faster lookups. A hash index is the simplest kind: an in-memory (or bucketed) hash map from key → location of value.

⚙️ How It Works Mechanism

Every key is hashed to a bucket. The bucket holds a pointer (byte offset / page pointer) to where the actual value lives on disk.

buckets[hash("alice@example.com")] -> [ptr to page 1]
buckets[hash("bob@example.com")]   -> [ptr to page 2]

Collisions: when two keys hash to the same bucket, chain them — a linked list, or (as PostgreSQL does) overflow pages linked off the bucket page. Average lookup stays O(1) with a good hash function and load factor.

📼 The Bitcask / Log-Structured Version DDIA

DDIA frames the simplest real implementation as: append-only log + in-memory hash map (this is literally what Bitcask, Riak's default engine, does).

write key=k, val=v
→
append to file
→
hashmap[k] = byte_offset
read key=k
→
hashmap[k] → offset
→
seek + read value

Constraint: all keys must fit in RAM (the hashmap is in-memory). Values can exceed RAM — they're read off disk with one seek.

🗑️ Compaction & Segment Merging

Since it's append-only, disk fills up. Fix: close a segment at a size threshold, start a new one. Then compact — keep only the latest value per key — and merge segments together in the background. Old segments become deletable once the merge completes; reads/writes continue uninterrupted on old files during the process.

Deletes use a tombstone record — a marker that tells the merge process to drop all older values for that key.

  • File format: binary (length-prefixed) beats CSV — faster, no escaping
  • Crash recovery: rebuilding the hashmap by replaying a full segment is slow; Bitcask snapshots each segment's hashmap to disk for fast reload
  • Partial writes: checksums detect and let you skip corrupted tail records
  • Concurrency: single writer thread (append order matters), but segments are immutable so many readers can read concurrently
Real scenario: counting video play counts (cat video URL → play count). Huge write volume, but relatively few distinct keys — all fit comfortably in memory. Classic Bitcask sweet spot.

🆚 Why Append-Only Instead of In-Place Updates? Design choice

  • Sequential writes >> random writes, especially on spinning disks (and still favored on SSDs)
  • Simpler crash recovery — no risk of a file containing half-old/half-new spliced data
  • Segments are immutable → trivially safe for concurrent reads
  • Merging avoids long-term fragmentation

⚖️ Hash Index vs B-Tree Trade-offs

Hash IndexB-Tree
Equality lookup (=)O(1) avg, very fastO(log n), nearly as fast
Range queries (>, BETWEEN)Not supported — hashing destroys orderNative support
Sorting / ORDER BYNoYes
Pattern match (LIKE 'john%')NoPrefix matches work
Disk-friendlinessPoor — on-disk hashmaps need lots of random I/O, costly to growGood — designed around disk page access
Best fitIn-memory stores, exact-match-only, high write-per-key workloadsGeneral-purpose, disk-based, mixed query patterns
-- Works: equality
SELECT * FROM users WHERE username = 'johndoe123';

-- Fails to use hash index: range / pattern
SELECT * FROM users WHERE username > 'johndoe123';
SELECT * FROM users WHERE username LIKE 'john%';

🌍 Real-World Usage hellointerview

PostgreSQL supports hash indexes (buckets + overflow-page chaining) but doesn't default to them — B-trees are nearly as fast for equality and handle everything else too.

Redis uses hash tables as its core structure — makes sense since it's entirely in-memory, no disk I/O penalty to worry about.

MySQL MEMORY engine defaulted to hash indexes historically — in-memory + exact-match was its whole use case.

Bitcask/Riak (per DDIA above) — log-structured hash index, ideal for high write-per-key, keys-fit-in-RAM workloads.

"Hash indexes solve a problem we rarely have." — Bruce Momjian

Interview tip: mention hash indexes briefly to show awareness, but don't over-index on them (pun intended). B-trees are the default answer in 90% of system design discussions — bring up hash indexes only when the workload is explicitly in-memory + pure equality lookups with no future range-query need.

✅ When To Actually Reach For One

  • You need the fastest possible exact-match lookup
  • You will never need range queries, sorting, or prefix search on that column
  • You have memory to spare (hash indexes tend to run larger than B-trees for the same data)
