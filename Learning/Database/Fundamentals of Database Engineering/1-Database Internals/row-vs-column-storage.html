2Row-Oriented Storage

Rows are stored contiguously on disk — ID, first name, last name, SSN, salary... then the next row starts immediately after. A disk read always pulls a full block (e.g. 512B–4KB), which typically contains several whole rows — with every column, whether you asked for them or not.

Block 1 (Row Store)
1001, John, Smith, SSN 111, 90k, ...
1002, Melissa, ..., SSN 222, 85k, ...
Block 2 (Row Store)
1003, ..., SSN 333, ...
1004, ..., SSN 444, ...
Block 3 (Row Store)
1005, ..., SSN 555, ...
1006, Hussein, ..., SSN 666, ...
Core mechanic

One IO on a row store hands you whole rows, all columns included. Once a row is in memory (RAM), reading any additional column of that same row costs zero extra IO — it's already there.

4Column-Oriented Storage (Columnar)

Every column gets its own dedicated storage region: all id values together, then all first_name values together, then all ssn values, etc. Each stored value carries the row ID it belongs to, since the columns must be re-joined logically at query time.

SSN column blocks
1001→111, 1002→222
1005→555, 1006→666 ✓
first_name column blocks
1001→John, 1002→Melissa
1005→..., 1006→Hussein ✓
salary column blocks
1001→90k, 1002→85k
1003→..., 1004→...
The tradeoff

Because the row ID is duplicated across every single column structure, writes/updates/deletes get expensive — touching one logical row means touching many separate physical structures (one per column).

Real-life scenario

A checkout service doing SELECT * FROM orders WHERE order_id = X thousands of times a second wants a row store — every lookup needs the full record, and row stores hand that back in one read. A BI dashboard doing SELECT AVG(order_total) FROM orders WHERE region = 'EU' over 50 million rows wants a column store — it only touches 2 of 40 columns and skips the rest entirely.

7Pros & Cons Summary

🟦 Row-Oriented (OLTP)

  • ✅ Fast reads & writes for transactional workloads
  • ✅ Simple structure → simpler write-ahead logging, easy to reason about
  • ✅ Efficient when queries touch many/most columns of a row
  • ❌ Poor compression (adjacent bytes are different types/values — nothing repeats)
  • ❌ Poor aggregate performance (must read unrelated columns to get one)

🟪 Column-Oriented (OLAP)

  • ✅ Excellent for aggregations/analytics on few columns over many rows
  • ✅ Excellent compression (similar/repeated values stored together)
  • ❌ Slow writes (updating 1 row touches N separate column structures)
  • ❌ Terrible when a query needs many/all columns (SELECT * is worst-case)
  • ❌ More complex to implement/maintain (row ID duplicated everywhere)

8Real-World Usage & Engine Swizzling

  • PostgresMySQLOracle default to row-oriented storage — optimized for OLTP (transactional apps).
  • SAP HANA and dedicated analytics warehouses default to columnar — optimized for OLAP (analytics/BI).
  • Some engines let you pick a storage engine per table — e.g. row store for your orders table (constant writes), columnar for your orders_history_analytics table (read-heavy reporting).
  • Joining a row-store table directly with a column-store table is generally unsupported or discouraged — the physical models don't mix cleanly.
Practical takeaway

Pick storage orientation based on your actual query shape: lots of writes and point lookups touching most columns → row store. Heavy aggregates/analytics touching a narrow slice of columns across huge row counts → column store. And remember: SELECT * is expensive on a row store, but it's a genuine anti-pattern on a column store.
