🔑 Primary Key vs Secondary Key

Clustered (Index-Organized) vs Heap-Organized tables — Postgres, MySQL, Oracle
Problem
A table's rows have no order by default — inserting 7, then 1, then 2 just appends them in whatever order they arrive (the heap). A "primary key" isn't just "unique" — it implicitly tells you how the table itself is physically organized on disk, which changes query performance.
How It Works
🟦 Primary Key → Clustered / Index-Organized Table (IOT)
Heap IS the index

Table rows are physically stored sorted by the primary key. The heap and the index are the same structure.

🎯 Example: MySQL InnoDB — every table must have a clustered primary key (auto-assigned if you don't declare one). Oracle calls this an IOT (Index-Organized Table).
🟧 Secondary Key → Heap-Organized Table + Separate Index
Heap ≠ index (2 structures)

Table rows stay in a jumbled, unordered heap. A separate B-tree stores key → row-ID mappings.

🎯 Example: Postgres — all indexes are secondary by default (no true primary-key clustering). A random/UUID PK in this setup means constant random-page jumps across the heap.

Your Note — New Discovery ✅
Correct refinement: it's not "only PK can organize the heap." The real split is:
  • Index-Organized Table → heap is organized around the key (no second fetch needed for range scans).
  • Postgres model → every index (including on the PK column) is a secondary index: search index → get row ID(s) → fetch from an unordered heap. Two hops, always.
That's why Postgres has CLUSTER table USING index — a manual, one-time physical reorg that mimics IOT behavior but doesn't stay maintained automatically like MySQL/Oracle's true clustered structures.
💡 Practical / Interview Tip
  • If asked "why avoid random UUIDs as primary keys?" → answer in terms of clustering: random values cause page splits/fragmentation in clustered (IOT) tables — much less of an issue in Postgres since the heap is unordered anyway.
  • If asked "why is SELECT * slower on a secondary-indexed column?" → because after the index lookup, DB must do an extra heap fetch per row ("bookmark lookup").
  • Remember: Postgres has no primary-key clustering by default — a common trick question.
