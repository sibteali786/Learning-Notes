📄 Database Pages — Deep Dive

How rows, columns, docs & indexes become fixed-size bytes on disk (Postgres focus)
Problem / Why Pages Exist
Every DB — rows, indexes, sequences, documents — eventually stores data as bytes in fixed-size pages. This separates the storage engine from the query/API layer, and makes reading, writing, and caching uniform: everything is "a page."

Row-Store vs Column-Store vs Document vs Graph Pages
🟦 Row Store

All columns of a row packed together, one row after another → good for OLTP.

🟧 Column Store

Values of one column packed together across many rows → good for OLAP aggregates.

❓ Your Questions Answered
1. What is OLTP?
OLTP = Online Transaction Processing. Many small, fast read/write operations touching few rows — inserts, updates, point lookups. Optimized by row-store (all columns of one row together = one I/O gets the whole row).
🎯 Real-life analogy: An ATM withdrawal — check your balance, deduct amount, log the transaction. Fast, single-customer, single-row operations happening thousands of times a second.

Examples: e-commerce checkout, banking transfers, ride-booking apps, inventory scan-at-checkout.
2. What is OLAP?
OLAP = Online Analytical Processing. Few, heavy queries scanning millions of rows but only a handful of columns — SUM, AVG, GROUP BY. Optimized by column-store (only pull the columns you're aggregating, skip the rest entirely).
🎯 Real-life analogy: A company's finance team asking "what was total revenue per region last quarter?" — they need 2 columns (region, revenue) out of a 50-column sales table, across millions of rows. Reading full rows would waste massive I/O on irrelevant columns.

Examples: BI dashboards, quarterly sales reports, data warehouses (Snowflake, Redshift, ClickHouse).

3. Row vs Tuple vs Item — explained more
Three layers of the same logical thing, from "what the user sees" down to "what's physically stored":
  • Row = the logical concept: what you get back from SELECT, e.g. "id=5, name=Ali".
  • Tuple = one physical, versioned copy of that row in the page. Postgres uses MVCC — every UPDATE doesn't overwrite in place, it writes a new tuple. Old tuples stay around because some other transaction may still be mid-read of the old version.
  • Item = the tuple's stored bytes in the page, addressed via its ItemId pointer.
So the same "row" can have 10 tuples on disk: 1 currently active/visible tuple, 7 still needed by ongoing/older transactions (MVCC snapshot isolation), and 2 fully dead ones no transaction needs anymore (cleaned up later by VACUUM).
🎯 Real-life analogy: Think of Google Docs version history. The "document" (row) you see is one thing, but there are 10 saved snapshots (tuples) behind it — some still open in other people's tabs (visible to other transactions), some fully stale and safe to delete (dead, awaiting cleanup/VACUUM).
4. Is the Buffer/Shared Pool the same as the OS Cache?
No — they're two separate caches, stacked on top of each other.
  • DB Buffer Pool: managed by the database itself, understands page structure, tracks dirty pages, pins pages in use, controlled by settings like Postgres' shared_buffers.
  • OS Page Cache: managed by the operating system, just caches raw file bytes with no idea what a "tuple" or "row" is.
So a read can actually be served from either layer — DB buffer pool (fastest, no syscall) → OS cache (fast, syscall but no disk I/O) → real disk (slowest). This is why the article says "the OS checks its filesystem cache and if the required data isn't there, the OS issues the read" — that's a separate hop from the DB's own buffer pool.
🎯 Real-life analogy: Buffer pool = notes on your desk (you organized them, you know exactly what's there). OS cache = the photocopier's memory that happened to keep a copy of the last page you scanned (helpful, but it doesn't know it's "page 4 of your book" — just raw bytes).
💡 Practical / Interview Tip
  • If asked "why does Postgres need VACUUM?" → tie it directly to dead tuples from MVCC described above — VACUUM reclaims space from tuples no transaction can see anymore.
  • If asked to compare row vs column store → answer via I/O pattern: row-store minimizes I/O per row, column-store minimizes I/O per column scanned across many rows.
  • Two-cache trick question: "if a page is evicted from the DB buffer pool, is it definitely gone?" → No, it likely still lives in the OS page cache, so the next read might still avoid real disk I/O.
