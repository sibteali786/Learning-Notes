🐘 Generating a Million-Row Test Table (Postgres + Docker)

Quick recipe for spinning up test data to play with indexing/partitioning
Goal
Spin up a throwaway Postgres container and generate 1,000,000 rows of random data in one INSERT — no external tools, no CSV files, no loops.
Steps
1
Spin up Postgres in Docker
docker run --name pg1 -e POSTGRES_PASSWORD=postgres -d postgres:13
No port exposed — access happens via docker exec, not from the host.
2
Shell into the container's psql
docker exec -it pg1 psql -U postgres
3
Create a simple table
CREATE TABLE temp (t INTEGER);
One column just to keep the demo minimal.
4
Bulk-insert a million random rows in ONE statement
INSERT INTO temp
SELECT random() * 100
FROM generate_series(0, 1000000);
5
Verify
SELECT t FROM temp LIMIT 10;
SELECT COUNT(*) FROM temp;  -- ~1,000,000
How The Insert Trick Works
Extending It
  • Change row count: swap 1000000 in generate_series for any number.
  • Multiple columns: just add more expressions, comma-separated, in the SELECT.
  • Text/character columns: generate an integer with random(), then convert to ASCII characters (e.g. chr()) instead of leaving it numeric.
CREATE TABLE temp (t INTEGER, label TEXT);

INSERT INTO temp
SELECT random() * 100,
       chr((random() * 26)::int + 65)   -- random A–Z letter
FROM generate_series(0, 1000000);
🎯 Real-life scenario: Testing whether adding an index on a temp table actually speeds up range queries (WHERE t BETWEEN 20 AND 40) — you need realistic volume (millions of rows) and non-sequential values to see genuine I/O behavior, not an artificially fast sequential scan.
💡 Practical Tip
  • generate_series + random() is the standard Postgres pattern for synthetic load-testing data — no need for external seed scripts for simple cases.
  • Skip exposing the container port (-p 5432:5432) entirely if you only need to poke around via docker exec — one less thing to clean up.
  • Ties directly back to the earlier primary-key/clustering discussion: this is exactly the kind of table you'd use to physically compare a clustered/IOT layout vs Postgres's heap + secondary index behavior at real scale.
