1The Table, Row & Row ID

Logically, a table is just columns and rows — same idea even in "document" databases (a document is just a row once you strip away the marketing).

Key concept

Most databases don't reference the columns you gave them internally — they generate their own system-maintained Row ID (a physical/positional pointer to where the row lives). This is the row's true unique identifier at the storage layer.

PostgresRow ID

Calls it a Tuple ID (TID). Every index points to this system-generated TID — not to your primary key.

MySQL (InnoDB)Row ID

No separate row ID concept — your primary key itself becomes the pseudo row ID that the table is physically organized around.

2What Is a Page?

A page is a fixed-size chunk of storage (memory ↔ disk) that holds multiple rows. The database never stores or fetches a single row in isolation — it operates in page-sized units.

Worked example

If each page fits 3 rows, and you have 1000 rows, you need roughly 1000 ÷ 3 ≈ 333 pages. That's the physical footprint of your table on disk — every query has to reason about pages, not rows.

3What Is an IO?

An IO is a request to read from disk. It is the "currency" of a database — fewer IOs = faster queries, always.

  • Disk is not like RAM. RAM = byte-addressable, "give me exactly this byte." Disk = page-addressable, "give me this page (or more)."
  • One IO fetches one page or more — never a single row, and you can't opt out of columns you don't need within that page.
  • Some IOs get served from the OS cache instead of physical disk (Postgres relies heavily on this) — so "IO" doesn't always mean a literal disk seek.
Why SELECT * is expensive

In a row-store, once you touch the page, you get every column of every row on that page whether you asked for it or not — the database then has to deserialize it all into memory and throw away what you didn't need. SELECT name FROM employees pays almost the same IO cost as SELECT * FROM employees if there's no index.

4The Heap

The heap is the full collection of pages holding all your table's data — everything about every row lives here. It's called a "heap" because it's unordered/unsorted by default.

Why it's expensive to search

Traversing the heap means reading page after page hoping to find what you want — you always get everything on a page, never a filtered slice. This is exactly why indexes exist: to tell you which page to jump to instead of reading the whole heap sequentially.

5Indexes & B-trees

An index is just another data structure — usually a B-tree — stored separately from the heap. It holds a subset of column values plus pointers back to the Row ID in the heap.

Index on EmployeeID
10 → RowID 1, Page 0
20 → RowID 2, Page 0
30 → RowID 3, Page 0
40 → RowID 4, Page 1
...
10000 → RowID 1000, Page 333
  • You index only the column(s) you actually search on — you can't index "everything" without paying massive storage/write cost.
  • The index itself is stored as pages too, and reading it also costs IO — it's not free magic, it's a smaller, ordered structure that's cheaper to search than the whole heap.
  • B-trees let you binary-search: go left if smaller, right if bigger, instead of scanning sequentially (the linear layout shown above is simplified for teaching).
  • Smaller indexes are more likely to fit fully in memory — huge indexes may not, making even index lookups costlier.

B-tree traversal is logarithmic, not linear — a handful of IOs to walk the tree, then exactly 1 IO to grab the correct heap page. Dramatically fewer IOs than a full scan.

Real-life scenario

Imagine a 10-million-row orders table. SELECT * FROM orders WHERE order_id = 9999999 without an index on order_id could mean scanning millions of pages — seconds or minutes. With a B-tree index on order_id, the same query does maybe 3-4 IOs to walk the tree plus 1 to fetch the row — milliseconds. This is the entire reason "add an index" is the first fix for a slow query.

8Clustered Index vs Secondary Index

Sometimes the heap itself is physically reordered around one index — this is called a clustered index, a.k.a. IOT (Index-Organized Table) in Oracle terminology.

MySQL (InnoDB)

Primary key = always a clustered index. The table's physical row order is the primary key order. Every secondary index points back to the primary key value.

Postgres

Primary key is just a secondary index — not clustered by default. All indexes point to the system-maintained Row ID (TID), not to your primary key. Editing a row means every index referencing that TID may need updating.

Real-life pitfall: random UUID primary keys

In a clustered-index database (like MySQL), if your primary key is a random UUID, every insert lands on a random, unpredictable page instead of appending to the end. This "scattershot" write pattern destroys write performance and bloats the index/heap — a classic reason experienced engineers prefer sequential IDs (or UUIDv7/ULID) for clustered primary keys.

9Visual Summary Cheat Sheet

Row ID — system-maintained pointer uniquely identifying a row's physical location (Postgres: TID; MySQL: primary key acts as it).
Page — fixed-size block (8KB Postgres / 16KB MySQL) holding multiple rows; the real unit of storage.
IO — a disk read that always returns one full page (or more), never a single row/byte. Fewer IOs = faster query.
Heap — the full set of pages containing all table data, unordered by default; scanning it fully is expensive.
Index — separate B-tree structure of chosen column(s) pointing to Row IDs, letting you skip straight to the right heap page.
Clustered Index / IOT — heap physically ordered around one index (usually the primary key); MySQL always does this, Postgres does not by default.
Practical takeaway

Every query optimization ultimately reduces to one question: "How many pages/IOs does this touch?" Select only the columns you need, index the columns you filter/join on, and be deliberate about primary key data types in clustered-index databases — these decisions directly control IO count, and IO count is what makes a query feel instant or feel stuck.
