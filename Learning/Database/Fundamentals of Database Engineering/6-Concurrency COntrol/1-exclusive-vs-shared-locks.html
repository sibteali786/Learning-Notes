🔒 Exclusive Lock vs Shared Lock

DBMS Concurrency Control — EX Lock vs S Lock

The Problem

When multiple transactions touch the same row/column concurrently, you risk:
  • Dirty reads — reading a value mid-update
  • Lost updates — two writers clobbering each other
  • Inconsistent reporting — value changes while you're still reading it
Locks are the DB's way of saying: "only one writer at a time, and readers can block writers."

How It Works

🔴 Exclusive Lock Write Lock

Acquired when a transaction wants to write/update a row. Guarantees total isolation — nobody else can read or write it.

  • Only one transaction can hold it
  • Blocks all other reads and writes on that row
  • Needed for: UPDATE, DELETE, INSERT

🔵 Shared Lock Read Lock

Acquired when a transaction wants to read a row and guarantee it won't change mid-read.

  • Many transactions can hold it simultaneously
  • Blocks writes, but not other reads
  • Needed for: SELECT in a consistency-sensitive context (e.g. reporting)

The Golden Rule

Wants to acquireBlocked if...
Exclusive Lockany Shared Lock already exists on the row
Shared Lockan Exclusive Lock already exists on the row
Shared Lockother Shared Locks exist — this is fine, they stack
💡 Key insight: 7 shared locks on a row = nobody can acquire an exclusive lock until all 7 are released. Reads can "starve out" writes.

Worked Example — Alice, Bob & Charlie

Starting balances: Alice $1000Bob $600Charlie $1200

Exclusive Lock Alice's Shared Lock Bob's Shared Lock Charlie's Exclusive Attempts
  1. Alice starts a transaction to deposit $200 → acquires Exclusive Lock on her own row. No one else connected → SUCCESS. Balance updates to $1200, transaction commits, lock released.
  2. Alice starts a long-running reporting job on her account → acquires a Shared Lock. No exclusive lock exists → SUCCESS.
  3. Bob starts his own reporting job on his account → acquires a Shared Lock on his row. Different row than Alice's → SUCCESS (unrelated to Alice's lock).
  4. Charlie wants to transfer $300 to Bob → needs an Exclusive Lock on Bob's row. But Bob already holds a Shared Lock there → FAILS.
  5. Bob finishes his reporting job → releases his Shared Lock.
  6. Charlie retries the transfer → acquires the Exclusive Lock on Bob's row → SUCCESS. $300 moves: Charlie $1200→$900, Bob $600→$900.
💡 Why this matters: the system deliberately blocked Charlie's write while Bob was mid-read, protecting Bob's report from seeing a half-finished transfer.

Real-World Scenarios

🏦 Banking Systems
Transfers need EX locks on both accounts; reporting/statements need S locks. This is why banks sometimes go "unavailable" for transactions during nightly batch reporting — long S locks block writers.
⚙️ Central Config Systems
While pushing a critical config change, you want an EX lock so no client reads a half-updated config. Once committed, all clients read the latest & consistent value.

Advantages vs Disadvantages

✅ Advantages

  • Guarantees consistency — no dirty reads/writes
  • Critical for financial & config systems
  • Predictable, well-understood model

⚠️ Disadvantages

  • Concurrency suffers — writers can starve behind long-held shared locks
  • Increased chance of transaction failures/retries
  • Can cause visible downtime windows (e.g. batch reporting hours)

Interview / Practical Tips

  • Be ready to explain: EX ⊥ EX EX ⊥ S S ✓ S — only shared locks can co-exist.
  • Connect it to isolation levels (Read Committed, Repeatable Read, Serializable) — shared/exclusive locking is one mechanism to implement these.
  • Mention MVCC (Postgres, MySQL InnoDB) as the modern alternative — readers don't block writers because they read a snapshot instead of taking a shared lock.
  • Good follow-up question to expect: "How would you avoid the concurrency penalty of shared locks?" → Answer: MVCC / optimistic concurrency / row versioning.
