🎟️ Building a Race-Safe Booking System

Express + Node.js + Postgres — applying exclusive locks & 2PL to a real app

The App

A seat-booking grid: green = available, red = booked. Frontend polls GET /seats, renders a table, and clicking a seat prompts for a name then fires PUT /:id/:name to book it.

Frontend logic (index.html)

const res = await fetch(`/${id}/${name}`, {"method": "PUT"})
const j = await res.json();
if (j.error) alert("FAILED! Couldn't book! already booked.")
else alert("Booked successfully!")

❌ Version 1 — Race Condition (broken)

The naive approach: check availability, then update — as two separate steps with a plain SELECT. 
-- Step 1: check
SELECT * FROM seats WHERE id = $1 AND isbooked = 0
-- Step 2: if found → update
UPDATE seats SET isbooked = 1, name = $2 WHERE id = $1

Reproduced with a debugger breakpoint

  1. Client A (Rick) books seat 15 → SELECT runs, finds it available → paused here on breakpoint, hasn't updated yet.
  2. Client B (Edmund) books the same seat 15 → no breakpoint, runs freely → SELECT also finds it available → UPDATE → COMMIT. Seat is now Edmund's.
  3. Debugger resumes Client A → its SELECT result is stale but it doesn't know that → proceeds to UPDATE anyway → overwrites Edmund's booking with Rick's name.
⚠️ Result: both users are told "Booked successfully!" — but only one of them actually owns the seat. Classic double booking / lost update.

✅ Version 2 — Fixed with Exclusive Lock

The fix is a two-character addition: FOR UPDATE on the check query. This turns the read into a row-level exclusive lock (see Two-Phase Locking). 
SELECT * FROM seats WHERE id = $1 AND isbooked = 0 FOR UPDATE

Full server route (index.mjs)

app.put("/:id/:name", async (req, res) => {
  try{
    const id = req.params.id
    const name = req.params.name

    const conn = await pool.connect();
    await conn.query("BEGIN");

    // row-level exclusive lock — phase 1 (growing)
    const sql = "SELECT * FROM seats where id = $1 and isbooked = 0 FOR UPDATE"
    const result = await conn.query(sql,[id])

    if (result.rowCount === 0) {
      res.send({"error": "Seat already booked"})
      return;
    }

    const sqlU = "update seats set isbooked = 1, name = $2 where id = $1"
    const updateResult = await conn.query(sqlU,[id, name]);

    // phase 2 (shrinking) — lock released here
    await conn.query("COMMIT");
    conn.release();
    res.send(updateResult)
  }
  catch(ex){ res.send(500); }
})
  1. Client A: SELECT ... FOR UPDATE on seat 15 → available → exclusive lock acquired, paused mid-debug.
  2. Client B: tries the same query on seat 15 → blocks / hangs indefinitely (Postgres has no built-in lock timeout — unlike Oracle, which lets you set one).
  3. Client A: resumes → UPDATE → COMMIT → lock released → "Booked successfully!"
  4. Client B: unblocks instantly → re-runs its now-fresh SELECT ... FOR UPDATE → row count is 0 (already booked) → correctly returns {"error": "Seat already booked"}.
✅ Result: no matter how close in time the two requests are, only one booking wins — the other is correctly rejected instead of silently overwritten.

Key Distinctions

Plain SELECT (v1)SELECT ... FOR UPDATE (v2)
Locks the row?NoYes
Second reader sees stale data?Yes — race possibleNo — it waits, then sees committed truth
User experience if contestedBoth may get "success" (wrong)Loser waits, then gets a clean rejection
DownsideCorrectness bugIndefinite wait in Postgres (no lock timeout)
Note: Oracle supports a lock WAIT n timeout on FOR UPDATE; vanilla Postgres blocks indefinitely unless you set lock_timeout or statement_timeout at the session/connection level.

Real-World Scenarios

🎥 Cinema/Concert Booking
This is literally the historical example — "online cinema booking ~10 years ago always had double booking" because check-then-update wasn't atomic.
✈️ Flight Seat Selection
Same pattern: seat map, race between two passengers picking the same seat during high-traffic booking windows (holiday sales, flash sales).

Trade-offs of This Fix

✅ Advantages

  • Truly eliminates the race — verified via debugger-forced interleaving
  • Tiny code change: 2 words (FOR UPDATE)
  • The "loser" gets an honest, immediate rejection once unblocked

⚠️ Disadvantages

  • Postgres has no default lock timeout → a stuck/slow transaction can hang other requests indefinitely
  • Under real load (not a debugger), the wait is normally milliseconds — but worth setting a statement_timeout as a safety net in production
  • Locks reduce concurrency on hot rows (popular seats/events)

Practical Tips

  • This is a textbook check-then-act race condition — the general fix pattern is: make the check and the lock happen in a single atomic step, not two.
  • In production, always set a lock_timeout (e.g. SET lock_timeout = '3s') so a blocked FOR UPDATE fails fast instead of hanging the request/connection pool.
  • Alternative to locking: an atomic conditional UPDATE —
    UPDATE seats SET isbooked=1, name=$2 WHERE id=$1 AND isbooked=0 — then check rowCount. No explicit lock needed since the whole check+write is one statement.
  • This connects directly to the earlier lessons: Exclusive Locks Two-Phase Locking — this app is FOR UPDATE in phase 1, COMMIT triggering phase 2 release.
