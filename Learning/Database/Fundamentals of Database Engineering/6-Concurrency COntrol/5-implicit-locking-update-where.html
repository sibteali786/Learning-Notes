🕵️ Implicit Locking — The UPDATE...WHERE Trick

Follow-up to double-booking prevention: why a plain conditional UPDATE also works, and why you shouldn't trust it blindly

The Alternative People Suggested

Instead of SELECT ... FOR UPDATE then UPDATE (two explicit steps), skip straight to a conditional update and check its row count: 
UPDATE seats SET isbooked = 1, u = 'Hussein'
WHERE id = 1 AND isbooked = 0;
💡 This works — but the video's real point is why it works, and that "why" is Postgres-specific, not a universal database guarantee.

What Actually Happens Under the Hood

Transaction 1 — Hussein
BEGIN; UPDATE seats SET isbooked=1, u='Hussein' WHERE id=1 AND isbooked=0; → UPDATE 1 ✅ (uncommitted)
Transaction 2 — Rick
BEGIN; UPDATE seats SET isbooked=1, u='Rick' WHERE id=1 AND isbooked=0; ⏳ BLOCKS (row is implicitly locked)
  1. Transaction 1 runs its UPDATE → Postgres does a b-tree lookup on the id index, finds the tuple, and implicitly acquires an exclusive lock on that row the instant it updates it — no explicit FOR UPDATE needed.
  2. Transaction 2 runs the identical query → index lookup finds the same tuple → Postgres sees the row is locked → blocks, waiting.
  3. Key detail: Transaction 2's isbooked=0 condition was still true at the moment it started — it began at the same time as Transaction 1 and, under isolation, still sees the row as unbooked. It's not blocked because the condition failed; it's blocked because the row is locked.
  4. Transaction 1 commits → lock released, row now permanently isbooked=1, u='Hussein'.
  5. Transaction 2 unblocks → but instead of blindly resuming with its old (stale) view, Postgres re-evaluates the WHERE clause against the fresh committed row → isbooked=0 is now false → 0 rows match → UPDATE 0, Rick's booking silently fails (no error, just no rows affected).
✅ Desired outcome achieved — but through Postgres's specific behavior of re-checking the WHERE clause after being unblocked, under Read Committed isolation.

Why the Re-check Matters

Critical nuance: Postgres doesn't just "wake up and continue" — it goes back to the heap and re-evaluates the predicate. That re-check is exactly what makes the trick safe here.

Explicit vs Implicit Locking

🔒 Explicit — SELECT ... FOR UPDATE

  • You control exactly when the lock is taken
  • Can do multiple things before committing
  • Clear intent — self-documenting
  • Works predictably across databases that support row locks

🎭 Implicit — conditional UPDATE ... WHERE

  • Lock is a side-effect of the UPDATE, not something you asked for
  • Single statement — less flexible, but arguably more efficient
  • Correctness depends on isolation level (must be Read Committed) and on the specific DB's re-check behavior
  • Not guaranteed portable — MySQL, SQL Server may resolve the WHERE clause differently
⚠️ Not guaranteed everywhere: if id and isbooked were both in a composite index, some engines might resolve the WHERE entirely from the index without touching the heap for a fresh value — behavior varies by implementation.

Postgres Internals Worth Knowing

ConceptWhat's happening
Lock storagePostgres stores lock info as a field inside the row itself (in the heap), not a separate global lock table only
Index vs heapA b-tree index lookup finds the tuple pointer; the actual lock/value check happens when you jump to the heap
Isolation levelThis trick requires Read Committed — the re-check on unblock is a Read Committed behavior
Concurrency modelPostgres is pessimistic concurrency control — it always takes a lock rather than detecting conflicts after the fact

Pessimistic vs Optimistic Concurrency Control

🔒 Pessimistic (Postgres, MySQL, most RDBMS)

  • "Take the umbrella before it rains" — lock first, act second
  • No retries needed — a failure is a real business rejection, not a concurrency artifact
  • Costs: lock management overhead, waiting transactions

🎲 Optimistic (common in NoSQL)

  • Proceed without locking; detect conflicts at commit time and fail/retry
  • Higher throughput when contention is rare
  • Application must handle retry logic for concurrency failures
💬 Instructor's stated preference: pessimistic — he'd rather a transaction fail for a real business reason (seat already booked) than fail from a retry-worthy concurrency artifact he now has to handle separately.

Practical Takeaways

  • Don't just copy a trick — understand why it works. A conditional UPDATE ... WHERE can prevent double booking, but only because of Read Committed + Postgres's re-check-on-unblock behavior, not because the SQL "looks safe."
  • Prefer SELECT ... FOR UPDATE when you need multiple steps inside one transaction before committing — it gives explicit, portable control.
  • The conditional-UPDATE approach is a valid, arguably leaner shortcut for simple single-statement check-and-write operations — just verify your isolation level and your specific database's semantics before relying on it in production.
  • Good interview question to expect: "Why does UPDATE ... WHERE isbooked=0 alone prevent a race condition?" → Answer: implicit row lock on update + Read Committed re-evaluates the predicate against the committed value once unblocked.
  • Remember: lock info lives in the row/heap in Postgres — that's why the engine has to "jump" from index to heap to determine if something is locked and what its current value is.
