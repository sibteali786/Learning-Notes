🔁 Deadlocks in Databases

Two transactions, waiting on each other forever — until the DB steps in

The Problem

A deadlock happens when two (or more) transactions each hold a lock the other needs, and each is waiting for the other to release theirs. Neither can proceed — an infinite stalemate.
💡 Builds directly on Exclusive Locks: when transaction A holds an EX lock row #1 and wants row #2, but transaction B holds EX lock on row #2 and wants row #1 → deadlock.

How It Works — Setup

Two Postgres client terminals, one table test with a single PRIMARY KEY column (unique values only). 
-- Client 1                    -- Client 2
BEGIN;                          BEGIN;
Both transactions are open and uncommitted at the same time.

Scenario 1 — The Deadlock

  1. Client 1: INSERT INTO test VALUES (21); → succeeds, EX lock held on value 21 (uncommitted).
  2. Client 2: INSERT INTO test VALUES (20); → succeeds, EX lock held on value 20 (uncommitted).
  3. Client 1: tries INSERT INTO test VALUES (20); → blocks (Client 2 holds the EX lock on 20).
  4. Client 2: tries INSERT INTO test VALUES (21); → blocks too (Client 1 holds the EX lock on 21).
  5. Now both are waiting on each other → circular wait → Postgres detects it (~1 second later).

What Postgres actually returned

ERROR:  deadlock detected
DETAIL:  Process 56 waits for ShareLock on transaction 706; blocked by process 43.
         Process 43 waits for ShareLock on transaction 705; blocked by process 56.
HINT:    See server log for query details.
CONTEXT: while inserting index tuple (0,17) in relation "test_pkey"
Rule of thumb: the transaction that entered the deadlock last is the one the database kills/rolls back. The other one wins and can continue.

Visualizing the Circular Wait

Scenario 2 — No Deadlock, Just a Wait

When there's no circular wait, the blocked transaction just waits — it's a normal lock queue, not a deadlock.
Client 1
BEGIN; INSERT INTO test VALUES (23); -- ok INSERT INTO test VALUES (30); -- ok INSERT INTO test VALUES (20); -- ⏳ blocks (waiting on Client 2's lock)
Client 2
BEGIN; INSERT INTO test VALUES (20); -- ok ROLLBACK; -- releases lock
✅ The moment Client 2 rolls back, Client 1's blocked insert of 20 immediately succeeds — the row is now free.

Scenario 3 — Wait Ends in a Real Conflict

Same setup, but this time Client 2 commits instead of rolling back.
Client 1
BEGIN; INSERT INTO test VALUES (30); -- ok INSERT INTO test VALUES (20); -- ⏳ blocks... then: ERROR: duplicate key value violates unique constraint "test_pkey" DETAIL: Key (id)=(20) already exists.
Client 2
BEGIN; INSERT INTO test VALUES (20); -- ok COMMIT; -- 20 is now permanent
⚠️ Once Client 2 commits, 20 is permanently taken — Client 1's blocked insert wakes up and fails with a duplicate key error instead of succeeding.

Real-World Scenarios

💸 Fund Transfers
Two concurrent transfers moving money between the same two accounts in opposite order (A→B and B→A) is a textbook deadlock trigger. Fix: always lock accounts in a consistent order (e.g. by ID).
📦 Order Processing
Two batch jobs updating overlapping rows of an orders and inventory table in reversed sequence can deadlock under load — common in e-commerce checkout systems.

Handling Deadlocks — Trade-offs

✅ What the DB does well

  • Detects cycles automatically (usually within ~1s)
  • Rolls back one transaction to unblock the other
  • Prevents infinite hangs

⚠️ What you must handle

  • Your app must catch & retry the failed transaction
  • Deadlocks are non-deterministic under load — hard to reproduce
  • Frequent deadlocks usually signal a lock-ordering design flaw

Interview / Practical Tips

  • Definition to nail: "circular wait where each transaction holds a lock the other needs."
  • Best-known fix: consistent lock ordering — always acquire locks on resources in the same global order (e.g. sort account IDs before locking) so cycles can't form.
  • Mention deadlock detection vs. deadlock prevention: Postgres/MySQL detect after the fact and kill a victim; some systems use timeouts or wait-graphs to prevent them proactively.
  • Good follow-up: "What's the difference between a deadlock and just a slow/blocked query?" → A block resolves once the lock is released; a deadlock never resolves on its own — it needs external intervention.
  • Mention retry logic as the standard app-side mitigation — deadlock errors are expected and recoverable, not exceptional failures.
