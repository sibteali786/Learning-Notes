🌳 B-Tree: Index Scan Backward, Step by Step

A real multi-level b-tree, walked in reverse — for ORDER BY id DESC LIMIT 3

The Table & Index

A tiny news table with an index on id (values 1–16). A real b-tree has a small root node pointing to internal nodes, which point to leaf nodes — and the leaf nodes are chained together left-to-right (and back), which is exactly what makes both forward and backward scans possible without re-reading the whole tree.

The B-Tree — Query: ORDER BY id DESC LIMIT 3

rightmost child — largest values live there 3 Land on leaf [14, 15, 16] — the very last leaf. Scan starts at 16 and reads backward: 16 → 15 → 14 4 That's already 3 rows (our LIMIT) → STOP. Never touch leaves [11,12,13], [9,10], or anything to the left. Total work: 1 root read + 1 internal read + 1 leaf read = 3 node reads, for 3 rows returned This is exactly what "Index Scan Backward" means in the EXPLAIN output
Root Internal node (routing only, no data) Leaf nodes touched (has the actual data) Leaf sibling chain

Now Add OFFSET — Same Tree, More Work

Query: ORDER BY id DESC OFFSET 6 LIMIT 3 → we want rows 10, 9, 8 (skip the top 6: 16,15,14,13,12,11).
  1. Same descent: root → rightmost internal node → rightmost leaf [14,15,16].
  2. Backward scan begins: 16, 15, 14 — that's 3 rows, but they must all be discarded (they're inside the offset window).
  3. Scan crosses the leaf sibling pointer to the previous leaf [11,12,13] — reads 13, 12, 11 — 3 more discarded (total 6 skipped now).
  4. Crosses another sibling pointer into leaf [9,10] — reads 10, 9 — these are finally kept (offset satisfied).
  5. Stops once 3 rows are collected. Total: 3 leaf nodes visited, 8 rows physically read, only 2–3 actually returned.
🔑 The pattern that matters: the tree navigation itself (root → internal → leaf) is always cheap — it's O(log n). What makes OFFSET expensive is the horizontal walk across leaf siblings, discarding rows one by one, before collection even starts. A bigger offset = more sibling hops = more discarded reads. A keyset condition like WHERE id < 10 lets the root/internal nodes route you directly to the right starting leaf — skipping that entire horizontal walk.

Side-by-Side: Tree Descent vs Leaf-Chain Walk

💬 One-line takeaway: "Index Scan Backward" just names the direction (right-to-left through the leaf chain). It's fast by itself. OFFSET makes it slow by forcing a long horizontal walk through that chain before collection starts — WHERE id < cursor avoids the walk entirely by letting the tree route you straight to the start point.
