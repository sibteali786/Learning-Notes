📄 Why OFFSET Pagination Is Slow

And the keyset/cursor-based fix — inspired by "Use The Index, Luke"

The Problem

A typical paging API: GET /news?page=10 → server translates to OFFSET 100 LIMIT 10 (10 rows/page). Simple, obvious... and gets catastrophically slower as the page number grows.
💡 What OFFSET actually means: "fetch the first N+offset rows, then physically throw away the first N." The database still does all the work of producing those discarded rows.

⚠️ Linear degradation: rows pulled = offset + limit, every single time. Page 100,000 does 10,000× the work of page 0 — for the exact same 10 rows returned to the user.

🔍 What Is "Index Scan Backward"?

A b-tree index (like the default index Postgres builds for a primary key) stores its entries physically sorted in ascending order — smallest value first, largest value last. That's just how a b-tree is built.

When your query says ORDER BY id DESC (newest/largest first), Postgres doesn't need a separate "descending index" or an expensive re-sort — it just walks the same ascending index from the end towards the beginning. That traversal direction is called an Index Scan Backward.

Worked Example

Imagine an index on id with entries 1 through 10, physically stored like this (small → large, left to right):

For ORDER BY id DESC LIMIT 3, Postgres starts at the last entry (id=10) and walks backward: 10 → 9 → 8 — stops as soon as it has 3 rows. It never touches entries 1–7 at all. That's why OFFSET 0 is instant: the scan starts exactly where the answer is and stops immediately.

🔑 The catch with OFFSET: when you say OFFSET 1000000, Postgres still has to walk backward through the index one entry at a time, counting — id 10, 9, 8 ... all the way down past a million entries — before it even starts collecting the 10 rows you asked for. The backward direction is free; skipping a million rows to get there is not.

Bonus Problem — Phantom Duplicates

  1. User requests page 10 (OFFSET 100) → sees rows 101–110.
  2. Someone inserts a new row at the top of the sort order while the user is browsing.
  3. User requests page 11 (OFFSET 110) → because everything shifted by one, the database now returns a row the user already saw on page 10 — a duplicate, purely from OFFSET's positional counting.
⚠️ OFFSET counts position, not identity — it has no idea what the user already saw.

✅ The Fix — Keyset (Cursor-Based) Pagination

Instead of counting positions, use the last seen value (the indexed column) as the starting point for the next page. 
-- Page 1 (first page)
SELECT title, id FROM news ORDER BY id DESC LIMIT 10;
-- client remembers the last id it saw, e.g. 100999993

-- Page 2 (next page) — no OFFSET at all
SELECT title, id FROM news
WHERE id < 100999993
ORDER BY id DESC LIMIT 10;

✅ Why it's fast: the WHERE id < ... condition becomes an Index Cond the b-tree can jump straight to — Postgres seeks directly to that position instead of counting through every row before it. Rows pulled ≈ just the page size, regardless of how "deep" the page is.

Real-World Scenarios

📰 News / Social Feeds
Infinite-scroll feeds (Twitter/X, Reddit, news apps) are a perfect fit for keyset pagination — users only ever go "next," never jump to "page 4,213."
🛠️ Admin Dashboards with Page Numbers
If the UI genuinely needs numbered pages (1, 2, 3 ... jump to page N), OFFSET is often unavoidable — but cap how deep users can page, or pair it with a search/filter to keep offsets small.

Trade-offs

⚠️ OFFSET

  • Simple to implement, works with any table
  • Supports true random page-jumping
  • Performance collapses at scale — SQL Server even risks lock escalation scanning huge row ranges (Postgres avoids that specific issue, but still pays the I/O cost)

✅ Keyset / Cursor

  • Constant-time performance at any depth
  • No phantom duplicates from concurrent inserts
  • No arbitrary page-number jumping — only sequential next/prev
  • Needs a well-indexed, unique sort key to work

Interview / Practical Tips

  • Definition to nail: "OFFSET fetches and discards N rows before returning the next page — the database does O(offset + limit) work every time, not O(limit)."
  • Index Scan Backward ≠ slow by itself — it's just walking a b-tree in reverse (free). It only gets expensive when combined with a large OFFSET forcing a long walk before results start.
  • The keyset trick: replace OFFSET n with WHERE <sort_col> < <last_seen_value> — turns a counted scan into a direct index seek (an Index Cond, visible in EXPLAIN).
  • Good follow-up to expect: "How would you let users jump to page 500 with keyset pagination?" → Honest answer: you generally can't efficiently — that's the real trade-off; some systems precompute cursor checkpoints for common page numbers as a hybrid approach.
  • Always read the actual EXPLAIN ANALYZE "rows" number, not just execution time — it tells you how much work the engine did versus how much you actually needed.
