🔐 Two-Phase Locking (2PL)

Acquire, acquire, acquire → release, release, release. Never go back.

The Problem — Double Booking

Two users try to book the same cinema seat at the same millisecond. Both check availability, both see it's free, both update it, both commit. Without a locking discipline, the last write wins silently — someone paid for a seat they don't actually own.
💡 Builds on Exclusive Locks: the fix is to stop a second transaction from reading a "clean" but soon-to-be-stale row in the first place.

How It Works — Two Phases

📈 Phase 1 — Growing

Transaction acquires locks as it goes. It can keep taking more locks, but can't release any yet.

  • Acquire, acquire, acquire...
  • No releases allowed here

📉 Phase 2 — Shrinking

Transaction starts releasing locks (on commit/rollback). Once it releases one, it can never acquire a new lock again.

  • Release, release, release...
  • No new acquisitions allowed here
The core rule: once you release a lock, you can't go back and acquire another. This strict separation is what guarantees serializability.

Scenario A — Without 2PL (Double Booking Happens)

Client 1 (Hussein)
BEGIN; SELECT * FROM seats WHERE id=13; → isbooked=0 (looks free) UPDATE seats SET isbooked=1, name='Hussein' WHERE id=13; COMMIT; SELECT * FROM seats WHERE id=13; → 13 | 1 | Hussein ✅ "it's mine!"
Client 2 (Edmond)
BEGIN; SELECT * FROM seats WHERE id=13; → isbooked=0 (also looks free!) UPDATE seats SET isbooked=1, name='Edmond' WHERE id=13; ⏳ waits (Postgres row lock) ... (unblocks after Client 1 commits) COMMIT; → 13 | 1 | Edmond 😬 overwrote it
⚠️ Both transactions read the row as "available" before either committed. The plain SELECT gave no protection — the second writer silently clobbers the first the moment it commits.

Scenario B — With 2PL (Fixed)

The fix: SELECT ... FOR UPDATE — this grabs an exclusive lock on the row at read time, not just at write time.
Client 1
BEGIN; SELECT * FROM seats WHERE id=14 FOR UPDATE; → 14 | 0 | (EX lock acquired ✅ phase 1)
Client 2
BEGIN; SELECT * FROM seats WHERE id=14 FOR UPDATE; ⏳ BLOCKS — can't get EX lock, Client 1 already holds it
  1. Client 1: SELECT ... FOR UPDATE → phase 1 (growing), row 14 is now exclusively locked.
  2. Client 2: same FOR UPDATE query → blocked, can't acquire the same EX lock.
  3. Client 1: UPDATE seats SET isbooked=1, name='Hussein' WHERE id=14; then COMMIT; → enters phase 2 (shrinking), lock released.
  4. Client 2: immediately unblocks the moment Client 1 commits — re-reads the row and now sees isbooked=1, name='Hussein' → app correctly rejects the second booking instead of overwriting it.
✅ Because the lock was taken before the read result was trusted, the second transaction never acts on stale data — it waits, then sees the truth.

Real-World Scenarios

🎬 Seat/Ticket Booking
Cinemas, flights, concerts — any inventory with exactly one unit per slot needs FOR UPDATE at read time, not just an update-time check.
🛒 E-commerce Inventory
"Last item in stock" race conditions are the same problem: two checkouts reading stock=1 simultaneously. 2PL (or optimistic locking with a version column) prevents overselling.

Advantages vs Disadvantages

✅ Advantages

  • Guarantees serializability — no double-booking / lost updates
  • Simple mental model: grow then shrink, never mix
  • Well supported natively (SELECT ... FOR UPDATE in Postgres/MySQL)

⚠️ Disadvantages

  • Second transaction has to wait — reduced throughput under contention
  • Can lead to deadlocks if multiple rows are locked in inconsistent order
  • Long-held locks (slow transactions) can stall many waiters

Interview / Practical Tips

  • Definition to nail: "a concurrency control protocol where all lock acquisitions happen before any lock release, in a transaction."
  • Know the two variants: Strict 2PL (all locks held until commit/rollback — what Postgres does, and what avoids cascading rollbacks) vs. basic 2PL (can release early, riskier).
  • Connect it forward to Deadlocks: since 2PL holds locks across multiple statements, it's exactly the mechanism that creates the circular-wait conditions deadlocks are about.
  • Good follow-up: "Why not just always use FOR UPDATE?" → Answer: it serializes access and hurts concurrency; use it only where a genuine check-then-act race exists (booking, inventory, balance transfers).
  • Mention the alternative: optimistic concurrency control (version/timestamp column, fail-and-retry on conflict) avoids holding locks at all, trading blocking for occasional retries.
