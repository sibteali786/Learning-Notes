⚠️ Cons of Partitioning

The trade-offs behind the performance gains
1 Updates that move a row across partitions are slow

In a normal single table, updating a row is straightforward: find it, update it, done. But if a partitioned table's row is updated in a way that changes which partition it belongs to (e.g. changing a grade from 30 to 60, moving it from the 0–35 partition into the 35–60 partition), the database can't just update the row in place.

Instead, it effectively has to delete the row from the old partition and insert it into the new one — which is slower than a plain in-place update.

g0035 partition
grade: 30
✂️ delete + insert →
g3560 partition
grade: 60
"If you're doing this so many times, that could hurt your SSD — jumping pages from one partition to another repeatedly."

Practical implication: choose a partition key that rows rarely "cross" over time (e.g. don't partition by a value that frequently changes into another range).

2 Inefficient queries can accidentally scan every partition

If your query's WHERE clause lets the database know exactly which partition to hit, everything works as intended — fast and targeted. But if the query doesn't filter on the partition key, the database has to check all partitions.

select * from grades_parts where id > 1;
-- no filter on the partition key (g) → hits every partition

Instead of querying one table, the database now has to jump between 5, 7, or however many partitions exist — this can end up slower than just having a single unpartitioned table in the first place.

This is the flip side of partition pruning — pruning only helps if the query gives the planner something to prune with.

3 Schema changes can be challenging

DBMSs usually handle this well — e.g. creating an index on the master/parent partition table typically cascades that index to all child partitions automatically (as seen in the demo).

But this doesn't always work seamlessly — the underlying database engine has to explicitly support this feature, and behavior can vary between databases or versions. Schema changes across many partitions are inherently more complex to reason about than a single table.

Quick Recap

  • Cross-partition updates — slow, effectively a delete + insert; repeated often, can wear on SSDs
  • Non-selective queries — scanning all partitions can be slower than a single unpartitioned table
  • Schema changes — usually handled by the DBMS, but support and reliability vary by engine

Partitioning is a trade-off: it can dramatically speed up well-targeted queries at scale, but it adds real complexity around updates, query design, and schema management.
