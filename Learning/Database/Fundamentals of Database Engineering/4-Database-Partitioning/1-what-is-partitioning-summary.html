🧩 What is Partitioning?

Database concept summary — splitting large tables for faster queries

The Problem Querying a huge table

You have a CUSTOMERS table with 1 million rows. You want one row:

SELECT Name
FROM CUSTOMERS_TABLE
WHERE ID = 700,001
💻 Query sent
→
🗄️ One big table
(1,000,000 rows)
  • With an index: DB jumps straight to the row on disk — fast, but the index itself grows huge over billions of rows and gets slower to maintain/traverse.
  • Without an index: DB does a sequential scan — checks every single row until it finds ID 700,001. Worst case.
  • Now imagine this table has 10 million, 1 billion rows — even indexed lookups and maintenance overhead start dragging.
"The quickest way to query a table with a billion rows is to avoid querying a table with a billion rows."

The Solution Partitioning

Break the 1M-row table into smaller tables called partitions — each with the same schema, holding a slice of the ID range. The original table becomes a "parent" with no data of its own; it just points to its partitions.

200,001 – 400,000CUSTOMERS_400K
400,001 – 600,000CUSTOMERS_600K
600,001 – 800,000CUSTOMERS_800K ✅
800,001 – 1,000,000CUSTOMERS_1M
🏠 Real-world analogy: Think of a giant library with 1 million books shelved in one continuous row. Finding book #700,001 means walking past 700,000 books (or using a catalog card = index). Now split the library into 5 rooms by book number range. To find #700,001, you instantly know "that's in Room 4 (600,001–800,000)" — you never even enter the other 4 rooms.

How the query runs now

1 Same query is sent: WHERE ID = 700,001
2 The DB checks partition metadata (the ID ranges each partition owns) — a very cheap check, not a data scan.
3 It determines: 700,001 falls in the 600,001–800,000 range → routes straight to CUSTOMERS_800K.
4 The DB now searches only 200,000 rows instead of 1,000,000 — a 5x smaller haystack.
5 If that partition also has an index, it jumps straight to the row: ID 700,001 → "Kim".

Before vs After

❌ Without Partitioning

  • One table, 1M rows
  • Sequential scan = check up to all 1,000,000 rows
  • Even indexed lookups slow down as the table (and index) keeps growing

✅ With Partitioning

  • 5 tables, 200K rows each, same schema
  • DB uses cheap metadata check to pick 1 partition
  • Query only touches 200,000 rows — smaller, faster searches (and index, if any, is smaller too)

Vertical vs Horizontal Partitioning

↔️ Horizontal Partitioning

Splits the table by rows — like slicing the table with a knife across the middle, again and again.

  • Customers with ID 1–200,000 → one partition
  • Customers with ID 200,001–400,000 → another partition
  • Every partition keeps the same columns/schema, just a different slice of rows
  • This is exactly what we saw with CUSTOMERS_200K, 400K, 600K, 800K, 1M

↕️ Vertical Partitioning

Splits the table by columns — slicing top to bottom, separating certain columns into their own partition/table.

  • Useful when a table has a large column (e.g. a blob/document) that's rarely queried
  • That heavy column is moved into its own tablespace — its own storage, possibly on slower/cheaper disk
  • The "master" table keeps only the fast, frequently-accessed columns, compact and lean
  • When a query needs the blob, the DB knows to jump into that separate table to fetch it
🏠 Real-world analogy: Imagine a customer record with a fast-access id, name, email plus a rarely-opened signed_contract_pdf blob.

Horizontal: like splitting a phonebook into separate volumes — Volume A–M, Volume N–Z — same columns (name, number) in each, just different row ranges.

Vertical: like keeping a compact index card per customer (name, phone) in your desk drawer for quick access, while their full paper contracts sit in a filing cabinet in another room — you only walk over there when someone specifically needs the contract.

Partitioning Types (how horizontal partitions are defined)

  • By Range: dates or IDs — e.g. by logdate or customer_id from X to Y (what we saw with CUSTOMERS_200K…1M)
  • By List: discrete values — e.g. zip code 90205 in one partition, 91111 in another; or states CA, AL, etc.
  • By Hash: using a hash function (consistent hashing) to assign rows to partitions

Key Idea

  • Partitioning = splitting one large table into multiple smaller tables ("partitions"), each responsible for a defined slice of data.
  • Horizontal partitioning splits by rows (same schema, different row ranges) — by range, list, or hash.
  • Vertical partitioning splits by columns — separating large/rarely-used columns (like blobs) into their own tablespace.
  • The main/parent table has no data itself — partitions hold the actual rows.
  • The database uses lightweight metadata to route a query to the right partition instead of scanning everything.
  • This is essential at scale (millions → billions of rows), where even a well-indexed single table becomes a bottleneck.
