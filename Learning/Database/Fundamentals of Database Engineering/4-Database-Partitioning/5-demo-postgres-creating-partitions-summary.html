🧪 Demo: Creating Partitions in Postgres

Continuing the demo — building 4 range partitions, populating them, and indexing them

Step 1 Create the partitioned "master" table

1
Same columns as before (id, g, both NOT NULL), but declared with PARTITION BY RANGE(g). This table itself stays empty — it's just the parent that routes rows.
create table grades_parts (
  id serial not null,
  g int not null
) partition by range(g);

Postgres does not auto-create the partitions — you're responsible for defining each range yourself.

Step 2 Create 4 partition tables

2
Each partition is created with LIKE grades_parts INCLUDING INDEXES — copies the structure. No indexes exist yet since none exist on the master at this point.
create table g0035  (like grades_parts including indexes);
create table g3560  (like grades_parts including indexes);
create table g6080  (like grades_parts including indexes);
create table g80100 (like grades_parts including indexes);
g0035Grades 0 – 35
g3560Grades 35 – 60
g6080Grades 60 – 80
g80100Grades 80 – 100

Step 3 Attach each partition to the master table

3
Each partition is attached with an explicit value range using ALTER TABLE ... ATTACH PARTITION ... FOR VALUES FROM (x) TO (y).
alter table grades_parts attach partition g0035  for values from (0)  to (35);
alter table grades_parts attach partition g3560  for values from (35) to (60);
alter table grades_parts attach partition g6080  for values from (60) to (80);
alter table grades_parts attach partition g80100 for values from (80) to (100);

At this point, partitions are wired up, but the master table (and all partitions) are still completely empty — no indexes anywhere yet.

Step 4 Populate by copying from the original table

insert into grades_parts
select * from grades_org;

This copies all 10,000,001 rows row-by-row. The key magic: for every row inserted, Postgres automatically decides which partition it belongs to based on the value of g.

If g = 20, it lands in g0035 (since 20 is between 0 and 35) — and so on automatically for every row.

Verifying the distribution:

select count(*) from grades_parts;   -- 10,000,001 (matches original)
select max(g)   from grades_parts;   -- 99 (max grade overall)

select count(*) from g0035;         -- ~3,000,000 rows
select count(*) from g3560;         -- ~2,000,000 rows
select max(g)   from g3560;         -- 59 (largest value that fits this range)

Distribution is essentially random since grades were randomly generated — real-world range partitions (e.g. by date) would distribute more predictably over time.

Step 5 Create ONE index — it cascades to all partitions

Before Postgres 11, you had to index every partition individually. From Postgres 11/12+, creating an index on the master (leader) partition table automatically creates the matching index on every partition.

create index grades_parts_idx on grades_parts(g);
✅ Result: Checking \d grades_parts shows the index on the parent, and checking any partition (e.g. \d g0035) shows g0035_g_idx — an index Postgres created automatically, even though it was never created manually on that specific partition table.

Key Takeaways

  • Postgres requires manual definition of each partition range — it won't auto-generate them.
  • The parent/master table stays empty; it only exists to route rows and hold shared metadata (like indexes).
  • Inserting into the master table automatically routes each row to the correct partition based on its range.
  • Creating an index once on the master table propagates it to every partition — no need to repeat it per partition.
