🧪 Demo: Postgres Setup (Before Partitioning)

Spinning up a 10M-row table to establish a baseline — partitioning comes next

Setup Spin up Postgres with Docker

1
Run a Postgres container (no port exposure needed — we'll bash directly into the container to run SQL).
# from host terminal
docker run --name pg_main -d -e POSTGRES_PASSWORD=postgres postgres

docker exec -it pg_main bash
psql -U postgres
2
Create a simple grades_org table — an ID and a grade column. Both columns must be NOT NULL — this is a requirement for partitioning later.
create table grades_org (
  id serial not null,
  g int not null
);
3
Insert 10 million rows with random grades (0–99), generated using generate_series + random().
insert into grades_org(g)
select floor(random() * 100)
from generate_series(0, 10000000);
-- INSERT 0 10000001
4
Create an index on g after inserting — faster than maintaining the index during 10M inserts.
create index grades_org_index on grades_org(g);
Table check via \dt confirms one table: grades_org.

Baseline Query 1 Exact match g = 30

select count(*) from grades_org where g = 30;
-- count: 100271
explain analyze select count(*) from grades_org where g = 30;

📊 Plan result

Used an Index Only Scan on grades_org_index — condition g = 30, ~100,271 rows matched.

Planning: 0.261 ms Execution: 75.97 ms

Baseline Query 2 Range match g between 30 and 35

explain analyze select count(*) from grades_org
where g between 30 and 35;

📊 Plan result

Range condition is heavier — Postgres used a Parallel Index Only Scan (2 parallel workers) to cover the wider match (~268,194 rows per worker estimate).

Planning: 0.140 ms Execution: 107.37 ms

A range query touches more of the index/table than a single exact match, so it costs more — even with parallelism and an index in place.

Why this baseline matters

This is the before picture: one giant 10M-row table, indexed, queried directly. Both queries still have to work through a large index over the full table. The next step in the demo is to create partitions for this data and attach them to a master table — then re-run similar queries to compare performance.

🧭 What to watch for next: once grades_org is split into partitions (e.g. by grade range), the same EXPLAIN ANALYZE should show the planner doing partition pruning — skipping irrelevant partitions entirely instead of scanning one big index across all 10M rows.
