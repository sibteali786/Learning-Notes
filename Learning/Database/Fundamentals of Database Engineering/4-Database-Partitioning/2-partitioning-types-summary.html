🗂️ Partitioning Types

Three ways to decide which partition a row belongs to (horizontal partitioning)

Overview

When splitting a table by rows (horizontal partitioning), the database needs a rule to decide which partition each row lands in. There are three common strategies:

📏 By Range

Rows are grouped by a continuous range of values — most commonly dates or IDs.

  • e.g. customer ID 1–200,000 → Partition 1
  • e.g. IoT sensor logdate → partition per year, quarter, or month (2012 data, 2013 data, 2020 data...)

📋 By List

Rows are grouped by discrete values, not a range.

  • e.g. all California customers → Partition CA
  • e.g. all Alabama customers → Partition AL
  • Same idea works for zip codes or countries

🔢 By Hash

A hash function spreads rows across partitions based on the hashed value of a key.

  • Hash of the value → determines which partition it lands in
  • Popular in Cassandra for spreading data evenly
  • Similar idea to IP hashing in load balancers/proxies — hash of client IP decides which backend server gets the request

Real-world payoff: Range partitioning + archiving

One big advantage of range partitioning by date: old partitions can be identified and moved off fast storage since nobody queries them anymore.

🏠 Real-world analogy: An IoT company logging sensor readings every second keeps this year's partition on fast SSD for active dashboards, but ships 2019's partition off to cheap cold storage — it's rarely touched, so speed doesn't matter there.

Quick Comparison

📏 Range

Best for: ordered data (dates, sequential IDs). Bonus: easy to archive old partitions.

📋 List

Best for: categorical/discrete values (state, country, zip) where grouping by known value makes sense.

🔢 Hash

Best for: evenly spreading load/data when there's no natural range or category to split on (e.g. Cassandra, load balancer IP hashing).
