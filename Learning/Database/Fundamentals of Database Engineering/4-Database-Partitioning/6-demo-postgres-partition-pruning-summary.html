🔍 Demo: Partition Pruning & Index Size

Verifying that queries hit only the right partition — and why that matters at scale

Query test g = 30 on the partitioned table

explain select count(*) from grades_parts where g = 30;

Result: only one partition is touched —

g0035 ✅
Index Only Scan
g3560
g6080
g80100

Since g = 30 falls in range 0–35, Postgres knows to go straight to g0035_g_idx and ignore the other three partitions entirely.

Surprising result: not much faster (on this machine)

QueryExecution Time
Original table (grades_org), g = 30~75.97 ms
Partitioned table (grades_parts), g = 30~43.3 ms
"Hussein, you said partitions are great and are going to be faster — not really, if you think about it."

Why the gap isn't dramatic here: the demo machine (16GB RAM) has no memory or I/O limits on the Docker container. Both the full 69MB index and the smaller per-partition indexes comfortably fit in memory — so there's little difference to observe.

Where it would matter: if the container were memory-constrained (e.g. capped at 500MB) and the original index didn't fit in memory, hitting a huge index vs. a small one would show a real, visible performance gap.

The single original index (69.4 MB) is ~3x larger than any individual partition index (13.9–24.3 MB). Smaller indexes are cheaper to scan, cheaper to keep in memory, and cheaper to maintain.

🏠 Real-world takeaway: at 10M rows the difference is minor on a beefy machine. But scale this up to 100M–500M+ rows, or run it on a resource-constrained server (like a typical production container with memory limits), and a 3x smaller index can mean the difference between an index living fully in RAM vs. spilling to disk — a massive real-world performance gap.

The setting that makes it all work: enable_partition_pruning

This Postgres setting controls whether the planner is allowed to skip irrelevant partitions. It should always be on (the default).

-- turning it off to demonstrate the danger
set enable_partition_pruning = off;
explain select count(*) from grades_parts where g = 30;
⚠️ With pruning OFF: the query hit all four partitions (g0035, g3560, g6080, g80100) — even though only one could possibly contain g = 30. This defeats the entire purpose of partitioning.
g0035 ✅
g3560 ❌ wasted
g6080 ❌ wasted
g80100 ❌ wasted
-- restoring correct behavior
set enable_partition_pruning = on;
explain select count(*) from grades_parts where g = 30;
-- back to hitting only g0035

The presenter notes he's unsure why this "off" option even exists — possibly a safeguard for edge cases — but stresses it should always be left on in practice.

Key Takeaways

  • A correctly pruned query on a partitioned table touches only the relevant partition(s) — verified via EXPLAIN showing a single Index Only Scan.
  • Performance gains from partitioning may not be dramatic on an unconstrained machine — they become much more visible under real memory/I/O limits.
  • Partition indexes are individually much smaller than one giant index — this matters more as data scales into hundreds of millions of rows.
  • enable_partition_pruning must stay ON — otherwise Postgres scans every partition anyway, and you lose the entire benefit of partitioning.
