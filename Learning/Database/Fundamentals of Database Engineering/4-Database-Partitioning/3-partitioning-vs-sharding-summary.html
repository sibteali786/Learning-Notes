⚖️ Partitioning vs Sharding

Same-sounding, very different architectures

Core Difference

🧩 Horizontal Partitioning

  • Splits a big table into multiple tables within the same database (server)
  • The database engine manages routing internally
  • Client is agnostic — you send one query, the DB decides which partition to hit based on the WHERE clause
  • Table names/schema on the backend actually change (multiple partition tables exist)

🌐 Sharding

  • Splits a big table into multiple tables across completely different database servers
  • Used for distributed processing and reducing latency (e.g. geo-based)
  • Client is aware of the shard — a proxy (e.g. ProxySQL) or app logic must route you to the correct server
  • Table name/schema stays the same everywhere — only the server you hit changes

🏠 Real-world analogy: Partitioning is like one giant warehouse with labeled aisles — you tell the front desk what you need, and their internal system tells a forklift which aisle to grab it from; you never see the aisles.

Sharding is like having separate warehouses in different cities — a dispatcher (proxy) looks at your delivery address and routes your order to the nearest warehouse entirely. Different building, different address, same catalog of products.

Trade-off to know

"The client is aware of the shard — that's a big no-no in sharding. Tools like Vitess try to solve this, but it's still a big investment for backend engineers."

Partitioning keeps complexity hidden inside the database. Sharding pushes that complexity out to the application/proxy layer — powerful for scaling across servers and reducing latency, but harder to build and maintain.
