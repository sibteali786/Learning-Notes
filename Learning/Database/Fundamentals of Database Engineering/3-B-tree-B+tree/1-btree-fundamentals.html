B-Tree Fundamentals

From "Full Table Scan" to "B-Tree Limitations" — Hussein Nasser, B-Trees vs B+Trees

The Problem — Full Table Scan

  • A table is stored as a data file made of fixed-size pages (Postgres = 8K by default, MySQL = 16K).
  • To find one row, the naive approach reads the table page by page, pulling each into memory and checking every row — that's a full table scan.
  • Cost = number of pages read. Worst case, the row you want is the very last one.
  • DBMS engines aren't dumb about it — they parallelize scans (multiple workers, top-down + bottom-up), but the scan is still O(n) in table size.
  • Goal: shrink the search space so we don't touch every page — that's what a B-Tree is for.
💡 Reading "8K from disk" isn't 1:1 with the underlying hardware either — disks have their own sector/SSD page sizes (e.g. 4K), which is a separate layer of complexity.

How the B-Tree Works

Vocabulary

node = 1 disk page degree (m) = max children m−1 = max elements/node element = key + value
  • A B-Tree has a degree (m) — the max number of child nodes a node can have. DBMS engines choose this automatically; you don't configure it.
  • A node with m children holds up to m−1 elements (e.g. 3 children → 2 elements).
  • Every element = a key (what you search for) + a value (the "data pointer" to the actual row — sometimes called α in the original 1970 B-Tree paper).
  • Layers: root node → internal nodes → leaf nodes (leaves have no children).
⚠️ Most textbook diagrams only draw the key and hide the value/data-pointer — which confuses B-Trees with B+Trees. In a real B-Tree, every node at every level stores both key and value.

Worked Example — searching for ID 3

Table: ID, Name with an internal Tuple ID (TID/RID) → 1:701 John, 2:702 Ali, 3:703 Rick, 4:704 Sara, 5:705 Edmond

Why this matters
You never fetch the whole table — the key tells you which page to pull next. Each hop eliminates a whole branch, so a tree of thousands of nodes still resolves in a handful of I/Os (its height, not its size).

Inserting & Splitting

  • Adding elements 1→11 into a degree-3 tree (max 2 elements/node): once a node overflows, it splits, pushing a middle key up to the parent.
  • Splits are expensive — one reason engines try to keep nodes large (fewer splits needed) rather than tiny toy-sized nodes.
  • Insert order matters: random keys land on scattered pages → more splits, slower inserts. Sequential/ordered keys (like an auto-increment ID) insert more cheaply since new rows always land at the "end."

Limitations of B-Trees

LimitationWhy it happens
Wasted memory per node Every node stores both key and value even when only the key is needed to route the search — space that could've held more elements.
Big values = fewer elements/page A UUID or long string as the indexed key means larger key+value pairs → fewer fit per page → more pages → more I/O → slower traversal. (Think twice before indexing a UUID/string PK.)
Slow range queries Values live scattered across every level, so "give me IDs 4–9" means separate top-to-bottom traversals for each key — even though 4,5,6,7,8,9 are logically adjacent.
Hard to cache internal nodes in memory Since internal nodes also carry full values, they're heavier — costlier to keep the "routing layer" resident in RAM, especially with large key types.
Real-world example — range scan pain
Finding IDs 4 through 9 in the example tree requires separate root→leaf walks for each value (4 is lucky/at root, 5 needs 3 hops, 6 might be cached, 7/8/9 each re-traverse) — despite the rows being contiguous. That thrashing is exactly the range-query weakness B+Trees were built to fix (leaf nodes get linked together).
