B+Tree, DBMS Considerations & Storage Cost

Continuing from B-Tree Limitations — Hussein Nasser, B-Trees vs B+Trees

How B+Trees Fix the Limitations

keys only in internal/root nodes values only in leaves leaves linked together
  • Structurally the same as a B-Tree, but internal nodes (and root) store only keys — no values, no data pointers.
  • Slimmer internal nodes = each fits far more keys per page = one I/O gets you way more routing information than a plain B-Tree.
  • All values live in the leaf nodes — since leaves need everything, keys get duplicated between internal nodes and leaves. That duplication cost is proven to be small relative to the benefit.
  • Leaf nodes are linked (like a doubly/singly linked list) — find one key, and you can walk forward/backward to every adjacent key for free. This is what makes range queries fast.
Real-world example — range query redo
Finding IDs 4–9 now costs one top-down traversal to reach 4, then it's a straight sideways walk: 4→5→6→7→8→9 via leaf pointers. Best case, all 5 elements fit in a single page = 1 I/O instead of the B-Tree's repeated re-traversals.

DBMS Considerations

  • Leaf pointer has a cost — cheap, but not free; it's an extra field every leaf carries.
  • 1 node = 1 DBMS page in most systems.
  • Slimmer internal nodes → easier to keep the whole "routing layer" resident in memory → fast traversal even on huge tables.
  • Leaf nodes can live on disk in the heap/data files — they don't need to be in memory the way internal nodes ideally are.
  • Most DBMS engines use B+Trees — including MongoDB's WiredTiger engine (WiredTiger also offers an LSM-tree variant that skips leaf pointers entirely, since Mongo doesn't prioritize range queries the same way).
  • Whether an index "should" fit fully in memory depends on what you're indexing on — small ints fit easily; UUIDs/strings/blobs don't.

Storage Cost — Postgres vs MySQL

PostgresMySQL (InnoDB)
Secondary index value points to Tuple directly (small, fixed pointer ~32/64-bit) The primary key value itself
Table storage model Heap table Clustered / Index-Organized Table (IOT) — table is the PK's B+Tree, leaf holds full row
Risk with expensive PK (UUID/string) Low — pointer size unaffected by PK type High — every secondary index duplicates that large PK in every entry → index bloat
Insert cost with random PK (UUID) Not clustered on PK, less impacted Slow — inserts land randomly across the clustered structure, causing splits
⚠️ This is a real reason Uber famously moved from Postgres to MySQL — write/index amplification from Postgres's tuple-pointer model at their scale. (One of several reasons, not the whole story.)
💡 Practical takeaway: avoid UUID/string primary keys on MySQL/InnoDB-style clustered tables. If you must, storing the UUID in binary (16 bytes) instead of string form (36 bytes) helps but doesn't eliminate the bloat.

Summary — The Full Arc

  • Full table scan → the problem: too many I/Os to find a row.
  • B-Tree → balanced tree, keys+values at every node, shrinks search space.
  • B-Tree limitations → wasted space per node, slow range queries, hard to cache internal nodes.
  • B+Tree → keys-only internal nodes, values only in linked leaves → fixes both problems.
  • Considerations → leaf pointer cost, what fits in memory, engine choices (WiredTiger/LSM).
  • Storage cost → Postgres (tuple pointer) vs MySQL (PK pointer + clustered table) — no universal "best," it depends on your access patterns and key types.
💡 Core lesson repeated throughout: every index design decision has a cost. Understanding B+Trees is what lets you reason about why a UUID PK, a wide index, or a range query behaves the way it does in production.
