Multi-Master Replication

a.k.a. Multi-Leader · Active-Active — many nodes accept writes, so writes can scale… at the cost of conflicts.

01

The Problem It Solves

Master/Backup's ceiling

In master/backup, every write goes to one instance. Adding standbys scales reads, but when that single master can't keep up with writes anymore, you're stuck.

The idea

Let more than one node accept writes. Each master replicates its changes to the other masters (and to its own followers). Writes now spread across nodes.

Heads-up: Multi-master is one way to scale writes — and a very complex one. It's not the only option (see Alternatives).
02

Architecture

Masters

Several leader nodes, each accepting writes and DDLs.

Master ↔ Master

Masters exchange changes with each other so they converge on the same data.

Followers

You can still attach read-only backups. Each one follows a different master, one-way, like in Part 1.

03

The Core Problem — Write Conflicts

Once two nodes accept writes, two people can write completely different values to the same row on different masters, at nearly the same time.

Without a rule, the masters diverge — Asia shows 100, Europe shows 120, forever. So the system needs conflict resolution: a deterministic rule every node applies the same way.
-- Same row, same moment, two masters:
-- on Master 1
UPDATE products SET price = 100 WHERE id = 42;
-- on Master 2
UPDATE products SET price = 120 WHERE id = 42;
-- both commit locally ✓ … then replicate to each other → CONFLICT
update–update

Same row changed differently on two masters (above).

insert–insert

Two masters insert the same unique key (e.g. same username or same auto-increment id).

update–delete

One master updates a row that another master just deleted.

04

Conflict Resolution Strategies

StrategyHow it worksProsCons
Avoid conflictsRoute all writes for a given record to the same master (e.g. a user's region always owns their data)Simplest, no resolution neededBreaks if a user moves regions or a master fails
Last-Write-Wins (LWW)Keep the write with the latest timestampEasy, automaticSilently loses data; clock skew can pick the "wrong" winner
Priority / node winsA higher-priority master always winsDeterministicWrites on low-priority nodes are lost
Merge / CRDTsCombine values with data types designed to merge (counters, sets)No data lossOnly fits some data shapes; complex
App-level / manualStore both versions; the app or user picksBusiness-correctMore code, UX burden
-- Last-Write-Wins idea: apply an incoming change only if it's newer
UPDATE products
SET    price = :incoming_price, updated_at = :incoming_ts
WHERE  id = 42 AND updated_at < :incoming_ts;   -- older write loses

-- Avoid insert–insert on ids: use UUIDs instead of per-node sequences
CREATE TABLE orders (id uuid DEFAULT gen_random_uuid() PRIMARY KEY, ...);
05

Why Most Databases Prefer One-Way Replication

Master/Backup (one-way)

  • Changes flow in one direction
  • No conflicts by design
  • Much, much easier to implement and reason about
  • Default mode in Postgres & MySQL

Multi-Master (two-way)

  • Changes flow in every direction
  • Conflicts must be detected & resolved
  • Harder to debug, test and operate
  • Usually an extension or special product
Some teams do run multi-master, but most systems stick with one-way replication and only adopt multi-master when there's a clear need for it.
06

Pros & Cons

✓ Pros

  • Scales writes beyond one node
  • Local writes per region — low write latency for global users
  • High availability for writes — if one master dies, others keep accepting writes
  • Still supports read followers for read scaling

✗ Cons

  • Write conflicts + conflict resolution logic
  • Complex to implement and operate
  • Eventual consistency between masters
  • Constraints (unique keys, foreign keys, auto-increment ids) get tricky
  • Every write still has to replicate to all masters, so gains are limited under heavy write load
07

Real-World Scenarios

Global SaaS

Region-owned writes

A master in the US and one in the EU. Each tenant's data is written in its home region (conflict avoidance), then replicated to the other for reads and disaster recovery.

Offline-first apps

Calendar / notes on phone

Each device acts like a "master" while offline. On reconnect, changes sync and conflicts get merged, or the user is asked "keep which version?"

Collaborative editing

Docs edited together

Multiple users write at once. Tools use merge algorithms (OT/CRDTs) instead of LWW, so nobody's typing gets lost.

Shopping cart

Merge, don't overwrite

User adds item X in one region and item Y in another. Merging gives X+Y. LWW would drop one, and you'd lose a sale.

Where it goes wrong

Inventory count

Two regions each sell the "last" item at the same moment → oversold. Stock that must be exact often lives on a single master instead.

Tools

Where you'll see it

MySQL Group Replication (multi-primary mode), Galera Cluster, Postgres extensions such as BDR/pgEdge. Check each tool's docs for how it handles conflicts.

09

Interview / Practical Tips

  • The moment you say "multiple masters," say "conflicts" next — interviewers expect it.
  • Default answer: single-leader + read replicas. Justify multi-master only for multi-region writes or offline use.
  • If asked to scale writes, mention sharding as the more common alternative.
  • Best resolution is avoidance: give each record a home master.
  • Know the LWW trap: it's simple but silently drops writes.
  • Use UUIDs (not per-node auto-increment) for primary keys in multi-master setups.
