Postgres 13 streaming replication, step by step

A hands-on demo: two Postgres containers in Docker, one master and one standby, connected with synchronous streaming replication. The presenter stresses that this is the simplest working setup to show how it works, not a best-practice or production design.

1. The big picture

Why a two-way configuration? The standby must know how to reach the master (primary_conninfo), and the master must know which standbys it trusts and waits for (pg_hba.conf + synchronous_standby_names). Both sides use the same application_name, which is case-sensitive.

2. Setup, step by step

1

masterCreate the master container

Create a replication folder on the host. Data for both instances lives there because the data files get edited and copied a lot. The master maps host port 5432 and mounts its own data folder (the full host path is required).

docker run --name pg-master \
  -p 5432:5432 \
  -v /path/to/replication/master_data:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=postgres \
  -d postgres:13

docker logs pg-master   # confirm it started and created config files

The master_data folder appears on the host with the Postgres data and config files.

2

standbyCreate the standby container

Same command with three changes: a new name, host port 5433 (5432 is taken), and its own folder. Inside the container it still listens on 5432. At this point the two are completely independent Postgres instances.

docker run --name pg-standby \
  -p 5433:5432 \
  -v /path/to/replication/standby_data:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=postgres \
  -d postgres:13
3

bothStop both, then clone master data into standby

Replication requires the standby to start from data identical to the master. Different data leads to many errors (the presenter hit these repeatedly). Because everything is on the host, it is just a folder copy.

docker stop pg-master pg-standby

mv standby_data standby_data_backup
cp -r master_data standby_data

The presenter mentions pg_basebackup as the other common way, but prefers the copy for simplicity.

4

masterAllow replication connections: pg_hba.conf

Edit the file inside master_data and append one line. This lets the user connect in replication mode with password (md5) auth.

# TYPE  DATABASE     USER      ADDRESS  METHOD
host    replication  postgres  all      md5
Demo shortcut: this uses the postgres admin user with password postgres. In real setups create a dedicated user that can only replicate.
5

standbyPoint the standby at the master: postgresql.conf

In standby_data, enable primary_conninfo. This is the only change needed in the standby config (other knobs exist but are out of scope).

primary_conninfo = 'application_name=standby1 host=<master-host> port=5432 user=postgres password=postgres'
  • application_name: unique, case-sensitive ID for this standby. The master references it so only known nodes replicate (otherwise anyone could replicate from the database).
  • host + port: where the master is reachable. Both containers are on the same machine and the master port is exposed to the host, so the host name works. (The transcript is unclear on the exact host name; on Docker Desktop, host.docker.internal is the usual value.)
  • user / password: same credentials as the master container, here postgres.

The config file itself notes that standby settings are ignored on the master.

6

standbyCreate standby.signal

In the standby data folder, create an empty file named standby.signal. This turns the instance into a read-only standby.

touch standby_data/standby.signal
7

masterMake commits synchronous: synchronous_standby_names

In the master’s postgresql.conf, list the standbys by their application_name. Syntax matters here.

synchronous_standby_names = 'FIRST 1 (standby1)'
FormMeaning
FIRST 1 (standby1)Commit succeeds once at least one listed standby confirms. With one standby this is trivially that one.
FIRST 2 (standby1, standby2, standby3)Priority order: the first two in the list are preferred, the third is a fallback.
ANY 2 (standby1, standby2, standby3)Any two of the three may confirm; no priority.
8

bothStart both and read the logs

docker start pg-master pg-standby
docker logs pg-master
docker logs pg-standby
Master log: standby1 is now a synchronous standby with priority 1.
Standby log: started streaming WAL from primary.

3. Verify it works

Check replication state on the master

docker exec -it pg-master psql -U postgres
SELECT * FROM pg_stat_replication;

An empty result means no replication. A healthy one shows one row: state streaming, sync state sync, application name standby1, user postgres.

Then open a second terminal on the standby: docker exec -it pg-standby psql -U postgres. Tests the presenter ran:

WhereActionResult
masterCREATE TABLE test (id integer, t varchar(200));Appears on standby (\d test shows it immediately).
standbyCREATE TABLE test1 (id integer, t varchar(200));Error: cannot write to a replica; it is read-only.
masterInsert 10,000 rows with random values, e.g. INSERT INTO test SELECT random()*1000 FROM generate_series(1,10000);Standby SELECT count(*) shows 0 first, then the rows appear almost instantly (same machine, so very fast).
masterALTER TABLE test ADD COLUMN ...Schema change shows up on the standby immediately.
masterTRUNCATE TABLE test;All rows disappear from the standby too.
Takeaway: data (inserts), structure (create/alter) and deletes (truncate) all flow from master to standby through the WAL. The standby is read-only.

4. Key concepts from the demo

WAL (write-ahead log)

A compact record of every transaction. Changes go to the WAL first (in memory, then disk). Replication simply ships the WAL to the standby, which replays it.

Synchronous vs asynchronous

Synchronous: the master waits for the named standby(s) to confirm before the commit returns. Asynchronous: the master does not wait. The demo uses synchronous.

application_name

The unique, case-sensitive identity of a standby. It must match between the standby’s primary_conninfo and the master’s synchronous_standby_names.

Identical starting data

The standby must begin as an exact copy of the master. Anything different causes errors, hence the stop, copy, start sequence.

standby.signal

An empty file that tells Postgres 12+ to start as a read-only standby.

pg_stat_replication

View on the master listing connected standbys, their state (streaming) and sync mode. Empty means nothing is replicating.

5. Shortcuts taken in the demo (don’t copy to production)

  • Using the postgres admin user for replication; create a user with only the replication privilege.
  • Password equal to the username.
  • Address all in pg_hba.conf instead of the standby’s specific address.
  • Master and standby on one machine: no real fault isolation.
  • A production system needs a designed architecture; it can’t be done in five minutes.
Behavior to know: with synchronous replication and a single standby, if that standby goes down, commits on the master wait for it and writes can stall until it returns or the setting is changed.

6. Alternatives and trade-offs

Approach used: copy the data folder

Pros

  • Very simple with host-mounted volumes
  • No backup tooling to learn

Cons

  • Needs both instances stopped
  • Manual; standby.signal and primary_conninfo set by hand
  • Not suitable for a live production master

Alternative: pg_basebackup -R

pg_basebackup -h <master-host> -U postgres \
  -D standby_data -R -X stream

Pros

  • Works against a running master
  • -R writes standby.signal and connection info for you

Cons

  • One more command and user privileges to manage

Synchronous (used)

Pros

  • No data loss on master failure for confirmed commits

Cons

  • Higher commit latency; writes can block if the standby is unavailable

Asynchronous

Pros

  • Faster commits; master unaffected by a slow or down standby

Cons

  • Recent commits can be lost on failover

ANY / FIRST with several standbys

Pros

  • Tolerates one standby failing without stalling writes

Cons

  • More nodes to run and monitor

Logical replication (not in the demo)

Pros

  • Replicate selected tables; different versions possible

Cons

  • Different mechanism; schema changes are not replicated automatically

7. Real-world scenarios

Payments service

A payments table cannot lose a confirmed transaction. Synchronous replication means a commit is acknowledged only after the standby has it, so if the master dies, the standby has every confirmed payment.

Reporting and analytics

Heavy dashboard queries run on the read-only standby so they never slow the master that serves customer writes.

Failover and upgrades

If the master machine fails, the standby holds a current copy and can be promoted to take over, shortening downtime.

Learning lab

Exactly what this demo is: two containers on a laptop to see WAL streaming, read-only behavior and pg_stat_replication before designing a real architecture.

docker run --name pg-master  -p 5432:5432 -v $PWD/master_data:/var/lib/postgresql/data  -e POSTGRES_PASSWORD=postgres -d postgres:13
docker run --name pg-standby -p 5433:5432 -v $PWD/standby_data:/var/lib/postgresql/data -e POSTGRES_PASSWORD=postgres -d postgres:13

# 3. clone
docker stop pg-master pg-standby
mv standby_data standby_data_backup && cp -r master_data standby_data

# 4. master pg_hba.conf
host replication postgres all md5

# 5. standby postgresql.conf
primary_conninfo = 'application_name=standby1 host=<master-host> port=5432 user=postgres password=postgres'
# 6. standby
touch standby_data/standby.signal

# 7. master postgresql.conf
synchronous_standby_names = 'FIRST 1 (standby1)'

# 8. run + verify
docker start pg-master pg-standby
docker exec -it pg-master psql -U postgres -c "SELECT * FROM pg_stat_replication;"
