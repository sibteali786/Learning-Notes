Database Replication · Part 3

Synchronous vs Asynchronous Replication

When a client writes to the master, does it wait for the standbys too — or return right away?

Sync = wait for replicas Async = return after master Consistency vs speed FIRST N / ANY N Quorum
01

The Question

Every write must commit on the master first — that's true for any database. The open question from Part 1: after the master commits, is the client unblocked immediately, or only after the standbys have the change too?

Master + its standbys together are called a cluster.

02

Side by Side — Timeline

03

Synchronous Replication

1
Client writes to the master and waits for the master's commit (as in any DB).
2
The master also has to get the transaction committed on the standby replicas.
3
Only then is the client unblocked.
Result: strong consistency instead of eventual — a write isn't "done" until the master and the required standbys have it. The cost is slower writes: each commit waits on network round trips to replicas.
04

"I have 7 standbys — wait for all 7?"

Waiting on every replica is overkill: the slowest one sets your write latency. So databases let you choose how many and which replicas to wait for.

FIRST 1

Wait for the top-priority one

Standbys are ranked. Wait for the highest-priority one that's connected.

FIRST 2

Wait for the top two by priority

Stronger durability: two copies are guaranteed before success.

ANY N

Whoever answers first

Unblock as soon as any N standbys confirm. This is quorum-style, like Cassandra's QUORUM.

You can mix per replica: for example, one sync backup that must never lose data, plus several async replicas that serve reads. Turning sync on for every node makes the cluster behave almost like one single database, fully consistent but paying the full latency cost.
05

In Postgres

Configured on the master in postgresql.conf. Names are the standbys' application_name.

# wait for the highest-priority 1 of these (A preferred, then B)
synchronous_standby_names = 'FIRST 1 (standby_a, standby_b)'

# wait for the top 2 by priority
synchronous_standby_names = 'FIRST 2 (standby_a, standby_b, standby_c)'

# quorum: any 2 of these 3, whoever answers first
synchronous_standby_names = 'ANY 2 (standby_a, standby_b, standby_c)'

# empty = fully asynchronous (the default)
synchronous_standby_names = ''

synchronous_commit controls how far a sync standby must get before the client is unblocked. It can be set per transaction:

ValueClient unblocked when…Speed
offBefore even the master's WAL is flushed to diskFastest
localMaster flushed; standbys not waited onFast
remote_writeStandby received it (in OS memory)Medium
on (default)Standby flushed it to disk (durable)Slower
remote_applyStandby applied it, so it's visible to reads thereSlowest
-- critical write: make it visible on standbys before returning
BEGIN;
SET LOCAL synchronous_commit = 'remote_apply';
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;

-- check which standbys are sync / async / quorum
SELECT application_name, sync_state, sync_priority, replay_lag
FROM   pg_stat_replication;
Nuance: With the default on, the data is durable on the standby but may not be visible there yet. For true read-your-writes on a replica, you need remote_apply.
06

Asynchronous Replication

1
Client writes to the master; once the master commits, the client is done and unblocked.
2
A background process ships the changes to the standbys afterwards.
3
Standbys catch up a little later, which means eventual consistency.

Faster writes & throughput

The client never waits on the network to replicas. This is the default in most databases.

Hidden background cost

The background workers use CPU and I/O on the master. Under a heavy write load they can slow things down, and replicas fall further behind.

Data-loss risk: If the master crashes after acking the client but before shipping the change, and a standby gets promoted, those last writes are gone, even though the client was told "success".

08

Real-World Scenarios

Banking / payments

Sync to a DR standby

A confirmed transfer must survive a master crash. Wait for at least one standby (FIRST 1) and accept slower writes.

Social feed

Async everywhere

A like or post appearing half a second late on a replica is fine. Speed and throughput matter more.

Mixed SaaS

Per-transaction choice

Billing writes use remote_apply; activity logs use local. One cluster, different guarantees.

Cross-region

Sync nearby, async far

A sync standby in the same region (a few ms away) plus an async replica on another continent, so writes stay fast.

Cassandra

Quorum

A write at QUORUM waits for a majority of replicas to acknowledge. It's the same "ANY N" idea, chosen per query.

Outage trap

Single sync standby dies

With FIRST 1 (a) and only one name listed, if a goes down every commit hangs. Always list backup candidates.

10

Interview / Practical Tips

  • Frame it as a trade-off: durability/consistency vs write latency.
  • The common production answer: sync to one nearby standby, async to the rest.
  • Mention that async can lose acknowledged writes on failover.
  • Sync doesn't automatically mean "readable on the replica". Know about remote_apply.
  • Never configure exactly one sync standby with no fallback.
  • Monitor replay_lag; async lag is your stale-read window.
