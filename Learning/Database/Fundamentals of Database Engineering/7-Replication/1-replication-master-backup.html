Database Replication · Part 1

Master / Backup Replication

a.k.a. Master/Standby · Leader/Follower · Primary/Replica — one node writes, many nodes read.

1 Master (writes) N Standbys (reads) No write conflicts Eventual consistency Horizontal read scaling
01

The Problem

One database = one bottleneck

A single DB node handles every read and write. As traffic grows, reads (usually the majority) crush it. Users far from that node (Asia vs US) suffer high latency, and if it dies, everything dies.

The idea

Keep copies of the data on multiple nodes. Let exactly one node accept changes and push them to the others. Everyone else only serves reads.

02

What Goes to the Master

DDL — Data Definition Language

Changes to the structure of the database.

CREATE DATABASE shop;
CREATE TABLE orders (id serial, total numeric);
ALTER TABLE orders ADD COLUMN status text;

DML (writes) — Data Manipulation

Changes to the rows inside tables.

INSERT INTO orders(total) VALUES (99);
UPDATE orders SET status='paid' WHERE id=1;
DELETE FROM orders WHERE id=7;
Rule: Clients never write to standby nodes directly. All writes + DDLs → master. The master replicates to the standbys.
03

Write Path

1
Client sends a write/DDL to the master.
2
Master commits it (recorded in its write-ahead log).
3
Master pushes the change to each standby over an already-open, full-duplex TCP connection authenticated with a dedicated database replication user.
4
Standbys apply the change and now hold the same data — eventually.
04

Read Path

Read from Master

Always up-to-date. But adds load to the one node that must also handle every write.

Read from Standby

Totally fine and the whole point — offloads the master. Data may lag behind by a bit.

Write to Standby

Not allowed. Standbys are read-only; the DB rejects the write.

-- On a Postgres standby (hot standby):
INSERT INTO orders(total) VALUES (10);
ERROR:  cannot execute INSERT in a read-only transaction

SELECT pg_is_in_recovery();   -- true on standby, false on master
05

Why It's Simple — No Conflicts

Single writer = single source of truth

Only one node takes writes, so two nodes can never modify the same row at the same time. There's nothing to merge or resolve — changes flow one direction, in one order.

Contrast: Multi-Master later video

Multiple masters accept writes → two users can update the same row on different masters simultaneously → you must resolve conflicts. More power, far more complexity.

06

Regions & Eventual Consistency

Key insight: Eventual consistency is not just a NoSQL thing. A plain relational database (Postgres, MySQL) running master/backup replication is eventually consistent for reads served by replicas. Propagation across regions takes time — if your use case can tolerate that, great. If not, there are ways to handle it (see tips below).
Teaser — does the client wait for standbys? Either the write returns once it's in the master's WAL (asynchronous), or it waits until standbys confirm (synchronous: first 1, first 2, or any N). A trade-off between speed and consistency — covered in the next video.
07

Pros & Cons

✓ Pros

  • Horizontal scaling of reads — add more standbys as read traffic grows
  • Region-based queries — a DB copy per region, near its users
  • Simple — one writer, no conflict resolution
  • Redundancy — standbys are live copies that can be promoted if the master fails

✗ Cons

  • Eventual consistency — replica reads can be stale
  • Writes don't scale — every write still hits one master
  • Slow writes if you choose synchronous replication
  • Master is still a write single point of failure until failover happens
08

Real-World Scenarios

E-commerce

Product catalog

Thousands browse products (reads) for every one who places an order (write). Browsing → replicas; checkout → master. Classic 95/5 read-heavy split.

The stale-read bug

"I just updated my profile!"

User saves a new name (master), page reloads and reads from a lagging replica → old name shows. Fix: read-your-own-writes by sending that user's reads to master for a few seconds.

Analytics

Heavy reports

Run expensive dashboard/BI queries on a dedicated replica so they never slow down production writes on the master.

Multi-tenant SaaS

Global users

Master in the US, replicas in EU & Asia. Dashboards load fast everywhere; settings changes route to the US master.

Failover

Master crashes

A standby is promoted to master (e.g. pg_promote()). Managed services like AWS RDS / Aurora automate this.

Banking

Balance check

Balance before transfer must be fresh → read from master (or use synchronous replication). A stale read here costs money.

09

In Code — Read/Write Splitting

The app decides where each query goes. Writes → master pool; reads → replica pool.

import { Pool } from "pg";

const master   = new Pool({ host: "db-master"  });
const replicas = [new Pool({ host: "db-replica-1" }),
                  new Pool({ host: "db-replica-2" })];

const pickReplica = () => replicas[Math.floor(Math.random() * replicas.length)];

// writes + DDL always go to master
export const write = (sql, params) => master.query(sql, params);

// reads can go to replicas, unless caller needs fresh data
export const read = (sql, params, { fresh = false } = {}) =>
  (fresh ? master : pickReplica()).query(sql, params);

// usage
await write("UPDATE users SET name=$1 WHERE id=$2", ["Ali", 1]);
await read("SELECT * FROM users WHERE id=$1", [1], { fresh: true }); // read-your-writes

Check replication status & lag from the master:

SELECT client_addr, state, sync_state, replay_lag
FROM   pg_stat_replication;

Alternatives & When to Pick Them

ApproachScales readsScales writesComplexityBest for
Master/BackupYesNoLowRead-heavy apps, geo reads, HA
Multi-MasterYesPartlyHigh (conflicts)Writes needed in many regions
ShardingYesYesHigh (routing, cross-shard joins)Data too large / write-heavy for one node
Caching (Redis)YesNoMedium (invalidation)Hot, repeated reads
Vertical scalingLimitedLimitedVery lowEarly stage — just buy a bigger box

These combine: most production systems use master/backup + a cache, and add sharding only when writes outgrow one master.

11

Interview / Practical Tips

  • Name it clearly: "single-leader replication — writes to leader, reads fan out to followers."
  • Always follow with "reads from replicas are eventually consistent" and how you'd handle it.
  • Fixes for staleness: read-your-writes routing, sticky sessions to master after a write, sync replication for critical data.
  • Remember: it scales reads, not writes. Write-heavy? → sharding.
  • Mention failover: promote a standby; beware of async lag = possible loss of last few writes.
  • Monitor replication lag — a replica far behind should be taken out of the read pool.
