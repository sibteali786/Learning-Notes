Multiple Indexes:
How the Optimizer Chooses

Table T has two separate single-column indexes — not a composite. Query: which index (or indexes) does Postgres/Oracle/SQL Server actually use?

SELECT * FROM T WHERE F1 = 1 AND F2 = 4  →  F1_IDX, F2_IDX
CASE 1

Both indexes used — merge the row IDs

Each index is searched independently for its value, collecting matching row IDs. The two ID lists are then intersected (AND) or unioned (OR). Happens when the result set is neither too small nor too large — worth paying for two index searches.

F1_IDX → search 1

1 – row7
1 – row8
1 – row9
1 – row10
AND

F2_IDX → search 4

4 – row7
4 – row22
4 – row12
4 – row10
✓ Intersection → result set = row7, row10 (only rowIDs present in both lists)
CASE 2

Only one index used — then filter

Optimizer picks the index it trusts most (usually the one returning fewer rows, or a primary key) — searches it, fetches those rows from the table, then re-filters the rest of the WHERE clause in memory. Only works for AND — anything not matching F1 is already excluded.

F1_IDX → search 1 → rowIDs: row7, row8, row9, row10
↓ fetch from table, then filter F2 = 4:
1 – 4 – row07 ✓ keep
1 – 8 – row08 ✗ discard
1 – 9 – row09 ✗ discard
1 – 4 – row10 ✓ keep

Typical trigger: F1 is a primary key, or stats show F1 returns very few rows relative to F2.

CASE 3

Neither index used — full table scan

Optimizer estimates the combined condition will match most of the table (e.g. ~75%) — so searching either index is wasted work. Goes straight to a (often multi-threaded / parallel) table scan instead.

↓ full scan, top to bottom, filter both F1=1 and F2=4 inline
3 – 9 – row01
5 – 5 – row02
1 – 3 – row03
1 – 4 – row07 ✓
1 – 8 – row08
1 – 9 – row09
1 – 4 – row10 ✓
3 – 4 – row12
4 – 4 – row22

Table statistics are critical here — this decision lives or dies on how accurate the row estimates are.

The stale-statistics trap

⚠ Got bitten by this? Here's why.

01Fresh empty table — stats say "0 rows"
02Bulk insert 300M rows in one transaction
03Query runs immediately — stats still say "~0 rows"
04Optimizer: "table is tiny, just scan it" → full scan on 300M rows

Statistics update asynchronously — a bulk insert doesn't refresh them instantly. Always run an explicit refresh right after large data changes, before querying.

PostgreSQL
VACUUM ANALYZE
Oracle
GATHER SCHEMA STATS
SQL Server
UPDATE STATISTICS
Overriding the optimizer — hints
SELECT * FROM T /*+ INDEX(f1 F1_IDX) */ WHERE F1 = 1 AND F2 = 4

When you know something the optimizer doesn't — e.g. stats are stale right after a bulk load — a hint forces a specific index or plan. Use with caution: hints bypass the optimizer's judgment entirely, and a hint that's right today can become wrong as data shape changes.

Real-world intuition

SparsityAn index is only as good as how spread out the values are

A state column index is useless if 99% of customers are in California — that query returns almost the whole table anyway (Case 3). But if only 3 rows have state = 'Florida', that index is gold (Case 2/1).

Post-migrationBulk data load followed by immediate reporting queries

Classic stats-trap scenario: an ETL job inserts millions of rows, then a dashboard query runs seconds later and gets a full table scan because stats haven't caught up — run ANALYZE/equivalent as the last ETL step.
