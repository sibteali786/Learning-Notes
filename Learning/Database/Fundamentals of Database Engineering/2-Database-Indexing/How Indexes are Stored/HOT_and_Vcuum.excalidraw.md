"N" = however many separate indexes exist on that table — because each index is its own independent structure, each with its own (value → TID) entries pointing at the row.

Example: orders(id PK, customer_id, status, updated_at) with:

Index 1: PK on id

Index 3: on status (for "get all pending orders")

If a page is packed 100% full, there's no room to squeeze the new tuple onto the same page → HOT fails → new tuple goes elsewhere → indexes must be updated the normal (expensive) way. That's why the article says HOT "only happens if the page has enough space." ^lQrs5uoR

Example  ^kUUdo1mR

Table orders(id PK, status, updated_at) with an index only on id. If you frequently 
UPDATE orders SET status = 'shipped' — status isn't indexed — HOT lets these updates skip touching the index entirely, as long as pages have spare room. This is why people intentionally lower fillfactor (e.g. to 80-90%) on heavily-updated tables to keep HOT working longer. ^Lpkv1u5W
