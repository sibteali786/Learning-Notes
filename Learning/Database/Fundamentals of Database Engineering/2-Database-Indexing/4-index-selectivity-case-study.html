Case Study: Index Exists, Planner Still Chose Seq Scan

Table students — 50M rows, index on g, mixed results across your test queries
Problem

What you observed

After creating g_index ON students(g): g BETWEEN 10 AND 20 LIMIT 1000 used the index (~4ms), but g BETWEEN 8 AND 95 — with or without LIMIT 1000 — still ran a Parallel Seq Scan + external merge sort (16–36 seconds).

Answer

Short answer: it's selectivity, not memory

g is random()*100, so it's roughly uniform across 0–100. That means:

Condition% of table matchedRows matched (of 50M)
g > 8 AND g < 95~87%~43,000,000
g > 10 AND g < 20~10%~4,500,000
g > 8 AND g < 95 — 87% of rows
g > 10 AND g < 20 — 10% of rows
This is the real cause. Your own EXPLAIN output confirms it — for the 8–95 query the planner estimates rows=43056508 (an Index Scan line even shows rows=43051483 as its own estimate). When a query matches ~87% of a table, walking the B-Tree and randomly jumping to the heap 43 million times is far more expensive than just reading the table straight through. The planner correctly avoids the index here — this isn't a bug or a memory shortfall, it's the planner doing its job.
Q&A

Your specific questions

Q: Even after having an index on g, we still get a sequential scan — why?

Because g BETWEEN 8 AND 95 matches ~87% of the 50M rows. Above roughly 5–15% selectivity (the exact crossover depends on cost settings), a full sequential scan is cheaper than an index scan: reading the table straight through is sequential I/O, while an index scan on this many matches means ~43M random heap lookups. The planner's cost model picked correctly.

Q: Is it because Docker's shared memory on my Ubuntu machine is too small to hold the whole index?

Not the primary cause here — though it's a real, secondary factor. Your own vacuum output shows 953,365 pages for the table alone (heavily read from disk: read=952650 buffers vs only ~800 cache hit), so yes, the working set doesn't fit in shared_buffers. That does make disk-heavy plans slower in absolute terms. But it does not explain why the planner chose Seq Scan over Index Scan — that choice is driven by estimated selectivity/cost, computed before any actual I/O happens. Even with unlimited RAM, Postgres would still prefer Seq Scan for an 87%-selectivity predicate, because touching 87% of pages via random access is inherently more work than one sequential pass — cache size just changes how painful each approach is, not which one wins.

Q: Why did LIMIT 1000 with g BETWEEN 10 AND 20 use the index, but g BETWEEN 8 AND 95 (with or without LIMIT) still didn't?

ORDER BY g DESC LIMIT 1000 only helps the planner when it can avoid sorting the whole result — i.e. by reading rows already in g-sorted order straight from the index and stopping after 1000. For 10–20 (~4.5M candidate rows), reading the index backward and stopping at 1000 matches is nearly free — that's exactly what your Index Scan Backward / Index Only Scan Backward plans show (2–4ms). For 8–95 (~43M candidate rows), the planner estimates it may still need to scan a large fraction of the index before finding 1000 that satisfy the range in descending order — worst case, the first row of the whole index doesn't fall in [8,95] and it has to skip millions of unmatching entries via random heap-adjacent index reads. Past a certain selectivity threshold, the "let's Seq Scan + Sort + cut top 1000" plan wins even with the LIMIT, since a full sort of the actual 43M-row filtered set is still cheaper than an unpredictable, possibly-huge random walk through the index. Your EXPLAIN confirms this: with the 8–95 LIMIT 1000 query, the plan is still Gather Merge → Sort (top-N heapsort) → Parallel Seq Scan, executing in ~16.6s.

Key Distinction

Index Scan vs. Index Only Scan — the INCLUDE(id) step

You dropped the plain g_index and recreated it as:

create index g_index on students(g) include(id);

This is the non-key column technique — id isn't part of the search key, it just rides along inside the index entries. Since your query only selects id, g, both columns now live entirely in the index. That's what upgraded the plan from a regular Index Scan to an Index Only Scan:

Index definitionPlan for SELECT id, g WHERE g BETWEEN 10 AND 20 LIMIT 1000Heap FetchesTime
g_index on students(g)Index Scan Backward — still jumps to heap for idimplicit (one per row)4.1ms
g_index on students(g) include(id)Index Only Scan Backward1000 (before VACUUM)3.3ms
same, after VACUUMIndex Only Scan Backward00.46ms
Why VACUUM still mattered here: even with id included in the index, Postgres can only skip the heap entirely if the visibility map says those pages have no dead/uncommitted rows to double-check. Right after a bulk load, that map isn't populated yet — so you still see Heap Fetches: 1000 despite having a "covering" index. Running VACUUM updates the visibility map and drops Heap Fetches to 0, which is the ~7x jump from 3.3ms → 0.46ms above.
Real-world scenario: An API endpoint that always does SELECT user_id, score FROM leaderboard WHERE score > X ORDER BY score DESC LIMIT 100 — indexing (score) INCLUDE (user_id) means this hot path never touches the table heap at all, as long as the table is vacuumed regularly. Trade-off: the index itself gets larger (it now stores user_id too), so it's a deliberate choice per query pattern, not a default you'd apply to every index.
Practical Tips

Takeaways

🔹 Selectivity, not index existence, drives the choice. A B-Tree index only wins when the match set is small relative to the table (rule of thumb: roughly under ~5–15% for random heap access, but there's no fixed universal cutoff — it's cost-based).

🔹 ORDER BY + LIMIT on an indexed column can make the index attractive even for a wide range, because Postgres can walk the pre-sorted index and stop early — but only if it doesn't expect to skip too much before filling the LIMIT.

🔹 Run VACUUM after bulk loads — it's what gets you Heap Fetches: 0 (true Index Only Scan) by updating the visibility map; without it, even an index-only-eligible query still touches the heap.

🔹 Watch Buffers: shared hit vs read in EXPLAIN (ANALYZE, BUFFERS) — high read counts relative to hit mean you're going to disk a lot, which is a real perf issue, just a separate one from plan choice.

Real-world scenario: An orders table filtered by status = 'pending' when 90% of rows are pending will Seq Scan even with an index — same reasoning as your 8–95 case. But status = 'cancelled' at 2% of rows will happily use the index. Same column, same index, opposite plan — because selectivity, not the presence of an index, is what the planner actually optimizes for.
