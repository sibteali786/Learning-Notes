CREATE INDEX CONCURRENTLY

Building an index on a large production table normally locks out writes for the whole duration. Postgres has a slower, safer alternative.

Default vs. concurrent

Default

CREATE INDEX g ON grades(id);
Readsallowed
Writesblocked
Build speedfast
Table scans neededsingle scan

Concurrently

CREATE INDEX CONCURRENTLY g ON grades(id);
Readsallowed
Writesallowed
Build speedmuch slower
Table scans neededmultiple scans
What happens under the hood
Scan 1
initial index build
Wait
pauses for in-flight write txns to finish
Scan 2
catch up on rows changed during scan 1
Scan 3
final validation pass

Multiple passes over the table (instead of one) is exactly what buys the "no write lock" guarantee — and exactly why it costs more time, CPU, and memory.

The trade-offs

⏱ Takes way longer

Multiple full scans + waiting on writers means build time can be several times longer than a normal index build.

🔥 More CPU & memory

Extra scans consume resources that could otherwise go to other queries running on the same production box.

⚠ Can fail into an invalid index

If a conflict happens mid-build (e.g. duplicate values for a unique index), the operation can leave a broken index behind.

CREATE UNIQUE INDEX CONCURRENTLY running
→
Concurrent writer inserts a duplicate value
→
Build fails → index left in INVALID state
→
Fix: DROP INDEX then rebuild
Rule of thumb: on a live production table, the extra time CONCURRENTLY costs is almost always worth it — a slower background index build beats blocking every write on the table. Postgres has been trending toward making this closer to the default behavior for exactly this reason. Always check for INVALID indexes after a concurrent build (\d or pg_index.indisvalid) and drop/retry if one shows up.
Real-world scenario

MIGRATION  Adding an index to a busy orders table

A 50M-row orders table needs a new index for a reporting query, but checkout writes to it constantly. A plain CREATE INDEX would freeze checkout for the build duration — CONCURRENTLY lets checkout keep running while the index builds in the background, at the cost of a longer migration window.
