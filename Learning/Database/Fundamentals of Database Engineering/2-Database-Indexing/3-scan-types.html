Seq Scan vs Index Scan vs Bitmap Index Scan

Visual summary — how Postgres picks a scan strategy (table: grades, ~50M rows, index on id and on g)
Problem

Same table, three different plans for three different queries

Postgres doesn't always use an index just because one exists. It picks whichever plan its cost estimator thinks is cheapest — and that decision depends heavily on how many rows it expects to match.

Table: grades(id serial primary key, name text, g int) — id indexed (PK), g indexed, name not indexed.
Key Distinctions

Three scans, three row-count regimes

🟢 Index Scan

WHERE id = 1000

Very few rows match. Postgres jumps straight into the B-Tree, finds the row, then does one heap fetch.

Cheap — few random heap lookups

🟡 Bitmap Index Scan

WHERE g > 95

Moderate number of rows match. Postgres scans the index and builds a bitmap of pages to visit, then fetches each page once.

Balanced — one sorted pass over the heap

🔴 Sequential Scan

WHERE id > 100

Almost all rows match. Jumping page-by-page via the index would touch nearly the whole table anyway — cheaper to just read it straight through.

Full scan — but no wasted index overhead

Rule of thumb: few matches → Index Scan. Some matches → Bitmap Index Scan. Most/all matches → Sequential Scan. The index is only worth using when it actually narrows things down.

Why this beats a plain index scan: a plain index scan jumps to the heap once per matching row (random access, expensive at scale). A bitmap scan jumps to the heap once per matching page, and each page usually holds several matching rows — far fewer trips.
Bonus

Combining two bitmaps (AND)

WHERE g > 95 AND id < 10000 — Postgres builds two bitmaps (one from the g index, one from the id index) and ANDs them together before touching the heap at all.

Bitmap Heap Scan on grades
  Recheck Cond: ((g > 95) AND (id < 10000))
  ->  BitmapAnd
        ->  Bitmap Index Scan on grades_g_idx
              Index Cond: (g > 95)
        ->  Bitmap Index Scan on grades_pkey
              Index Cond: (id < 10000)
Any page present in one bitmap but not the other is guaranteed to have zero matching rows — so it's skipped entirely, shrinking thousands of candidate rows down to only the pages that satisfy both conditions.
Practical Tips

Interview / real-world takeaways

🔹 Having an index doesn't force its use — the planner estimates match count (via ANALYZE statistics) and picks the cheapest strategy.

🔹 Bitmap scans exist because random I/O is expensive. They trade a little index-scanning overhead for far fewer heap page visits.

🔹 Multiple indexes can combine via BitmapAnd/BitmapOr even without a composite index — useful when you can't create one for every column combination.

🔹 Run ANALYZE table_name periodically so the planner's row estimates (and thus its scan choice) stay accurate.

Real-world scenario: An e-commerce orders table filtered by status = 'pending' AND region = 'EU' — neither filter alone is selective enough for a plain index scan, but a BitmapAnd across both indexes narrows it to just the qualifying pages before hitting disk, instead of falling back to a full table scan.
