Bloom Filters

Not "what are they" — why do they exist? Worked through with a real "does this username exist?" problem.

The problem: username availability check

Query the DB every time

User types a name → hit the DB with SELECT username FROM ... on every keystroke/check.

✗ slow at scale

Cache usernames in Redis

Mirror the username set in-memory. Faster, but now two copies of data can drift out of sync.

~ doubles memory, adds sync risk

Bloom filter

A tiny bit array (e.g. 64 bits) answers "definitely not here" instantly — no DB hit needed for most negative checks.

✓ tiny memory, huge query savings

Limitations

Collisions → false positives

A set bit can mean "maybe this name" not "definitely this name" — different strings can land on the same bit. Never a false negative, always a possible false positive.

Filter saturation

If every bit ends up set to 1, the filter always says "maybe" — you're back to hitting the DB every time. Not harmful, just useless.

Size trade-off

Bigger bit array → fewer false positives, more memory. Smaller array → less memory, more false positives (more unnecessary DB hits).

Real implementations use multiple hashes

Production Bloom filters typically hash each item 3+ times into different positions, sharply lowering the collision/false-positive rate versus this single-hash example.

Core idea: a Bloom filter never lies when it says NO — that's a hard guarantee — but a MAYBE always needs a real lookup to confirm. It's a cheap, tiny pre-filter that skips expensive lookups for the common "doesn't exist" case.
Real-world use

CassandraSSTable lookups

Cassandra keeps a Bloom filter per SSTable so it can skip disk reads for SSTables that definitely don't contain a given key — core to how its consistent-hashing storage engine stays fast.
