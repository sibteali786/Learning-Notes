Index Scan vs. Index Only Scan

Visual summary — table grades(id, g, name), ~10M rows
Problem

Same lookup, three different costs

SELECT name FROM grades WHERE id = 7 was tested three ways: no index, a plain index on id, and an index on id that also carries name along with it (non-key column).

The pattern: the plan flips to Index Only Scan whenever every column you SELECT is present in the index — either as the search key or as an included non-key column. Ask for anything not in the index, and it drops back to a regular Index Scan (extra heap trip).
Compare

Index Scan vs. Index Only Scan

🟡 Index Scan

Finds the match in the B-Tree, then jumps to the heap to fetch any column not stored in the index (here: name, g).

Two data structures touched per row.

VS

🟢 Index Only Scan

Every requested column is already inside the index entry — no heap trip at all.

One data structure touched per row — the fastest lookup Postgres can do.

How it works

Making a query "index only" with a non-key column

-- key column: what you SEARCH by
-- non-key (INCLUDE) column: what you also want STORED, not searched
drop index id_idx;
create index id_idx on grades(id) include (name);
You cannot filter or sort by a non-key (INCLUDE) column — e.g. WHERE name = 'x' won't use this index's B-Tree structure for name, since it's not part of the search key, only carried as extra payload.
Practical Tips

Interview / real-world takeaways

🔹 Index Only Scan is the fastest lookup possible — no second data structure touched.

🔹 Design indexes around your actual SELECT list, not just your WHERE clause — include the columns you commonly fetch alongside the filter column.

🔹 Trade-off: every included column grows the index size on disk — larger indexes mean more pages to read, which can offset the benefit if overused. Only include columns you genuinely fetch often.

🔹 Bare index vs. covering index — same key, different capability: a plain (id) index can still do Index Only Scan for SELECT id alone (the key itself is "free"); it's only extra selected columns like name that require INCLUDE.

Real-world scenario: A "get user profile summary" endpoint that always runs SELECT id, display_name FROM users WHERE id = ? — indexing (id) INCLUDE (display_name) turns every profile lookup into a pure index-only read, skipping the users heap table entirely on a hot path that gets hit on every page load.
Setup

Table + queries used

create table grades (
  id serial,
  g int,
  name text
);

insert into grades (g, name)
select
  random()*100,
  substring(md5(random()::text), 0, floor(random()*31)::int)
from generate_series(0, 10000000);

create index id_idx on grades(id);
-- later, upgraded to a covering index:
drop index id_idx;
create index id_idx on grades(id) include (name);
