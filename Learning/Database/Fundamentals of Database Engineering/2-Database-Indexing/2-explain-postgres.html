Reading Postgres EXPLAIN Output

Visual summary — cost estimates, sorting, row width, index vs index-only scans
Problem

EXPLAIN shows the plan, not the actual runtime

EXPLAIN asks Postgres "what would you do with this query?" — it returns an estimated plan and cost based on table statistics, without running the query. (Running it too is EXPLAIN ANALYZE — a separate command, covered elsewhere.)

Table used: grades(id serial primary key, g int, name text), ~10M rows. id has a PK index; g and name have no index in this run.
Anatomy

Decoding one line of output

Seq Scan on grades  (cost=0.00..167363.25 rows=10000425 width=22)
Startup cost rises when Postgres has to do work before returning the first row — e.g. sorting, aggregating. Total cost is the full estimated cost to return everything.

Practical Tips

Interview / real-world takeaways

🔹 EXPLAIN alone never runs the query — it's a plan + estimate. Use EXPLAIN ANALYZE to get real timings.

🔹 Watch startup cost for sorts/aggregates before the real work — a huge startup cost usually means "no index to help this ORDER BY."

🔹 Use estimated row counts instead of SELECT COUNT(*) for approximate counts on huge tables — the planner's estimate is nearly free, a real count on billions of rows is not.

🔹 width matters over the network — fewer/smaller columns selected means less data shipped to your backend.

🔹 Watch for int overflow — a serial (4-byte int) PK caps at ~2.1 billion; use bigserial if the table might outgrow that (mentioned Parler hit this).

Real-world scenario: A leaderboard table sorted by score with no index on score — fine at 10K rows, but at 10M rows every "top 100 players" query pays that same huge Sort→SeqScan startup cost you just measured on g. Adding CREATE INDEX ON grades(g) turns the ORDER BY into a cheap index-ordered read.

  random()*100,
