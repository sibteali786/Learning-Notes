Setup 1 — separate index on A, separate index on B

CREATE INDEX ON a; CREATE INDEX ON b;

index scan
a = 70 (few rows)
Planner skips the bitmap — rows returned are small & sorted, so it walks the index directly into the heap.
bitmap index scan
a = 70 (~9000 rows)
C isn't in the index, so Postgres builds a bitmap of matching tuples, then jumps back to the heap. ~253ms.
bitmap index scan
b = 100
Same story on the B index. ~250ms, heap hit for C.
bitmap AND — fast
a = 100 AND b = 100
Both indexes scanned in parallel, bitmaps ANDed together → tiny result set (6 rows) → very fast.
bitmap OR — slow
a = 100 OR b = 100
Both indexes scanned, bitmaps ORed → far more rows survive → double the index work, double the heap hits.
Setup 2 — single composite index (a, b)

DROP old indexes → CREATE INDEX ON test(a, b);

uses index
a = 70
A is the leftmost column in (a,b), so Postgres can still scan the composite index just fine.
parallel seq scan
b = 100
B alone can't use (a,b) — index is only scannable left→right. Full table scan across worker threads instead.
~0.5ms — best case
a = 70 AND b = 80
Both columns constrained, in order → the composite index nails it directly. This is the scenario composite indexes are built for.
seq scan — "all bets off"
a = 70 OR b = 80
OR can't be satisfied by one composite index scan on the leftmost column alone — planner gives up and does a full table scan.
Setup 3 — composite (a, b) plus a standalone index on B

Keep idx(a, b) → ADD CREATE INDEX ON test(b);

composite index
a = 70
Same as before — leftmost column, fast.
new B index — fixed!
b = 100
The B-only query is no longer a table scan — it now has its own index to use.
composite index — genius
a = 70 AND b = 80
Still uses the composite index directly — fastest path, unchanged.
bitmap OR — recovered
a = 70 OR b = 80
Now Postgres can bitmap-scan the composite index (on a) AND the B index separately, then OR the bitmaps — no seq scan needed.

Postgres scans the index from a=5, b=42 up through the last a=5 entry. The c < 77 constraint is checked inside the index (saves a heap trip) but does not shrink the scanned range — indexes are built and walked strictly left → right.

Takeaways

Bitmap vs. plain index scan

Few rows → plain Index Scan straight into the heap. Many rows → planner builds a Bitmap Index Scan first (cheaper than random heap hits at scale).

AND loves multiple indexes

Two separate indexes can be scanned in parallel and their bitmaps ANDed — often the cheapest plan for multi-column filters.

Composite index ≠ works for every column

An index on (a, b) only helps queries filtering on a, or a AND b — never b alone.

OR defeats a single composite index

a OR b against one (a,b) index usually forces a full table scan — you need a separate index on b to recover it.

Best case: composite + query matches column order

a = ? AND b = ? against (a,b) is the fastest plan observed — sub-millisecond.

Composite indexes cost more to build

They store more data per entry, so writes/inserts get slower and the index is larger — trade-off for the read speed.

Real-world scenarios

SaaSMulti-tenant table filtered by tenant_id + status

If every query looks like WHERE tenant_id = ? AND status = ?, a composite index (tenant_id, status) is the Setup-2 best case — sub-ms lookups, exactly matching this video's "genius" result.

ReportingDashboard that sometimes filters by status alone

If analysts also run WHERE status = ? without tenant_id, that query can't use (tenant_id, status) — you'd need Setup-3: keep the composite index and add a standalone index on status.

Search"Find by email OR username" login lookup

An OR across two columns needs two separate indexes (one per column) so Postgres can bitmap-OR them — a single composite index on (email, username) won't help an OR query at all.
