Random UUIDs vs ULIDs: Why Index Ordering Matters

A visual breakdown of B+Tree page splits, why Shopify moved off UUIDv4, and what "ordered IDs" actually save you.
Problem Statement
Database indexes (B+Trees) require keys to be stored in sorted order on disk pages. When you insert a random UUID (v4) as a primary/indexed key, each new value lands in a random position in that order — forcing the database to repeatedly split full pages, rewrite sibling-page pointers, and thrash pages in and out of the buffer pool. Insert an ordered ID (ULID/UUIDv7) instead, and new keys always land at the tail — pages fill sequentially with almost no splitting or random disk I/O.

Shopify: ULID Benefit vs UUID

Shopify tags every purchase/order with a unique ID for idempotency (catching duplicate submits). With UUIDv4:

  • Thousands of purchases in the same minute generate IDs scattered randomly across the whole index.
  • Every insert risks a page split; every idempotency lookup risks pulling a "cold" page from disk.
  • The buffer pool (shared memory cache, LRU-evicted) constantly evicts pages it will need again seconds later → I/O thrashing.

Switching to ULID (time-ordered):

  • IDs created in the same time window are numerically clustered → land on the same "hot" trailing pages.
  • Both writes (sequential inserts, few splits) and reads (idempotency re-checks happen within minutes/hours of creation, i.e. still on hot pages) benefit.
Example Scenario
10,000 checkouts happen between 2:00–2:01 PM. Each gets an order ID.

With UUIDv4: order IDs like a3f1.., 08e4.., f921.. are inserted in totally random spots across the order-index B+Tree. The DB has to split leaf pages constantly and pull cold, unrelated pages into memory — even though all 10,000 rows were created in the same 60 seconds.

With ULID: all 10,000 IDs share the same millisecond-based prefix range, so they insert into the same handful of trailing pages. If a customer double-clicks "Pay Now" and the app re-checks "does this order ID already exist?" a second later, that check hits a page that's already hot in the buffer pool — fast write, fast idempotency read, minimal disk I/O.
Note: this benefit is workload-specific. A URL shortener's read pattern is random regardless of ID order (any short link can be hit at any time), so ULID mainly helps write-heavy, time-clustered workloads like Shopify's — not everything.
B+Tree vs B-Tree
B-Tree
  • Keys and data/values can live in any node (internal or leaf).
  • No linked list between leaf nodes.
  • Range scans require traversing back up and down the tree.
B+Tree
  • All actual data/values live only in leaf nodes; internal nodes hold just keys for routing.
  • Leaf pages are linked (often doubly) to their siblings.
  • Range scans just walk the linked leaf list — no going back up the tree.
  • Used by MySQL (InnoDB), Postgres, most relational DBs — matches what's described in the transcript (linked leaf pages, page splits, sequential scans).
