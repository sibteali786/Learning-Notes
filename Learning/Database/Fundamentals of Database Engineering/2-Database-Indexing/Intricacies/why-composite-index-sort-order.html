Why C Isn't Globally Sorted

Index on (a, b, c) sorts like ORDER BY a, b, c — each column only breaks ties within the one before it.

The phone book analogy
Sort keylast_name, first_name
Adams —group starts
Adams, John
Adams, Mary
Smith —group starts
Smith, Alice
Smith, John
Zimmerman —group starts
Zimmerman, John

"John" isn't sorted globally — Adams, John and Zimmerman, John are pages apart. First names only sort within a last name. Same reason c isn't globally sorted: it only sorts within one fixed (a,b) pair.

The index, unrolled — a=5 AND b>=42 AND c<77
a = 5
b = 42
c = 3✓ c<77
c = 12✓ c<77
c = 99✗ skip
↳ b changes → c resets to its own sorted order
b = 43
c = 1✓ c<77
c = 5✓ c<77
c = 200✗ skip
↳ b changes → c resets again
b = 44 … up to b = 999 (last a=5 entry)
c = 80✗ skip
c = 1✓ c<77

Every time b changes, c's sort order restarts from scratch. Rows matching c<77 are scattered across every b-group — Postgres must walk the entire a=5, b>=42 range, checking c row by row. It skips the heap trip on a miss, but not the index walk.

Range vs. equality on B — does C help?
C can't narrow range

B is a range

a=5 AND b>=42 AND c<77

Spans many b-groups (b=42, 43, 44...999). Each has its own independently-sorted c. Low-c rows are scattered — full walk required.

C narrows the range!

B is an equality

a=5 AND b=42 AND c<77

Only one b-group (b=42). Within it, c is sorted — Postgres can seek straight to the c<77 portion. Fast.

Rule: as many equality columns as you have, left to right, plus one trailing range/inequality on the next column — that's what actually shrinks the scanned portion of the index. Everything after that first range condition is filtered in-index (saves heap trips) but does not reduce how much of the index gets walked.
