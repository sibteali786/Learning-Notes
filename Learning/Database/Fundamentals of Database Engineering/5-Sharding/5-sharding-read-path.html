Library Bug — consistent-hash → hashring

⚠Same key, different server every time
SymptomQuerying with a urlId that was just written returned 0 rows — the read was hitting the wrong shard.
Root causeThe consistent-hash npm library was buggy: calling .get(key) with the same key did not reliably return the same server — which completely defeats the purpose of consistent hashing. The package also hadn't been updated in 4 years.
FixReplaced it with hashring, a correct implementation of the same idea. Only two lines changed — the import and the constructor. Everything else (hr.add(port), hr.get(key)) stayed the same:
// before (buggy)
const ConsistentHash = require("consistent-hash");
const hr = new ConsistentHash();

// after (fixed)
const HashRing = require("hashring");
const hr = new HashRing();

hr.add("5432"); hr.add("5433"); hr.add("5434");
// hr.get(key) now reliably returns the same server for the same key

All shards were truncated and repopulated with fresh IDs after the swap, so the demo below reflects the corrected library.

The GET Route

app.get("/:urlId", async (req, res) => {
  const urlId = req.params.urlId;

  // same hash ring, same key → same shard as when it was written
  const server = hr.get(urlId);

  const result = await clients[server].query(
    "SELECT * FROM url_table WHERE url_id=$1",
    [urlId],
  );

  if (result.rowCount > 0) {
    res.send({
      urlId: urlId,
      url: result.rows[0].url,
      server: server,
    });
  } else {
    res.sendStatus(404);
  }
});

No lookup table, no broadcasting to all three shards — the same hr.get(urlId) call used at write time tells you exactly which shard to read from.

Verifying via pgAdmin

Confirmed end-to-end by picking rows straight out of each shard's url_table in pgAdmin, then hitting the API with that exact urlId:

A urlId picked out of shard2's table came back with server: "5433" — matching shard2's own port — proving the read path lands on exactly the shard that holds the row.

Not-found case

Requesting a urlId that doesn't exist correctly returns HTTP 404 — the hash ring still resolves a shard, the query just finds zero rows there.

Caveat: Resharding Isn't Free

Known limitation

This implementation's hash ring is fixed to 3 nodes. Adding a 4th shard changes the ring, which reshuffles which keys map to which server — most existing rows would suddenly "belong" to the wrong shard according to the new hash. Resharding (safely redistributing existing data when the node count changes) is a separate, harder problem from the basic write/read sharding shown here — it's one of the real downsides of sharding in practice.
