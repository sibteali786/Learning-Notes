Identify the Actual Problem First

Sharding sounds sophisticated, but it's a genuinely complex architecture to build and operate — it shouldn't be reached for just because it sounds impressive.

The typical starting point: a single relational database instance behind a web/API server. As a table grows into the millions of rows, an index only helps so much — past a certain size, even indexed queries start approaching a full index scan, and reads slow down (writes usually stay fine, since they're mostly append-only).

Key principle

You can't fix a problem you haven't named. Before reaching for any solution, pin down exactly what's slow — is it reads? Writes? Connection count? Each has a different, much simpler fix than sharding.

The Decision Ladder — Try These Before Sharding

1

Horizontal partitioning (same server)

Slice a huge table into smaller partitions by a partition key (often the primary key) — e.g. rows 1–100K in partition 1, 100K–200K in partition 2, etc. Still one database instance, so transactions, joins, and rollbacks keep working. Modern Postgres does this transparently — the client doesn't even need to know which partition it hit.

2

Caching (optional)

A Redis layer in front of the database can absorb read load — at the cost of cache-invalidation and consistency complexity.

3

Read replication (master + backups)

One master handles writes; the master periodically pushes writes to one or more read replicas. A reverse proxy (nginx, HAProxy, etc.) routes reads to replicas and writes to the master. Reads scale out easily because reads rarely conflict — writes still hit a single server.

4

Multi-master, geo-partitioned writes

Two masters in different regions (e.g. US-East / US-West), each handling writes for its own region's customers. Since traffic rarely overlaps between regions, cross-region sync stays simple and conflicts stay rare.

5

Sharding — last resort

Only after every option above is exhausted. Sharding is horizontal partitioning taken one step further: instead of separate tables on the same server, each partition lives on a completely separate server. That's the one change that breaks everything else.

What sharding costs you

With partitioning (same server), transactions still work. With sharding, ACID transactions, atomicity, and rollbacks across shards are effectively gone — you can't atomically write to two separate database servers. The client also needs shard-routing logic baked in (e.g. "customer 100 → range 1–10,000 → server 1"), which means connection pooling per shard and real coupling between the application and the data layout.

Case Study: YouTube & Vitess

YouTube ran on a single MySQL server for a long time and scaled it using the same ladder above — until write volume became unmanageable and they had no choice but to shard.

Their sharding was application-level: the app itself knew which shard (partition range) to hit. That created tight coupling between application logic and data layout — exactly the kind of coupling you want to avoid in software. When they later wanted to reshard (e.g. change a range from 10,000 to 100,000 rows per shard), it would have broken every client that had that range logic baked in.

Vitess was built to solve exactly this coupling problem: it's an open-source middleware (built on Kubernetes, Redis, and related tech) that sits in front of MySQL. The client sends a normal SQL query; Vitess parses it and transparently routes it to the correct shard — the application no longer needs to know shards exist at all.

Takeaway

Before you shard, ask

Have you tried partitioning? Caching? Read replicas? Regional multi-master writes? Every one of these is simpler to build, operate, and reason about than sharding — and every technology choice has a maintenance cost. Shard only when every simpler option is genuinely exhausted, not because it sounds like the sophisticated thing to do.
