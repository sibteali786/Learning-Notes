Pros & Cons of Sharding

Scalability and security for free — at the cost of client complexity, broken transactions, and joins.
Pros Cons

Pros

Scalability

Spreads data, memory, and CPU load across multiple machines instead of hogging one server's resources — horizontal scaling instead of vertical.

Security

Shards can be access-controlled independently. Example: put VIP customers on one shard and everyone else on another, then restrict which clients can reach which shard — access control you don't get with one big table.

Optimal, smaller index size

Each shard holds a fraction of the data, so its index stays small — smaller indexes mean quicker, more efficient queries.

Cons

Complex client

The client has to know which shard an input lives in. Consistent hashing hides some of that complexity, but the awareness of sharding still leaks into the application and gets messy at scale.

Emerging fix

Backend-hidden sharding (mentioned: a tool called Vitess from YouTube) lets the client just issue normal queries while the sharding logic runs transparently behind the scenes.

Transactions across shards

An atomic operation that spans two shards means two separate database transactions — near-impossible to make truly atomic. Transactions work fine within a single shard, just not across shards.

Rollbacks

If an insert on shard A succeeds but the related insert on shard B fails, rolling back "the transaction" really means manually rolling back two independent transactions — despite it being one logical operation.

Schema changes are hard

Adding a field (e.g. a new date column) has to be applied to every shard individually. Rolling it out slowly is possible but risky — miss one shard and schemas drift out of sync.

Joins

Joining across separate database instances isn't really feasible. This is one reason to reach for horizontal partitioning instead — same database, multiple tables, so joins still work.

Must know the shard key up front

Queries are fast only when you're filtering by the sharding key (e.g. URL ID). Query on any other field and you lose that shortcut — you're forced to hit every shard to find the data.

Real-world example

A customer list sharded by customer ID, but you search by name: name has nothing to do with the shard key, so the query has to scan both shards — no shortcut.
