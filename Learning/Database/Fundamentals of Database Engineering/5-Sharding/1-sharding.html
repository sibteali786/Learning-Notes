Sharding & Consistent Hashing

Splitting one giant table across many database servers — and how to find the right one every time.
Problem What is Sharding Consistent Hashing

The Problem

Traditionally, everything lives in one centralized database with big tables and indexes on top. That works — until the data grows.

As a table grows (say, a URL-shortener table with 1 million+ rows), its indexes grow too. Bigger indexes mean slower lookups, and you eventually need more memory and CPU just to keep queries fast. It's a scale problem, not a bug.

Real-world example

A URL shortener has a URL_TABLE mapping a short code like 5FTOJ to a long URL. At 1M rows, SELECT URL FROM URL_TABLE WHERE URLID = '5FTOJ' keeps getting slower as the table keeps growing — even with an index.

What is Sharding?

Sharding = split a big table's rows across multiple database servers, each holding a slice of the data, using the same schema.

Example: split 1M URL rows into 5 servers (S1–S5) of 200K rows each. Each shard is a full, independent Postgres instance with the identical table structure — just fewer rows.

The hard part isn't splitting the data — it's knowing which server to query. For numeric IDs you can range-partition (users 1–500K → DB1, etc). But for a string key like 5FTOJ, you need a deterministic function that always routes to the same server: consistent hashing.

Consistent Hashing

Given a key (like a URL shortcode), consistent hashing deterministically maps it to one specific server — every time, without a lookup table.

Take any input string, run it through a hash function, and it tells you which of the three database instances owns it. The core guarantee: the same input always maps to the same server — submit "Input2" once or a hundred times, it always lands on 5433.

One possible implementation — modulo hashing:

# 1. Turn the input string into a number
#    (e.g. ASCII codes → binary → decimal)
value = to_number("input")   # let's say this comes out to 10

# 2. Modulo by the number of shard nodes (3 here)
remainder = value % 3          # 10 % 3 = 1

# 3. Map the remainder onto an actual server/port
port = 5432 + remainder     # 5432 + 1 = 5433
connect(port)              # → postgres:5433

This is one implementation, not the only one — but the shape is always: hash → number → modulo by node count → map to a real server.

This layout — nodes placed around a circle, keys hashed onto the ring and routed to the nearest node — is literally called a hash ring. It's the standard mental model for consistent hashing.

Real-world example

Cassandra uses this hash-ring approach for its shards: every write/read key gets hashed onto the ring so the client (or coordinator node) always knows exactly which node owns that key, without asking every node.

Why it matters

You never query all shards to "find" data — you compute the hash once, go straight to the one server that owns it. That's the whole point: O(1) routing instead of a broadcast search.
