⚡ Why Prompt-Based Dev Skips the Test-Set-First Habit

Traditional supervised ML forces you to collect a large labeled dataset up front — so adding a dedicated test/dev set on top is a small incremental cost. Prompt-based development is fast enough (minutes to hours) that pausing to collect 1,000 test examples before you can even try anything would be a disproportionate drag. So the natural workflow is to build up your evaluation set gradually, as you go.

🪜 The 5-Step Evaluation Ladder

You don't need to climb all 5 steps — stop wherever you have enough confidence for your use case. Many real deployed apps stop at step 1 or 2.

1Tune the prompt on a small handful of examples (1–5)
2Add additional "tricky" examples opportunistically as you find failures
3Develop metrics to measure performance on this growing example set (e.g. average accuracy)
4Collect a randomly sampled development/hold-out cross-validation set — needed if you must detect smaller differences (e.g. 91% → 93% accuracy)
5Collect and use a hold-out test set you never look at while tuning — needed for a truly unbiased performance estimate

Important caveat For high-stakes / safety-critical applications (risk of bias or harm), rigorously collecting a proper test set (steps 4–5) becomes a responsibility, not optional polish. For low-risk personal-use tools, stopping early is often fine.

Manually eyeballing 5+ outputs becomes tedious — so the lesson builds a 10-example dev set of {customer_msg, ideal_answer} pairs (category → expected product set), including a deliberately irrelevant query ("I would like a hot tub time machine" → expects []).

✅ Scoring Function: eval_response_with_ideal

Parses the model's JSON-like string, compares each category's product set against the ideal set, returns the fraction of categories matched exactly. Debug mode reports whether a wrong answer was a subset or superset of the ideal — useful signal for how the prompt is failing, not just that it failed.

def eval_response_with_ideal(response, ideal, debug=False):
    json_like_str = response.replace("'", '"')  # single → double quotes for JSON
    l_of_d = json.loads(json_like_str)

    if l_of_d == [] and ideal == []:
        return 1
    elif l_of_d == [] or ideal == []:
        return 0

    correct = 0
    for d in l_of_d:
        cat, prod_l = d.get('category'), d.get('products')
        if cat and prod_l:
            prod_set = set(prod_l)
            ideal_cat = ideal.get(cat)
            if ideal_cat and prod_set == set(ideal_cat):
                correct += 1
    return correct / len(l_of_d)

💡 Key Takeaway

The prompt-based workflow feels very different from classic supervised ML — much faster iteration, and even a "statistically invalid" set of 10 hand-curated tricky examples can be surprisingly effective for guiding prompt improvements. This lesson only covers evaluation with a single objectively "right" answer; the next lesson covers evaluating outputs where correctness is more ambiguous (open-ended answers).

Also worth knowing: for the exact "extract category/product JSON" task this lesson evaluates, current OpenAI docs recommend Structured Outputs (response_format={"type": "json_schema", ...}) instead of prompt instructions + replace("'",'"') + json.loads(). That would eliminate the whole class of "model added explanatory text after the JSON" failures this lesson's v1→v2 fix worked around, and avoid the fragile quote-replacement parsing (breaks on apostrophes in product text). For running this kind of dev-set evaluation loop at scale, OpenAI's Evals platform is also worth checking as a more robust alternative to the hand-rolled scoring loop shown here.
