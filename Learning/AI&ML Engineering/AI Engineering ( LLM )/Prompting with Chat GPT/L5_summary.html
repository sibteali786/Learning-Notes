DeepLearning.AI · ChatGPT Prompt Engineering for Developers — Lesson 5 summary

🎯 Why Chain Prompts Instead of One Big Prompt?

Rather than cramming an entire complex workflow into a single prompt (as in the L4 Chain-of-Thought approach), break the task into a sequence of simpler prompts, tracking system "state" externally between calls and injecting only the instructions relevant to the current state.

🍳 Analogy 1 — Cooking: One giant prompt is like cooking an entire complex meal in one go, juggling every ingredient and timing at once. Chaining prompts is like cooking in stages — one component at a time, verified before moving to the next.
🧩 Analogy 2 — Code: One long prompt is spaghetti code — ambiguous, tangled dependencies, hard to debug. Chained prompts are modular functions — each step has one clear job.

✅ Benefits of Chaining

  • Each subtask only needs the instructions for its own state → simpler, more reliable
  • Lower cost — shorter prompts use fewer tokens per call
  • Easier to test/debug which specific step is failing
  • Easier to insert a human-in-the-loop at a specific step
  • Enables calling external tools (APIs, catalogs, knowledge bases) mid-workflow — not possible in a single prompt

🧠 When Is a Problem "Complex"?

A task is complex when there are many different instructions and any of them could potentially apply depending on context — making it hard for the model to reason about which rules matter right now. This is the signal to switch from one CoT mega-prompt to a chained, state-tracked workflow.

1️⃣ Step 1 — Extract Products/Categories

System instructs the model to output a Python-list-of-objects, each with category and products, using only allowed values, or an empty list if nothing matches.

User: "tell me about the smartx pro phone and the fotosnap camera, the dslr one. Also tell me about your TVs."
Model output: [{"category":"Smartphones and Accessories","products":["SmartX ProPhone"]}, {"category":"Cameras and Camcorders","products":["FotoSnap DSLR Camera"]}, {"category":"Televisions and Home Theater Systems","products":[]}]
User: "my router isn't working" (no router in catalog) → Model output: []

2️⃣ Step 2 — Look Up Product Info (Helper Functions)

def get_product_by_name(name):
    return products.get(name)

def get_products_by_category(category):
    return [p for p in products.values()
            if p["category"] == category]

🔄 Parsing Model Output Safely

import json

def read_string_to_list(s):
    if s is None:
        return None
    try:
        s = s.replace("'", '"')
        return json.loads(s)
    except json.JSONDecodeError:
        print("Error: Could not decode.")
        return None

Converts the model's string output into a real Python list so it can drive the next step's lookups.

3️⃣4️⃣ Steps 3–4 — Build Context, Then Answer

generate_output_string() loops over the extracted category/product list: for named products it fetches exact info; for bare categories (e.g. "Televisions") it fetches all products in that category. That string is injected into the final messages array as an assistant message containing "Relevant product information:\n" + the looked-up details, followed by a system message setting a friendly, concise, follow-up-question-asking tone.

Final response: The model describes the SmartX ProPhone, the FotoSnap DSLR Camera, lists the available TVs, and asks a helpful follow-up question — all grounded in the looked-up product data instead of guessing.

❓ Why Not Just Dump the Entire Catalog Into the Prompt?

ReasonWhy it matters
Confusing contextToo much irrelevant info makes reasoning harder (less of an issue for stronger models with well-structured context)
Context window limitsA large catalog simply won't fit within the model's token limit
CostYou pay per token — loading only what's relevant keeps costs down

Key mental model Think of the LLM as a reasoning agent that needs the right context fed to it — not an oracle that already knows everything. This selective, dynamic context-loading is the seed idea behind tool use / plugins.

🔭 Looking Ahead: Embeddings & Semantic Search

This lesson's lookup only works via exact name/category matching. The lesson previews text embeddings as a more powerful approach — enabling fuzzy/semantic search over a large product catalog so a query like "a mobile phone" can retrieve relevant products without needing the exact product name.

💡 Current-day note: OpenAI's embeddings API (client.embeddings.create(model="text-embedding-3-small", input=...)) and vector-store-backed retrieval (e.g. via the Responses API's file_search / vector stores) are the modern way to implement this semantic lookup — worth checking OpenAI's current embeddings guide if extending this workflow beyond exact-match lookups.
