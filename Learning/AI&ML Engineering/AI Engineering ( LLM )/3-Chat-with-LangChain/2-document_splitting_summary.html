LANGCHAIN RAG PIPELINE — STEP 2 DOCUMENT SPLITTING

Document Splitting in LangChain

Turning loaded Documents into smaller, semantically coherent chunks that retrieval can pull individually.

Problem Statement

Splitting sounds trivial ("just cut by character count") but sloppy splitting breaks meaning apart. Example from the lesson: a sentence describing Toyota Camry specifications gets cut mid-sentence — half the spec lands in chunk A, half in chunk B. Later, when a user asks "what are the Camry's specs?", neither chunk alone has the full answer, so retrieval fails even though the information technically exists in the document.

Why it matters: Splitting quality directly determines whether your RAG system can even find the right answer — this happens after loading, before the vector store.

How It Works — Chunk Size & Overlap

chunk_size — size of each chunk, measured via a length_function (usually len() for characters, or a token counter).

chunk_overlap — a small repeated region between consecutive chunks (like a sliding window) so context at a boundary isn't fully lost.

All LangChain text splitters expose two equivalent methods:

MethodInputUse case
create_documents()list of raw stringssplitting plain text
split_documents()list of Document objectssplitting already-loaded docs (keeps metadata)

Splitters Vary Across 3 Dimensions

How

Which characters/rules it splits on (newlines, spaces, regex, language syntax)

Length measure

Characters vs. tokens vs. even smaller ML models detecting sentence boundaries

Metadata handling

Whether/how it preserves or adds new metadata (e.g. section headers) to each chunk

Splitters Covered in Detail

1. RecursiveCharacterTextSplitter vs CharacterTextSplitter

RecursiveCharacterTextSplitter is the recommended default — it tries a list of separators in priority order: double-newline → newline → space → empty string (char-by-char), falling back only when a bigger unit is still too large. This keeps paragraphs/sentences intact whenever possible.

CharacterTextSplitter splits on a single separator only (default \n) — if that separator isn't present in the text, it won't split at all unless you set one explicitly (e.g. a space).

from langchain_text_splitters import RecursiveCharacterTextSplitter, CharacterTextSplitter

chunk_size = 26
chunk_overlap = 4

r_splitter = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_overlap)
c_splitter = CharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_overlap)

text1 = "abcdefghijklmnopqrstuvwxyz"   # exactly 26 chars — no split needed
r_splitter.split_text(text1)  # ['abcdefghijklmnopqrstuvwxyz']

text2 = text1 + "abcdefg"              # longer than 26
r_splitter.split_text(text2)
# ['abcdefghijklmnopqrstuvwxyz', 'wxyzabcdefg']  → 'wxyz' is the 4-char overlap

# CharacterTextSplitter needs an explicit separator if there's no \n:
c_splitter = CharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_overlap, separator=' ')
Toy example insight: On a string full of spaces, overlap of "4" can look like just 2 letters (L, M) because surrounding spaces count toward the character length too.

2. Real-World Paragraph Example — Why Recursive Wins

some_text = """...paragraph 1 text...\n\n...paragraph 2 text..."""

c_splitter = CharacterTextSplitter(chunk_size=450, chunk_overlap=0, separator=' ')
r_splitter = RecursiveCharacterTextSplitter(
    chunk_size=450, chunk_overlap=0,
    separators=["\n\n", "\n", " ", ""]
)

c_splitter.split_text(some_text)   # cuts mid-sentence (splits on spaces)
r_splitter.split_text(some_text)   # splits cleanly at the \n\n paragraph break

Adding a period "." to the separators list splits by sentence — but a naive regex leaves periods at the start of the next chunk. Fix with a regex lookbehind so the period stays attached to its sentence:

r_splitter = RecursiveCharacterTextSplitter(
    chunk_size=150, chunk_overlap=0,
    separators=["\n\n", "\n", "\(?<=\. \)", " ", ""]  # lookbehind keeps '.' in place
)
Tip: Default separators ["\n\n", "\n", " ", ""] mirror natural text hierarchy: paragraph → line → word → character.

3. Applying to Real Documents (PDF & Notion)

text_splitter = RecursiveCharacterTextSplitter(chunk_size=1500, chunk_overlap=150, length_function=len)

docs = text_splitter.split_documents(pages)        # from the PDF loader
notion_docs = text_splitter.split_documents(notion_db)  # from the Notion loader

# len(docs) > len(pages)  → splitting produced more, smaller documents
Real-world scenario: A 22-page PDF loaded as 22 Documents might explode into 70+ smaller chunks after splitting — each small enough to embed and retrieve precisely.

4. TokenTextSplitter — Splitting by Tokens, Not Characters

LLM context windows are measured in tokens, not characters — so splitting by token count better reflects how the model actually "sees" the text.

from langchain_text_splitters import TokenTextSplitter

text_splitter = TokenTextSplitter(chunk_size=1, chunk_overlap=0)
text_splitter.split_text("foo bar bazzyfoo")
# ['foo', ' bar', ' b', 'az', 'zy', 'foo']  → tokens ≠ characters ≠ words

text_splitter = TokenTextSplitter(chunk_size=10, chunk_overlap=0)
docs = text_splitter.split_documents(pages)
docs[0].metadata  # {'source': '...pdf', 'page': 0} — metadata still carries through
Tip: Metadata (like source and page) is automatically propagated from the parent Document to every chunk split from it.

5. MarkdownHeaderTextSplitter — Context-Aware Metadata

Splits on markdown headers/subheaders, and — uniquely — injects the header hierarchy into each chunk's metadata, so downstream retrieval knows which section a chunk came from.

from langchain_text_splitters import MarkdownHeaderTextSplitter

headers_to_split_on = [
    ("#",   "Header 1"),
    ("##",  "Header 2"),
    ("###", "Header 3"),
]

markdown_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on)
md_header_splits = markdown_splitter.split_text(markdown_document)

# md_header_splits[0].page_content → "Hi this is Jim.\nHi this is Joe."
# md_header_splits[0].metadata → {'Header 1': 'Title', 'Header 2': 'Chapter 1'}
Real-world scenario: Applied to the Notion export of "Blendle's Employee Handbook," each chunk's metadata records which section/subsection it came from (e.g. Header 1: "Blendle's Employee Handbook") — letting a chatbot answer "which section discusses X?" accurately.

Key Distinctions

Character-based vs Token-based splitting

Character-based = simple, consistent across text types.
Token-based = matches how the LLM actually consumes input; important when respecting context-window limits.

Generic splitters vs Structure-aware splitters

Recursive/Character/Token splitters are format-agnostic.
MarkdownHeaderTextSplitter and the language-aware splitter (Python/Ruby/C, etc. via from_language()) split according to the document's actual structure and enrich metadata.

Practical Tips

✅ Default to RecursiveCharacterTextSplitter — it degrades gracefully from paragraph → sentence → word → character splits.

✅ Keep a small chunk_overlap so context isn't lost right at a chunk boundary — this is what prevented the Toyota Camry spec problem.

✅ Match your length_function to how your embedding/LLM will actually consume the text — tokens for LLM context budgeting, characters for simplicity.

✅ For structured content (Markdown, code), prefer a structure-aware splitter — you get both better chunk boundaries AND free metadata (headers, language constructs).

✅ Splitting → next step is embedding these chunks into a vector store for retrieval.
