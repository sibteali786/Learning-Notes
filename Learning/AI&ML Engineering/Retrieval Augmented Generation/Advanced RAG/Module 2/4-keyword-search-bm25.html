BM25: TF-IDF, with diminishing returns

TF-IDF is the classic, but most production retrievers use BM25. It keeps TF-IDF’s ideas and adds term frequency saturation, gentler length normalization, and two tunable knobs.

Where BM25 comes from

“Best Matching 25” was the 25th variant in a series of scoring functions proposed by its creators. It works very similarly to TF-IDF, with a few key additions.

TF-IDF
refined into
BM25

The formula (score for one keyword in one document)

IDF× TF × (k₁ + 1) TF + k₁ × (1 − b + b × document length / average document length)
IDF same idea as before: rare words weigh more.
TF and k₁ control term frequency saturation.
b and length ratio control document length normalization.

Same recipe as TF-IDF: compute this score for each prompt keyword, then sum across all keywords to get the document’s total relevance score. Rank by that total.

Two improvements over TF-IDF, plus tunable knobs

1. Term frequency saturation

Extra occurrences of a keyword earn diminishing returns. A document with “pizza” 20 times isn’t really twice as relevant as one with it 10 times.

TF-IDF20× = score 2X ✗
BM2520× = score 1.3X ✓

Slide values are illustrative (10 times = score X). The exact ratio depends on k₁; try the playground below.

2. Document length normalization

Long documents are still penalized, but with diminishing additional penalties as they grow. TF-IDF can penalize too aggressively and overly discount longer documents.

TF-IDFheavy penalty
BM25smaller penalty

Result: a long document still scores highly if its keyword frequency is fairly high.

3. Two tunable hyperparameters

They control how fast documents stop being rewarded for repeated keywords and stop being penalized for extra length.

k₁ term frequency saturation. Typically 1.2 to 2.0. Higher: term frequency matters more. Lower: it matters less.
b length normalization, 0 to 1. 0 = no normalization, 1 = full. Balances favoring shorter vs longer documents.

In production you tune k₁ and b to land on the scoring system that best fits the data in your knowledge base.

Keyword search, in review

Sparse vectorsScoredRanked

Match documents to prompts by how frequently the prompt’s keywords appear in each document. Prompts and documents become sparse vectors counting each vocabulary word. TF-IDF and BM25 are two ways of processing those vectors into scores, accounting for keyword rarity, how often a document contains a keyword, and document length.

Strengths

Simplicity

Straightforward and works well in practice; often performs quite well on its own and sets a competitive benchmark that advanced techniques struggle to beat.

Proven

BM25 has withstood decades since its invention and balances complexity and performance in real-world applications.

Guaranteed keywords

Retrieved documents will contain the prompt’s keywords. Vital when users use technical terminology or exact product names.

Weakness

It depends on the prompt containing words that exactly match the document’s words. A prompt with the same meaning but different words finds nothing.

Prompt
“How many vacation days do new hires get?”
≠
Document
“Paid time off: employees accrue leave from day one.”

No shared keywords, so keyword search misses it. The slides add the reverse problem: the same word can have different meanings (“python” the language vs the snake). Semantic search addresses this, and it’s next.

BM25 in a few lines

Sketch of the lesson’s formula; for learning, not production.

def bm25_term(tf, doc_len, avg_len, idf, k1=1.2, b=0.75):
    # score of ONE keyword in ONE document
    norm = k1 * (1 - b + b * doc_len / avg_len)   # length normalization
    return idf * (tf * (k1 + 1)) / (tf + norm)    # saturating TF

def bm25_score(prompt_words, counts, doc_len, avg_len, idf, k1=1.2, b=0.75):
    # sum the per-keyword scores for a document's total
    return sum(
        bm25_term(counts.get(w, 0), doc_len, avg_len, idf.get(w, 0), k1, b)
        for w in prompt_words
    )

Library route: for real projects, use an established implementation (for example the rank_bm25 package, or the BM25 scoring built into search engines like Elasticsearch/OpenSearch) instead of rolling your own. Defaults for k₁ and b and the exact IDF formula differ by library, so check the docs of the one you use. I haven’t verified current versions or defaults.

Alternatives and trade-offs

TF-IDF

Pros
  • Simplest to explain and implement
Cons
  • Unbounded TF reward; aggressive length penalty; no knobs

BM25 with library defaults

Pros
  • Strong out of the box, standard in production
  • Zero tuning effort
Cons
  • Defaults may not suit unusual data (very long or very short documents)

BM25 with tuned k₁ and b

Pros
  • Fits your knowledge base
Cons
  • Needs labelled queries and evaluation metrics to tune safely (covered later in this module)

Keyword search only

Pros
  • Fast, exact, great for product names and technical terms
Cons
  • Blind to synonyms and paraphrases, so pair it with semantic search

Key takeaways

  • BM25 = IDF × a saturating TF term with length normalization, computed per keyword and summed across keywords.
  • Term frequency saturation: repeated keywords earn diminishing returns (pizza ×20 isn’t 2× pizza ×10).
  • Length normalization: long documents are penalized, but with diminishing additional penalties, so TF-IDF’s over-penalizing is avoided.
  • k₁ (typically 1.2 to 2.0) and b (0 to 1) let you tune it to your data.
  • Better than TF-IDF, roughly the same compute, more flexible: the production standard.
  • Strength: simple, benchmark-setting, guarantees exact keywords. Weakness: needs exact word matches. Next: semantic search.
