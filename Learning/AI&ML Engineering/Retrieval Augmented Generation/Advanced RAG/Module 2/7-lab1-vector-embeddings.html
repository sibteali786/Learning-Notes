Lab summary, plus: why check shapes in Euclidean but not cosine?

Your question first, then the whole lab in order: the two distance functions, the embedding model, ranking real sentences, and the 512-token truncation trap.

Your question

In euclidean_distance the lab raises an error if v1.shape != v2.shape, but cosine_similarity has no such check. Why?

Short answer: Euclidean uses subtraction, which NumPy lets “broadcast” silently, so mismatched shapes can produce a wrong number with no error. Cosine uses np.dot, which already raises an error when the lengths don’t line up, so the check would be redundant.

The notebook doesn’t state its reason; this is my reading of the code, and I ran the cases below in NumPy to confirm the behavior.

Euclidean: v1 - v2

dist = np.sqrt(np.sum((v1 - v2) ** 2))

Element-wise subtraction follows NumPy broadcasting rules: a length-1 array is silently stretched to match, and a (2,1) array against a (2,) array becomes a (2,2) matrix. Either way you get a number back, just not the distance you meant.

Cosine: np.dot(v1, v2)

dot_product = np.dot(v1, v2)
similarity  = dot_product / (norm_v1 * norm_v2)

For 1-D vectors, np.dot needs equal lengths and raises ValueError: shapes ... not aligned otherwise. The safety net is built in.

See it: same inputs, three behaviors

Outputs come from running the lab’s formulas in NumPy with v1 = [1, 2]. “Without check” is the Euclidean formula with the shape check removed.

Why it matters in RAG: a silent broadcast bug (for example a stray (1, 768) query against (768,) document vectors) would quietly corrupt rankings, which is much harder to notice than a crash. The explicit check turns it into a clear message that prints both shapes.

Side notes: (1) np.dot is not bulletproof either: with a scalar it just scales the vector, and the later float() conversion is what would break. (2) Neither function guards against a zero vector, where cosine divides by zero. (3) A check in cosine too would give a friendlier error message, so the asymmetry is a style choice more than a necessity.

1. What the lab teaches

Embeddings act like a map for text: words and sentences become positions in vector space that capture meaning.

Powering search

Capturing meaning: vectors locate information matching a query. Comparing similarity: the prompt becomes a vector too, and is compared against the stored vectors to find the closest texts.

Understanding context

Context matters: helps the best-matched information be found. Flexibility: contextual embeddings adapt to different meanings and catch details otherwise overlooked.

The three-step framework

1. Create the embeddingConvert the query and documents into vectors.
2. MeasureUse a similarity metric to see how close each document is to the query.
3. SortTake the top few. Careful: for cosine higher is better, for Euclidean lower is better.

2. The two distance functions

Cosine similarity

cos(q, d) = (q · d) / (‖q‖ ‖d‖)

Based on the angle. A value close to 1 means very similar. Higher = closer.

Euclidean distance

dist(q, d) = √( Σ (qⱼ − dⱼ)² )

The “straight-line” distance. Smaller = closer.

Both functions accept a vector and an array of vectors (or a single vector) and always return a list of floats.

Surprise: Kyoto ranks only 6th

Kyoto is clearly in Asia, yet Santorini and Banff outrank it. The lab’s explanation: embedding models capture similarity from contexts where words co-occur in training data, so generic “places to visit” sentences can be strongly associated with other famous destinations. The model matches the shape of the sentence as well as the place name.

Takeaway: semantic search is powerful but fuzzy. For a precise requirement like “only Asia”, pair it with keyword search or metadata filtering (hybrid search).

7. The input-size trap

Embedding models can only read a limited amount of text. Anything beyond the limit is truncated and completely ignored, so meaning in the cut-off part never reaches the vector.

first 512 tokens: embedded
the rest: ignored
  • The lab loads a text of 3,955 characters and embeds it twice: the whole text, and only its first 3,000 characters.
  • Per the notebook, the two vectors are identical, not a single element different. This model’s context window is 512 tokens.
  • The fix comes in later modules (handling large texts, for example by splitting them into chunks).

Real-life scenario: a 40-page policy PDF embedded as one block. A rule on page 30 never influences its vector, so a prompt about that rule can’t find the document. Chunking the PDF so each piece fits the limit avoids this.

Making the shape handling consistent

An optional improvement: share one validation helper so both metrics fail the same friendly way.

def _as_matrix(v1, vectors):
    v1 = np.asarray(v1, dtype=float)
    M = np.atleast_2d(np.asarray(vectors, dtype=float))   # one vector or many
    if M.shape[1] != v1.shape[0]:
        raise ValueError(f"Shapes don't match: v1 {v1.shape}, vectors {M.shape}")
    return v1, M

def cosine_similarity(v1, vectors):
    v1, M = _as_matrix(v1, vectors)
    return (M @ v1 / (np.linalg.norm(M, axis=1) * np.linalg.norm(v1))).tolist()

def euclidean_distance(v1, vectors):
    v1, M = _as_matrix(v1, vectors)
    return np.linalg.norm(M - v1, axis=1).tolist()

Not part of the lab. It rejects the silent-broadcast cases above for both metrics and avoids the Python loop.

Alternatives and trade-offs

Explicit shape check (lab’s Euclidean)

Pros
  • Catches silent broadcasting bugs
  • Clear error message with both shapes
Cons
  • Extra code to maintain
  • Applied to only one function, so behavior is inconsistent

Rely on NumPy errors (lab’s cosine)

Pros
  • Minimal code
  • np.dot already rejects mismatched 1-D vectors
Cons
  • Less friendly message
  • Edge cases (scalars, higher dimensions) slip through

Shared validation helper

Pros
  • Same protection for every metric
  • Easy to vectorize
Cons
  • Slightly more setup

Library functions (SciPy, scikit-learn)

The lab says later assignments import from specialized libraries.

Pros
  • Tested, optimized, handles batches
Cons
  • Conventions differ (some return cosine distance, not similarity), so check the docs before ranking

Key takeaways

  • Your question: Euclidean needs an explicit shape check because v1 - v2 broadcasts silently; cosine is guarded by np.dot, which errors on mismatched lengths.
  • Cosine = angle (higher is closer). Euclidean = straight-line distance (lower is closer). They can disagree on raw vectors, but on unit-length embeddings they rank identically.
  • The model BAAI/bge-base-en-v1.5 maps text to 768-dim vectors; encode takes one string or a list.
  • Semantic search captures contextual similarity but can surprise you (Kyoto ranked 6th), which is why hybrid search exists.
  • PCA reduces 768 dimensions to 2 for visualization, at the cost of some distortion.
  • The model reads only 512 tokens; anything beyond is ignored, so long documents need chunking.
