How a retriever finds the right documents

Before diving into each search technique, hold one mental model: a prompt goes in, two different searches run side by side, a metadata filter trims both lists, and the survivors are merged into one ranking.

The big picture: where the retriever sits

When a RAG system receives your prompt, it goes to the retriever first. The retriever has access to the knowledge base, which you can think of as a bunch of text files sitting in a database. Its job is to quickly decide which documents are most relevant to the prompt and return them so they can be passed to the LLM.

Two ways to search, used together

Most modern retrievers use two different search techniques as part of the process.

Keyword search

Looks for documents that contain the exact words found in the prompt. Time-tested; it has powered information retrieval systems for decades.

“How can I make New York style pizza at home?”
Doc 1Use bread flour for New York pizza dough.
Doc 2New York pizzerias stay open late for home delivery.
Doc 3At New York Pizza Mexico, they serve pizza with jalapeño.

Strength: sensitive to the exact words the user typed. Weakness: Doc 2 and Doc 3 match words but not the intent.

Semantic search

Looks for documents with a similar meaning to the prompt. More flexible: it can find relevant documents even if they don’t contain the user’s exact words.

“How many vacation days do new hires get?”
Match“Paid time off overview: employees accrue leave from day one.” No shared keywords, same meaning.
Match“Annual leave entitlement for first-year staff.”

Strength: finds meaning without matching words. Weakness: it doesn’t guarantee that specific words (a product code, a name) appear.

Two lists, not one. Each search returns its own collection of roughly 20 to 50 documents. The scoring style differs, so the same document may be ranked high in one list and low in the other.

The two filtered lists are combined into a single ranked list of the most relevant documents.

The metadata filter: a rigid yes/no gate

Some documents in your knowledge base are relevant to engineers, others to people in HR. The system knows which team the user belongs to and applies a metadata filter, so only documents relevant to that department move forward.

Real-life scenario: internal company assistant

Priya works in Engineering and asks the company assistant a question. Her profile says department = Engineering, so HR-only documents (leave approval playbooks, for example) are removed from both the keyword list and the semantic list before merging.

The filter never reads the prompt. It narrows results using attributes of the user and the document, not the query content.

Heads-up from the slides: metadata filtering isn’t true search. It’s rigid, ignores content, can’t rank anything, and is useless alone. Its value is enforcing strict rules that neither search technique can enforce. Next lesson covers it in depth.

Why it’s called hybrid search

The final ranking relies on multiple techniques, and each one contributes something the others can’t.

Keyword search

Keeps the system sensitive to the exact words the user included in the prompt.

Semantic search

Gives flexibility to find documents with similar meaning, even without the same words.

Metadata filtering

Excludes documents by rigid criteria in a way neither of the other approaches allows.

The design job: a high-performing retriever means understanding each technique’s relative strengths, then tuning the balance between them to fit your project’s needs. This whole module builds toward that tuning.

The whole flow in a few lines

Conceptual pseudocode, not a specific library API. The real scoring methods (BM25, embeddings) and the merge step come in later lessons.

def hybrid_retrieve(prompt, user, top_k=5, n=50):
    kw  = keyword_search(prompt, limit=n)    # exact-word matches
    sem = semantic_search(prompt, limit=n)   # similar-meaning matches

    kw  = [d for d in kw  if allowed(d.metadata, user)]   # filter list 1
    sem = [d for d in sem if allowed(d.metadata, user)]   # filter list 2

    return merge_rankings(kw, sem)[:top_k]   # one final ranking, top_k out

Alternative designs and their trade-offs

Hybrid with post-filtering is the setup described in this lesson. Here’s how it compares.

Keyword search only

Pros
  • Simple and fast
  • Guaranteed exact-word matching
Cons
  • Misses synonyms (“vacation” vs “time off”)
  • Can match the wrong meaning

Semantic search only

Pros
  • Finds relevant text without shared words
  • Flexible with messy, conversational prompts
Cons
  • Slower and more computationally expensive
  • Can miss exact terms like names or codes

Hybrid + post-filter (this lesson)

Pros
  • Covers both exact words and meaning
  • Filter enforces strict rules on both lists
  • Balance can be tuned per project
Cons
  • More moving parts to tune and evaluate
  • Filtering after search can leave fewer documents (50 becomes 30)

Pre-filtering before search

Pros
  • Search runs only over allowed documents
  • Still returns a full list of results
Cons
  • Depends on your database supporting filtered search
  • Not the flow shown in this lesson, so check your tooling

Key takeaways

  • The retriever’s job: quickly pick the documents most relevant to the prompt from the knowledge base and hand them to the LLM.
  • Two searches run in parallel: keyword (exact words) and semantic (similar meaning), each returning about 20 to 50 documents.
  • Each list is then filtered on metadata, such as the user’s team, before anything is merged.
  • The filtered lists are combined into one ranking, and the top-ranked documents go to the augmented prompt.
  • This multi-technique setup is hybrid search. Good retrievers balance all three techniques for the project’s needs.
