📏 Developing & Evaluating an Anomaly Detection System

Real-number evaluation · Train / CV / Test with a few labeled anomalies · Choosing ε and features

Key Idea: Real-Number Evaluation

When developing a learning algorithm (choosing features, tuning ε, etc.), decisions are far easier if you have a way to evaluate it, even while it's being built.

Change something
(a feature, or ε)
→
Compute one number for how well the algorithm does
→
Better or worse?
Keep or revert the change
That fast loop (change, measure, decide) lets you improve the system much more quickly. It's called real-number evaluation.

Twist: A Little Labeled Data

So far anomaly detection used unlabeled data. For evaluation we relax that assumption: assume we have a small number of previously observed anomalies.

y = 1 → anomalous

  • Known flawed engines (usually very few)

y = 0 → normal

  • Everything we believe is normal

Robustness: if a few anomalies slip into the training set, or a few anomalies are accidentally labeled y = 0, the algorithm usually still does okay.

Aircraft Engine Example: How to Split

Years of manufacturing → 10,000 good engines and 20 flawed engines (typical anomaly count: 2 to 50).

Standard split

TRAIN · 6,000 good
CV · 2,000 good
TEST · 2,000 good
■ red slivers = 10 anomalous engines in CV and 10 in test (tiny in proportion)
  • Train on the 6,000 good engines (fit the Gaussians).
  • CV: 2,000 good + 10 anomalous → tune ε and features: does it catch the 10 anomalies without flagging too many of the 2,000 good ones?
  • Test: 2,000 good + 10 anomalous → after tuning, see how many of the 10 it finds and how many good engines it wrongly flags.
Still primarily unsupervised: the training set has no labels (all assumed y = 0) and you learn by fitting Gaussians. The few labels are used only for tuning and evaluating.

Alternative: no test set

TRAIN · 6,000 good
CV · 4,000 good + all anomalies

Pros

  • Makes sense when you have very few flawed engines (e.g. only 2)
  • Not enough data for a separate test set anyway

Cons

  • No fair way to judge performance on future examples after tuning
  • Higher risk of overfitting ε and feature choices to the CV set

In Code: Choosing ε with F₁ on the CV Set

import numpy as np

def select_threshold(y_val, p_val):
    best_eps, best_F1 = 0, 0
    for eps in np.linspace(p_val.min(), p_val.max(), 1000):
        pred = (p_val < eps)                         # True → predicted anomaly (y=1)
        tp = np.sum(pred & (y_val == 1))
        fp = np.sum(pred & (y_val == 0))
        fn = np.sum(~pred & (y_val == 1))
        if tp == 0: continue                       # avoid divide-by-zero
        prec, rec = tp/(tp+fp), tp/(tp+fn)
        F1 = 2*prec*rec/(prec+rec)
        if F1 > best_F1:
            best_eps, best_F1 = eps, F1
    return best_eps, best_F1

# 1) fit on TRAIN (normal only)   2) p(x) on CV   3) pick ε   4) report once on TEST

Real-life example (fraud): 100,000 normal transactions and 30 confirmed frauds. A high ε floods the security team with false alarms (low precision); a low ε lets fraud slip through (low recall). The CV set lets you pick the balance your team can actually handle.
