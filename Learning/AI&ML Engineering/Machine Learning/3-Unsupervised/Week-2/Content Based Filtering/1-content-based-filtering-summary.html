Content-based filtering: learning to match users and items

A second way to build a recommender. Instead of leaning only on who rated what, it uses descriptions of the user and descriptions of the item, and learns whether they fit.

1. Collaborative vs content-based

Slide: “Collaborative filtering vs Content-based filtering”.

Collaborative filtering

Recommends items based on ratings of users who gave similar ratings as you.

Input: the rating table only.

Content-based filtering

Recommends items based on features of the user and features of the item to find a good match.

Input: user descriptors + item descriptors (still uses the ratings as training labels).

Notation is unchanged.
  • r(i,j) = 1 if user j has rated item i
  • y(i,j) is the rating user j gave item i (only if defined)
The key idea: using features of both sides can find better matches than pure collaborative filtering might.

2. Features you can build

Slide: “Examples of user and item features”. Each side gets squeezed into one feature vector.

User features → xu(j) for user j

Age Gender · one-hot (male / female / unknown) Country · one-hot, about 200 values Movies watched · ~1000 features, one per top-1000 catalog movie (watched or not) Average rating per genre · e.g. mean of all romance ratings, mean of all action ratings, … …

Movie features → xm(i) for movie i

Year Genre / genres Reviews · one or several features summarising what critics say Average rating of the movie Average rating per country or per user demographic …
Features may be built from ratings. “Average rating per genre” (user) and “average rating” (movie) both depend on ratings, and that is completely fine.
The two vectors can be very different in size. For example, xu could have 1500 numbers while xm has only 50. That is okay, because the next step maps both to a common size.

3. The prediction: from w·x + b to vu·vm

Slide: “Learning to match”.

Before (collaborative filtering): predict user j’s rating of movie i as

w(j) · x(i) + b(j)

Now (content-based): drop b (it does not hurt performance), and replace w and x with two computed vectors

vu(j) · vm(i)
  • vu(j) is a list of numbers computed from the user’s features xu(j). It summarises the user’s preferences compactly.
  • vm(i) is a list of numbers computed from the movie’s features xm(i).
  • Hope: if both vectors are chosen well, their dot product predicts the rating user j gives movie i.

Pipeline

The “compute” step is the open question, answered in the next video. Different input sizes in, one shared size out.

Hard rule: vu and vm must have the same dimension (say, both 32 numbers), otherwise the dot product is undefined, even though xu and xm can differ.

5. Real-life scenarios

Romance fan, rom-com release

A user whose rated romances average 4.8 has a high romance entry in vu. A new rom-com gets a high romance entry in vm. Their dot product is large, so it is recommended, even though nobody has rated that movie yet.

Music or shopping app

Same recipe outside movies: user features (age, country, past plays) and item features (genre, release year, average rating) are each mapped to vectors, and the dot product scores the match for songs, products, or articles.

6. Approaches compared

The lecture contrasts the first two. The pros, cons, and the hybrid row are my own additions for your “alternatives” notes.

UsesRatings from many usersUser features + item featuresBoth
ProsNeeds no hand-built features; can surface surprising picksCan score an item or user with few or no ratings if their features are known (cold start); works with ratings turned into featuresCovers each side’s weak spots

Key takeaways

  • Collaborative filtering matches you to similar raters; content-based matches user features to item features.
  • Still use r(i,j) and y(i,j) as the training signal.
  • Build xu(j) and xm(i) from demographics, behaviour, content, and rating-derived stats. They may differ in length.
  • Predict the rating as vu(j) · vm(i) (no bias term).
  • vu and vm must share one size.
