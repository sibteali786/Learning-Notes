Recommending from a large catalogue

The two-network model from last time scores one user-item pair well. But real sites must pick a handful of items out of thousands, millions, or tens of millions. The lecture’s answer: a two-step pipeline, retrieval then ranking.

1. The scale problem

Slide: “How to efficiently find recommendation from a large set of items?”

Catalog sizes (slide)

Bars are not to scale (the movie bar is made visible on purpose).

Why the naive way fails

When a user shows up with features xu, scoring every item means running the neural network thousands to millions of times, every visit. That is computationally infeasible.

Real-life case: a music site with tens of millions of songs cannot run 10M+ network inferences each time someone opens the app.

2. The two steps

Retrieval

Generate a large list of plausible candidates. Goal: broad coverage. It is fine if the list contains items the user will not like, as long as it has many good ones.

Ranking

Take that shorter list and fine-tune using the learned model. Pick and order the best items to show.

3. Retrieval: where candidates come from

Slide: “Two steps: Retrieval & Ranking”. Retrieval should be very fast and ends with about 100s of items.

Source 1

Similar to what they watched

For each of the last 10 movies watched, find the 10 most similar movies using ‖vm(k) − vm(i)‖2. This is pre-computed, so it is just a look-up table.

Source 2

Favourite genres

For the user’s 3 most-viewed genres, add the top 10 movies of each. Example: lots of romance, comedy, and historical dramas watched, so top 10 of each.

Source 3

Local popularity

Add the top 20 movies in the user’s country.

Then clean up: combine everything into one list, remove duplicates, and remove items already watched or purchased that you may not want to recommend again.

4. Ranking: score only the candidates

Slide: “Two steps: Retrieval & ranking”.

  1. Take the retrieved list (~100s).
  2. Feed the user features and each movie’s features into the network and compute the predicted rating (or probability) for every user-movie pair.
  3. Sort by prediction and display the ranked items, highest expected rating first.
Extra speed-up: if vm is pre-computed for every movie, you run only the user half of the network once to get vu for the person on the site right now. Then just take the inner product vu · vm with each retrieved movie’s stored vector.

5. How many items to retrieve?

Slide: “Retrieval step”. The slide’s handwritten numbers compare 100 and 500.

The trade-off

Retrieve morebetter performance slower recommendations
Retrieve fewerfaster may miss good items

How to decide

Run offline experiments. Check whether the model’s estimated p(y(i,j) = 1), or predicted rating, for the items you would display is noticeably higher when you retrieve, say, 500 instead of 100. If so, retrieve more, even if it slows things a bit.

Why it works: retrieval prunes away items not worth the detailed inference and inner product. Ranking then makes a careful prediction on what is left. Many recommenders today get both fast and accurate results this way.

6. Ethics: the lecture’s closing note

Recommender systems are commercially important, but they come with significant ethical issues, and some systems have created harm. Ng asks you to build with an ethical approach that serves your users, society at large, yourself, and the company you work for. The next video covers these issues in detail.

7. Alternatives and trade-offs

OptionProsCons
Pre-computed similar-item look-up (lecture)Very fast at request time; simpleStale until the next batch run; only covers “similar to X”, not “similar to this user”

Ranking sketch in NumPy (illustrative, not from the lecture)

import numpy as np

# Pre-computed offline: one 32-d vector per item
item_vecs = np.load("item_vecs.npy")        # shape (num_items, 32)

def recommend(user_features, candidate_ids, user_nn, top_n=10):
    vu = user_nn(user_features[None, :])[0]  # user network run ONCE
    scores = item_vecs[candidate_ids] @ vu   # one inner product per candidate
    best = np.argsort(-scores)[:top_n]
    return [candidate_ids[i] for i in best]

Here candidate_ids comes from the retrieval step after de-duplicating and removing watched or purchased items. The names item_vecs and user_nn are my own placeholders.

Key takeaways

  • Scoring every item with the network per visit is infeasible for catalogues of thousands to tens of millions.
  • Retrieval: fast, broad, about 100s of candidates (similar to recent watches via look-up, top items in favourite genres, top items in the country), then remove duplicates and already watched or purchased items.
  • Ranking: score the candidates with the learned model, sort, and display. Pre-compute vm and run the user network once.
  • More retrieved items means better quality but slower. Use offline experiments (100 vs 500) to choose.
