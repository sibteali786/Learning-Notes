🖼️ K-Means for Image Compression

Practice Lab Walkthrough — reshaping pixels, running K-means, and the compression math

The Big Idea

An image is just a big list of pixels, and each pixel is a 3-feature data point: (Red, Green, Blue) intensity. Run K-means on all the pixels treating each as a point in 3D color space → the K centroids you get back are the K most representative colors in the image. Replace every pixel with its nearest centroid's color = compression.

Step-by-Step Pipeline

Load image → original_img.shape = (128, 128, 3). Three indices: row, column, and RGB channel.
Reshape the 3D matrix into a 2D matrix of pixel colors: (16384, 3) — one row per pixel, 3 columns (R,G,B). This is the "dataset" K-means actually sees.
Run K-means with K=16 → get 16 centroids, each a (R,G,B) triple = the 16 representative colors.
Reassign every pixel to its closest centroid using find_closest_centroids → each pixel now only needs to store which of the 16 colors it uses, not its own RGB.
Rebuild the image using centroid colors in place of original pixel colors → visibly similar image, far less data.

Q1 Why Multiply Shape[0] × Shape[1] in the Reshape?

X_img = np.reshape(original_img, (original_img.shape[0] * original_img.shape[1], 3))
# i.e. np.reshape(original_img, (128 * 128, 3))

This has nothing to do with 8-bit color values — it's pure shape arithmetic. original_img is a 3D block: 128 rows × 128 columns × 3 channels = 16,384 individual pixels, each with 3 numbers.

K-means needs a flat 2D table (like any dataset X): one row per example. So you multiply 128 × 128 just to compute how many total pixels/rows the flattened table needs — that number becomes the row count, and 3 stays as the column count (R, G, B stay 3 features, they're not reduced to 2).

Think of it as unstacking a 128×128 grid of pixels into one long list of 16,384 pixels — the multiplication just counts the grid's total cells.

Tiny worked example — a 2×2 image instead of 128×128, so it's easy to see nothing gets merged:

# Before reshape: shape (2, 2, 3)
original_img[0,0] = [255,   0,   0]   # top-left, red
original_img[0,1] = [  0, 255,   0]   # top-right, green
original_img[1,0] = [  0,   0, 255]   # bottom-left, blue
original_img[1,1] = [255, 255,   0]   # bottom-right, yellow

4 pixels total, each still holding its own 3 separate RGB numbers. After reshape((2*2, 3)) → shape (4, 3):

X_img = [
  [255,   0,   0],   # was original_img[0,0]
  [  0, 255,   0],   # was original_img[0,1]
  [  0,   0, 255],   # was original_img[1,0]
  [255, 255,   0],   # was original_img[1,1]
]

Same 4 pixels, same 12 numbers (4×3) — just relaid out as 4 rows × 3 columns instead of a 2×2 grid of triples. 2*2=4 only computed the row count. Scale up: 128×128 = 16,384 rows, each still keeping its own 3 RGB values as separate columns — no pixel's RGB is summed or averaged into one number. It's a reshape (relayout), not a reduction.

Q2 Why Divide by 255 for JPG but Not PNG?

It comes down to what plt.imread() hands back, which differs by file format:

Formatplt.imread() returnsValue rangeDivide by 255?
PNGfloat array (already normalized)0.0 – 1.0❌ No — already in range
JPG/JPEGuint8 array (raw pixel intensities)0 – 255✅ Yes — must normalize
K-means (and the distance formula) work fine on either range, but it's good practice to keep features on a consistent 0–1 scale. If you skip the divide on a JPG, your "distances" will just be numerically larger, but relative comparisons still hold — the note in the lab is about consistency, not correctness-breaking.

Q3 The Compression Bit Math, Explained

Original (no compression)
128 × 128 × 24 = 393,216 bits
Every single pixel stores its own full R+G+B (8+8+8 = 24 bits)
Compressed (K=16)
16×24 + 128×128×4 = 65,920 bits
~6× smaller

Break the compressed formula into its two separate costs:

TermWhat it pays forWhy that number
16 × 24The color dictionary (the "palette")16 centroids, each is a full RGB color needing 24 bits (8+8+8) — stored once, not per pixel
128 × 128 × 4Each pixel's label (which of the 16 colors it uses)16,384 pixels, but now each just stores an index 0–15. Since 2⁴=16, that index fits in 4 bits instead of 24
The key shift: instead of paying 24 bits per pixel (16,384 × 24), you pay 24 bits 16 times total (once per color) + a cheap 4-bit pointer per pixel. That's the entire compression trick — store the expensive full-color data once, and reference it cheaply everywhere else.

Only a small saving here: with 6 pixels, the 96-bit palette dominates. With the real 16,384 pixels the palette (384 bits) becomes negligible next to 16,384 × 4 bits, giving 393,216 → 65,920 bits (~6× smaller). The more pixels share one palette, the bigger the win.

💡 Key Takeaways

Pixels = data points in RGB space Reshape (H×W, 3) — just flattening the grid ÷255 only needed for uint8-range formats (JPG) Compression = palette cost + per-pixel index cost
Trade-off to keep in mind: bigger K → better image quality, bigger dictionary, less compression. Smaller K → more compression, more visible color banding.
