Lesson 12 — The Iterative Loop of ML Development

Pulling bias/variance together into the actual day-to-day workflow of building a model — using a spam classifier as the running example.

1 The Loop

1. Choose architecture — pick the model type, what data to use, hyperparameters.
2. Train model — implement and train. It almost never works as well as hoped on the first pass.
3. Run diagnostics — bias/variance analysis, plus error analysis (next lesson) — to see what's actually going wrong.
4. Act on insights — bigger network? Change λ? More data? More/fewer features? Then loop back to step 1.

This loop typically runs multiple times before reaching the desired performance — it's the normal, expected shape of building a model, not a sign something's wrong.

2 Running Example: Building a Spam Classifier

Spam
"Deal of the week! Buy now! Rolex w4tches, med1cine, m0rtgage..."
Not Spam
An actual email from a family member about getting together for the holidays.

Note the spam email's deliberate misspellings — "w4tches", "med1cine", "m0rtgage" — a tactic spammers use specifically to trip up keyword-based spam filters.

3 Constructing Features: Bag-of-Words

One classic approach: take the top 10,000 English words, and for each email, check whether each word appears.

This gives a 10,000-dimensional feature vector x₁...x₁₀₀₀₀ per email, fed into logistic regression or a neural network to predict y (spam / not spam). A variant: instead of 0/1 presence, count how many times each word appears — "if 'buy' appears twice, set that feature to 2" — which works decently well too.

4 After the First Model: Which Idea to Chase?

Once the first model underperforms, there's usually no shortage of ideas — the real skill is knowing which one is actually worth the time:

Collect more data — e.g. a "honeypot" project: create fake email addresses, let spammers find them, and harvest confirmed-spam data at scale.
Sophisticated features from email routing — the header metadata tracking which servers/networks an email passed through en route can hint at spam origin.
Better features from the email body — e.g. treating "discount" and "discounting" as the same underlying word instead of separate features.
Misspelling detection — algorithms to catch deliberate obfuscations like "w4tches", "med1cine", "m0rtgage".
Why diagnosis comes before action

A honeypot project can take months to bear fruit. If the classifier's real problem is high bias (Lesson 5-9's diagnostic), pouring months into more data won't help much — the model's architecture is the bottleneck, not the data volume. If it's high variance, more data is exactly the right move. Picking the right direction from the start, using bias/variance as a guide, can speed up a project by an order of magnitude compared to guessing.

5 Key Takeaway

Diagnostics decide direction, not intuition

The iterative loop only works efficiently when the "diagnostics" step is taken seriously. Bias/variance analysis is the first tool; error analysis — actually looking at which specific examples the model gets wrong — is the second, and is the subject of the next lesson.
