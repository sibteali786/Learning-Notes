Lesson 16 — Full Cycle of an ML Project

Training the model is one piece of a much bigger picture — scoping, data, deployment, and ongoing maintenance, illustrated with a speech recognition example.

1 The Four-Stage Cycle

The feedback loops matter: training can send you back to collecting more (or more targeted) data, and deployment can reveal problems that send you back to training — or even back to collecting more data, now sourced from real production traffic.

2 Walking Through Each Stage — Speech Recognition Example

Scope the project — decide what to build. e.g. "voice search: let people search by speaking into their phone instead of typing."
Collect data — decide what data is needed, then go get the audio clips and their transcripts (labels).
Train the model — train, run error analysis, iterate. It's completely normal for this stage to loop back to "collect more data" — sometimes broadly, sometimes very specifically.
Deploy in production — make it available to real users, then monitor and maintain it, since performance can degrade after launch.
A concrete error-analysis-to-data loop

The instructor found their speech system performed poorly specifically on car-background-noise audio. Rather than collecting more data generally, they used data augmentation (Lesson 14) to synthesize more car-noise training examples — directly closing the gap error analysis had revealed.

3 Deployment Architecture: Inference Server

The mobile app records audio and sends it via API call as input x to the inference server. The server runs the trained model and returns a prediction ŷ — here, the transcribed text. This request/response pattern (send x, get back ŷ) is the common shape for serving any trained model.

4 Software Engineering Behind Deployment

reliability Ensure predictions are consistently correct and available
efficiency Keep computational cost of inference low
scaling Handle anywhere from a handful of users to hundreds of millions
logging Record inputs (x) and predictions (ŷ), with user privacy/consent respected
monitoring Watch for performance degradation over time
updates Retrain and redeploy the model as needed
Real example: why monitoring matters

A speech system trained on a fixed dataset started performing poorly whenever new celebrities became famous or new politicians got elected — names that simply weren't in the training data. Monitoring surfaced this data shift, which triggered retraining and a model update to bring accuracy back up. Without monitoring, this degradation could have gone unnoticed indefinitely.

5 MLOps

MLOps (Machine Learning Operations) is the practice of systematically building, deploying, and maintaining ML systems — ensuring reliability, scalability, good logging, active monitoring, and a clear path to model updates. It's a growing field of its own, distinct from the model-training work covered throughout this course, and the team that trains a model isn't always the same team that deploys and operates it.

6 Key Takeaway

Training is the critical piece — not the only piece

Everything covered about bias/variance, error analysis, and adding data is essential to getting a high-performing model. But shipping that model to real users at any meaningful scale brings a second, genuinely different set of engineering concerns — reliability, scaling, logging, monitoring, and the discipline to keep improving after launch, not just before it.
