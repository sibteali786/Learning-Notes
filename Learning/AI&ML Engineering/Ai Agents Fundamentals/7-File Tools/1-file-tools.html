FILE SYSTEM TOOLS

readFile + writeFile

Tools are just functions — but what they return is meant for an LLM to reason over, not for code to consume. That changes how you write them.
💡 A regular function throws errors and returns data. A tool returns human-readable strings — including on errors — so the LLM can understand what happened and decide what to do next.
File system access is the single most powerful capability you can give an agent. readFile alone lets a coding agent understand an entire codebase.
WHY FILES MATTER FOR AGENTS
📖 Context loading (read codebase) 🧠 Persistent memory (scratchpad.md) 📊 State tracking (progress.json) 🗂️ External working memory (large data) 🔗 Inter-agent communication 📋 Audit trail logging
CLAUDE.md and cursor rules are just markdown files the agent reads to configure itself. If you took away every tool and left only readFile + writeFile, a coding agent could still help you write code.
readFile
description
"Read the full contents of a file at the given path. Use this always to read a file." — adding "always" nudges tool preference over shell cat.
inputSchema
path: z.string().describe("The path to the file to read")
returns
File contents as UTF-8 string on success. Readable error string on failure — never throws.
execute: async ({ path: filePath }) => {
  try {
    return await fs.readFile(filePath, 'utf-8');
  } catch (err) {
    if (err.code === 'ENOENT') return `Error: File not found: ${filePath}`;
    return `Error reading file: ${err.message}`;
  }
}
Error codeLLM seesExpected agent response
ENOENT"File not found: ./foo.ts"Call listFiles to discover what exists, or ask user for correct path
EACCES"Error reading file: permission denied"Try different path or report to user
other"Error reading file: [native message]"Reason over native Node.js message to decide next step
writeFile
description
"Write content to a file at the specified path. Creates the file if it does not exist and will overwrite it if it does." — be explicit about overwrite behavior or agent panics.
inputSchema
path: z.string() · content: z.string().describe("The content to write to the file")
returns
"Successfully wrote N characters to path" — character count confirms full write, not partial.
execute: async ({ path: filePath, content }) => {
  try {
    const dir = path.dirname(filePath);
    await fs.mkdir(dir, { recursive: true });   // auto-create parent dirs
    await fs.writeFile(filePath, content, 'utf-8');
    return `Successfully wrote ${content.length} characters to ${filePath}`;
  } catch (err) {
    return `Error writing file: ${err.message}`;
  }
}
mkdir recursive: true — if path is ./output/reports/q3.md and neither folder exists, it creates both automatically. No extra "create directory" tool needed.
TOOL DESIGN vs REGULAR FUNCTION DESIGN
Regular function
Throws on error → calling code catches
Returns typed data → code processes
ENOENT = exception, caller handles
Doesn't suggest next steps
Error message for developers
Agent tool
Never throws → returns error string
Returns string → LLM reads and reasons
ENOENT = "File not found: path" string
Can suggest: "you should list files next"
Error message for an LLM
⚠️ Atomic tools = more steps = more error surface. A 99% accurate agent over 20 steps is less than 82% accurate end-to-end. As your agent matures, combine related operations: instead of writeFile + listFiles separately, make a tool that writes and verifies in one call. Fewer steps = fewer failure points.
WNP scenario: Agent needs to export a project report. writeFile returns "Successfully wrote 2,847 characters to ./exports/Q3-report.md". Agent sees the character count, knows it wasn't truncated, and responds to user: "Done — full report saved to exports/Q3-report.md." Without the count, agent might call readFile to verify, adding an unnecessary step.
listFiles
description
"List all files and directories in the specified directory path." — not a file path. Default is "." so agent doesn't need to ask user when no path given.
inputSchema
directory: z.string().default(".") — default makes it optional without z.union(null). Agent skips follow-up question.
returns
Formatted string with [dir] / [file] prefixes joined by newline. Not raw JSON — LLM reads language, not brackets.
execute: async ({ directory }) => {
  try {
    const entries = await fs.readdir(directory, { withFileTypes: true });
    const items = entries.map(e => `${e.isDirectory() ? '[dir]' : '[file]'} ${e.name}`);
    return items.length > 0
      ? items.join('\n')
      : `Directory ${directory} is empty`;
  } catch (err) {
    if (err.code === 'ENOENT') return `Error: Directory not found: ${directory}`;
    return `Error listing directory: ${err.message}`;
  }
}
withFileTypes: true — distinguishes [dir] from [file]. Without it, index.py and index.js look identical. LLM needs type to reason about what to do next.
Token efficiency: 100 entries as JSON = hundreds of wasted bracket/colon tokens. Formatted string = clean, dense, readable.
deleteFile
description
"Delete a file at the specified path. Use with caution as this is irreversible and cannot be recovered from." — explicit warning trains cautious models to hesitate/confirm before calling.
inputSchema
path: z.string().describe("The path to the file to delete")
fs method
fs.unlink() not fs.rm() — unlink handles symbolic links safely. Removes the link without affecting the target file/dir it points to.
execute: async ({ path: filePath }) => {
  try {
    await fs.unlink(filePath);     // safe for symlinks too
    return `Successfully deleted ${filePath}`;
  } catch (err) {
    if (err.code === 'ENOENT') return `Error: File not found: ${filePath}`;
    return `Error deleting file: ${err.message}`;
  }
}
tools/index.ts — REGISTRATION 
import { readFile, writeFile, listFiles, deleteFile } from './file.ts';

// All tools for the agent loop
export const tools = { readFile, writeFile, listFiles, deleteFile };

// Named exports for selective use in evals (import just what you need)
export { readFile, writeFile, listFiles, deleteFile } from './file.ts';

// Tool set — pass all file tools as one pack to evaluate() or sub-agents
export const fileTools = { readFile, writeFile, listFiles, deleteFile };
Three export shapes: tools (all tools for agent loop) · named exports (pick individual tools for evals) · fileTools set (group for sub-agents or restricted evals that should only have file access).
⚠️ Making schema fields optional in strict mode: You can't just leave a field out — use z.union([z.string(), z.literal(null)]). Or use .default(".") like listFiles does — the default tells the agent it can skip asking the user, while still satisfying the strict schema requirement.

DESIGN DECISIONS
Why 4 separate tools, not one tool({ operation: "read|write|..." })?
Clearer intent per tool → better LLM descriptions → simpler schemas → easier permission control (allow readFile, block deleteFile). One generic tool means ambiguous descriptions and one schema trying to cover all cases.
Why return errors as strings instead of throwing?
Throwing crashes the agent loop or causes unpredictable behavior. A string error lets the agent read what went wrong and decide: try a different path, call listFiles to explore, or tell the user. The agent is the error handler — not your catch block.
Why auto-create parent directories in writeFile?
Requiring the agent to manually mkdir each level before writing is tedious and error-prone — that's 2–3 extra tool calls per write. mkdir({ recursive: true }) matches how every developer expects file writes to work.
COMMON AGENT PATTERNS
Read → Modify → Write
readFile("config.json")
→ parse + modify
→ writeFile("config.json", updated)
Explore → Drill Down → Read
listFiles("src/")
→ listFiles("src/components/")
→ readFile("Button.tsx")
Write → Verify (paranoid)
writeFile("output.txt", content)
→ readFile("output.txt")
→ confirm matches expected
Scratch Pad (temp memory)
writeFile("/tmp/scratch.json", big)
→ readFile (chunks as needed)
→ process → deleteFile cleanup

Flow: listFiles("./exports") → sees [file] Q3-tasks.json → readFile("./exports/Q3-tasks.json") → generates summary → writeFile("./exports/Q3-archive.md", summary) → "Wrote 1,204 chars" → deleteFile("./exports/Q3-tasks.json") → "Successfully deleted". All 4 tools, all returning readable strings the agent reasons over at each step.
