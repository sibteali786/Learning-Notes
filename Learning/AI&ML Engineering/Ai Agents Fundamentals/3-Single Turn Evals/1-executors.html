SINGLE TURN EVALS

Eval Data + Executors

Mock tools → feed data → run one turn → score tool selection. TDD for AI.
💡 An executor = a dynamic run() function that takes eval data as input and returns what tools the agent picked.
You don't need working tools to eval. The agent only sees descriptions — so just mock those. Like TDD: write the test before the function exists.
EVAL DATA SHAPE
📥
data (input)
The user prompt fed to the agent. E.g. "read this file, write that file, delete this file."
🎯
target (expected)
The tool(s) we expect the agent to call in response. This is the ground truth.
🏷️
category
golden must-solve   secondary nice-to-have   negative must-avoid
Example: data = "Can you start the dev server?" → target = run_command → category = secondary (no context given, agent might not know the command — cool if it figures it out, not critical if it doesn't).
MOCKED TOOL DEFINITIONS
No execute() needed — agent only sees description + parameters. That's all that matters for tool selection evals.
ToolDescriptionKey Param(s)
read_fileRead the contents of a file at the specified pathpath: string
write_fileWrite given content to the file at the given pathpath, content: string
list_filesList all the files in a directorydirectory: string
delete_fileDelete a file at the given pathpath: string
run_commandExecute a shell command and return its outputcommand: string
Why mock? Real tools hit the file system, make it slow, and require everything to be wired up. Evals only care about did the agent pick the right tool — not whether the tool actually ran.
SINGLE TURN EXECUTOR — FLOW
eval data in→ buildMessages()→ dynamically build tool set→ generateText()→ extract toolCalls→ return { toolCalls, toolNames, toolsSelected }
1
buildMessages(data)
Formats system prompt + user prompt into a messages[] array. Last message must be role: user or the model won't respond.
2
Dynamic tool set from data.tools
Loops over the tool names in eval data → looks up mock definition → calls tool({ description, parameters }). No execute needed.
3
generateText with maxSteps=1
stopWhen: stepCountIs(1) — single turn only. Model defaults to o1-mini; temperature omitted for reasoning models (undefined = omitted in JSON stringify over wire).
4
Return structured result
toolCalls (name + args), toolNames (string[]), toolsSelected (boolean — did it pick anything at all?).
CODE — executor.ts (skeleton) 
// Mock tool definitions (no execute)
const toolDefinitions = {
  read_file:    tool({ description: 'Read the contents of a file at the specified path', parameters: z.object({ path: z.string() }) }),
  write_file:   tool({ description: 'Write given content to the file at the given path',   parameters: z.object({ path: z.string(), content: z.string() }) }),
  run_command:  tool({ description: 'Execute a shell command and return its output',        parameters: z.object({ command: z.string() }) }),
  // ...list_files, delete_file
};

// Single turn executor
export const singleTurnExecutor = async (data: EvalData) => {
  const messages = buildMessages(data);

  // Dynamically build tool set from eval data
  const tools: ToolSet = {};
  for (const toolName of data.tools) {
    const def = toolDefinitions[toolName];
    if (def) tools[toolName] = def;
  }

  const { toolCalls } = await generateText({
    model: data.model ?? openai('o1-mini'),
    messages,
    tools,
    stopWhen: stepCountIs(1),
    temperature: data.config?.temperature ?? undefined, // omitted for reasoning models
  });

  const calls      = toolCalls.map(tc => ({ toolName: tc.toolName, args: tc.args ?? {} }));
  const toolNames  = toolCalls.map(tc => tc.toolName);

  return { toolCalls: calls, toolNames, toolsSelected: toolNames.length > 0 };
};
⚠️ messages[] rule: Last message must always be role: "user". If the last message is role: "assistant", the model thinks it's waiting on you and returns nothing.
You can fake an entire conversation history in messages[] to prime the agent to any state — great for testing "what does the agent do after 3 back-and-forths?"
TRADE-OFFS OF THIS APPROACH
✅ Pros
One executor handles all experiments
Data can supply model/config per test case
No need for real tools to exist yet
Fast — no file system or network calls
❌ Cons
Options in data (category, model) won't exist in live/production data
Needs human annotation before live data can be used in offline evals
One executor might get too complex as system grows
WNP scenario: Mock create_task, assign_user, list_projects tool definitions with just descriptions + Zod schemas. Run evals against prompts like "create a task for Ali in the dev project" → score whether the agent picks create_task with list_projects first. No DB, no API calls needed.
