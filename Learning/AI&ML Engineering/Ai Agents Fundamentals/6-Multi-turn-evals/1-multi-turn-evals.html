EVALS — LEVEL 2

Multi-Turn Evals

Stop checking individual steps. Start checking whether the agent actually got the job done.
💡 Single-turn: "Did you pick the right tool?"  |  Multi-turn: "Did you finish the task?"
Multi-turn = run the full loop, mock the tools, judge the output with another LLM.
Users don't care what order you called tools in. They care that the job got done correctly. That's what multi-turn evals measure.

WHAT SINGLE-TURN EVALS MISS
✅ Right tool #1, ❌ Wrong tool #2
First call correct but next decision breaks. Only visible across multiple steps.
🔄 Stuck in a loop
Agent calls same tool repeatedly after seeing its result. Infinite loop detected only over full run.
🤷 Gives up too early
Vague prompt + granular tools = too much work. Agent lies "can't do this" instead of trying.
🤯 Misinterprets tool results
Tool returns base64 image. Can agent decode meaning? Can only test by feeding result back.
♾️ Doesn't know when to stop
Has all info needed but keeps calling tools. Early AGI problem — still happens on complex tasks.
📉 Quality of final response
Tool calls were perfect but the summary to the user was wrong or incomplete. Single-turn can't catch this.
LLM-AS-JUDGE
Agent output is text. You can't === text. You need intelligence to judge intelligence. Enter: another LLM.
✅ Why it works
Semantic understanding — "file contains 'hello'" = "content: hello"
Handles natural language variation
Criteria defined in plain English
Catches nuance regex never could
❌ Limitations
Expensive — 1 eval = 1+ LLM calls
Non-deterministic — same output, different scores
Model bias toward verbose/formal answers
Gaming — smart models can satisfy judge without being correct
Gaming risk: Don't hint at what "good" looks like in judge criteria. Models trained on goal-achievement will optimize for the judge, not actual quality. Like the Mom Test in product research — don't bias the interviewer.
MAKING THE JUDGE RELIABLE
SCORING RUBRIC (define what each number means)
10
Fully addresses task using tool results correctly
7–9
Mostly correct, minor issues
4–6
Partially addresses task
1–3
Mostly incorrect or irrelevant
// Structured output schema for judge — force a number, not prose
const judgeSchema = z.object({
  score:  z.number().min(1).max(10),
  reason: z.string()
});

// Judge call — use stronger model than the agent
const judgment = await generateObject({
  model: openai('o1'),           // stronger than agent's gpt-4o-mini
  schema: judgeSchema,
  prompt: `Task: ${task}
Tool results: ${JSON.stringify(mockResults)}
Agent response: ${agentOutput}
Did the agent correctly use the tool results to address the task?`
});
TEST DATA STRUCTURE
Fresh task
Single user prompt. Agent starts from scratch. Good for testing full task completion from zero context.
Mid-conversation (primed)
Pre-filled messages[] with fake history. Test follow-up handling. Leave off on a user message — LLM takes over from there.
// Each test case shape
{
  "prompt": "Read config and report the DB host",
  "tools": ["readFile", "writeFile"],
  "mockTools": {
    "readFile": { "result": "DB_HOST=localhost\nDB_PORT=5432" },
    "writeFile": { "result": "Successfully wrote 45 chars" }
  },
  "expectedToolOrder": ["readFile"],          // deterministic scorer
  "forbiddenTools": ["deleteFile"],            // deterministic scorer
  "originalTask": "Read config and report DB host"  // fed to judge
}
COMBINED EVALUATORS — MULTI-TURN
Mix deterministic scorers (cheap, fast) with LLM judge (expensive, semantic). Average or weight them.
toolOrderCorrect
Binary · deterministic
Did tools execute in expected sequence?
toolsAvoided
Binary · deterministic
Were forbidden tools never called?
llmJudge
1–10 score · non-deterministic
Did final response make sense given task + tool results?
⚠️ LLM judge cost creep: 1000 evals × judge call = LLM costs can exceed your actual product usage costs. Use open-source models (Llama, Mistral) hosted on your own infra for judges. Same intelligence, fraction of the cost. Alternatively: run deterministic scorers always, LLM judge only on failures.

Pre-fill: user asked to "set up Q3 project" → agent created it → user follow-up: "now assign the senior devs"
Mock: list_users returns [Ali, Sara] · assign_user returns "success"
