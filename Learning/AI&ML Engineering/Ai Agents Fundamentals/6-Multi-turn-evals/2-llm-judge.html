📜 BEFORE generateObject EXISTED — THE HACK
Developers needed structured output. LLMs only returned text.
Solution: define a fake tool with input schema. No execute(). Just grab the structured args the LLM passed in.
generateObject is the official, clean version of that same pattern. Same concept, no hacks.
JUDGE SCHEMA + IMPLEMENTATION 
// Schema — forces judge to return a number + reason, never prose
const judgeSchema = z.object({
  score:  z.number().min(1).max(10).describe("Score from 1-10 where 10 is perfect"),
  reason: z.string().describe("Brief explanation for the score")
});

export async function llmJudge(output: MultiTurnResult, target: MultiTurnTarget) {
  const result = await generateObject({
    model:             openai('gpt-4o'),   // stronger than agent model
    schema:            judgeSchema,
    schemaName:        'evaluation',
    schemaDescription: 'Evaluation of an AI agent response',
    providerOptions:   { openai: { reasoningEffort: 'high' } },
    messages: [
      { role: 'system', content: /* rubric — see below */ },
      { role: 'user',   content: `Task: ${target.originalTask}
Tools called: ${JSON.stringify(output.toolCallOrder)}
Tool results: ${JSON.stringify(target.mockToolResults)}
Agent response: ${output.text}` }
    ]
  });

  return result.object.score / 10; // convert 1-10 → 0-1 range
}
SCORING RUBRIC (system prompt)
10
Fully addresses task using tool results correctly
7–9
Mostly correct, minor issues
4–6
Partially addresses the task
1–3
Mostly incorrect or irrelevant
Why 1–10 not 0–1? LLMs struggle with floating point precision in structured outputs. Use integers, divide by 10 yourself.
💬
Ask for a reason
Forces the model to think before scoring. On non-reasoning models this alone dramatically improves score quality. Less critical on o1/o3 but still good practice.
🧠
Stronger model as judge
Judge must be at least as capable as the agent. Use GPT-4o or o1 to judge a gpt-4o-mini agent. Same model = blind spots overlap.
⚡
reasoningEffort: high
Tells reasoning models to think deeply before judging. Default is low/medium. For evals where accuracy matters, always set high.
⚠️ Don't tip off the judge. If your rubric hints at what "good" looks like in too much detail, smart models optimize for the rubric instead of actual quality. Keep criteria outcome-focused ("addresses the task") not method-focused ("mentions all 3 tool calls by name").
WHAT THE JUDGE RECEIVES (user message)
✦ originalTask — what the user asked for
✦ toolCallOrder — what tools the agent actually called
✦ mockToolResults — what those tools returned (known, deterministic)
✦ output.text — what the agent said to the user
→ Judge decides: given all of this, was the response correct?
WNP scenario: Task = "Who are the senior devs on the Q3 project?" · list_users returned [Ali, Sara] · Agent responded "The senior devs are Ali and Sara." → judge score: 10/10 (used tool result, directly answered). Agent responded "I found some users in the system." → judge score: 4/10 (vague, didn't use results to answer). Same tool call, very different quality — only LLM judge catches this.
