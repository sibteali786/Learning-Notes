MULTI-TURN EVALS

Wiring It All Together

Dataset + Executor + 3 Evaluators → evaluate(). The eval file is the thinnest layer — all the hard work is already done.
💡 The eval file is a thin wiring layer. It imports the executor, the evaluators, and the dataset — and hands them to evaluate(). The complexity lives elsewhere.
Writing the mock dataset is the highest-value activity. It forces you to think through exactly what your agent should and shouldn't do — before a single line of agent code is written.
MOCK TOOL ANATOMY (per tool)
EACH TOOL IN mockTools NEEDS 3 FIELDS
"description"
What the LLM sees to decide if it should call this tool. This is what you're evaluating.
→ Change this to improve tool selection evals.
"parameters"
Schema the agent uses to construct arguments. Must match real tool's shape.
→ Wrong schema = agent can't form valid call.
"mockReturn"
The fixed string returned when execute() fires. Agent reasons over this as if it were real.
→ Change this to test how agent handles edge cases (empty, error, partial data).
THE 3 TEST CASES — agent-multiturn.json
1
Fresh Task — Tool Preference
task-completion
PROMPT
"Read package.json and tell me the project name"
EXPECTED ORDER
["readFile"]
FORBIDDEN
["shell"] — could do cat but should prefer readFile
MOCK RETURN
{"name":"ai-agent-course","version":"1.0.0",...}
Tests tool category preference. If agent keeps using shell cat, fix: add "Always use readFile over shell for reading" to system prompt or tool description.
2
Mid-Conversation — Sequential Dependency
conversation-continuation
PRE-FILLED MESSAGES
user: "I'm working on Node.js…" → assistant: "Happy to help!" → user: "List src/ then read main entry"
EXPECTED ORDER
["listFiles", "readFile"] — must see index.ts from step 1 before reading it in step 2
listFiles RETURN
"index.ts\nApp.tsx\ncomponents/\nutils/"
readFile RETURN
"import {App} from './App';\nconsole.log(...);\nApp.run();"
Tests multi-step reasoning: agent must use listFiles result to determine which file to read next. Can't know index.ts without step 1.
3
Negative — Avoid Shell for File Ops
negative
PROMPT
"What files are in the src directory?"
EXPECTED ORDER
["listFiles"]
FORBIDDEN
["shell"] — ls src/ works but agent should use listFiles
MOCK RETURN
"index.ts\nApp.tsx\ncomponents/"
Same task solvable two ways. Tests that agent prefers the specific tool over the generic bash escape hatch.
THE 3 EVALUATORS
toolOrder
Binary · deterministic
Did tools fire in the expected sequence? Catches step 2 correct but step 1 wrong.
No target → return 1 (skip)
toolsAvoided
Binary · deterministic
Were all forbidden tools never called? Zero tolerance — one forbidden call = 0.
No forbiddenTools → return 1 (skip)
outputQuality
0–1 float · LLM judge
Did the final response correctly answer the task given the mock tool results? Semantic, not deterministic.
No target → return 1 (skip)
evaluate({
  data:     dataset,
  executor: async (data) => multiTurnWithMocks(data),
  evaluators: {
    toolOrder:     (output, target) => !target ? 1 : toolOrderCorrect(output, target),
    toolsAvoided:  (output, target) => !target?.forbiddenTools?.length ? 1 : toolsAvoided(output, target),
    outputQuality: async (output, target) => !target ? 1 : llmJudge(output, target),
  },
  config:    { projectApiKey: process.env.LMNR_API_KEY },
  groupName: 'agent-multiturn'
});
WHY MOCK TOOLS IN EVALS
✅ Reproducibility
Real file system changes between runs. Same mock = same result every run. Evals stay deterministic.
✅ Speed + Safety
No I/O, no network, no accidental deletes. Evals run fast and can't cause side effects.
✅ Edge cases on demand
Change mockReturn to "file not found" or "permission denied" to test failure paths without breaking anything real.
⚠️ Tradeoff
Not testing real tool implementations. That's what unit tests are for. Evals test decision-making, not tool code.
💡 Online eval → golden dataset pipeline: Thumbs up on a live conversation = add to golden dataset. Thumbs down = add to failures dataset, run targeted evals, fix, re-run. That's the production eval flywheel. Building it is a billion-dollar business.
