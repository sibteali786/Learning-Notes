RUNNING EVALS

Results, Debugging & the Whack-a-Mole Loop

Run → inspect failures → form hypothesis → change one thing → re-run. That's AI engineering.
💡 Every failure is a signal. Consistent failures = it's you. Random failures = non-determinism. The goal isn't 100% — it's knowing why you're not there.
You will never have enough evals. Every new tool or capability needs new data. This never stops.
RUNNING THE EVAL
▶️
npm run eval
Runs all evals. Each data point in the dataset = one executor call. 9 samples = 9 runs.
📊
Output: avg score
Laminar averages all scorer results. Scott got 88% avg selection score on first run.
📈
P90 matters most
Average can be skewed by outliers. P90 tells you what 90% of runs look like — the real reliability floor.
Naming tip: Use the name field as a commit message — describe what changed since last run. e.g. "Updated delete_file description to include 'remove' synonym". No description field in Laminar yet, so name is your only diff log.
DEBUGGING A FAILED RUN — THE LOOP
Score = 0 on a golden case
Example: "Remove the old backup.txt file" → expected delete_file → agent called nothing (or called list_files first).
Check: was it your eval setup?
Did you forget to include delete_file in the tools list for that data point? Verify first — don't chase a prompt fix for your own mistake.
Form a hypothesis
Options: tool description is ambiguous · prompt uses "remove" but description says "delete" · reasoning model is over-cautious about destructive ops · system prompt missing permission signal.
Change ONE thing → re-run
Don't change 5 things at once — you won't know what worked. Change description, or prompt wording, or reasoning_effort, or system prompt. One at a time.
Score ↑? Commit. Score same? Try next hypothesis.
Merge to main only when evals don't drop. No drop or going up = green light. Consistent failures after multiple fixes → architectural change needed.
REAL FAILURES FROM THIS LESSON + FIXES
Prompt Expected What happened Fix
"Remove the old backup.txt" delete_file No tool called / called list_files first Add to system prompt: "If user asks to delete, call delete_file directly. Approvals happen elsewhere." Use word "delete" not "remove" in golden data.
"What's in this project, show me around" list_files No tool called Changed description from "list all files in a directory" → "list all files in a directory or project". One word fix, eval passed.
⚠️ Reasoning model (o1) gotcha: Reasoning models are trained to be cautious with destructive ops (delete, overwrite). Don't over-instruct them — they perform worse when told what to do step-by-step. Instead: increase reasoning_effort: 'high' and give permission signals in system prompt.
providerOptions: { openai: { reasoningEffort: 'high' } } in your executor config.
BONUS: DYNAMIC TOOL SELECTION (advanced)
When you have 50+ tools, passing all of them degrades selection quality. Solution: give the agent a toolbox with just 2 tools.
🔍
search_tool
Semantic search over tool descriptions + examples. Returns top 5 relevant tool IDs.
⚙️
install_tool
Fetches tool definitions by ID and adds them to the agent's active tool set for this run only.
Store installed tool IDs in DB per run → load definitions each loop → agent always has 5 relevant tools, not 50. Boost search quality by adding example prompts alongside tool descriptions for better semantic matching.
