AGENT LOOP — IMPLEMENTATION

Building run.ts from Scratch

streamText + messages[] + tool execution + callbacks = a working conversational agent.
💡 The messages[] array IS the agent's memory.
Whatever is in it = truth. Whatever isn't = never happened. You can fake, manipulate, or surgically remove anything.
The LLM doesn't store state. It only sees what you put in messages[]. Every loop iteration = fresh LLM call with a growing array.
MESSAGES[] — THE 4 ROLES
system
Hidden instructions, personality, context. Always first. Never shown to user. Gets less critical as reasoning models improve.
↓
user
User's message. If last message in array = user → LLM responds. If last = assistant → LLM waits. Always end with user to trigger response.
↓
assistant
LLM's response — text and/or tool calls. Must be pushed back into messages[] or LLM won't remember it said anything.
↓
tool
Tool execution results. Must include toolCallId to match the original request. All tool results must be strings. OpenAI errors if next message after tool-call isn't a tool result.
THE LOOP — STEP BY STEP
Setup messages[]
filterCompatibleMessages() strips UI-only objects from history. Then: [system, ...history, user]. UI sees rich objects; LLM only sees what's compatible.
Call streamText (no await)
Same args as generateText — model, messages, tools, telemetry. Returns an async iterable, not a promise. Tokens flow as generated.
for await chunk of result.fullStream
Each chunk has a type. Handle two types — text-delta and tool-call. Wrap in try/catch; collect streamError to handle gracefully.
text-delta → append to currentText + callbacks.onToken()
tool-call → push {toolCallId, toolName, args} to toolCalls[] + callbacks.onToolCallStart()
Check finishReason
await result.finishReason — waits for stream to fully complete before checking.
≠ "tool-calls" OR toolCalls.length === 0 → push responseMessages → break
=== "tool-calls" → push responseMessages → execute tools → loop again
Execute tools → push results
For each toolCall: executeTool(name, args) → push {role:"tool", content:[{type:"tool-result", toolCallId, toolName, output:{type:"text", value:result}}]}. Result MUST be a string.
Loop back → LLM sees new messages
Only thing that changed = messages[]. LLM sees tool results, decides next action. This continues until no tool calls or a stop condition fires.
CORE LOOP — run.ts 
// messages[] bootstrap
const messages: ModelMessage[] = [
  { role: 'system',    content: SYSTEM_PROMPT },
  ...workingHistory,              // filtered conversation so far
  { role: 'user', content: userMessage }
];

while (true) {
  const result = streamText({ model, messages, tools }); // no await
  const toolCalls: ToolCallInfo[] = [];
  let currentText = '';

  for await (const chunk of result.fullStream) {
    if (chunk.type === 'text-delta')  { currentText += chunk.text; callbacks.onToken(chunk.text); }
    if (chunk.type === 'tool-call')   { toolCalls.push({ toolCallId: chunk.toolCallId, toolName: chunk.toolName, args: chunk.input }); }
  }

  const finishReason = await result.finishReason;

  // BREAK CASE 1: done — no tool calls needed
  if (finishReason !== 'tool-calls' || toolCalls.length === 0) {
    messages.push(...(await result.response).messages);
    break;
  }

  // Tool calls path — push assistant message first
  messages.push(...(await result.response).messages);

  // Execute each tool, push result back
  for (const tc of toolCalls) {
    const res = await executeTool(tc.toolName, tc.args);
    messages.push({
      role: 'tool',
      content: [{ type: 'tool-result', toolCallId: tc.toolCallId, toolName: tc.toolName, output: { type: 'text', value: res } }]
    });
  }
  // loop continues — LLM sees new messages on next iteration
}
⚠️ toolCallId is sacred. The LLM generates it. You must echo it back exactly in the tool result. Wrong/missing ID = OpenAI API error. It's how the LLM matches "I asked you to do X" with "here's the result of X" when multiple tools run in parallel.
CALLBACKS — UI BRIDGE
The loop is pure logic. It doesn't know about any UI. Callbacks are the hook that lets the terminal/browser react to events.
onToken(text)
Streams each text token to the terminal as generated. This is the "typing" effect.
onToolCallStart(name, args)
Shows tool name + spinner in UI. User knows agent is doing work, not frozen.
onToolCallEnd(name, result)
Stops spinner. Optionally show result preview (careful — raw JSON = bad UX for non-devs).
onComplete(fullResponse)
Loop is done. Final full response string. Used to persist, display summary, etc.
COMMON PITFALLS
♾️
Infinite loop
Model keeps calling tools. Add maxIterations counter as safety net — always.
👻
Forgetting to push assistant message before tool results
Must push responseMessages.messages first, then push tool results. OpenAI requires tool result to immediately follow the tool call that requested it.
🔤
Tool result isn't a string
Everything returned to the LLM must be a string. JSON objects are fine — JSON.stringify() them. Raw objects will break or get ignored.
🎭
UI messages in LLM messages[]
Rich UI objects (spinners, status cards, approvals) must be stripped via filterCompatibleMessages() before sending to LLM. LLM will error on unknown message shapes.
🔀
Not aborting tool calls gracefully
To abort a tool call: just don't push it into messages[]. LLM never knew it asked. No error thrown — the array is the truth.
WNP scenario: User says "Set up the Q3 project and assign all senior devs to it."
Loop iteration 1 → LLM calls list_users(role:"senior") → result: [Ali, Sara, Omar]
Loop iteration 2 → LLM calls create_project("Q3") → result: projectId=42
Loop iteration 3 → LLM calls assign_user × 3 in parallel → all results pushed with matching toolCallIds
Loop iteration 4 → finishReason = "stop" → LLM responds: "Done! Q3 project created and 3 devs assigned." → break.
Key: messages[] = truth · streamText chunks · finishReason check · toolCallId matching · always push before looping
