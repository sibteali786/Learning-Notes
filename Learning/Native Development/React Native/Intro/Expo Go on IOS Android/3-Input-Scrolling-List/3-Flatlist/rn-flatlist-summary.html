Chapter 7.3

ScrollView vs FlatList — When to Use Which

Decision Rule
SituationUseWhy
Mixed content (text, images, sections) that might overflow ScrollView Renders everything at once — fine for short, heterogeneous content
Array of items mapped to identical-shaped rows FlatList ✓ Virtualizes rendering — only mounts visible items. Essential for 20+ items.
Full-screen list (Instagram feed, chat, shopping list) FlatList ✓ ScrollView + .map() renders all 1000 items immediately — sluggish UI
★ Kadi's rule from transcript: "If you have an array of items you map over, you should not use a ScrollView." FlatList is the correct tool whenever data is array-shaped, regardless of list length — for correctness and future-proofing.

How Virtualization Works

Concept

FlatList tracks the visible window and only mounts items near the viewport. Items far above/below are unmounted to save memory.

ScrollView + .map()
Item 1 (rendered)
Item 2 (rendered)
Item 3 (rendered)
Item 4 (rendered)
... 996 more

All 1000 mounted at once

FlatList ✓
Item 1 ← visible
Item 2 ← visible
Item 3 ← visible
Item 4 (buffer)
Item 5+ (unmounted)

~129/1000 mounted at a time

From the transcript — live demo

Kadi tested 1,000 items. Only 129 rendered at initial load. As you scroll, more are mounted and off-screen ones are unmounted. This is the entire value of FlatList over ScrollView.

💡 renderItem is the key: FlatList can virtualize because it calls renderItem on-demand per item, rather than rendering everything at once like .map().

FlatList — Complete API for This Chapter

Code
- import { ..., ScrollView } from "react-native"; + import { ..., FlatList, View, Text } from "react-native"; <FlatList // ─── Data ─────────────────────────────────────────── data={shoppingList} // your array renderItem={({ item }) => ( // called per visible item <ShoppingListItem name={item.name} /> )} // keyExtractor not needed — data has .id field // ─── Slots ────────────────────────────────────────── ListHeaderComponent={ // not a function — avoids remount! <TextInput value={value} onChangeText={setValue} placeholder="E.g Coffee" returnKeyType="done" onSubmitEditing={handleSubmit} style={styles.textInput} /> } ListEmptyComponent={ <View style={styles.listEmptyContainer}> <Text>Your shopping list is empty</Text> </View> } // ─── Inherited from ScrollView ────────────────────── style={styles.container} contentContainerStyle={styles.contentContainer} stickyHeaderIndices={[0]} />
data + renderItem

Core props. renderItem receives { item, index, separators }. Destructure item for the row data.

keyExtractor

Optional if your objects have .id or .key — auto-used. Only needed when objects use a different unique field.

Bonus built-ins

onRefresh (pull-to-refresh), scrollToIndex(), ListFooterComponent, numColumns for grid layouts.

Critical Gotcha — ListHeaderComponent as JSX, Not Function

Trap
❌ Wrong — function wrapper

Every state change re-creates the component → TextInput unmounts → keyboard disappears mid-typing.

ListHeaderComponent={() => <TextInput ... />}
✓ Correct — JSX directly

Stable reference → TextInput stays mounted → keyboard stays open.

ListHeaderComponent={<TextInput ... />}
★ Same rule applies to ListEmptyComponent and ListFooterComponent. Pass JSX elements directly, not arrow functions returning JSX — unless the component truly needs to be re-created on each render for a reason.
