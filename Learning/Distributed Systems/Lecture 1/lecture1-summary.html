0:00 Distributed Systems — Why Bother?

Definition, motivations, and what makes them hard
  • Definition: cooperating computers communicating over a network to accomplish a coherent task (storage for big websites, MapReduce-style big data, P2P systems).
  • Rule #1: if a single computer can do the job — do it that way. Distributed systems are never simpler.

4 Reasons to Go Distributed

  • Performance via parallelism (CPUs, disks, memory)
  • Fault tolerance (failover between replicas)
  • Physical necessity (data inherently spread out, e.g. banks in different cities)
  • Security / isolation (untrusted code split across machines)

3 Reasons They're Hard

  • Concurrency — many parts executing at once
  • Partial failures — some pieces work, others don't (unlike a single PC which mostly just works or crashes)
  • Hard to actually achieve promised speed-up
Real-life example: a bank transfer between NYC and London isn't a design choice — the computers are physically in different places and must cooperate over a network.

23:17 Scalability

2x computers → 2x performance (the dream, and why it breaks)
  • Scalable speedup: doubling machines should double throughput — huge win because you buy it with money, not costly re-engineering.
  • Classic pattern: add more web servers in front of a single shared database. Works great — until the database becomes the bottleneck.

Real-life example: Reddit-style site adds 100 web servers to handle traffic — fine, until all 100 hammer one database and reads/writes start queueing. Fixing it means redesigning storage (sharding), which is real engineering work, not just "buy more machines."

29:21 Failure at Scale

Why rare events become routine
  • A single reliable server might run for years without a crash.
  • With 1,000 servers, even at "1 failure/year/machine," you get roughly ~3 failures every day — something is always broken.
  • Failure-handling must be a first-class part of the design, not an afterthought — because it's not "if," it's "constantly."

31:33 Availability & Recoverability

Two flavors of fault tolerance, and the two big tools

Availability

System keeps serving correctly through certain failures (e.g., one replica dies, the other keeps going).

Recoverability

System may stop entirely on failure, but resumes correctly once repaired (e.g., after power comes back).

  • Tool 1 — Non-volatile storage: checkpoints/logs on disk so you can recover state after a crash (writing it is expensive, so a lot of engineering goes into minimizing this).
  • Tool 2 — Replication: keep multiple copies; the hard part is keeping replicas from silently drifting out of sync.

37:15 Consistency

What should get(key) actually return?
  • With one copy of data, put/get semantics are obvious. With replicas, they're not — a crash mid-update can leave replicas disagreeing.
  • Strong consistency: a get returns the value of the most recently completed put. Simple to reason about, but expensive — often requires contacting every replica.
  • Weak consistency: gets may return stale data for an unbounded time, in exchange for much lower latency/communication cost.
  • Geographically distant replicas (different cities, for independent failure domains) make strong consistency very costly — tens of milliseconds per operation just from speed-of-light network delay.
Real-life example: a client writes key=1 → 21 to Replica A, then crashes before updating Replica B (still holds 20). A later get(1) may return 21 or 20 depending on which replica answers — inconsistent unless the system enforces a strong-consistency rule.

46:50 MapReduce — The Programming Model

Google's answer: let engineers write map/reduce, not distributed systems
  • Origin: Google, ~2004, built to index/analyze the entire web (tens of TB) without every engineer becoming a distributed-systems expert.
  • Idea: programmer writes a simple map(k,v) and reduce(k, values[]); the framework handles parallelism, data movement, and failures.

Worked example — Word Count:
map("f1", "a b") → (a,1) (b,1)  |  map("f2", "b") → (b,1)  |  map("f3", "a c") → (a,1) (c,1)
Shuffle groups by key: a→[1,1], b→[1,1], c→[1]
reduce("a",[1,1]) → 2  |  reduce("b",[1,1]) → 2  |  reduce("c",[1]) → 1
  • A full run is a job; each map or reduce call is a task.
  • Chained MapReduce jobs are common (e.g. Google's PageRank ran as repeated MapReduce iterations).
  • Limitation: only fits "map → shuffle → reduce" shaped computations; multi-stage pipelines need several chained jobs (later systems generalize this).

50:04 MapReduce — Under the Hood

Master/worker architecture, GFS, and the network bottleneck
  • Master + workers: a master server assigns map/reduce tasks to worker machines.
  • Map output is written to the local disk of the worker that ran it (no network needed yet).
  • Shuffle is where the network gets hit hard: each reduce worker must fetch its key's data from every map worker's local disk — output size ≈ input size (e.g., 10 TB in → 10 TB shuffled).
  • GFS (Google File System): cluster file system splitting big files into 64MB chunks across the same machines that run MapReduce, keeping 2–3 replicas for fault tolerance.

Key optimization (2004-era)

Network was the bottleneck (~50 Mbps/machine share of the root switch). Google's fix: co-locate GFS and MapReduce on the same machines, and schedule each map task on the machine that already stores its input — turning network reads into local disk reads. Reduce output still had to cross the network once, to satisfy GFS's replication.

Real-life example: modern data centers use multiple root switches instead of one, giving far more bandwidth — which is why later MapReduce versions stopped bothering to co-locate compute with data at all.

Loose ends
  • Chained MapReduce jobs: yes, routine — output of one job feeds the next (e.g., iterative PageRank).
