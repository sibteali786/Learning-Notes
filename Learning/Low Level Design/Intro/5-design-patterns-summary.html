Design Patterns

Reusable structures for recurring design problems — the ~7 that actually show up in LLD interviews (not all 23 GoF)

🧩 Why so few patterns matter

Gang of Four (1994) catalogued 23 patterns for C++/Smalltalk. Most don't matter anymore — modern languages absorbed half as primitives (iterators), and composition/functional style made others obsolete. You'll get asked about ~5 in interviews, not 23.
The #1 mistake: forcing a pattern where it doesn't belong. Patterns should arise from good design decisions, not drive them. Only use one when the problem naturally calls for it.
Regional note: US interviews usually don't test whether you can name patterns — they evaluate design quality. India-region interviews more often ask about patterns directly. Be ready for either.

🏗️ Creational Patterns

Control how objects get created — hide construction, swap implementations, avoid tight coupling
Factory Method POLARIZING

A helper that creates the right object so you don't decide which one. Hides creation logic, keeps code flexible when the needed type varies.

Trigger phrases: "support different notification types," "handle multiple payment methods"
interface Notification { send(message: string): void } class EmailNotification implements Notification { send(m) {...} } class SMSNotification implements Notification { send(m) {...} } class NotificationFactory { static create(type: string): Notification { if (type === "email") return new EmailNotification() if (type === "sms") return new SMSNotification() throw new Error("Unknown type") } } // Usage const notif = NotificationFactory.create("email") notif.send("Hello")
Add push notifications → update the factory only. Rest of the code never changes.
Note: this is technically "Simple Factory," not GoF's Factory Method (which uses abstract factory classes + subclasses overriding a factory method — more complex, rarely shows up in real code/interviews). What's shown here is what people actually build and what "use a factory" means in practice.
Builder RARE FIT

Create a complex object step-by-step without worrying about order/messy construction. Use for objects with many optional parts.

class HttpRequest { private url?: string private method?: string private headers = new Map() private body?: string private constructor() {} static Builder = class { private request = new HttpRequest() url(url) { this.request.url = url; return this } method(method) { this.request.method = method; return this } header(key, value) { this.request.headers.set(key, value); return this } body(body) { this.request.body = body; return this } build() { if (!this.request.url) throw new Error("URL is required") return this.request } } } // Usage const request = new HttpRequest.Builder() .url("https://api.example.com") .method("POST") .header("Content-Type", "application/json") .body('{"key": "value"}') .build()
Reality check: most interview problems involve simple domain objects with 2-4 required fields — a normal constructor works fine. If the interviewer didn't describe a complex object with lots of optional details, Builder probably isn't needed. In TypeScript specifically, a config object with Partial<T> is often simpler than implementing this pattern.
Singleton USUALLY UNNEEDED

Ensures only one instance of a class exists — shared config manager, connection pool, logger.

class DatabaseConnection { private static instance: DatabaseConnection private constructor() {} static getInstance(): DatabaseConnection { if (!DatabaseConnection.instance) { DatabaseConnection.instance = new DatabaseConnection() } return DatabaseConnection.instance } query(sql: string): void {...} } // Usage const db = DatabaseConnection.getInstance()
Most of the time you don't need this. Passing shared objects through constructors is clearer and easier to test — Singletons hide dependencies and make testing harder. If asked "should this be a Singleton?", the answer is usually no unless they explicitly want one shared instance across the whole system.
Thread-safe Singleton implementations exist, but interviewers don't expect you to implement them in LLD rounds. In modern TS/JS, ES modules are singletons by default — prefer export const db = new DatabaseConnection() over this pattern.

🔗 Structural Patterns

How objects connect — flexible relationships without tight coupling
Decorator LESS COMMON

Adds behavior to an object without changing its class — layers extra functionality at runtime.

Trigger phrases: "add logging to specific operations," "encrypt certain messages," "optional features," "stack behaviors," "combine multiple enhancements"
interface DataSource { writeData(data: string): void readData(): string } class FileDataSource implements DataSource {...} class EncryptionDecorator implements DataSource { constructor(private wrapped: DataSource) {} writeData(data) { this.wrapped.writeData(this.encrypt(data)) } readData() { return this.decrypt(this.wrapped.readData()) } } class CompressionDecorator implements DataSource { constructor(private wrapped: DataSource) {} writeData(data) { this.wrapped.writeData(this.compress(data)) } readData() { return this.decompress(this.wrapped.readData()) } } // Usage let source: DataSource = new FileDataSource("data.txt") source = new EncryptionDecorator(source) source = new CompressionDecorator(source) source.writeData("sensitive info") // compressed, then encrypted, then written
Why not just subclass? Avoids combinatorial explosion — LoggedEmailNotification, EncryptedEmailNotification, LoggedEncryptedEmailNotification... Instead you wrap and stack.
Decorator vs. Subclass — the decision rule: if behavior depends on runtime conditions (debug-mode logging, per-request caching) → Decorator. If it's a predefined, fixed type difference → Subclass.
Facade YOU ALREADY DO THIS

A coordinator class that hides complexity. You're probably already building these without naming them — your orchestrator IS a facade.

Example: Tic Tac Toe's Game class coordinates Board, Player, and state — caller just does game.makeMove(row, col) and never touches internals.
class Game { private board: Board private playerX: Player private playerO: Player private currentPlayer: Player private state: GameState makeMove(row, col): boolean { // Coordinates board, player, and state logic // Caller doesn't need to understand internal details if (this.state !== GameState.IN_PROGRESS) return false if (!this.board.placeMark(row, col, this.currentPlayer.getMark())) return false if (this.board.checkWin(row, col)) this.state = GameState.WON else if (this.board.isFull()) this.state = GameState.DRAW else this.currentPlayer = (this.currentPlayer === this.playerX) ? this.playerO : this.playerX return true } }
The pattern name mostly matters when wrapping existing messy code with awkward APIs. In LLD interviews you're designing clean orchestrators from scratch — same structure, you just don't need to announce the name.

🎬 Behavioral Patterns

Control how objects interact — flow of control and communication
Strategy #1 MOST COMMON — LEARN THIS ONE

Replaces conditional logic with polymorphism. Different ways of doing the same thing, swappable at runtime (vs. compile-time, where behavior is fixed in the class definition).

Trigger: a pile of if/else or switch statements based on type — that's Strategy waiting to happen. (Same idea as the vehicle-type example from OOP Concepts.)
interface PaymentStrategy { pay(amount: number): boolean } class CreditCardPayment implements PaymentStrategy { pay(amount) {...} } class PayPalPayment implements PaymentStrategy { pay(amount) {...} } class ShoppingCart { private paymentStrategy?: PaymentStrategy setPaymentStrategy(strategy) { this.paymentStrategy = strategy } checkout(amount) { this.paymentStrategy!.pay(amount) } } // Usage cart.setPaymentStrategy(new CreditCardPayment("1234-5678")) cart.checkout(100.00) cart.setPaymentStrategy(new PayPalPayment("user@example.com")) cart.checkout(50.00)
Strategy vs Factory: Factory decides which type to instantiate. Strategy decides which behavior to use after the object already exists. Strategy = polymorphism with a pattern name.
Observer TOP-TIER INTERVIEW PATTERN

Objects subscribe to events, get notified when something happens. Changes in one object trigger updates in others.

Trigger phrases: "notify," "update multiple components" — e.g. stock price changes → multiple displays update; order placed → inventory, notifications, analytics all react.
interface Observer { update(symbol: string, price: number): void } interface Subject { attach(observer: Observer): void detach(observer: Observer): void notifyObservers(): void } class Stock implements Subject { private observers: Observer[] = [] setPrice(price) { this.price = price this.notifyObservers() // Price changed, tell everyone } notifyObservers() { for (const observer of this.observers) observer.update(this.symbol, this.price) } } class PriceDisplay implements Observer { update(symbol, price) { console.log(`Display updated: ${symbol} = $${price}`) } } class PriceAlert implements Observer { constructor(private threshold: number) {} update(symbol, price) { if (price > this.threshold) console.log(`Alert! ${symbol} exceeded $${this.threshold}`) } } // Usage stock.attach(display); stock.attach(alert) stock.setPrice(145.00) // both observers notified
The stock doesn't need to know what observers do with the info — full decoupling between the event source and the reactors.
State Machine LESS COMMON, BUT BECOMES THE CENTERPIECE

Handles state transitions cleanly. Use when an object's behavior changes based on internal state with complex transition rules. (Also called "State pattern.")

Trigger: the word "state" appears multiple times in requirements — vending machines, document workflows, game states.
interface VendingMachineState { insertCoin(machine): void selectProduct(machine): void dispense(machine): void } class NoCoinState implements VendingMachineState { insertCoin(machine) { machine.setState(new HasCoinState()) } selectProduct(machine) { /* "Insert coin first" */ } dispense(machine) { /* "Insert coin first" */ } } class HasCoinState implements VendingMachineState { insertCoin(machine) { /* "Coin already inserted" */ } selectProduct(machine) { machine.setState(new DispenseState()) } dispense(machine) { /* "Select product first" */ } } class DispenseState implements VendingMachineState { dispense(machine) { // "Dispensing product" machine.setState(new NoCoinState()) } } class VendingMachine { private currentState: VendingMachineState = new NoCoinState() insertCoin() { this.currentState.insertCoin(this) } selectProduct() { this.currentState.selectProduct(this) } dispense() { this.currentState.dispense(this) } setState(state) { this.currentState = state } }
Interview tip: draw a state diagram — circles for states, labeled arrows for transitions. Interviewers appreciate the visual; it shows clear thinking about the problem.
If a state machine is in your design, it's probably the centerpiece — the interview will likely be organized around walking through it.

📋 Wrapping Up — Cheat Sheet

Most interview-ready designs use no patterns, or at most one or two. Reaching for 3+ patterns = you're probably over-engineering.

Creational

Factory → callers shouldn't care which concrete class gets created
Builder → lots of optional fields / messy construction
Singleton → need one global instance (rare)

Structural

Decorator → layer optional behaviors at runtime, avoid subclass explosion
Facade → hide internal complexity behind a simple entry point

Behavioral

Strategy → replace if/else with interchangeable behaviors
Observer → multiple components react to one event
State Machine → behavior depends on current state, transitions get messy
Final takeaway: focus on solving the problem cleanly — name the pattern afterward, only if it helps communicate.
