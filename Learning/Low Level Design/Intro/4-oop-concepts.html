OOP Concepts

The language mechanisms that implement the design principles — Encapsulation, Abstraction, Polymorphism, Inheritance

🔧 Why this page exists

Design Principles taught you how to think about clean code. OOP concepts are the mechanisms your language gives you to actually implement those ideas. Four core concepts, each covered as: what it is → why interviewers care → how it shows up in real LLD problems.

🔒 Encapsulation

Keep an object's data private; let the object control how that data is used
Interact through simple methods, not by reaching in and changing internals directly.
Benefit — predictability: when Account owns balance and only lets you change it via deposit()/withdraw(), you can enforce rules there — prevent negative balances, log transactions, update related state. Public field = no guarantee those rules run.
❌ Bad — public spots
class ParkingLot { public spots: ParkingSpot[] = [] }
✅ Good — private + controlled access
class ParkingLot { private spots: ParkingSpot[] = [] parkVehicle(vehicle): boolean { const spot = this.findAvailableSpot(vehicle) if (!spot) return false spot.occupy(vehicle) return true } getSpots(): ParkingSpot[] { return [...this.spots] // return a copy } }
Interview hygiene check: do your classes expose fields directly, or provide methods? Are you returning references to mutable internal collections, or copies? Rule of thumb: when in doubt, write the getter — and if returning a collection, return an unmodifiable view or copy.

🎭 Abstraction

Expose only what's essential; hide implementation details behind clear interfaces
Define what something can do without revealing how. Benefit = simplification — swap implementations (Stripe API vs. stored tokens) without touching the caller.
❌ Bad — tightly coupled to StripeAPI
class OrderService { private apiKey = "" checkout(order: Order): void { const stripe = new StripeAPI() stripe.setApiKey(this.apiKey) stripe.createCharge(order.total, order.creditCard) } }
✅ Good — depends on PaymentMethod interface
interface PaymentMethod { process(amount: number): boolean } class CreditCardPayment implements PaymentMethod {...} class PayPalPayment implements PaymentMethod {...} class OrderService { constructor(private paymentMethod: PaymentMethod) {} checkout(order: Order): void { this.paymentMethod.process(order.total) } }
When to reach for it: where there's real complexity — lots of variations, rules, or messy details. In interviews: logic feels tangled, or requirements suggest multiple approaches → good signal to introduce an abstraction.
The hard part — right level of abstraction: too abstract → meaningless interface names (doWork(), handleRequest()). Too specific → you haven't actually abstracted anything. Think about what operations the caller needs, not how they happen internally.

🔀 Polymorphism

What replaces if/switch statements on type — same method call, each object handles itself
Naturally follows from abstraction. Define an interface (Vehicle) → each implementation provides its own behavior. No type checking required.
❌ Bad — type checks
parkVehicle(v: Vehicle): boolean { if (v.type === "car") { const spot = this.findSpotBySize("regular") return spot !== null } else if (v.type === "motorcycle") { ... } else if (v.type === "truck") { ... } return false }
✅ Good — polymorphic dispatch
interface Vehicle { getRequiredSpotSize(): SpotSize } class Car implements Vehicle { getRequiredSpotSize() { return "regular" } } class Motorcycle implements Vehicle { getRequiredSpotSize() { return "motorcycle" } } parkVehicle(v: Vehicle): boolean { const required = v.getRequiredSpotSize() const spot = this.findSpotBySize(required) return spot !== null }
Payoff: add a new vehicle type → just create a new class implementing Vehicle. ParkingLot code never changes.
Tradeoff to voice in interviews: highly polymorphic code can be hard to trace/debug as implementations grow. Companies vary in tolerance — some prefer explicit branches per type, others embrace the extensibility. Signal: if you're writing type checks or switch statements on an enum, that's your cue to use polymorphism instead.

🧬 Inheritance

One class as a more specific version of another — powerful, but comes with tight coupling
A tool for sharing implementation. Big cost: the "fragile base class" problem — any parent change can break every child.
Safer default: composition + interfaces. You still get abstraction and polymorphism, without forcing a parent-child relationship or shared state.
✅ When inheritance works — stable, shared implementation abstract class BankAccount { protected balance = 0 deposit(amount): void { this.balance += amount } withdraw(amount): boolean { if (this.balance < amount) return false this.balance -= amount return true } getBalance(): number { return this.balance } } class SavingsAccount extends BankAccount { private interestRate: number constructor(rate) { super(); this.interestRate = rate } } class CheckingAccount extends BankAccount { private overdraftLimit: number constructor(limit) { super(); this.overdraftLimit = limit } }
Why it fits here: both subclasses are genuinely forms of BankAccount — deposit/withdraw/balance logic is identical, and neither needs to override inherited behavior in ways that break the parent's contract.
❌ When it breaks down — modeling behavior differences class Car { startEngine(): void { /* gasoline logic */ } } class ElectricCar extends Car { startEngine(): void { /* completely different — electric motor */ } }
Electric cars don't have engines — no shared logic. You're forcing a behavior difference into a hierarchy. Add a hybrid? Doesn't extend cleanly from either Car or ElectricCar.
✅ Fix — composition for behavior variation interface Drivetrain { start(): void } class GasEngine implements Drivetrain { start() {...} } class ElectricMotor implements Drivetrain { start() {...} } class Car { constructor(private drivetrain: Drivetrain) {} start(): void { this.drivetrain.start() } }
Want a hybrid? Give it two drivetrains. Want hydrogen? Add a new Drivetrain implementation. Car class never changes.
Interview default: reach for interfaces + composition first. Only use inheritance when sharing stable implementation across classes. In most LLD interviews, you don't need inheritance at all.

📋 Putting It Together

Don't recite the terms — the concepts should show through in how you design, not what you name.
Encapsulation → Hide state, expose behavior. Private fields, methods for access.
Abstraction → Define interfaces for variations. Multiple payment methods? Different vehicle types? → interface.
Polymorphism → Let objects handle themselves. No type checking, no switch on types.
Inheritance → Compose behavior, don't inherit it. Interfaces first; inheritance only for sharing stable implementation.
The trigger to remember: "support multiple X" in requirements → you know to define an interface. Writing type checks → switch to polymorphism instead.
