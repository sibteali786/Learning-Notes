Low-Level Design in a Hurry

Lecture 1 — Introduction · Hello Interview

🎯 What is this interview?

You're given a self-contained system — Parking LotElevatorConnect Four — and asked to design the classes, interfaces, and relationships that make it work. Also called Object-Oriented Design (OOD) — same interview, different name.
Focus = code organization: right objects, clean interactions, methods that make sense, extendable without rewrites.

🗺️ LLD vs System Design

System DesignLow-Level Design
LevelArchitecture at scaleA single feature/service
OutputBoxes & arrows (services)Classes, methods, state machines
TopicsTraffic, storage, caching, shardingObjects, encapsulation, patterns
CodingNonePseudocode / real code
Analogy: System Design is the map of a city. Low-Level Design is the blueprint for one building on that map.

🌍 Regional Variants

US Big Tech
  • Real code (Java/Python/C++), not just pseudocode
  • Patterns matter less by name — reasoning > vocabulary
  • Requirements are more defined upfront
India / Asia
  • Structured pseudocode is enough
  • Interviewers expect you to name the pattern (Factory, Strategy, etc.)
  • Requirements are vaguer — you must ask more to scope it
Tip: Unsure what your interview expects? Just ask your recruiter — they'll tell you directly.

💡 Example: Ride-Sharing, Two Ways

System Design view

Ride Service, Matching Service, Location Service, DB, Queue — how they scale & talk over the network.

LLD view

A Trip class, a TripState enum, a PricingCalculator interface — how they collaborate in-process.

Real scenario: trip.startTrip() throws if state isn't DRIVER_ASSIGNED — that guard-rail logic (not network calls) is the whole game in LLD.
