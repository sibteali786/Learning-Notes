Low-Level Design Delivery Framework

Full lecture + your Q&A, folded together — the 5-step structure for a ~35 min LLD interview

⏱️ Why you need a framework at all

35 minutes to clarify requirements, define your object model, design class APIs, and walk through core logic. Most candidates lose points on pacing, not knowledge.
Failure mode 1: Dive straight into code, get bogged down in edge cases before the interviewer even understands your structure.
Failure mode 2: Move too slow through setup, define every tiny detail, run out of time before showing real design.
Golden rule: if your interviewer pulls you off-framework to probe something, follow their lead — don't fight it. Just gently steer back after.

1️⃣ Requirements

~5 minutes
Prompt is intentionally minimal ("Design Tic Tac Toe"). Turn it into a spec by asking questions across 4 themes:
ThemeAsk
Primary capabilitiesWhat operations must this system support?
Rules & completionWhat conditions define success, failure, or state transitions?
Error handlingHow should invalid inputs/actions be handled?
Scope boundariesWhat's in scope (core logic, rules) vs out (UI, storage, networking, concurrency, extensibility)?
Tic Tac Toe example output:
Requirements: alternating X/O on 3×3 grid · win via row/col/diagonal · draw if board full & no winner · reject invalid moves (occupied cell, move after game over) · query state + reset.
Out of scope: UI, AI opponent, networked multiplayer, NxN grids, undo/redo.
Tip: Write down what's explicitly not being built too — prevents scope creep later.

2️⃣ Entities & Relationships

~3 minutes
Step A — Identify entities. Scan requirements, pull out meaningful nouns. Apply the filter:
  • Entity — maintains changing state or enforces rules
  • Field — just information attached to something else
Parking Lot: ParkingSpot is its own entity — state flips available→occupied, enforces "can this vehicle fit?". A car's licensePlate is just data → a field on Vehicle. ParkingLot - spots: List<ParkingSpot> ParkingSpot - spotId, size, parkedVehicle + canFit(vehicle) + park(vehicle) + unpark() Vehicle - licensePlate, vehicleType
Step B — Define relationships. Ask 4 questions:
  • Which entity is the orchestrator — drives the main workflow?
  • Which entities own durable state?
  • How do they depend on each other? (has-ausescontains)
  • Where should specific rules logically live?
Parking Lot: ParkingLot has-a List<ParkingSpot> uses ParkingSpot.findAvailableFor(vehicle) uses TicketService.createTicket(vehicle, spot) "Can this vehicle fit?" → lives in ParkingSpot (owns size/occupancy). "Assign spot + create ticket" → lives in ParkingLot (coordinates multiple objects).
Whiteboard tip: just a list of entities + a few arrows for ownership/usage is enough. No formal UML needed — don't fixate on notation, just communicate structure clearly.
Entities: Game, Board, Player Relationships: Game → Board, Game → Player (2x)

🎯 Deep Dive: What is an Orchestrator?

An entity that coordinates other entities to complete a workflow — manages the sequence, while each supporting entity keeps its own data & rules.
SystemOrchestratorWhy
Tic Tac ToeGameChecks turn, asks Board to place a mark, decides win/draw, switches players
TicketmasterBookingServiceChecks user, asks SeatInventory for seat status, creates reservation, starts payment
Parking LotParkingLotFinds a spot, parks the vehicle, creates a ticket
BookingService has-a SeatInventory uses ReservationService uses PaymentService SeatInventory - seats + isAvailable(seatId) + markReserved(seatId) ReservationService - reservations + createHold(userId, seatId, expiresAt)
Why isn't SeatInventory the orchestrator? It owns seat state (is A12 available? can it be reserved?) — not the full booking workflow. BookingService coordinates across objects: check user → reserve seat → create hold → start payment. Cross-object coordination = orchestrator.

3️⃣ Class Design

~10–15 minutes
Go entity by entity, top-down — start with the orchestrator, then supporting entities. For each: derive State and Behavior from requirements. Deriving State — for each entity: which requirements does it own? What must it remember?
RequirementGame must track
"Two players alternate placing X/O on 3×3 grid"The two players, whose turn, the Board
"Game ends when a player wins or board is full"Game state (in progress/won/draw), winner
Game – State: - board: Board - playerX: Player - playerO: Player - currentPlayer: Player - state: GameState (IN_PROGRESS, WON, DRAW) - winner: Player? (null if no winner) Deriving Behavior — what does the outside world need to call?
NeedMethod
Players make movesmakeMove(player, row, col) → bool
Whose turn?getCurrentPlayer() → Player
Check stategetGameState() → GameState
Who won?getWinner() → Player?
Inspect boardgetBoard() → Board
Core principle — "Tell, Don't Ask" (Encapsulation): keep rules with the entity that owns the relevant state.
Workflow/lifecycle rules
("can this run right now?") → orchestrator
Data-specific rules
("is this cell occupied?") → entity that owns the data
ParkingLot.park(vehicle) spot = findAvailableSpot(vehicle) spot.park(vehicle) // tell, don't ask createTicket(vehicle, spot) ParkingSpot.park(vehicle) if occupied → reject if vehicle doesn't fit → reject parkedVehicle = vehicle
Why it matters: keeps APIs small & predictable — when something breaks, you know exactly which class to check.
On UML: not used in these breakdowns — it's outdated, rarely used in production (MS dropped UML tooling from Visual Studio in 2016). Simple class notation (state + methods) is enough. If an interviewer explicitly wants UML, ask if simplified notation is okay — usually is.

4️⃣ Implementation

~10 minutes
Ask the interviewer their preferred depth first — pseudocode, near-complete code, or just talk-through. Default: pseudocode for the most interesting methods.
  • Happy path first — inputs, sequence of steps, calls to other classes, return/state change.
  • Then edge cases — invalid inputs, illegal operations, out-of-range values, state violations.
makeMove(player, row, col) if state != IN_PROGRESS → return false if player != currentPlayer → return false if !board.canPlace(row, col) → return false board.placeMark(row, col, player.mark) if board.checkWin(row, col, player.mark) state = WON; winner = player else if board.isFull() state = DRAW else currentPlayer = (player == playerX) ? playerO : playerX return true
Patterns caution: Singleton/Factory/Builder can help — but candidates more often overengineer by forcing patterns than by skipping needed ones. Only add if it earns its place.
Verification step (1-2 min): trace a concrete scenario tick-by-tick — initial state → each operation → state changes → edge transitions. Catches bugs like forgetting to switch turns or win-detection not triggering. Fix on the spot if found — that's a positive signal, not a negative one.

5️⃣ Extensibility

~5 minutes, if time/level allow
Interviewer-led — they propose a twist to test if your design evolves cleanly (not hacks bolted on).
LevelWhat to expect
JuniorLittle or no extensibility discussion
Mid-levelOne or two small follow-ups
SeniorSeveral "what if we…" questions in a row
Example — "How would you add undo?":
"All state transitions flow through a single action method — makeMove. To add undo, introduce a command history stack: each successful action records prior state before mutating. undo() pops the stack and reverts — rest of the system doesn't change."
Stay high-level here — point to why your design's boundaries make the change clean, don't rewrite code.

🗣️ Questions You Asked — Answered

Q: Give real-life examples of entity vs. field?
Parking lot: ParkingSpot is an entity (changing state: available↔occupied, enforces fit rules). licensePlate is just a field on Vehicle — no behavior of its own, just data.
Q: Explain entity relationships with an example?
Parking lot: ParkingLot is the orchestrator — has-a list of spots, uses ParkingSpot.findAvailableFor() and TicketService.createTicket(). Rule placement follows ownership: fit-check rule → ParkingSpot; assign+ticket workflow → ParkingLot.
Q: What is an orchestrator entity — what does it mean?
The entity coordinating the main workflow between other objects. Tic Tac Toe: Game checks turn, asks Board to place a mark, decides win/draw, switches players — Board just owns grid-specific rules.
Q: Any other orchestrator example, like Ticketmaster?
BookingService is the orchestrator — checks user eligibility, asks SeatInventory if A12 is available, creates a temporary reservation, starts payment. It has-a SeatInventory, uses ReservationService and PaymentService.
Q: Why isn't SeatInventory the orchestrator?
It owns seat-specific state/rules (is A12 available? can it be marked reserved?), not the full booking sequence. BookingService coordinates across multiple entities — that cross-object coordination is what makes something the orchestrator.
Q: So orchestrator is basically an entity that manages other entities?
Yes — it coordinates other entities to complete a workflow, managing the sequence, while each supporting entity keeps its own data and rules.
Q: Explain "Tell, Don't Ask" with the Parking example?
ParkingLot owns the workflow; each ParkingSpot owns its own occupancy/size. So ParkingLot tells a spot to park a vehicle rather than fetching its fields and deciding the rules itself: ParkingLot.park(vehicle) spot = findAvailableSpot(vehicle) spot.park(vehicle) createTicket(vehicle, spot) ParkingSpot.park(vehicle) if occupied → reject if vehicle doesn't fit → reject parkedVehicle = vehicle This is encapsulation — each object protects and manages the data it owns.
