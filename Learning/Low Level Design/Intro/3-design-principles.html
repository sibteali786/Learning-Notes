Design Principles

The decision-making framework behind "should this be its own class?" — General principles + SOLID

🧭 Why these matter

These guide decisions like: should this be a separate class? Should I use inheritance? Is this abstraction worth it?
Key mindset: interviewers care that you apply the lessons, not that you can recite SOLID like the alphabet. Two categories exist — General principles and OOD principles (SOLID). SOLID gets more attention since most LLD problems expect class hierarchies.

⚙️ General Software Design Principles

If you remember only 3 from this whole guide: KISS, DRY, YAGNI.
KISS Keep It Simple, Stupid

The simplest solution that works is usually right. Solve with a conditional instead of a Strategy pattern if that's enough. Most commonly violated principle in LLD interviews — candidates over-engineer with factories/builders/decorators to show off knowledge.

When to add complexity: when simplicity stops working — e.g. a 500-line class with 10 responsibilities, or a new payment method requiring edits in 5 places → that's when Strategy pattern earns its place.
DRY Don't Repeat Yourself

Same logic in multiple places → pull into one. Benefit = fix/update once instead of hunting across the codebase.

Don't overdo it: if two pieces of code look similar but serve different purposes, duplication can be fine — forcing shared code creates artificial coupling. Key test: is the logic conceptually the same, not just textually similar.
DRY vs KISS tension (senior-level signal): "I expect this validation logic to appear in multiple places, but I'll start by keeping it in the User class to avoid premature complexity. If we see it duplicated 3-4 times, we pull it into a shared validator." — shows you can balance competing principles instead of blindly following rules.
YAGNI You Aren't Gonna Need It

Build what's needed now — not speculative future features. Don't add valet parking / EV charging to a parking lot design unless requirements mention it.

Why it fails when ignored: you usually guess future requirements wrong — you add complexity for scenarios that never happen, and the real new requirement ends up different from what you prepared for.
Nuance: doesn't mean "never think ahead" — means don't build ahead. Design with extension in mind, implement only what's needed now. This is exactly what "how would you extend this?" follow-ups are testing.
Separation of Concerns

Different parts of code handle different responsibilities and don't know each other's internals. UI shouldn't hold business logic; business logic shouldn't know storage details.

❌ Bad
class TicTacToe { board: string[][] play() { // display logic console.log(board) // input handling board[row][col] = "X" // win checking if (board[0][0]===board[1][1] && board[1][1]===board[2][2]) console.log("Winner!") } }
✅ Good
class TicTacToe { constructor( private board: Board, private display: Display, private input: InputHandler ) {} play() { while (!board.hasWinner()) { display.render(board) const move = input.getNextMove() board.makeMove(move) } display.showWinner(board.getWinner()) } }
Switch console→GUI: only touch InputHandler. Change display: only Display. New win conditions: only Board. Each change isolated → each part independently testable.
Law of Demeter ("Principle of Least Knowledge")

A method should only talk to its immediate friends, not reach through objects to access distant parts.

Violation: order.getCustomer().getAddress().getZipCode() — your code now knows the internal structure of 3 different objects; if any reorganizes its data, you break.
Fix: put getCustomerZipCode() on Order, handle navigation internally.
Not the same as method chaining: fluent interfaces like builder.setName("John").setAge(30).build() are fine — they return the same object type. The issue is specifically chaining that leaks internal structure across different object types.

🏛️ Object-Oriented Design Principles — SOLID

Apply when the problem calls for them — don't force SOLID where a simpler solution works (that breaks KISS).
Context: SOLID comes from Java's deep-inheritance era. Outside Java/C#, heavy SOLID application is falling out of fashion — modern languages favor composition over hierarchies, functions over interfaces.
S Single Responsibility Principle — a class should have one reason to change.
❌ Mixes content gen + PDF + storage
class Report { generateContent(): string printToPDF(): void saveToFile(): void }
✅ Split by responsibility
class Report { generateContent() } class PDFPrinter { print(report) } class FileStorage { save(content) }
PDF library changes → touch only PDFPrinter. Switch file→DB → only FileStorage. Each change isolated.
O Open/Closed Principle — open for extension, closed for modification. Add new behavior without touching existing code (usually via interfaces).
❌ Modify method for every new type
class PaymentProcessor { process(type: string, amount: number) { if (type === "credit") {...} else if (type === "paypal") {...} // adding crypto = editing this method } }
✅ New class per type, old code untouched
interface PaymentMethod { process(amount): void } class CreditCardPayment implements PaymentMethod {...} class CryptoPayment implements PaymentMethod {...} class PaymentProcessor { process(method: PaymentMethod, amount) { method.process(amount) } }
Adding crypto = just create CryptoPayment. PaymentProcessor never changes → can't break what already works.
L Liskov Substitution Principle — subclasses must work wherever the base class works, without breaking caller expectations.
Red flags: subclass throws for a method the parent provides; caller needs if (bird instanceof Penguin) special-casing.
❌ Penguin breaks "all birds fly"
class Bird { fly(): void {...} } class Penguin extends Bird { fly(): void { throw new Error("Penguins can't fly") } }
✅ Split flying into its own interface
interface Bird { eat(): void } interface FlyingBird extends Bird { fly(): void } class Sparrow implements FlyingBird { eat() {...}; fly() {...} } class Penguin implements Bird { eat() {...} }
Comes up when designing class hierarchies — think carefully about what belongs in the base class vs. subclasses.
I Interface Segregation Principle — prefer small, focused interfaces over large general-purpose ones.
❌ Robot forced to implement eat()/sleep()
interface Worker { work(): void eat(): void sleep(): void } class Robot implements Worker { work() {...} eat() { /* robots don't eat */ } sleep() { /* robots don't sleep */ } }
✅ Split into focused interfaces
interface Workable { work(): void } interface Feedable { eat(): void } interface Restable { sleep(): void } class Human implements Workable, Feedable, Restable {...} class Robot implements Workable { work() {...} }
Fat interfaces force empty implementations or exception-throwing stubs — that's a code smell.
D Dependency Inversion Principle — depend on abstractions, not concrete implementations.

"Inversion" = who defines the contract. Normally business logic conforms to whatever the implementation provides. With DIP: define an interface based on what business logic needs, then implementations conform to that interface — implementation adapts to business logic, not the reverse.

❌ Tightly coupled to EmailSender
class EmailSender { send(message): void {...} } class NotificationService { private emailSender = new EmailSender() notify(message) { emailSender.send(message) } }
✅ Depends on MessageSender interface
interface MessageSender { send(message: string): void } class EmailSender implements MessageSender { send(message) {...} } class NotificationService { constructor(private sender: MessageSender) {} notify(message) { sender.send(message) } }
Neither high-level nor low-level module knows about the other directly. Swap email→SMS by injecting a different implementation. Unit test with a mock MessageSender — no real emails sent.
Important distinction: DIP is a design principle. Dependency Injection (passing deps through constructor) is a technique for achieving it. Related, but not the same thing.

📋 Cheat Sheet

General Principles

KISS → Start simple, add complexity only when needed
DRY → Reduce duplication, simplify maintenance
YAGNI → Build for today, not hypothetical futures
Separation of Concerns → Enable independent testing and changes
Law of Demeter → Reduce coupling, hide internal structure

SOLID Principles

SRP → Keep classes focused on one responsibility
OCP → Support future requirements without modifying existing code
LSP → Prevent brittle hierarchies that break at runtime
ISP → Keep interfaces clean and focused
DIP → Decouple business logic from implementation details
Final takeaway: don't recite these constantly — use them to guide decisions, reference briefly when explaining tradeoffs. They're tools for thinking, not a checklist.

💬 Real Talk from the Comments (worth knowing)

  • Regional mismatch: some candidates report Indian-market interviewers expecting you to name patterns explicitly and tick off each SOLID letter — despite the "don't recite it" advice above. If your recruiter/interviewer signals this style, prep the vocabulary too, don't rely solely on "just reason well."
  • Functional-programming background friction: engineers from OCaml/Haskell/Rust backgrounds report LLD rounds feeling arbitrary/bookish — worth knowing this is a common pain point, not a personal gap, if OOP-heavy interviews feel unnatural to you.
  • DIP nuance raised in comments: testability really comes from how a dependency is provided (injected vs. hardcoded with new EmailSender()), not strictly from whether it's an interface — you could inject a concrete class and still mock it in some languages. Interface + injection together give you the full swap-implementation + mock-for-testing benefit described in the DIP example.
