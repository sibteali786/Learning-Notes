### Cloud Computing ( Open Stack )

### Components

- Nova
    
    Nova is a service within the OpenStack platform that provides the computing power necessary to run virtual machines and other instances.
    
    Think of Nova like a virtual construction worker that helps build and manage virtual machines. Just as a construction worker might use tools and materials to build a physical structure, Nova uses computing resources like CPU and memory to build and manage virtual machines and other instances.
    
    Nova is a critical component of OpenStack because it allows you to quickly deploy and manage large numbers of virtual machines to handle computing tasks. This scalability is important for cloud computing environments where workloads can vary in size and demand.
    
- Keystone
    
    Keystone is a service within the OpenStack cloud computing platform that helps manage user identities and permissions. It provides a central place to authenticate users and authorize their access to other OpenStack services, like storage or compute.
    
    Think of Keystone like a bouncer at a nightclub. Just like a bouncer checks your ID before letting you into the club, Keystone checks a user's credentials before allowing them access to the other OpenStack services. Keystone also keeps track of what each user is allowed to do within those services, just like a bouncer might only allow certain people into certain areas of the club.
    
    Additionally, Keystone helps services within OpenStack find and communicate with each other, kind of like a party planner who makes sure all the different vendors are working together to create a seamless event.
    
- Neutron
    
    Neutron is another service within the OpenStack platform that handles networking between different components of an OpenStack deployment.
    
    Think of Neutron like a postal service that ensures all the different parts of a city can communicate with each other. Just as the postal service helps deliver mail and packages to different addresses, Neutron helps route network traffic between different parts of an OpenStack deployment, like virtual machines or storage systems.
    
    This networking capability is crucial for OpenStack because it allows all the different components to work together seamlessly, making the cloud computing environment more efficient and easier to manage.
    
- Cinder
    
    Cinder is a service within the OpenStack platform that provides block storage to cloud computing applications. It allows users to create and manage persistent storage volumes that can be attached to virtual machines or other instances.
    
    Think of Cinder like a storage unit rental service. Just as you can rent a storage unit to store your belongings, Cinder allows you to create and manage storage volumes for your virtual machines or cloud computing applications. These volumes can be used to store data that needs to persist beyond the life of a single virtual machine or instance.
    
    Cinder is an important component of OpenStack because it provides a way to manage storage in a scalable and efficient way. This helps ensure that cloud computing applications have access to the storage they need to run effectively.
    
- Glance
    
    Glance is a service within the OpenStack platform that provides image services for cloud computing. These "images" are essentially virtual copies of hard disks that can be used as templates when deploying new virtual machine instances.
    
    Think of Glance like a library of virtual machine images. Just as a library contains books that can be borrowed and used as references, Glance provides a repository of virtual machine images that can be used as templates for new virtual machine instances. These images can be customized and configured to meet the specific needs of different applications or workloads.
    
    Glance is an important component of OpenStack because it provides a way to manage virtual machine images in a scalable and efficient way. This helps simplify the process of deploying new virtual machines and ensures consistency and reliability across different instances.
    
- Horizon
    
    Horizon is a service within the OpenStack platform that provides a web-based dashboard interface for managing OpenStack resources. It's the only graphical interface to OpenStack, so it's often the first thing that users see when they start using the platform.
    
    Think of Horizon like a control panel for OpenStack. Just as a control panel allows you to manage different aspects of a device or system, Horizon allows you to manage and monitor your OpenStack resources through a web-based interface. With Horizon, system administrators can view what's going on in the cloud, manage resources as needed, and perform other common tasks like launching virtual machines, creating storage volumes, and managing networks.
    
    Horizon is an important component of OpenStack because it provides a user-friendly interface for managing OpenStack resources. This makes it easier for system administrators to manage complex cloud environments and allows users to get started with OpenStack more quickly.

### Vertical Scaling

Vertical scaling, also known as scaling up or scaling vertically, refers to increasing the capacity of a single server, machine, or resource to handle more workload. This typically involves upgrading the hardware components of the system, such as adding more CPU power, increasing RAM, or attaching additional storage devices.

Vertical scaling can be a straightforward way to improve the performance and capacity of a system, especially in situations where the workload can be managed by a single, powerful machine. It is commonly used in environments where there are limits on horizontal scaling, such as legacy systems or applications that are not easily distributed across multiple servers.

    ### Chain
    
    Its called chain becuase each rule is a chain of many small rules.
    
    For instance, for a given input chain 
    
    ![Screenshot 2024-09-19 at 11.51.36 AM.png](DevOps%20a7887e7c18db481aa28390527d882a73/Screenshot_2024-09-19_at_11.51.36_AM.png)
    
    **1. INPUT Chain**
    
    •	**Purpose**: Controls incoming traffic directed to the local machine.
    
    •	**Function**: This chain determines how packets destined **for the system** itself are processed.
    
    •	**Example Use Case**: When someone tries to SSH into the machine or sends an HTTP request to a web server running on the machine, the packet would pass through the INPUT chain.
    
    •	**Common Actions**:
    
    •	Allow or block specific IPs from accessing services (like SSH or HTTP).
    
    •	Set rules to accept, reject, or drop packets based on certain conditions (e.g., source IP, protocol).
    
    **Example Rule**:
    
    ```bash
    iptables -A INPUT -p tcp --dport 22 -j ACCEPT
    ```
    
    (This rule allows incoming SSH connections on port 22.)
    
    **2. OUTPUT Chain**
    
    •	**Purpose**: Controls outgoing traffic from the local machine.
    
    •	**Function**: This chain determines how packets that originate **from the system itself** are handled.
    
    •	**Example Use Case**: When the machine is trying to reach out to external services (e.g., making an HTTP request or sending a ping), the packet goes through the OUTPUT chain.
    
    •	**Common Actions**:
    
    •	Restrict or allow traffic generated by the machine, such as HTTP requests or DNS queries.
    
    **Example Rule**:
    
    ```bash
    iptables -A OUTPUT -p tcp --dport 80 -j ACCEPT
    ```
    
    (This rule allows the machine to make outbound HTTP requests on port 80.)
    
    **3. FORWARD Chain**
    
    •	**Purpose**: Controls traffic that is routed **through** the machine but is not intended for the local machine.
    
    •	**Function**: This chain is used when the machine is acting as a router, forwarding traffic from one network interface to another.
    
    •	**Example Use Case**: If a system is set up to route traffic between two networks (e.g., a gateway or a NAT server), packets passing through the system will go through the FORWARD chain.
    
    •	**Common Actions**:
    
    •	Configure rules for traffic between two or more networks (e.g., NAT, routing).
    
    **Example Rule**:
    
    ```bash
    iptables -A FORWARD -p tcp -d 192.168.1.0/24 --dport 80 -j ACCEPT
    ```
    
    (This rule allows forwarding of packets to the 192.168.1.0/24 network on port 80.)

### Environment Variables

User profile scripts, such as `~/.profile`, `~/.bash_profile`, `~/.bashrc`, and others, are executed when a user logs in, allowing the setup of the environment according to personal preferences.

To make changes persistent in Unix-like operating systems, variables, aliases, and other configurations can be added to these profile files.

For example, to add a variable using the command line:

```
echo 'export MY_VARIABLE="example_value"' >> ~/.profile
```

This command appends the export statement to the end of the `~/.profile` file, making the variable `MY_VARIABLE` persistent across sessions.

To add an alias, like ll for ls -l, use:

```
echo 'alias ll="ls -l"' >> ~/.profile

```

### Large vs Small Batch Process

- Working in small batches is important for situations where fast feedback is required.
- It enables you to learn quickly from your decisions and experiment more to gain insights.
- Working in small batches minimizes waste by gaining feedback faster and avoiding the development of things the customer doesn't like.
- In contrast, working in large batches means waiting for feedback for months.
- Using small batches is aligned with DevOps practices and allows for rapid progress from development through test and operations into production.
- Working in small batches, also known as single piece flow, leads to faster feedback loops and the ability to quickly pivot if needed.
- To determine if your batches are small enough, consider the size of your stories in your backlog and if features can be completed in a sprint.
- Features should ideally be small enough to be completed in a week or less.
- Working in small batches means delivering something useful quickly and implementing other DevOps practices like Continuous Integration and Continuous Delivery.

Large Batches:

- Takes months to complete.
- Feedback is delayed for months.
- Increases the risk of developing things the customer doesn't like.
- Wastes time and resources on features that may not be desired.
- Difficult to identify and rectify errors or issues early on.
- Requires going back to the beginning if a problem is discovered.
- Slows down the overall development and delivery process.

Small Batches:

- Completed in a shorter time frame.
- Feedback is obtained quickly.
- Minimizes the risk of developing unwanted features.
- Reduces waste by focusing on features that are valuable to the customer.
- Enables early detection and resolution of errors or issues.
- Allows for quick adjustments and pivots if needed.
- Speeds up the overall development and delivery process.
- Supports the implementation of DevOps practices like Continuous Integration and Continuous Delivery.

- Test-Driven Development (TDD) means that your test case drives the design and development of your code.
- TDD involves writing test cases before writing the actual code.

### Behavior Driven Development

- Behavior Driven Development (BDD) focuses on the behavior of the system from the outside in.
- BDD is different from Test Driven Development (TDD), which focuses on the minutia of how the system works inside.
- BDD is great for integration testing to see if all components are behaving together.
- BDD describes behaviors in a single notation that is accessible to domain experts, testers, developers, and customers.
- BDD uses a language known as Gherkin to document behaviors.
- BDD tools like Behave, jBehave, and Cucumber are used to run examples as automated acceptance tests.
- Gherkin syntax uses a Given... When... Then... syntax to describe context, events, and outcomes.
- BDD improves communication among team members and provides precise guidance on system behavior.
- BDD leads to higher-quality code, reduces maintenance costs, and eliminates risk.
- BDD acceptance criteria can be converted to user stories and test scenarios before development begins.

consider a real-life example of a retail store. In this scenario, we'll focus on the behavior of the system when a customer returns an item that they have purchased. Here's how BDD can be applied:

1. Given that a customer previously bought a black sweater from the store.
2. And the store has 3 black sweaters in stock.
3. When the customer returns the black sweater for a refund.
4. Then the store should have 4 black sweaters in stock.

In this example, BDD helps define the behavior of the system in a formal syntax that can be executed as test cases. The stakeholders, including developers, testers, and product owners, collaborate to define the behavior using the Gherkin syntax. The acceptance criteria are documented as scenarios, which serve as test cases.

## Design For Failure

![Screenshot 2024-09-01 at 6.52.49 PM.png](DevOps%20a7887e7c18db481aa28390527d882a73/Screenshot_2024-09-01_at_6.52.49_PM.png)

### **Retry Pattern**

•	**Purpose**: Automatically retry a failed operation a specified number of times before giving up, to handle transient faults.

•	**Use Case**: When the failure is likely temporary, such as network timeouts or transient service unavailability.

•	**Key Points**:

•	Define the number of retry attempts.

•	Implement an exponential backoff strategy to avoid overwhelming the system.

•	Monitor and log retry attempts to identify persistent issues.

### **Circuit Breaker Pattern**

•	**Purpose**: Prevents a system from repeatedly trying to execute an operation that is likely to fail, protecting resources and allowing the system to recover.

•	**Use Case**: When a downstream service is unavailable or is failing consistently, to prevent further degradation.

•	**Key Points**:

•	Has three states: **Closed** (normal operation), **Open** (no requests are allowed), and **Half-Open** (test a few requests to check if the service has recovered).

•	Transitions to Open state after a certain number of consecutive failures.

•	Transitions to Half-Open state after a timeout period to test the availability of the service.

### **Bulkhead Pattern**

•	**Purpose**: Isolates different parts of a system to prevent a failure in one part from cascading to other parts, ensuring that critical services remain operational.

•	**Use Case**: When you want to limit the impact of a failure to a small portion of the system, preserving functionality elsewhere.

•	**Key Points**:

•	Partition system resources into isolated pools or bulkheads (e.g., separate thread pools).

•	Limit the resources (e.g., threads, memory) allocated to each partition.

•	Prevents resource exhaustion and ensures that failure in one service doesn’t bring down the entire system.

This material focuses on the advantages of cloud computing over traditional hosting, highlighting its flexibility, scalability, and essential characteristics.

Essential Characteristics of Cloud Computing

- The five essential characteristics include on-demand self-service, broad network access, resource pooling, rapid elasticity, and measured service.
- On-demand self-service allows users to access resources anytime, while broad network access ensures availability across various devices with internet connectivity.

Benefits of Cloud Computing

- Cloud computing provides businesses with greater flexibility and scalability compared to local server hosting, allowing for quick adjustments to bandwidth needs without costly infrastructure updates.
- Users can access and customize applications from anywhere with an internet connection, making it easier to market and maintain applications efficiently.

Understanding Resource Management

- Resource pooling enables cost savings through a shared model, allowing cloud providers to offer economies of scale to customers.
- Rapid elasticity allows for scaling resources up or down based on demand, such as during peak shopping times, while measured service means users only pay for what they use.

### History and Evolution of Cloud Computing

Historical Development of Cloud Computing

- The concept of cloud computing began in the 1950s with mainframes that allowed multiple users to share computing resources through time-sharing.
- In the 1970s, the introduction of Virtual Machine (VM) technology enabled multiple virtual systems to operate on a single physical machine, enhancing resource utilization.

Virtualization and Hypervisors

- Virtualization became a key driver in computing, allowing companies to split physical servers into multiple virtual systems, optimizing hardware use.
- Hypervisors play a crucial role by enabling multiple operating systems to run on the same hardware while keeping them logically separated to prevent interference.

The Rise of Pay-as-You-Go Model

- The growth of the internet and improved virtualization technologies led to the emergence of cloud services, allowing users to access resources without needing extensive physical servers.
- The pay-as-you-go model transformed how companies manage computing costs, enabling them to scale resources based on demand and shift from capital expenditures to operational expenditures.

### Key Considerations of Cloud Adoption

Key considerations for cloud adoption

- Organizations must evaluate their infrastructure and workloads, weighing the cost savings of cloud computing against the readiness of their workloads for the cloud.
- The choice between Software as a Service (SaaS) and traditional software purchases is crucial, as cloud solutions can offer faster deployment and productivity gains.

Benefits of cloud adoption

- Flexibility is a major advantage, allowing organizations to scale services as needed and access applications from anywhere with an internet connection.
- Efficiency is enhanced through quick application deployment, reduced infrastructure costs, and minimized risk of data loss due to remote backups.

Challenges in cloud adoption

- Organizations face risks such as data security, compliance issues, and the need for effective governance.
- Selecting the right cloud service providers and deployment models is essential to mitigate these risks and ensure business continuity.

### Summary

- Cloud computing is the delivery of on-demand computing resources over the internet on a pay-as-you-go basis; resources are dynamically assigned and reassigned among multiple users and scale up and down in response to users’ needs.
- The origins of cloud computing can be traced back to the mainframes of the 1950s, with virtualization technologies and hypervisors serving as catalysts for the emergence of modern-day cloud computing.
- Organizations must consider their business needs, investment viability, and risk capacity to create a cloud adoption strategy that delivers desired benefits without causing business disruptions and security, compliance, or performance issues.
- Cloud adoption is growing faster than predicted. Driving this technological wave are cloud service providers with a host of services ranging from Infrastructure, Platform, and Software services. Some major Cloud providers of our time include AWS, Alibaba Cloud, Google, IBM, and Microsoft Azure.

## Overview Of Cloud Service Models

Different Cloud models analogy 

![Screenshot 2024-12-29 at 9.35.19 PM.png](DevOps%20a7887e7c18db481aa28390527d882a73/Screenshot_2024-12-29_at_9.35.19_PM.png)

- **IaaS** provides virtualized computing resources, allowing system administrators to manage servers and storage.
- **PaaS** abstracts the infrastructure, enabling developers to focus on application development without worrying about the underlying hardware.
- **SaaS** delivers software applications over the internet, where users can access them without installation or manual updates, typically through a subscription model.

**Analogy:**

- **IaaS** is like leasing a car: You research the specifications, choose the model, and are responsible for maintenance, fuel, and driving.
- **PaaS** is akin to renting a car: You pick up a vehicle for a trip without caring about its specifics; you drive it but don’t worry about maintenance.
- **SaaS** is similar to using a taxi or Uber: You simply get in and go, with no concern for the car's details or costs, as everything is included in the fare.

### IaaS

- **Definition**: IaaS is a cloud computing model that provides fundamental compute, network, and storage resources on-demand over the internet, typically on a pay-as-you-go basis.
- **Components**:
    - **Physical Data Centers**: Managed by IaaS providers, housing the physical machines.
    - **Compute**: Users provision virtual instances with desired resources, supported by services like auto-scaling and load balancing.
    - **Network**: Access to networking resources through virtualization or APIs.
    - **Storage**: Includes object, file, and block storage, with object storage being the most common.
- **Use Cases**:
    - Rapid setup of test and development environments.
    - Business continuity and disaster recovery.
    - Faster deployment and scaling of web applications.
    - High-performance computing for complex problem-solving.
    - Data mining for valuable patterns and trends.
- **Concerns**: Issues include lack of transparency in configuration and dependency on third-party performance.
- **Growth**: IaaS is the fastest-growing cloud model today.
