02 go.mod & Makefile

📄 go.mod

Declares: module path (github.com/sibteali786/nclip — this doubles as the import prefix every internal package uses), the Go version, and two direct dependencies (atotto/clipboard, hashicorp/mdns).

JS analogySame role as package.json's name + dependencies fields combined. The // indirect comments mark transitive deps — packages your direct deps need, that you never call yourself. npm hides these inside node_modules/lockfile; Go surfaces them right in the manifest.
Why miekg/dns shows uphashicorp/mdns needs it because mDNS packets are regular DNS-format packets, just sent over multicast instead of to a resolver — same wire format, different delivery mechanism. That's why a "DNS" library underlies "service discovery."
📄 Makefile

build → go build ./..., vet → go vet ./... (static analysis, catches bugs gofmt can't), fmt → gofmt -l . (lists files not matching Go's canonical formatting).

JS analogyvet ≈ ESLint's logic rules; fmt ≈ Prettier — except gofmt isn't configurable. There's exactly one canonical Go style, enforced by the toolchain itself, not a config file you can tweak.

03 internal/protocol — the wire message format

📄 internal/protocol/message.go

What it does

Defines the envelope every message sent between machines must have, and the functions to build/read it.

type Message struct {
    Type      MsgType
    ID        string
    Payload   []byte   // ← raw JSON bytes, shape unknown until decoded
    Timestamp int64
    SrcDevice string
}
JS analogytype Message ≈ a TypeScript interface. The interesting part is Payload []byte — it's storing an already-JSON.stringify'd string (as bytes) inside the outer object, not a nested object. Think of it like an envelope/event-bus pattern: { type: "send", id: "...", payload: "{\"content\":\"hi\"}" } — the outer struct doesn't need to know the payload's shape until something decides to decode it based on Type. Similar to how Redux actions or webhook payloads often carry an opaque data blob keyed by an event field.

The four functions

FunctionDoesJS equivalent
Encode(...)JSON.stringify's your payload struct, wraps it in Message{} with id/timestamp/srca factory function building {type, id, payload: JSON.stringify(data), ...}
DecodePayload(msg, &dst)unmarshals msg.Payload bytes into dstObject.assign(dst, JSON.parse(msg.payload)) — Go mutates the thing you pass a pointer to, rather than returning a fresh parsed value
MarshalMessage(msg)JSON-encodes the whole envelope to bytes (for raw wire transmission)JSON.stringify(msg)
UnmarshalMessage(data)reverse of aboveJSON.parse(data)
Pointer gotcha (the unfamiliar part for JS devs)DecodePayload(msg *Message, dst any) takes a pointer to the destination (you call it as DecodePayload(msg, &got)). Go doesn't infer/return a typed value the way JSON.parse<T>() conceptually would in TS — instead it fills in a struct you already created, via its memory address. Mentally: it's like passing a ref object in React and having a function write into ref.current rather than returning a new value.
Error wrappingfmt.Errorf("protocol.DecodePayload type=%s: %w", msg.Type, err) — the %w verb "wraps" the original error so callers can still inspect it later via errors.Is/errors.As. Closest JS parallel: new Error("decode failed", { cause: err }) — Go's error-wrapping convention predates JS's cause option by years, same underlying idea.

04 internal/clipboard — OS clipboard wrapper

📄 internal/clipboard/clipboard.go — imports github.com/atotto/clipboard

Three tiny functions: Read(), Write(text), Supported() — all of them just call straight through to the third-party atotto/clipboard package and wrap its errors with context.

JS analogyExactly the pattern of writing your own lib/clipboard.ts thin wrapper around an npm package like clipboardy, instead of importing clipboardy directly in ten different files. Under the hood, atotto/clipboard shells out to OS tools — pbcopy/pbpaste on macOS, xclip/xsel on Linux — the same way a Node clipboard package would.
Why wrap it at allIf nclip ever needs to switch clipboard libraries (exactly what just happened with mDNS!), only this one file changes — every caller elsewhere in the codebase keeps calling clipboard.Read() unaware of what's underneath. This is the same reasoning behind the PLAN.md's §9 "evaluate both libraries, pick one" — the wrapper insulates that decision.
clipboard.UnsupportedA boolean flag the library sets if it couldn't find a working clipboard mechanism on this OS (e.g. headless Linux with no X11). Supported() just negates it. JS equivalent: typeof navigator.clipboard !== 'undefined' feature-detection before calling a browser API.

06 internal/transport/lan — raw TCP, hand-rolled request/response

📄 internal/transport/lan/lan.go — imports net, encoding/json, and internal/protocol

Listen(ctx, port, handler)

Starts a raw TCP server. For every incoming connection, spawns a goroutine that decodes one JSON message and calls your handler.

JS analogynet.createServer((socket) => {...}).listen(port) from Node's built-in net module — not Express/HTTP. There's no routing, no headers, no status codes — just raw bytes over a socket. nclip is inventing its own tiny protocol on top of TCP, the same category of thing as writing a custom binary/JSON protocol instead of reaching for HTTP.
Concurrency model difference (important)Node's net.createServer callback runs on Node's single event loop thread — concurrency comes from non-blocking I/O, not real parallelism. Go's go handleConn(conn, handler) spawns a genuinely independent goroutine per connection, scheduled by the Go runtime across potentially multiple OS threads. Both models let you "handle many connections without manually managing threads," but the mechanism underneath is different: Node is cooperative single-threaded async, Go is real (lightweight) concurrent execution.

handleConn(conn, handler)

json.NewDecoder(conn).Decode(&msg) — reads exactly one JSON object off the connection.

JS analogyCloser to a streaming JSON parser (like the JSONStream npm package) than JSON.parse(fullString). json.Decoder reads bytes as they arrive and tracks bracket-nesting to know where the JSON object ends — it doesn't need a length-prefix or a fixed buffer size up front.

Send(addr, msg)

Dials out, JSON-encodes the message, writes it, then synchronously blocks reading back exactly one ack message.

JS analogynet.connect(port, host) + manually writing/reading the socket — like rolling your own tiny RPC call instead of using fetch(). Conceptually it's the same shape as a minimal JSON-over-TCP version of what gRPC does with protobuf-over-HTTP/2: a request goes out, the same connection is reused to read the matching response back.
net.DialTimeoutEquivalent to wrapping net.connect() with AbortSignal.timeout(ms) in modern fetch, or the older manual-setTimeout-plus-socket.destroy() pattern in Node — bounds how long the connection attempt itself can take, separate from how long the whole exchange takes.

Why this file imports protocol (and nothing else does)

Transport is the one place that actually needs to know both "how to move bytes" (its own job) and "what shape those bytes are" (protocol's job) — it has to encode before sending and decode after receiving. Discovery and clipboard never touch message shape, so they never import it.

07 cmd/nclip, cmd/nclipd, cmd/nclip-relay — entrypoints (currently stubs)

All three are currently just func main() {} — empty. This is intentional at this point in Phase 1: per §0 Working Agreement ("one task at a time"), the daemon-wiring task comes after the individual pieces (protocol, clipboard, discovery, transport) are each built and tested standalone.

JS analogyLike having three empty index.ts files as placeholders for three separate bin targets in package.json, before you've actually imported and wired up your services into each entrypoint. The difference: each of these compiles to a fully standalone native binary — no shipping source code or a node_modules folder to the target machine, no runtime needed there at all.

08 End-to-end flow — once the daemon wires these together (planned, per PLAN.md — not built yet)

This is what the pieces above are for, even though no single file does this yet. Useful to hold this mental model while reading the individual files.

1
User runs nclip send "hello" --to macos on machine A.
2
CLI talks to the local daemon over the Unix socket (not built yet — separate IPC piece), which calls discovery.Browse(ctx, "macos") to resolve the name to an IP:port.
3
Daemon calls protocol.Encode(MsgSend, id, "laptop", SendPayload{Content:"hello"}) to build the wire message.
4
Daemon calls transport/lan.Send(addr, msg) — dials machine B's TCP port, writes the JSON-encoded message, blocks waiting for an ack.
5
On machine B, the daemon's transport/lan.Listen handler receives the connection, decodes the message, and — once wired — calls protocol.DecodePayload to get the actual text back out, then clipboard.Write(text) to put it on B's clipboard.
6
Handler builds an ack via protocol.Encode(MsgAck, ...) and writes it back on the same connection — Send on machine A reads it and returns.
