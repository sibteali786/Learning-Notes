Goroutines & the Fan-In Pattern

recall goroutines.md

01 What is a goroutine, actually

⟶

A goroutine is a lightweight thread managed by the Go runtime, not the OS. Starting one is just:

go func(){ ... }()

The call returns immediately — the caller does not wait. The function body runs concurrently, scheduled by Go itself (cheap enough to spin up thousands of them).

02 Real-world analogy — the party doorbell

You shout into the hallway: "Anyone who wants to join, knock in the next 10 minutes!" Then you go back inside.

the shout

resolver.Browse(ctx, …)

Tells the mDNS library to start listening on the network. Doesn't block — hands off the work and returns to you right away.

→ fires off the search, non-blocking
the doorbell

entries channel

Rings every time a device on the network responds. Could ring 0 times, once, or 10 times — timing is unknown in advance.

→ chan *zeroconf.ServiceEntry
the helper at the door

the goroutine

Sits by the door the whole time. Every ring, they open it, write the guest's name into the guestbook. Nothing else on their plate.

→ go func(){ for entry := range entries {...} }()
you

ctx.Done()

You're not answering the door — you're watching a kitchen timer set for 10 minutes. When it beeps, you stop caring about new knocks.

→ <-ctx.Done() unblocks on timeout/cancel
why you need both, at once

If you had to both answer the door and watch the timer, you'd fail at one: stuck waiting for the next knock means missing the beep, and vice-versa. So the job is split — the goroutine reacts to events whenever they happen, while the main function just watches the clock. This is exactly why Browse needs a separate goroutine draining entries concurrently with the 10s wait.

main calls Browse → tells zeroconf to start listening (the shout).
main launches the door-watcher goroutine, then itself just sits on <-ctx.Done() (the timer).
x N for up to 10s, any responding device rings the doorbell (entries) — goroutine logs each into found.
timer beeps → main stops waiting, returns whatever's in found — regardless of whether the goroutine is mid-write (the known race note).

03 Fan-in pattern — why it's needed here

Fan-in = multiple concurrent sources feeding into one consumer/destination.

RoleIn this code
Producer(s)zeroconf's internal browsing — pushes to entries asynchronously, any time over 10s
Consumerour goroutine — drains entries, writes into found
Why a channelresolver.Browse can't know in advance how many devices respond or when — a channel is Go's idiomatic way to stream an unknown count of results over time
Why a goroutine specificallya channel is useless unless something consumes it concurrently with the timeout being tracked elsewhere

04 Good vs. bad goroutine use cases

✓ good fits

  • Waiting on a long-lived cancellation signal e.g. <-ctx.Done() to call Shutdown() later — exactly the Register() case
  • Draining a channel while something else tracks a timeout the fan-in pattern above
  • Independent I/O that can run in parallel fetching from 5 APIs at once instead of sequentially
  • Background workers pulling off a shared job queue worker pool pattern — N goroutines, 1 channel of jobs
  • Fire-and-forget side effects writing a log line, sending a metric — caller shouldn't block on it

✗ bad fits / footguns

  • Spawning one with no way to know when it's done leaks silently — no sync.WaitGroup, no channel signal, no context
  • Mutating a shared variable from multiple goroutines without a lock exactly the found race note above — works by luck of timing, not by guarantee
  • Goroutine-per-item for things that finish in microseconds scheduling overhead can cost more than the work itself
  • Forgetting to close the channel a goroutine ranges over entries here never gets closed — goroutine technically lingers past return
  • Using a goroutine just to "feel async" with no concurrency need if nothing else is happening at the same time, you've only added complexity
