1. First, a correction: it isn't BullMQ

The interview draft says this feature was built with BullMQ. The commit history says otherwise, and it's better to learn that here than from an interviewer who asks what your Redis connection settings were.

What the code actually does The Channex queue (apps/backend/ChannelManager/services/channexSyncQueue.js, added in commit 5ebac9b on 2026-07-07) is a hand-written, in-memory queue: two JavaScript Maps of pending updates, a setInterval flush loop that fires every 5 seconds, and two token buckets per property. There is no Redis, no BullMQ worker, and no job objects.

BullMQ is in apps/backend/package.json, but nothing imports it. The only queue-shaped code outside Channex is in controllers/monitoring/analytics.controller.js, which calls require('bull') (the older library, not BullMQ) to enqueue a model-training job. bull isn't a declared dependency, and no worker consumes that queue.

BullMQ didn't disappear by accident. It was considered and deliberately deferred. The project's Known Issues log (CHANNEX_PROGRESS.md, issue #1) records the reasoning: at single-instance MVP scale, an in-memory queue was enough, and the daily full sync already repairs anything lost in a crash. It names a Redis-backed queue ("e.g. BullMQ or a Redis INCR+EXPIRE bucket") as the fix to make before running more than one backend instance.

How to tell the story honestly (and better) "I built a rate-limited batching queue for our Channex integration. I chose an in-memory design over BullMQ on purpose, and I know exactly when that choice stops holding." That's a stronger answer than "I used BullMQ", because it shows you understood the trade-off. Section 5 has the full script.

2. Background

2.1 The broad picture (skip if you know hotel distribution)

A hotel or hostel doesn't sell rooms only on its own website. It also lists them on OTAs (online travel agencies) such as Booking.com, Airbnb and Expedia. Each OTA needs to know three things for every room on every future date. The industry calls them ARI:

  • Availability: how many units of this room type can still be sold on 2026-10-03?
  • Rates: what does one night cost on that date?
  • Inventory restrictions: rules such as minimum stay, closed-to-arrival, or stop sell (don't sell this date at all).

Keeping five OTAs in sync by hand is hopeless, so hotels use a channel manager. The property management system (PMS, here HospitalityOS) tells the channel manager about ARI once, and the channel manager fans it out to every connected OTA. Bookings travel the other way: a guest books on Booking.com, Booking.com tells Channex, and Channex sends a webhook to the PMS.

HospitalityOS (PMS)source of truth for rooms, prices, bookings
→
Channexchannel manager POST /availability POST /restrictions
→
OTAsBooking.com, Airbnb, Expedia…
Key concept: token bucket A token bucket is the usual way to stay under a rate limit. You hold N tokens, and every outbound request spends one. When the bucket is empty you wait. Tokens come back over time. Here the bucket is a simple fixed window: every 60 seconds it's topped back up to 10.

2.2 The narrow picture: Channex's rules

Channex's documentation (docs.channex.io/api-v.1-documentation/rate-limits) sets out the constraints this queue was built around:

  • Per property, per endpoint: 10 availability requests a minute and, separately, 10 restriction/price requests a minute. They're two budgets, not one shared budget of 20. An earlier draft of the plan used one combined bucket, and that got corrected.
  • Batching is expected: a single POST /availability or POST /restrictions can carry a values array covering many rooms and dates. The docs recommend combining changes into one call every few seconds instead of sending many small ones.
  • On a 429, pause the whole property for one minute. Short exponential backoff is not what Channex recommends.
  • 200 OK isn't always success. A response can come back with meta.warnings listing values Channex rejected, such as "rate must be greater than 0".
  • Certification (CERT-4): during certification Channex watches real PMS actions trigger API calls. Every ARI push has to go through the rate-limited path, with no direct calls from resolvers or scripts.

These rules already rule out the obvious design. A single room price change applies to every date for a year ahead, and a naive integration would send one request per date. The next section shows how bad that gets.

3. Intuition

The core idea fits in one sentence: don't send updates when they happen; write them down and send what's been written down on a fixed schedule, one request per endpoint per property. The rest of the design handles what that sentence leaves open: duplicate updates, rate limits and failures.

3.1 The fan-out problem, with toy data

Say a manager edits the Deluxe Double: base price 100, weekend price 130, and a Christmas season (Dec 20 to Jan 5) at 180. enqueueRoomPriceUpdate in ChannelManager/index.js turns that one edit into per-date updates across the next 365 days:

LayerDates touchedExample entry
1. Base price3652026-12-24 → rate 100.00
2. Weekend override~1042026-12-26 (Sat) → rate 130.00
3. Seasonal override172026-12-24 → rate 180.00
Total enqueue calls~486

At 10 requests a minute, 486 individual calls would take about 49 minutes to reach Booking.com. If the manager edits the price twice in that time, the two batches of calls interleave and the final state on the OTAs depends on which call happened to land last.

3.2 Step one: merge by key (last write wins)

Each pending update is stored under the key propertyId:roomId:date. Writing to a key that already exists replaces the old value. Because the base layer is enqueued first, and weekend and seasonal layers after it, later layers overwrite earlier ones on the dates where they overlap:

OrderKeyValueResult
1p1:rp_dlx:2026-12-26{ rate: "100.00" }overwritten
2p1:rp_dlx:2026-12-26{ rate: "130.00" }overwritten
3p1:rp_dlx:2026-12-26{ rate: "180.00" }kept

So ~486 enqueues collapse into exactly 365 entries, one per date, each holding the correct final price. A JavaScript Map gives you this for free, since map.set(key, v) on an existing key overwrites it.

3.3 Step two: flush on a timer, one call per endpoint

Every 5 seconds, flush() collects all pending entries for each property and sends them as one POST /restrictions with all 365 values in the body, plus one POST /availability if there are pending availability entries. Each call spends one token from that endpoint's bucket.

Domain eventroom.updated price 100 / wknd 130 season 180
→
enqueueRestriction ×486validate rate > 0 Map.set(key, fields)
→

→

→

One request instead of 486. The rate limit stops being the bottleneck, and the batching window now decides latency: about 5 seconds from the edit to Channex.

3.4 Step three: what happens under pressure

Say restrictions keep getting enqueued continuously. Flushes run 12 times a minute (every 5 s), but the restriction bucket holds only 10 tokens. Here is one property's minute:

t=0ssend · 9 left
t=5ssend · 8 left
…send…
t=45ssend · 0 left
t=50s, 55sno token → skip; items keep merging
t=60srefill to 10 → send

A skipped tick loses nothing. The entries stay in the map, and any newer values keep overwriting older ones, so the next send carries the latest state rather than a backlog of stale ones. Waiting makes the next batch smaller relative to the work done, which is the opposite of what happens in a FIFO job queue.

If Channex still answers with 429, perhaps because a second process is also calling it, the property is paused for a flat 60 s:

t=0sPOST → 429
t=5spaused (both buckets)
…paused
t=55spaused
t=60spause cleared → send merged state
other propsunaffected throughout
Two kinds of failure, two different responses Transient (429, network error, 5xx): items stay pending and are retried on a later tick. Deterministic (meta.warnings in a 200, such as a rejected rate): items are dropped and recorded as a failed ChannelEvent, because resending the same invalid payload would fail the same way forever.

4. Code walkthrough

With that picture in mind, the code is short. It's easiest to read in the order data moves through it: enqueue, flush, error handling, and then the code around the queue that feeds and protects it.

4.1 State: two maps and a per-property record

apps/backend/ChannelManager/services/channexSyncQueue.js

const TOKENS_PER_BUCKET = 10;
const REFILL_WINDOW_MS = 60_000;
const PAUSE_MS = 60_000;
const DEFAULT_FLUSH_INTERVAL_MS =
  Number(process.env.CHANNEX_FLUSH_INTERVAL_MS) || 5000;

// Map<propertyId, { availabilityTokens, restrictionTokens, lastRefillAt, pausedUntil }>
const propertyState = new Map();

// Map<`${propertyId}:${roomId}:${date}`, item> — Map.set on an existing key overwrites,
// giving last-write-wins merge for free.
const pendingAvailability = new Map();
const pendingRestrictions = new Map();

All state lives in the Node process. That makes it fast and simple, and it's also why the design is limited to a single instance (see §5.4).

4.2 Enqueue: validate, then overwrite

function enqueueRestriction(propertyId, channexPropertyId, roomId, date, fields) {
  const errors = getRestrictionFieldErrors(fields);   // rate > 0, min_stay ≥ 1, …
  if (errors.length > 0) {
    logger.warn(`[channexSyncQueue] Skipping restriction enqueue: ...`);
    recordSyncFailure({ propertyId, eventType: "restriction.pushed", error: ... });
    return;                                           // never enters the map
  }
  const key = mergeKey(propertyId, roomId, date);
  pendingRestrictions.set(key, { propertyId, channexPropertyId, roomId, date, fields });
}

Enqueueing is synchronous and cheap. The caller, usually a GraphQL mutation that saved a room, returns right away. Bad data is rejected before it can use up a token, because Channex would only send it back as a warning.

4.3 The flush loop

async function flush() {
  const propertyIds = new Set();                       // every property with pending work
  for (const item of pendingAvailability.values()) propertyIds.add(item.propertyId);
  for (const item of pendingRestrictions.values()) propertyIds.add(item.propertyId);

  for (const propertyId of propertyIds) {
    const state = getOrInitState(propertyId);
    if (state.pausedUntil && Date.now() < state.pausedUntil) continue;   // 429 pause
    if (state.pausedUntil && Date.now() >= state.pausedUntil) state.pausedUntil = null;
    ...
    await flushAvailabilityForProperty(propertyId, channexPropertyId, state);
    await flushRestrictionsForProperty(propertyId, channexPropertyId, state);
  }
}

function startFlushLoop(intervalMs = DEFAULT_FLUSH_INTERVAL_MS) {
  if (flushTimer) return flushTimer;
  flushTimer = setInterval(() => {
    flush().catch((err) => logger.error(`[channexSyncQueue] flush cycle failed: ${err.message}`));
  }, intervalMs);
  return flushTimer;
}

4.4 Per-property push: token, batch, classify the outcome

async function flushRestrictionsForProperty(propertyId, channexPropertyId, state) {
  const { keys, items } = itemsForProperty(pendingRestrictions, propertyId);
  if (items.length === 0) return;
  if (!hasToken(state, "restriction")) return;          // skip tick, keep items

  consumeToken(state, "restriction");
  try {
    const payload = items.map((item) => ({ rate_plan_id: item.roomId, date: item.date, ...item.fields }));
    const res = await channexService.pushRestrictions(channexPropertyId, payload);
    const warnedKeys = processWarnings(res, propertyId, "rate_plan_id", "restriction.pushed");
    for (const key of keys) pendingRestrictions.delete(key);   // success or warned → done
  } catch (err) {
    if (err.status === 429) {
      state.pausedUntil = Date.now() + PAUSE_MS;               // whole property, 60s
      recordSyncFailure({ ..., error: "Rate limit reached, retrying automatically in 60 seconds" });
    }
    // items stay pending, retried next cycle
  }
}

The token bucket itself is a fixed-window counter, refilled lazily when it's checked:

function refillIfDue(state) {
  if (Date.now() - state.lastRefillAt >= REFILL_WINDOW_MS) {
    state.availabilityTokens = TOKENS_PER_BUCKET;
    state.restrictionTokens = TOKENS_PER_BUCKET;
    state.lastRefillAt = Date.now();
  }
}

The decisions log records why a fixed window was chosen over a rolling window: Channex states its limit as a per-minute quota, and a fixed window behaves predictably under jest.advanceTimersByTime().

A small change with a big effect: the service layer used to throw a plain string error, so the queue had no way to tell a 429 from any other failure.

4.6 Who feeds the queue

Core services (RoomService, BookingService) don't know Channex exists. They emit generic domain events, and ChannelManager/index.js turns those events into enqueues:

  • enqueueChannexARIForBooking: a booking created or cancelled sets availability to 0 or 1 for each night of the stay.
  • enqueueRoomPriceUpdate: base, then weekend, then seasonal rates over 365 days, as in §3.1.
  • enqueueRoomStatusUpdate: maintenance sets stop_sell: true for the next year.
  • runDailyFullSync: once a day it recomputes availability for every mapped room from the bookings table and enqueues all of it. This is the safety net that repairs drift.
CERT-4 is enforced by structure channexService.pushAvailability and pushRestrictions are called from exactly one file. ChannexAdapter.pushAvailability() deliberately throws, so an accidental direct call fails loudly in tests instead of quietly bypassing the rate limiter.

4.7 Graceful shutdown: a best-effort drain

apps/backend/server.js

async function shutdownChannexSyncQueue() {
  channexSyncQueue.stopFlushLoop();
  stopRevisionsPoll();
  stopDailyFullSync();
  await Promise.race([
    channexSyncQueue.flush(),                                         // one last batch
    new Promise((resolve) => setTimeout(resolve, SHUTDOWN_DRAIN_TIMEOUT_MS))  // 5s cap
  ]).catch(...);
}

On SIGTERM, the normal redeploy signal, pending items get one more chance to go out. The drain still respects token buckets and pauses, so it's explicitly not a durability guarantee.

It has 18 tests covering independent buckets, the 429 pause and resume, pause isolation between properties, meta.warnings being dropped, the rate/min-stay validators, one call per property per cycle, last-write-wins merging for both maps, and flush-loop start/stop.

5. Interview answers

With the mechanism understood, here are answers to the follow-up questions from the coaching notes, each grounded in what the code actually does.

5.1 The 60-second version of the story

"HospitalityOS syncs room availability and prices to OTAs through Channex, a channel manager. Channex allows 10 availability calls and 10 price/restriction calls per property per minute. A single price edit in our system touches 365 future dates, so one call per change would take close to an hour to go out and could reach the OTAs in the wrong order.

I built a sync queue between our domain events and the Channex client. Updates are written to an in-memory map keyed by property, room and date, so repeated updates to the same date overwrite each other. Every five seconds a flush sends everything pending for each property as one batched request per endpoint, gated by a token bucket per endpoint. On a 429 we pause that property for a minute, as Channex recommends. A price edit now reaches Channex in about five seconds as a single request.

I considered BullMQ and chose not to use it yet. We run a single instance, and a daily full resync repairs anything lost in a crash. I documented that the queue has to move to Redis before we scale horizontally."

5.2 "What happens if a batch fails halfway? Could updates be lost or double-processed?"

Halfway failure. A batch is one HTTP request, so it can't partly succeed on our side. Either the request fails and every item stays in the map to be retried on a later tick, or Channex accepts it and reports individual rejected values in meta.warnings. We sort failures into two groups:

  • Transient (429, 5xx, network): the items stay pending. A 429 pauses the property for a flat 60 s, per Channex's guidance. Other errors are retried on the next tick, limited by the token budget.
  • Deterministic (warnings on a 200): the items are dropped and written as a failed ChannelEvent, which the frontend shows to staff. Retrying would fail the same way every time.

Double-processing. This is where the design is safe by construction: every value we send is an absolute state, never a delta. We send availability: 0 for that date and rate: "180.00", never "subtract one" or "add 20". Sending the same batch twice leaves Channex in the same state, so retries are idempotent without idempotency keys.

Double-booking is a separate, inbound problem. Bookings arrive by webhook. bookingInjector.js looks up an existing booking by channel.channelBookingId before creating one, so a redelivered webhook updates or cancels the existing booking instead of duplicating it. If injection fails, the webhook returns HTTP 500 so Channex redelivers, and a revisions poll catches anything the webhooks missed.

5.3 "How did you choose the batch size and window?"

The trigger is time, not size. The flush runs on a 5 s setInterval, which can be overridden with CHANNEX_FLUSH_INTERVAL_MS. A size trigger doesn't help here: the constraint is how many requests go out a minute, not how big they are, and one request can already carry hundreds of values. So the right move is to send as much as possible in each request and control only how often requests go out.

Why 5 s? Channex's best-practice docs give "combine into one call every ~6 seconds" as an example. 5 s means 12 ticks a minute, slightly more than the 10 tokens available, so under sustained load the token bucket is what actually enforces the limit and a couple of ticks a minute are skipped. That's harmless because skipped items keep merging. We kept 5 s rather than 6 s as a deliberate choice: the latency is a little lower, the bucket guarantees compliance either way, and the value is one environment variable away from changing.

The trade-off: a shorter window gives lower latency but more calls, and would hit the token ceiling more often. A longer window gives bigger batches but slower OTA updates, which matters because the risk is overbooking: a room sold on Booking.com after it was already booked directly.

5.4 "Why not just use BullMQ?" and the weaknesses you should volunteer

Why not BullMQ yet: BullMQ is a FIFO job queue. Each job is a separate unit of work, so you'd have to layer a merge step on top to avoid sending stale values. What this problem needs is a latest-state map plus a rate limiter, and a Map is exactly that. Adding Redis to a single-instance MVP would bring in infrastructure without solving a problem we actually had.

Known limits, stated honestly:

  1. Crash loss. Unflushed items live only in RAM. Mitigations: the SIGTERM drain covers planned restarts, and the daily full sync repairs anything left after a crash.
  2. Multiple instances. Two backend processes would each keep their own bucket and could together send 20 calls a minute. The fix is a shared Redis limiter (BullMQ's built-in limiter, or INCR+EXPIRE) with the pending map also in Redis, for example as a hash per property.
  3. A lost-update race I found while writing this up. flush captures the keys, awaits the HTTP call, then deletes those keys. If a newer value for the same key is enqueued during the await, the delete removes it, and that update is never sent. The fix is one line: delete only if the entry is still the one that was sent (if (map.get(key) === item) map.delete(key)). Until then, the daily full sync repairs availability. Mentioning something like this, found by reading your own code closely, tends to land well with interviewers.

What changes with BullMQ: a repeatable job every 5 s replaces setInterval, Redis holds the pending state so it survives crashes and is shared across instances, BullMQ's rate limiter replaces the in-process buckets, and failed flushes get retries with backoff and a dead-letter view. The merge-by-key idea stays the same whichever tool runs it.
