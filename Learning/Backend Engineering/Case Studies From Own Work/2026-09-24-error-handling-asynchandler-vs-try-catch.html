asyncHandler or try/catch? Error handling in WNP and Hospitality OS

A case study from my own code: WhatsNextPlease (whatsnextplease-monolith/apps/backend) and Hospitality OS (hospitality-os/pms-backend, mirrored in ai-pms/apps/backend). Written 2026-09-24 from the source code and git history.

Short answer for interviews WNP: yes, I used an asyncHandler wrapper together with one centralized Express error middleware. I added both in January 2025 (c06534a, 5a7923f). Services throw typed errors, and the middleware maps Zod, Prisma, AWS SDK and custom BaseError errors to a consistent JSON response.
Hospitality OS: no wrapper. The REST monitoring controllers handle try/catch by hand in every function and build a 500 response inline. The GraphQL side, which is most of the API, needs no wrapper at all, because Apollo catches resolver errors and formatError centralizes them.
What to be honest about: in WNP I adopted the wrapper inconsistently. Many handlers still have their own try/catch that calls next(error), which is redundant but not harmful. The newest controllers use the clean style.

1. Background

Beginner primer: middleware, next, and error middleware (skip if familiar)

An Express app is a pipeline of functions. Each has the signature (req, res, next). A function either ends the request by writing a response (res.json(...)), or it passes control on by calling next().

Express has a second kind of middleware for errors. It has four parameters, (err, req, res, next), and Express recognizes it by that arity alone. When any function calls next(someError), Express skips every ordinary middleware and jumps to the next error middleware registered after it. That is why error middleware is always registered last, after all the routes.

Express 4 also catches a synchronous throw inside a handler and turns it into next(err) for you. The problem, as we will see, is asynchronous code.

The problem async handlers create in Express 4

Both projects run Express 4 (^4.21.x in every package.json). Express 4 was designed before async/await. When it calls your handler, it wraps the call in a synchronous try/catch and ignores the return value. An async function never throws synchronously. It returns a Promise, and if something inside fails, that Promise rejects. Express never looks at the Promise, so nobody observes the rejection.

Key idea An error that only exists as a rejected Promise is invisible to Express 4. It has to be caught and handed over by calling next(err). There are two ways to do that: write a try/catch in every handler, or write it once in a higher-order function that wraps every handler. That function is asyncHandler. (Express 5 forwards rejected Promises itself, which makes the wrapper unnecessary. Neither project has moved to Express 5 yet.)

How the two codebases differ

WNP backend

  • TypeScript, Express 4, Prisma/Postgres, Zod, AWS SDK
  • Layered: routes → controllers → services → repositories
  • Shared error classes in @wnp/types (BaseError, BadRequestError, NotFoundError…)
  • 19 controllers, all REST

Hospitality OS (pms-backend)

  • JavaScript (CommonJS), Express 4, Mongoose/MongoDB
  • Mostly GraphQL via Apollo Server 4 (/graphql)
  • A small REST surface: /api/monitoring (3 controllers)
  • Built with a teammate; I added the GraphQL modules and pino logging (fa9dfa2, 45d762f)

2. Intuition: three ways an error can travel

With that background, we can follow a single failing request through each style. We use one toy request throughout: a client calls an endpoint without a required parameter, or the database throws. Watch where the error is caught and who decides the HTTP status.

A · Centralized (WNP, the intended pattern)
ClientGET /task-sequences/suggest-prefix (no categoryId)
→
Handlerthrow new BadRequestError(...)
→
asyncHandlercatches, calls next(err)
→
errorMiddlewarerecognizes BaseError, adds request context, logs
→
Response400 {code, status, message, details}

The handler only describes what went wrong. One place decides how that becomes HTTP. A Prisma unique-constraint error, a Zod validation error and an AWS S3 404 all take this same route and come out in the same JSON shape.

B · Belt and braces (most WNP handlers)
ClientPOST /skill with bad body
→
HandlerSkillCreateSchema.parse throws ZodError
→
Inner try/catchcatch (e) { next(e) }
→
asyncHandlerits catch never fires
→
errorMiddlewareZodError → ValidationError

The result is identical to A. The error still reaches the middleware exactly once, because the inner catch swallows it before the wrapper could. The wrapper is only a safety net here, and the inner block is boilerplate.

C · Local handling (Hospitality OS REST)
ClientGET /api/monitoring/sensors
→
HandlerSensor.find() rejects
→
Its own catchlogs, res.status(500).json({... error: error.message})
→
errorHandler.jsdefined, never registered

Each function decides its own response. It works, but every function repeats the decision, every failure becomes a 500 (even ones that should be a 4xx), and the raw error.message goes to the client.

GraphQL is a fourth case, and it is centralized too Apollo Server catches any error thrown inside a resolver, sync or async, and puts it in the response's errors array. So Hospitality OS's resolvers simply throw, and formatError in server.js is the single place that logs errors and masks them in production. Architecturally, this is the GraphQL version of pattern A. The framework provides the wrapper.

3. Code walkthrough

3.1 WNP: the wrapper and how it changed

The wrapper went in on 22 January 2025. The first version (c06534a) used Promise chaining:

apps/backend/api/utils/handlers/asyncHandler.ts, c06534a
export const asyncHandler = (handler: AsyncRouteHandler) => {
  return (req: Request, res: Response, next: NextFunction): void => {
    Promise.resolve(handler(req, res, next).catch(next));
  };
};

Two hours later, 5a7923f rewrote it as async/await. That is the current version:

apps/backend/api/utils/handlers/asyncHandler.ts, current
type AsyncRouteHandler = (req: Request, res: Response, next: NextFunction) => Promise<unknown>;

export const asyncHandler = (handler: AsyncRouteHandler) => {
  return async (req: Request, res: Response, next: NextFunction): Promise<void> => {
    try {
      await handler(req, res, next);
    } catch (error) {
      next(error); // This ensures error is passed to error middleware
    }
  };
};
Why the rewrite was an improvement In the first version, Promise.resolve(...) wrapped the result of .catch(next), which is already a Promise, so it did nothing. Worse, handler(...).catch assumes the handler returns a Promise. If a non-async handler threw synchronously, the throw would escape before .catch was attached. await inside try handles both cases: a synchronous throw and a rejected Promise.

3.2 WNP: the one place errors become HTTP

The middleware is registered last in server.ts, after the 404 fallback. That order matters: the 404 handler catches unmatched routes, and error middleware only receives errors passed via next(err).

apps/backend/api/server.ts
  app.use((req, res) => {
    res.status(404).json({ message: 'Not Found' });
  });

  // error Middleware
  app.use(errorMiddleware);

The middleware is a chain of type checks. Each one turns a foreign error type into the app's own BaseError hierarchy, and ErrorHandler.handleError serializes it:

apps/backend/api/middleware/error/error.middleware.ts (condensed)
export const errorMiddleware = (error, req, res, next) => {
  if (res.headersSent) return next(error);          // response already started: let Express close it
  const requestContext = { method: req.method, path: req.path, ip: req.ip, ... };
  try {
    if (isAWSError(error))           → handleAwsErrors()  → NotFoundError | InternalServerError
    if (error instanceof ZodError)   → new ValidationError(messages, { errors })
    if (error instanceof Prisma.PrismaClientKnownRequestError)
                                     → PrismaErrorMapper.mapError(error)
    if (error instanceof BaseError)  → attach requestContext, use as-is
    otherwise                        → log "Unhandled error type", new InternalServerError(...)
    errorHandler.handleError(mapped, res);   // res.status(e.status).json(e.toResponse())
  } catch (handlerError) {
    // failsafe: if error handling itself throws, still send a plain 500
  }
};

Stack traces are only included in logs when NODE_ENV === 'development'. The services contain about 135 throw new …Error statements, so most failures arrive already typed.

The redundant style, where each class method has its own try/catch and is also wrapped:

The clean style, where the handler just throws and returns through a response helper:

apps/backend/api/controller/serialNumber.controller.ts
export const suggestPrefix = asyncHandler(async (req: Request, res: Response) => {
  const { categoryId } = req.query;
  if (!categoryId || typeof categoryId !== 'string') {
    throw new BadRequestError('categoryId query parameter is required');
  }
  const suggestion = await serialNumberService.suggestPrefixForCategory(categoryId);
  return SuccessResponse.ok(res, { message: 'Prefix suggestion generated successfully', data: suggestion });
});
The outlier chat.controller.ts (added Nov 2025 for the chat-app integration) uses static methods without the wrapper, and returns res.status(400|500).json({ success: false, error }) inline. Its error responses have a different shape from the rest of the API (error instead of code/status/message) and skip the centralized logging.

3.4 Hospitality OS: manual try/catch in REST controllers

The three monitoring controllers are plain async functions. Of their 39 try blocks, 36 end in a hand-written 500:

pms-backend/controllers/monitoring/sensor.controller.js
async function getSensors(req, res) {
  try {
    const { propertyId, type, zone, status } = req.query;
    ...
    const sensors = await Sensor.find(query).populate('propertyId', 'name address');
    res.json({ success: true, data: sensors });
  } catch (error) {
    logger.error('Get sensors error:', error);
    res.status(500).json({
      success: false,
      message: 'Failed to fetch sensors',
      error: error.message          // internal message leaks to the client
    });
  }
}

A generic error middleware does exist, but nothing registers it. grep errorHandler finds only its own definition, in both pms-backend and ai-pms/apps/backend:

pms-backend/middleware/errorHandler.js (dead code)
const errorHandler = (err, req, res, next) => {
  logger.error(err.stack);
  const statusCode = err.statusCode || 500;
  res.status(statusCode).json({ success: false, message: err.message || 'Internal Server Error', ... });
};
module.exports = errorHandler;   // never app.use()'d

Because every handler catches its own errors, the missing registration never caused a hang. That is exactly why nobody noticed it.

3.5 Hospitality OS: GraphQL, where the framework is the wrapper

The resolvers contain no try/catch at all (0 across all six modules). They guard, throw, and return the service's Promise:

pms-backend/graphql/modules/task.resolvers.js
tasks: (_, args, { userId }) => {
  if (!userId) throw new Error('Not authenticated');
  return taskService.getTasks(args);    // a rejection here is caught by Apollo
},

All errors meet in one hook:

pms-backend/server.js
formatError: (formattedError, error) => {
  logger.error({ err: error?.originalError || error }, 'GraphQL Error');
  if (process.env.NODE_ENV === 'production') {
    const code = formattedError.extensions?.code;
    if (!code || code === 'INTERNAL_SERVER_ERROR') {
      return { message: 'Internal server error', extensions: { code } };
    }
  }
  return formattedError;
}
Subtle consequence Apollo Server 4 gives a plain new Error(...) the code INTERNAL_SERVER_ERROR. So in production, 'Not authenticated' is masked as 'Internal server error', and the frontend cannot tell an expired session from a server crash. The fix is to throw new GraphQLError('Not authenticated', { extensions: { code: 'UNAUTHENTICATED' } }). That is the GraphQL version of WNP's typed BaseError subclasses.

4. What to say if asked

A version you can say out loud

"In WhatsNextPlease, which is TypeScript on Express 4, I wrote an asyncHandler higher-order function, because Express 4 doesn't forward rejected Promises. It awaits the handler inside a try/catch and calls next(err). Behind it is one error middleware, registered last, that maps Zod errors to validation errors, Prisma known-request errors through a mapper (P2002 unique and P2003 foreign-key violations to validation errors, P2025 to not-found, anything else to a generic database error), AWS SDK errors, and our own BaseError subclasses to one response shape {code, status, message, details}. It hides stack traces outside development and has a failsafe if the handler itself throws. Services just throw typed errors like NotFoundError."

"If I'm honest about the codebase, adoption wasn't perfectly clean. A lot of older handlers still had their own try/catch that called next(error) inside the wrapper, which is redundant. Newer controllers such as the serial-number API are just asyncHandler(async (req, res) => { … throw new BadRequestError(…) }). If I were cleaning it up, I'd delete the inner blocks, or move to Express 5 and drop the wrapper entirely."

"Hospitality OS was mostly GraphQL on Apollo, so there was no wrapper to write. Resolvers throw, and formatError is the central place where we log and mask internal errors in production. The small REST monitoring API used manual try/catch per controller that returned a 500. That's the part I'd refactor to the WNP pattern, since it maps every failure to 500 and leaks error messages."

Likely follow-up questions
  • Why not just use express-async-errors? It monkey-patches Express's router. An explicit wrapper is about 10 lines, typed, and has no global side effects. Express 5 makes both unnecessary.
  • Why check res.headersSent? If a response already started streaming (for example SSE), you can't send a new status. Delegating to Express's default handler closes the connection.
  • Where do you decide the status code? In the error class (BadRequestError → 400), not in the controller. Controllers express intent; the middleware owns the HTTP translation.
  • What's missing? Request IDs in the error response for correlation. Also a process.on('unhandledRejection') guard for errors that happen outside requests, such as schedulers and SSE.
