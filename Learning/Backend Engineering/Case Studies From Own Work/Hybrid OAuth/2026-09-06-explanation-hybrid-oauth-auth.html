Background

For readers new to JWTs and OAuth/OIDC identity providers

If you already know the difference between a symmetric JWT and an OIDC provider's JWKS endpoint, feel free to skip to the timeline. For everyone else, here's the ten-minute version.

A JWT (JSON Web Token) is just a signed bag of claims — a JSON object like { id, username, role } — base64-encoded and signed so that a server can trust it hasn't been tampered with. The simplest possible setup, and the one most homegrown systems start with, is HMAC signing (algorithm HS256): one secret string is used to both sign the token at login time and verify it on every subsequent request. Whoever holds that secret can mint tokens, so it lives only on your own servers.

The problem with rolling your own auth this way is that everything — password hashing, session/token lifetime, account recovery, MFA, brute-force protection, group/role management — is now your team's responsibility, forever. An identity provider (IdP) like Keycloak (open-source, self-hosted) or AWS Cognito (managed) exists to take that off your plate: it owns the user directory, issues tokens on your behalf, and — critically — signs tokens with a private key that never leaves the IdP. Your application only ever sees the public half of that key pair, published at a well-known URL as a JWKS (JSON Web Key Set). Verification becomes: fetch the public key matching the token's kid (key ID), and check the signature with asymmetric RS256 instead of a shared secret.

Key definition OIDC (OpenID Connect) is just OAuth2 plus a standard identity layer — it defines the token shapes (access, ID, refresh), the /token and /certs (JWKS) endpoints, and standard claims like sub (subject — the IdP's permanent user ID), groups, and email. Both Keycloak and Cognito are OIDC-compliant, which is precisely what lets one small library treat them almost interchangeably.

The situation these two repos are in

whatsnextplease-monolith ("WNP") is a task-management platform that has had its own JWT auth system, hand-rolled with the jsonwebtoken npm package and a bcrypt-hashed password column in Postgres, since day one. Identity-provider-shared-infra is a newer, separate repository whose job is to stand up a shared identity provider — a single AWS Cognito User Pool (defined as CDK infrastructure-as-code) usable by both WNP and a sibling product, HCC — plus a local Keycloak instance (via Docker Compose) that mirrors that Cognito setup for development, and a small TypeScript package, @HillCountryCoder/auth-client, published to GitHub Packages, that both apps can import to validate tokens from either provider through one common interface.

The problem this created: WNP already had real users, with real passwords, sitting in its own database, and none of them existed in Cognito or Keycloak. You can't migrate a live product's entire user base to a new identity system overnight without locking everyone out. That constraint — keep old users working with zero downtime while new users (and eventually everyone) move to the shared IdP — is the entire reason "hybrid" auth exists, and it shapes almost every code path described below.

The big picture Legacy JWT auth ran alone for about a year. In parallel, a completely separate repository built a shared, dual-provider identity service designed to serve two products (WNP and HCC) from one Cognito User Pool. In January 2026 the two were stitched together — not by ripping legacy auth out, but by layering the new system on top of it. WNP's own documentation (apps/docs/authentication/01-OVERVIEW.md) names this explicitly as "Phase 1: Coexistence" of a planned three-phase migration, ending eventually in "Phase 3: IDP Only," with legacy JWT removed.

Intuition: what "hybrid" actually means here

It's worth being precise about what "hybrid" does not mean in this system, because the term is overloaded. It is not "session cookies plus JWT," and it is not a browser-redirect SSO flow where WNP forwards the user to a Cognito or Keycloak login page. Users still type their username and password directly into WNP's own sign-in form. What's hybrid is which system verifies and issues the token behind the scenes, decided per-user and re-decided on every request.

Think of it as a system with three simple states, and a login/verification pipeline that walks through them in order every time:

State 1 — Unmigrated cognitoSub is NULL.
User only exists in WNP's own Postgres table, authenticated by passwordHash + local HS256 JWT.
→
State 2 — Migrating Happens transparently on this user's next successful sign-in: WNP creates them in Keycloak/Cognito, then stamps cognitoSub onto their row.
→
State 3 — Migrated cognitoSub is set. All future sign-ins get real IdP tokens (RS256, JWKS-verified), with legacy JWT kept only as an emergency fallback if the IdP is briefly unreachable.

Now picture two employees, Priya and Sam. Priya signed up for WNP back in March 2025 — long before any of this existed — so her row has passwordHash = "$2b$10$..." and cognitoSub = NULL. Sam signs up today, after the hybrid system shipped, so his row gets cognitoSub = "8f2a...-91cd" the moment his account is created, and his passwordHash is really only kept as a legacy safety net.

When Priya logs in, WNP checks her password the old way (bcrypt against passwordHash) — the same check as before — but instead of just handing her a JWT, it quietly creates her as a Cognito/Keycloak user in the background using the same password, records the resulting cognitoSub back onto her row, and hands her Cognito's access token as if nothing changed on her end. From that moment forward, Priya's account is indistinguishable from Sam's. The next time she logs in, the "already migrated" branch fires directly — no more one-time migration step.

Sign-in decision tree — AuthService.signin()

Does username + password match a row (User or Client)?
No → 401 "Invalid username or password"
Yes →
Is cognitoSub set on that row?
No (unmigrated) → create user in IdP → stamp cognitoSub → exchange credentials for an IdP token
If any of that fails → fall back to a locally-signed 12h JWT ("legacy mode")
Yes (migrated) → exchange credentials for a fresh IdP token directly
If the IdP call fails (outage, network) → fall back to a locally-signed 12h JWT anyway
A subtlety worth noticing The password check against passwordHash still runs even for migrated users — that's why passwordHash could only be made optional, not removed, on the Prisma schema. This is what lets legacy-JWT fallback keep working indefinitely, but it also means a migrated user's password is now, in effect, stored (as a hash) in two places that can silently drift apart if one system's password is changed without updating the other.

On the verification side — every subsequent API call the user makes — the logic is symmetric: try the IdP first, and only fall back to legacy JWT if that fails. This ordering matters: it means as more users migrate, the legacy path is exercised less and less often, and it degrades gracefully rather than needing a cutover date.

Notice that the two strategies key off different identifiers: an IdP token's owner is found by cognitoSub (a UUID-like string from the IdP), while a legacy token's owner is found by the local database's own primary-key id. This is exactly why the cognitoSub column had to be introduced — it's the bridge that lets a token minted by an external system be traced back to WNP's own user row.

Code walkthrough

1. The shared library: one interface, two providers

Everything downstream depends on @HillCountryCoder/auth-client exposing one shape (IAuthService.validateToken()) regardless of which provider is behind it. The factory function is refreshingly small:

Identity-provider-shared-infra/packages/auth-client/src/factory.ts
export function getAuthService(
  provider?: AuthProvider,
  config?: AuthServiceConfig
): IAuthService {
  const authProvider =
    provider || (process.env.AUTH_PROVIDER as AuthProvider) || "cognito";

  switch (authProvider) {
    case "keycloak":
      return new KeycloakAuthService({
        validateAudience: false,
        ...config,
      });
    case "cognito":
      return new CognitoAuthService(config);
    default:
      throw new Error(`Unknown auth provider: ${authProvider}`);
  }
}

One detail worth calling out: Keycloak is instantiated with validateAudience: false by default. Standard OIDC audience validation checks that a token's aud claim matches the expecting client; Keycloak's direct-grant (username/password) tokens don't reliably populate that claim the way authorization-code-flow tokens do, so this codebase validates the azp ("authorized party") claim instead when audience validation is off — you can see that fallback inside KeycloakAuthService.validateToken() below.

3. Making the schema hybrid-aware

The single commit that unlocks everything else is the Prisma migration adding cognitoSub:

whatsnextplease-monolith/apps/backend/prisma/schema.prisma (lines 39–47, 95–101)
model User {
    id                   String                   @id @default(uuid())
    ...
    username             String                   @unique
    email                String                   @unique
    passwordHash         String? // make optional since we are moving into cognito sub
    cognitoSub           String?                  @unique
    ...
}

model Client {
    id                   String                   @id @default(uuid())
    ...
    passwordHash         String? // Make optional for Cognito users
    cognitoSub           String?                  @unique
    ...
}

Both fields are nullable, and both are unique. Nullable cognitoSub is what makes the "unmigrated" state representable at all; unique cognitoSub is what allows a fast, unambiguous findUnique({ where: { cognitoSub } }) lookup — exactly the query the hybrid middleware runs on every request that authenticates via the IdP path.

4. Signin: auto-migration with a legacy safety net

The heart of the migration logic lives in AuthService.signin(). The comments in the source describe its own algorithm better than a paraphrase would:

whatsnextplease-monolith/apps/backend/api/services/auth.service.ts (lines 61–169, abridged)
/**
 * Signin with auto-migration
 * 1. Validate credentials
 * 2. Check if user needs migration
 * 3. If YES: Migrate to IDP, get IDP token
 * 4. If NO: Get IDP token directly
 * 5. Fallback to legacy JWT if IDP fails
 */
async signin(request: SigninRequest): Promise<SigninResponse> {
  ...
  // 2. Verify password (even if migrated, we keep passwordHash for fallback)
  const isValidPassword = await comparePwd(password, entity.passwordHash);
  if (!isValidPassword) {
    return { success: false, error: 'Invalid username or password' };
  }

  // 3. Check if user needs migration
  if (!entity.cognitoSub) {
    const migrationResult = await this.migrateUserToIdp(entity, entityType!, password);
    if (!migrationResult.success) {
      logger.warn(`Migration failed for ${username}, using legacy JWT`);
      return this.createLegacyJwtResponse(entity, entityType!);
    }
    return {
      success: true,
      token: migrationResult.token!,
      ...
      migrated: true,
      message: 'Logged in successfully (account upgraded)',
    };
  }

  // 4. User already migrated, get IDP token
  const tokenResult = await tokenExchangeService.getTokenWithPassword(username, password);
  if (!tokenResult.success) {
    logger.warn(`IDP token failed for ${username}, using legacy JWT`);
    return this.createLegacyJwtResponse(entity, entityType!);
  }
  return { success: true, token: tokenResult.tokens!.access_token, ... };
}

The one-time migration step itself is a small saga: create the user in the IdP, then commit cognitoSub to Postgres inside a transaction, then immediately exchange the same credentials for a real IdP token so the user's very first "upgraded" login already returns a Cognito/Keycloak token rather than the legacy one:

whatsnextplease-monolith/apps/backend/api/services/auth.service.ts (lines 174–255, abridged)
private async migrateUserToIdp(entity: any, entityType: 'user' | 'client', password: string) {
  // 1. Determine IDP group
  const role = entityType === 'client' ? Roles.CLIENT : (entity.role?.name ?? Roles.TASK_AGENT);
  const idpGroups = [idpAdmin.mapRoleToGroup(role)];

  // 2. Create user in IDP
  const createResult = await idpAdmin.createUser({
    username: entity.username, email: entity.email, password,
    groups: idpGroups, role, ...
  });
  if (!createResult.success) {
    return { success: false, error: createResult.error };
  }

  // 3. Update database with cognitoSub (within transaction)
  await prisma.$transaction(async tx => {
    if (entityType === 'user') {
      await tx.user.update({ where: { id: entity.id }, data: { cognitoSub: createResult.sub } });
    } else {
      await tx.client.update({ where: { id: entity.id }, data: { cognitoSub: createResult.sub } });
    }
  });

  // 4. Get IDP token
  const tokenResult = await tokenExchangeService.getTokenWithPassword(entity.username, password);
  ...
}

And the fallback is deliberately minimal — a plain HS256 sign, same as day one, just with an explicit usedLegacy: true flag so downstream code (and monitoring) can tell the two token flavors apart:

whatsnextplease-monolith/apps/backend/api/services/auth.service.ts (lines 259–281)
private createLegacyJwtResponse(entity: any, entityType: 'user' | 'client'): SigninResponse {
  const SECRET = process.env.SECRET!;
  const role = entityType === 'client' ? Roles.CLIENT : entity.role?.name || Roles.TASK_AGENT;

  const token = jwt.sign({ id: entity.id, username: entity.username, role }, SECRET, {
    expiresIn: '12h',
  });

  return {
    success: true,
    token,
    [entityType === 'user' ? 'user' : 'client']: this.sanitizeEntity(entity),
    usedLegacy: true,
    message: 'Logged in successfully (legacy mode)',
  };
}

5. Signup: IdP-first, with rollback on the way back

New accounts never enter the world "legacy-only" — they're created in the IdP first, and only committed to Postgres once the IdP confirms success. If the local database write then fails, the code compensates by deleting the just-created IdP user, so you don't end up with an orphaned Cognito/Keycloak account with no corresponding WNP row:

whatsnextplease-monolith/apps/backend/api/services/auth.service.ts (lines 326–431, abridged)
// 4. Create user in IDP FIRST (atomic operation #1)
const idpResult = await idpAdmin.createUser({ username, email, password, groups: idpGroups, role });
if (!idpResult.success) {
  return { success: false, error: `Failed to create account: ${idpResult.error}` };
}
const cognitoSub = idpResult.sub!;

// 5. Create user in database WITH cognitoSub (atomic operation #2)
try {
  entity = await prisma.user.create({
    data: { username, email, passwordHash: hashedPassword, cognitoSub, ... },
  });
  ...
} catch (dbError) {
  // Database creation failed, rollback IDP user
  logger.error('Database user creation failed, rolling back IDP user:', dbError);
  await idpAdmin.deleteUser(cognitoSub).catch(deleteError => {
    logger.error('Failed to rollback IDP user:', deleteError);
  });
  return { success: false, error: 'Failed to create account (database error)' };
}
This isn't a true distributed transaction Between "create in IDP" and "create in DB," there's a window where the process could crash and leave an orphaned IdP user with no compensating rollback ever run. The try/catch handles the common failure mode (DB write throws synchronously) but not a hard process crash mid-flight. WNP's own 04-MIGRATION-GUIDE.md acknowledges this as a known risk and proposes a future reconciliation job.

6. Request-time verification: two middlewares, same pattern

verifyTokenHybrid is the workhorse — used on the Authorization header for nearly every protected route — and follows exactly the "try IdP, fall back to legacy" order described in the diagram above:

whatsnextplease-monolith/apps/backend/api/middleware/auth/hybrid-auth.middleware.ts (lines 36–133, abridged)
// STRATEGY 1: Try Cognito/Keycloak authentication first
try {
  const cognitoResult = await authService.validateToken(token);
  if (cognitoResult.isValid && cognitoResult.user) {
    const { user: cognitoUser } = cognitoResult;
    const isInternalUser = cognitoUser.groups?.some(g => g.includes('WnpInternalUsers'));
    const isExternalClient = cognitoUser.groups?.some(g => g.includes('WnpExternalClients'));

    let dbEntity: any = null;
    if (isInternalUser) {
      dbEntity = await prisma.user.findUnique({ where: { cognitoSub: cognitoUser.sub }, include: { role: true } });
    } else if (isExternalClient) {
      dbEntity = await prisma.client.findUnique({ where: { cognitoSub: cognitoUser.sub }, include: { role: true } });
    }

    if (dbEntity) {
      req.user = { id: dbEntity.id, username: dbEntity.username, role: userRole!, cognitoSub: cognitoUser.sub, ... };
      return next();
    }
    // User found in IDP but not in DB - this is an error state
    return res.status(404).json({ message: 'User not found in database' });
  }
} catch (cognitoError) {
  // Continue to legacy JWT fallback
}

// STRATEGY 2: Fallback to legacy JWT authentication
try {
  const decodedUser = jwt.verify(token, SECRET) as UserJwtPayload;
  let dbEntity = decodedUser.role !== Roles.CLIENT
    ? await prisma.user.findUnique({ where: { id: decodedUser.id }, include: { role: true } })
    : await prisma.client.findUnique({ where: { id: decodedUser.id }, include: { role: true } });

  if (dbEntity) {
    req.user = { id: dbEntity.id, username: dbEntity.username, role: dbEntity.role?.name || decodedUser.role };
    return next();
  }
} catch (jwtError) { /* falls through */ }

// Both authentication methods failed
return res.status(401).json({ message: 'Invalid or expired token' });

A near-identical structure — same two strategies, same ordering — exists in verifyTokenFromQuery for the handful of endpoints (file downloads, SSE streams) that need the token in a query string instead of a header, since those requests are often triggered by a plain <a href> or EventSource where you can't set custom headers.

The original, legacy-only verifyToken is still present, unchanged since 2025, and is deliberately kept around as a minimal fallback used where hybrid behavior isn't needed:

whatsnextplease-monolith/apps/backend/api/middleware/auth/auth.middleware.ts (lines 12–32)
export const verifyToken = async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
  try {
    const token = req.headers.authorization?.split(' ')[1];
    if (!token) {
      res.status(401).json({ message: 'No token provided' });
      return;
    }
    const decodedUser = jwt.verify(token, SECRET) as UserJwtPayload;
    req.user = decodedUser;
    next();
  } catch (error) {
    if (error instanceof jwt.JsonWebTokenError) {
      res.status(401).json({ message: 'Invalid token' });
      return;
    }
    next(error);
  }
};

7. The frontend has to reconcile token shapes too

Next.js's edge middleware doesn't (and shouldn't) verify signatures — that's the backend's job — but it still needs to read a role out of the token to decide which routes to allow. Because a token might be a legacy JWT, a Keycloak token, or a Cognito token, extractRole() tries each known shape in a deliberate priority order:

whatsnextplease-monolith/apps/web/middleware.ts (lines 20–49)
/**
 * Extract role from token payload
 * Handles both legacy JWT and IDP tokens (Keycloak/Cognito)
 */
const extractRole = (payload: any): Roles | null => {
  // Legacy JWT format
  if (payload.role && typeof payload.role === 'string') {
    return payload.role as Roles;
  }

  // IDP token: wnp_role custom attribute (set for all WNP users)
  if (payload.wnp_role && typeof payload.wnp_role === 'string') {
    return payload.wnp_role as Roles;
  }

  // Cognito: custom:wnp_role attribute (set for all WNP users)
  if (payload['custom:wnp_role'] && typeof payload['custom:wnp_role'] === 'string') {
    return payload['custom:wnp_role'] as Roles;
  }

  // Safety net fallback: infer from groups if wnp_role missing
  const groups: string[] =
    payload.realm_access?.roles || payload['cognito:groups'] || payload.groups || [];

  if (groups.includes('WnpExternalClients')) return Roles.CLIENT;
  if (groups.includes('HccUsers')) return Roles.CLIENT; // HCC default
  if (groups.includes('WnpInternalUsers')) return Roles.TASK_AGENT; // safest default

  return null;
};

This function is a compact fossil record of the whole project's evolution: legacy role first (oldest), then the newer wnp_role/custom:wnp_role custom attribute (added April 2026, commit a3258e7), and finally a group-name-based fallback (the original January 2026 approach), kept as a safety net in case the custom attribute is ever missing on a token.

async refreshToken(refreshToken: string) {
  const provider = env.AUTH_PROVIDER;
  if (provider === 'keycloak') {
    return await this.refreshKeycloakToken(refreshToken);
  } else if (provider === 'cognito') {
    return await this.refreshCognitoToken(refreshToken);
  }
  return { success: false, error: `Unknown AUTH_PROVIDER: ${provider}` };
}
