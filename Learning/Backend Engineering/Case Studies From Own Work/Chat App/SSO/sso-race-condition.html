Background: two apps, one identity

There are two separate applications here, each with its own codebase, its own database, and — critically — its own idea of who is logged in.

whatsnextplease-monolith (I'll call it WNP) is the main product: a Next.js frontend (apps/web) talking to an Express-style backend (apps/backend), backed by Postgres via Prisma. Users log in here the normal way — session cookie, JWT, whatever WNP's own auth stack does — and that's the identity we start from.

chat app is a separate product: a Socket.IO-based real-time chat system, with its own Next.js frontend (Chat-App-Frontend) and its own Express + MongoDB backend (chat-app-backend). It has its own users, its own tenants, its own sessions. WNP embeds it as an iframe so that a WNP user can chat without leaving the page.

The problem this whole system solves is: a user is already authenticated in WNP — how do we get them authenticated in chat-app, inside an iframe, without asking them to log in a second time? That's Single Sign-On (SSO), and because the chat app is multi-tenant (many different customer organizations use the same chat-app deployment), it also has to answer which tenant does this user belong to, and is that tenant even fully set up yet?

If you already know SSO patterns
Skip ahead to Architecture Overview — the interesting part of this story is less "how SSO works" in general and more the specific handshake mechanism used here (Socket.IO's handshake-time auth field) and the multi-tenant provisioning race it replaced.

Architecture Overview — how SSO works today

Let's walk through exactly what happens, in order, when a logged-in WNP user opens the chat panel. I'll number each step so we can refer back to them later.

1. The iframe embed

Two WNP components render the chat iframe — one for a full-page chat view, one for a modal dialog. Both build the embed URL the same way, delegating the actual token-fetching to a shared hook.

const CHAT_BASE_URL = (process.env.NEXT_PUBLIC_CHAT_APP_URL || 'http://localhost:3000')
  .replace(/\/embed\/?$/, '');
const CHAT_EMBED_URL = `${CHAT_BASE_URL}/embed`;
...
<iframe
  ref={iframeRef}
  src={iframeUrl}   // built by useChatAuth(): `${CHAT_EMBED_URL}?ssoToken=...&ssoSignature=...&t=...`
  title="Messages"
  sandbox="allow-same-origin allow-scripts allow-popups allow-forms allow-top-navigation-by-user-activation ..."
  ...
/>

Notice the token and signature travel as plain query-string parameters on the iframe's src. That's a deliberate choice worth flagging now, because it becomes important later: whatever is in that URL is what the chat app's frontend has to work with the instant the iframe starts loading — there's no separate back-channel at load time.

2. Minting the SSO token (HMAC signing)

The actual token is produced by a WNP backend route, gated behind WNP's own authentication middleware (so only an already-logged-in WNP user can request one).

whatsnextplease-monolith/apps/backend/api/routes/chat.routes.ts
router.get('/init-token', verifyTokenHybrid, ChatController.generateInitToken);
whatsnextplease-monolith/apps/backend/api/controller/chat.controller.ts
const CHAT_SHARED_SECRET = env.CHAT_SHARED_SECRET!;
const TENANT_ID = env.TENANT_ID || 'whatsnextplease';

static async generateInitToken(req: AuthenticatedRequest, res: Response) {
  if (!req.user) return res.status(401).json({ error: 'Not authenticated' });

  let user = req.user.role === 'CLIENT'
    ? await prisma.client.findUnique({ where: { id: req.user.id }, select: {...} })
    : await prisma.user.findUnique({ where: { id: req.user.id }, select: {...} });

  const payload = {
    tenantUserId: user.id,
    email: user.email,
    name: /* contactName or firstName+lastName */,
    avatarUrl: user.avatarUrl || undefined,
    tenantId: TENANT_ID,
    externalSystem: 'wnp',
    timestamp: Date.now(),
    nonce: crypto.randomBytes(16).toString('hex'),
    iss: 'whatnextplease',
    aud: 'chat-app',
    exp: Math.floor(Date.now() / 1000) + 300, // 5-minute expiry
  };

  const token = Buffer.from(JSON.stringify(payload)).toString('base64');
  const signature = crypto.createHmac('sha256', CHAT_SHARED_SECRET).update(token).digest('hex');

  res.json({ success: true, token, signature, chatUrl: CHAT_APP_URL });
}
What's actually being signed
It's important to be precise here: the HMAC signs the base64 string, not the raw JSON object. So signature = HMAC-SHA256(CHAT_SHARED_SECRET, token) where token is already base64(JSON.stringify(payload)). The payload itself bundles: who the user is (tenantUserId, email, name), which tenant they belong to (tenantId), a 5-minute expiry (exp) to bound the token's useful lifetime, a random nonce to make each token unique even for the same user issued twice, and issuer/audience fields (iss, aud) that pin the token to this specific integration.

CHAT_SHARED_SECRET and TENANT_ID come from zod-validated environment config, backed in production by AWS Secrets Manager:

whatsnextplease-monolith/apps/backend/api/config/environment.ts
CHAT_APP_API_URL: z.string().url().default('http://localhost:5002'),
CHAT_SHARED_SECRET: z.string().min(64),
CHAT_APP_REGISTRATION_TOKEN: z.string().min(64),
TENANT_ID: z.string().min(1).default('whatsnextplease'),

3. Getting the token to the iframe

The frontend never calls the WNP backend's chat route directly from client code — it goes through a same-origin proxy so the request carries the user's session cookies (which the browser wouldn't attach to a cross-origin fetch to the backend's own host).

whatsnextplease-monolith/apps/web/hooks/use-chat-auth.ts
async function silentRefresh(): Promise<boolean> {
  const response = await fetch('/api/proxy/chat/init-token', { credentials: 'include' });
  const data = await response.json();
  sharedAuthState = { ...sharedAuthState, token: data.token, signature: data.signature };
  return true;
}

async function fetchChatToken(): Promise<void> {
  await silentRefresh();
  const { token, signature } = sharedAuthState;
  const url = new URL(CHAT_EMBED_URL);
  url.searchParams.set('ssoToken', token!);
  url.searchParams.set('ssoSignature', signature!);
  url.searchParams.set('t', Date.now().toString());
  sharedAuthState = { token, signature, iframeUrl: url.toString(), ... };
}

This hook is a module-level singleton — all the components that want to show chat share one fetch and one iframe URL, rather than each independently hitting the token endpoint.

There's a second delivery path worth mentioning, used only after the iframe is already loaded: if the chat app reports an auth error mid-session (say the token expired), WNP silently re-fetches a token and pushes it into the already-mounted iframe via postMessage, rather than reloading the iframe entirely:

iframe?.contentWindow?.postMessage(
  { source: 'wnp', type: 'CHAT_REAUTH', payload: { ssoToken: token, ssoSignature: signature } },
  CHAT_BASE_URL
);

So today's system actually uses both mechanisms — query params for the very first load, postMessage for silent re-auth without a remount. Keep that in mind; it matters for the history section below.

4. The Socket.IO handshake

On the chat app's side, the embedded page reads the token straight out of the URL on mount:

chat app/Chat-App-Frontend/app/embed/page.tsx
useEffect(() => {
  const searchParams = new URLSearchParams(window.location.search);
  const ssoToken = searchParams.get("ssoToken");
  const ssoSignature = searchParams.get("ssoSignature");

  if (ssoToken && ssoSignature) {
    authenticateViaSocket(ssoToken, ssoSignature);   // WebSocket-first auth
    return;
  }
  // else fall back to isAuthenticated (existing session) or show error
}, []);

The key architectural decision is in lib/socket.ts: rather than making a REST call to trade the token for a session and then opening a socket, the token and signature are handed straight to Socket.IO's connection options as the auth field.

chat app/Chat-App-Frontend/lib/socket.ts
export const initializeSocket = (options?: ConnectOptions): Socket => {
  if (options?.ssoToken && options?.ssoSignature) {
    if (socket) { socket.removeAllListeners(); socket.disconnect(); socket = null; }
  }
  const authConfig: any = {};
  if (options?.ssoToken && options?.ssoSignature) {
    authConfig.ssoToken = options.ssoToken;
    authConfig.ssoSignature = options.ssoSignature;
  } else {
    // fallback: existing JWT/tenantId from auth store
  }
  socket = io(SOCKET_URL, { autoConnect: false, withCredentials: true, auth: authConfig });
  return socket;
};
Why this matters
Socket.IO ships an auth option specifically so that credentials can be validated before a connection is fully established, via server-side middleware registered with io.use(...). That means the SSO token doesn't get its own bespoke REST endpoint on the chat-app side at all — the socket connection attempt is the login request. If validation fails, the connection simply never completes (a connect_error event fires instead).

The page then waits for one of two outcomes:

newSocket.once("authenticated", (data: any) => {
  if (data.success && data.user) {
    actions.login(..., data.accessToken, data.refreshToken, "15m", false, tenant);
  }
});
newSocket.once("connect_error", (err: Error) => { ... });

5. Verifying the token (HMAC checking)

On the server, a single middleware function is attached to every incoming socket connection before any handler runs:

chat app/chat-app-backend/src/socket/index.ts
io.use(socketAuthMiddleware);
io.on("connection", (socket) => {
  const userId = socket.data.user._id.toString();
  const tenantId = socket.data.tenantId;
  socket.join(`tenant:${tenantId}:user:${userId}`);
  socket.to(`tenant:${tenantId}`).emit("user_status_changed", { userId, status: "online" });
  registerDirectMessageHandlers(io, socket, userId, tenantId);
  registerChannelHandlers(io, socket, userId, tenantId);
  // ...more handler registrations
});
chat app/chat-app-backend/src/socket/middleware/auth.middleware.ts
export const socketAuthMiddleware = async (socket, next) => {
  const ssoToken = socket.handshake.auth.ssoToken || socket.handshake.query.ssoToken;
  const ssoSignature = socket.handshake.auth.ssoSignature || socket.handshake.query.ssoSignature;

  if (ssoToken && ssoSignature) {
    const payload = await SSOTokenService.validateToken(ssoToken, ssoSignature);
    const user = await SSOTokenService.findOrCreateUser(payload);
    const { accessToken, refreshToken } = await authService.generateTokenPair(user, false, ...);

    socket.data.user = user;
    socket.data.tenantId = user.tenantId;
    await user.save();

    socket.emit("authenticated", { success: true, accessToken, refreshToken, user: {...} });
    return tenantContext.run({ tenantId: user.tenantId }, () => next());
  }

  // Fallback: plain JWT auth for a returning (non-SSO) session
  const token = socket.handshake.auth.token || ...;
  const decodedUser = authService.verifyToken(token);
  const userFromDatabase = await userService.getUserByIdWithTenantId(decodedUser._id, decodedUser.tenantId);
  socket.data.user = userFromDatabase;
  socket.data.tenantId = userFromDatabase.tenantId;
  tenantContext.run({ tenantId: userFromDatabase.tenantId }, () => next());
};

And here's where the HMAC actually gets checked, in the token-validation service:

chat app/chat-app-backend/src/services/sso-token.service.ts
static async validateToken(token, signature) {
  const payload = JSON.parse(Buffer.from(token, "base64").toString("utf-8"));
  // require tenantId / tenantUserId / email / externalSystem present

  if (payload.exp < Math.floor(Date.now() / 1000))
    throw new UnauthorizedError("Token has expired");

  const tenant = await TenantService.getTenantWithSecret(payload.tenantId);
  if (!tenant || !tenant.isActive || tenant.status !== "verified")
    throw new ForbiddenError("Tenant is not active or verified");

  const expectedSignature = crypto
    .createHmac("sha256", tenant.sharedSecret)
    .update(token)
    .digest("hex");

  if (signature !== expectedSignature)
    throw new UnauthorizedError("Invalid token signature");

  return payload;
}
Hold this thought
Look closely at that middle check: if (!tenant || !tenant.isActive || tenant.status !== "verified"). This single line is the crux of the whole race-condition story below. The secret used to verify the signature isn't a global constant baked into the chat-app deployment — it's fetched per tenant from the database, and the tenant record has to already be in the "verified" state, or validation is refused outright, no matter how correct the signature is.

6. Tenant isolation, end to end

tenantId isn't just a field in the payload — it's threaded through literally every layer of the system, so that no code path can accidentally serve one tenant's data to another:

LayerHow tenantId is carried
SSO tokenEmbedded inside the HMAC-signed payload — tampering with it invalidates the signature
Token validationTenantService.getTenantWithSecret(payload.tenantId) looks up that tenant's own secret
User lookupfindOrCreateUser scopes users by {tenantId, externalSystem, externalId}
Socket handshakesocket.data.tenantId, wrapped in tenantContext.run({tenantId}, next)
Socket.IO roomsRoom names are namespaced: tenant:{id}:user:{userId}, tenant:{id}
Database queriesA Mongoose plugin auto-injects {tenantId} into every query

That last row is enforced quite aggressively — the plugin doesn't just default to some tenant if one isn't set, it throws:

chat app/chat-app-backend/src/plugins/tenantPlugin.ts
const tenantContext = new AsyncLocalStorage<{ tenantId: string }>();

schema.pre(['find', 'findOne', 'findOneAndUpdate', 'updateMany'], function () {
  const context = tenantContext.getStore();
  if (!context) throw new Error("🚨 SECURITY: Query attempted without tenant context!");
  this.where({ tenantId: context.tenantId });
});

This is a defense-in-depth choice: even if some future code path forgot to scope a query by tenant, the plugin refuses to run it rather than silently leaking data across tenants.

7. After authentication: rooms and events

Once the authenticated event fires, the client stores its tokens and renders the chat UI. From there it's a fairly standard real-time chat pattern: joining rooms as the user navigates, and listening for matching events.

Client
Opens a channel → emits join_channel
Server
channel.handler.ts adds the socket to that channel's room, scoped by tenant
Server
Broadcasts new_channel_message, message_updated, message_reaction_updated to that room
Client
ChannelWindow.tsx is subscribed and renders new messages as they arrive

Presence works the same way — user_status_changed is broadcast to the tenant room whenever someone connects or disconnects, and the frontend's use-presence.ts listens for it to show who's online.

Intuition: why any of this is tricky

Strip away the code and the core idea is simple: WNP writes a note that says "this is Alice, from tenant Acme, and this note expires in 5 minutes," seals it with a wax stamp only WNP and chat-app know how to make (the HMAC secret), and hands it to Alice's browser to carry over to chat-app. Chat-app checks the stamp, and if it matches, trusts the note.

The subtlety is in who holds the stamp. It would be simple — but wrong — for every tenant to share one global stamp. Instead, each tenant gets its own secret, generated when that tenant is first provisioned into the chat system, and stored in chat-app's own database. That's what lets tenant Acme's stamp be different from tenant Globex's stamp, so that a leaked secret only compromises one tenant.

But this design implies a strict ordering requirement: a tenant's secret has to exist and be marked "ready" in chat-app's database before anyone can present a token signed with it. If WNP tries to mint a token for a tenant that chat-app doesn't yet consider fully set up, the sealed note is technically correct but chat-app will refuse to even check the stamp — as we saw in the validateToken snippet above: if (!tenant.isActive || tenant.status !== "verified") throw ....

That ordering requirement is exactly where the race condition lived, and it's the story the rest of this document tells.

The Bug & the Fix

The architecture described above is the current state. It didn't arrive fully formed — it evolved through several commits across both repositories, in direct response to a real, reproducible failure mode. Here's the chronological story.

Early — original design
postMessage-based handshake

The very first SSO integration used window.postMessage to hand the token to the iframe, followed by a REST call to trade it for a session.

Mid — provisioning added
Three-step tenant registration introduced

To support multiple customer tenants (not just WNP itself), a generate → register → verify provisioning flow was built.

Observed failure
Race condition: auth attempted before verification completed

SSO/socket-auth requests landing between "register" and "verify" were rejected with ForbiddenError, and some failure paths threw raw exceptions instead of clean errors.

Fix, part 1
Socket.IO handshake-time auth replaces postMessage + REST

Collapsing the token hand-off and session creation into a single, atomic handshake step removed one whole class of ordering ambiguity on the client side.

Fix, part 2
Registration flow hardened

Error handling around the pending-verification window was made explicit and non-throwing, with debug logging added to catch the remaining edge cases.

Act I — the postMessage handshake

The original SSO integration worked like this: the iframe would announce itself as ready, the parent WNP page would respond with a token over postMessage, and the iframe would then make a separate REST call to actually log in.

Chat-App-Frontend/app/embed/page.tsx (original design)
const handleMessage = async (event: MessageEvent) => {
  if (event.data?.type === "INIT_CHAT" && event.data?.source !== "chat-app") {
    const { token, signature } = event.data.payload || {};
    await ssoAuth.mutateAsync({ token, signature }); // POST /tenants/sso/init
  }
};
window.addEventListener("message", handleMessage);
window.parent.postMessage({ source: "chat-app", type: "EMBED_READY" }, "*");

Meanwhile, the Socket.IO connection was established separately, using a JWT that only existed once the REST call above had already succeeded:

// hooks/use-sso-auth.ts (original) — plain REST call
apiClient.post("/tenants/sso/init", { token, signature });
// only after this resolves does lib/socket.ts have a JWT to put in socket.auth
Where the fragility came from
This is a three-step relay — postMessage → REST call → separately-initiated socket connection — with two asynchronous hops between "the iframe knows it needs to authenticate" and "the socket is actually connected as that user." Any one of those hops arriving late, out of order, or failing silently left the UI in an ambiguous state.

Act II — the three-step tenant registration

In parallel, chat-app needed a way to onboard a brand-new tenant (a new customer organization) — generating that tenant's own sharedSecret, handing it to WNP, and only trusting SSO tokens once both sides agreed the tenant was properly set up. The chat-app backend documents its own three-step process directly in its response payload:

chat-app-backend — AdminController.generateTenantCredentials response
instructions: {
  step1: "Send sharedSecret and registrationToken to client via secure channel",
  step2: "Client stores sharedSecret in their .env file",
  step3: "Client calls POST /api/tenants/register with all credentials",
  step4: "You verify domain and activate tenant",
}

Concretely, wired end-to-end across both repos, the three steps that matter are:

1

Generate chat-app

POST /api/admin/tenants/generate-credentials creates a Tenant document with status: "pending_registration", isActive: false, a random sharedSecret, and a single-use registrationToken (24h expiry).

2

Register WNP → chat-app

WNP calls POST /api/tenants/register with the registrationToken and sharedSecret it was given. On match, the tenant flips to status: "pending_verification", isActive: true, and the one-time registration token is cleared.

3

Verify chat-app

POST /api/tenants/verify checks the domain and flips the tenant to status: "verified", calling provisionTenant(tenantId).

Act III — the race condition

Here's the crucial detail: step 2 (register) already marks the tenant isActive: true — before step 3 (verify) has run. Anyone who kicked off SSO login (or a WNP user just trying the chat feature) in that in-between window would hit exactly the guard clause we flagged earlier:

if (!tenant || !tenant.isActive || tenant.status !== "verified")
  throw new ForbiddenError("Tenant is not active or verified");

Timeline of the race window

t=0
Step 2 completes: isActive: true, status: "pending_verification"
t=0 to N
⚠️ Race window — any SSO handshake attempted now is rejected, even with a perfectly valid signature, because status !== "verified"
t=N
Step 3 completes: status: "verified" — handshakes now succeed

Worse, some of the surrounding code didn't fail cleanly during this window. A tenant lookup for a not-yet-fully-registered tenant could throw rather than return null, turning what should have been a clean 403/404 into an unhandled 500.

Act IV — moving auth into the Socket.IO handshake

The fix that mattered most for the client-side ambiguity was collapsing the postMessage → REST → separate-socket-connect relay into a single step: hand the token straight to Socket.IO's handshake, as shown in the architecture section above. Compare the before and after directly:

Before (postMessage + REST)After (Socket.IO handshake)
Iframe waits for postMessage from parent Iframe reads token from its own URL on mount — no waiting on the parent's timing
Separate REST call: POST /tenants/sso/init No separate call — the socket connection attempt is the auth request
Socket connects afterwards using a JWT from the REST response Socket connects immediately with ssoToken/ssoSignature in auth; JWTs come back on the same handshake via the authenticated event
Three independent async steps, each a place to get out of sync One atomic handshake — success or connect_error, nothing in between
A shipped bug along the way
Interestingly, right after this migration landed, the server-side authenticated event was emitting a typo'd field — sucess: true instead of success: true — which silently broke the frontend's if (data.success && data.user) check and made the new, supposedly-more-reliable handshake look like it was hanging. A one-line fix corrected the field name. It's a good reminder that collapsing async steps reduces race conditions, but doesn't eliminate ordinary bugs.

postMessage wasn't deleted from the system entirely — it was demoted to a narrower job it's actually well-suited for: pushing a refreshed token into an already-open iframe without tearing it down, for the case where a long-lived session's token needs silent renewal:

// used only for re-auth of an already-connected session, not first load
iframe.contentWindow?.postMessage(
  { source: 'wnp', type: 'CHAT_REAUTH', payload: { ssoToken, ssoSignature } },
  CHAT_BASE_URL
);

Act V — hardening the registration window

The second half of the fix addressed the tenant-registration race directly, by making the pending-verification window fail predictably instead of unpredictably:

  • Tenant lookups return null, not exceptions. A fix changed getTenant so that an unregistered or mid-flight tenant lookup returns null instead of throwing, letting callers produce clean 403/404 responses rather than unhandled 500s.
  • Custom error classes. Error handling in tenant authentication was refactored to use dedicated error types (like the ForbiddenError/UnauthorizedError seen in validateToken above) rather than generic thrown errors, so the failure mode during this window is explicit and catchable.
  • Debug logging around the exact failure points. Logging was added around origin verification and around the token/shared-secret comparison in the registration handler specifically to diagnose failures occurring during this window — i.e., instrumentation aimed squarely at making the race visible when it happened.

Notice what this fix does not do: it doesn't eliminate the ordering requirement between "register" and "verify" — a tenant genuinely can't accept SSO tokens signed with a secret it hasn't finished verifying. What it does is make the in-between window observable and safe to fail, rather than an unhandled crash — the correct response to "not ready yet" is a clean, expected rejection, not a 500.
