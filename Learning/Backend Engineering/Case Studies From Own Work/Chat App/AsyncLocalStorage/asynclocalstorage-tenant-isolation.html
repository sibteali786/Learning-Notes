AsyncLocalStorage Tenant Isolation: Who Opens the Box, and When

Three places open the tenant context, one plugin reads it, and the gap between "opened" and "still open" is where a socket-based chat app quietly earns its keep.

This is a companion piece to "The findById That Slipped Past the Tenant Guard" in this same folder, which walks through a specific incident where a missing entry in a method-name array let one tenant's user data leak to another. That article is about the enforcement side — the plugin that reads the tenant context. This one is about the plumbing side — where that context actually comes from, how long it stays alive, and what happens the moment it isn't there. You can read either one first.

Background: three kinds of "top of a request"

If you've never worked with Node's AsyncLocalStorage before, here's the one-paragraph version: it's a way to make a value — here, a tenant ID — implicitly available to every function called during some span of asynchronous work, without threading it through every function signature as an explicit parameter. You open it once, at the top, with asyncLocalStorage.run(value, callback), and for as long as callback is executing — including every await inside it, and every function it calls, no matter how many layers deep — any code that calls asyncLocalStorage.getStore() gets that same value back. Once callback returns, the value is gone; a later, unrelated piece of code calling getStore() gets nothing.

If you're already comfortable with that, skip ahead — the part specific to this codebase, and the part actually worth understanding carefully, is where "the top" actually is. In a typical request/response web framework, there's exactly one obvious "top": the request comes in, a middleware chain runs, a handler runs, a response goes out, done. This chat app isn't that simple, because it has three genuinely different shapes of "a unit of work that needs a tenant," and each one has to open the box for itself.

The narrow background: the three entry points

  1. A normal HTTP request — has one clear beginning and end, matching the AsyncLocalStorage model closely.
  2. A WebSocket connection — has one beginning (the handshake), but then stays alive indefinitely, receiving many separate events over time. Each event is its own "unit of work," but they don't share a single call stack the way a request's middleware chain does.
  3. Everything else — background jobs, scheduled tasks — has no framework-provided "top" at all; something has to manually decide where a unit of work begins.

All three eventually rely on the same underlying primitive, and the same helper function, runInTenantContext. But only one of them (HTTP) gets that helper "for free," wired into a middleware chain that runs on every request automatically. The other two have to call it by hand, and — as you'll see — the socket case has to call it by hand repeatedly, once per event, which is the detail most worth internalizing from this whole article.

Intuition: a box that closes the moment you stop asking

Picture tenantContext as a single labeled box that lives for the duration of some span of work. Something places a sticky note with the tenant ID written on it inside the box at the start of that span. Any code running "inside" that span — however deeply nested, however many functions removed — can open the box and read the sticky note. The moment the span ends, the box empties. There is no way to reach back in time and read a note left by a span that has already finished.

For an HTTP request, this maps cleanly onto real life: the request starts, the note goes in, every downstream function call is "part of" that request, and when the response is sent, the request is over — box empties, and that's fine, because nothing needs to read the note after the response ships.

A WebSocket connection breaks that clean mapping. The connection itself is a single long-lived "thing" — a user connects once and might stay connected for hours — but the actual work happens in bursts: an event arrives, gets handled, and then nothing happens until the next event. If you naively wrote tenantContext.run({tenantId}, () => { registerAllMyEventHandlers(); }) at connection time, thinking that would cover every future event, you'd be wrong: registering an event handler is not the same as running it. The actual handler function gets invoked later, by Socket.IO's internal event loop, as a brand new call — not nested inside your original .run() callback at all. By the time a message-send event fires, the box from connection time has long since closed.

HTTP request — one span, one box

Request arrives context opens
authMiddleware verifies user, calls tenantContext.run()
next() called inside that callback
Controller runs
Service runs, queries fire
Response sent context closes

Socket connection — one handshake, many disconnected spans

Handshake context opens
next() called inside that callback
Connection idles... context closed
"send_message" event fires later no context
Handler re-opens its own context manually
Handler finishes context closes again
...idle until next event, repeat
The core intuition to take away
AsyncLocalStorage context tracks call-stack nesting, not wall-clock connection lifetime. A WebSocket connection lasting three hours has zero continuous tenant context for almost all of that time — context only exists in the narrow slices where a handler is actively executing, and each of those slices has to open its own box from scratch.

That's why, if you go looking at the socket-handling code, you find the tenant ID stashed somewhere durable — socket.data.tenantId, set once at handshake time — and then every single event handler re-reads that stashed value and re-opens a fresh runInTenantContext box around its own work. The handshake-time context isn't wasted — it protects anything that happens synchronously as part of the handshake continuation — but for the actual chat functionality (sending messages, joining channels, reacting to messages), the handshake's box is already long closed by the time any of that runs.

Code walkthrough: where the box opens, and who reads it

1. HTTP requests — opened once, in authMiddleware

src/common/middlewares/auth.middleware.ts
// CRITICAL: Set tenant context for database isolation
// This ensures all subsequent database queries are automatically
// filtered by the user's tenantId via the tenantIsolationPlugin
return tenantContext.run({ tenantId: user.tenantId }, () => {
  (req as TenantAuthenticatedRequest).tenantId = user.tenantId;
  next();
});

The detail that makes this correct is not obvious on first read: next() — the call that hands control to the rest of the middleware chain, the controller, and everything the controller calls — is invoked from inside the .run() callback. That's what keeps the box open for the entire rest of the request. (This wasn't always true here — an earlier version of this exact file awaited a `Promise` that resolved and returned before calling `next()`, which silently closed the box before any real work ran. That's covered in the companion article's fix commit, 37d7930.)

2. Socket connections — opened at handshake, re-opened per event

src/socket/middleware/auth.middleware.ts
// Attach user to socket data
socket.data.user = userFromDatabase;
socket.data.tenantId = userFromDatabase.tenantId;

// Run next() INSIDE tenant context
tenantContext.run({ tenantId: userFromDatabase.tenantId }, () => {
  next();
});

Same shape as the HTTP version — next() inside .run() — but this only covers the handshake continuation. The real work happens later:

src/socket/channel.handler.ts (representative of ~5 handler files)
socket.on("send_message", async (data) => {
  const tenantId = socket.data.tenantId;
  const result = await runInTenantContext(tenantId, async () => {
    // ...service calls and queries happen here, inside a fresh context...
  });
});

direct-message.handler.ts, message-reaction.handler.ts, attachment.handler.ts, and socket/index.ts all repeat this same pattern — read socket.data.tenantId, wrap the actual work in a fresh runInTenantContext call. It's the correct thing to do, but notice that it's a convention, not something the framework enforces: nothing stops a future event handler from being added that forgets to wrap its body this way — a bug shaped exactly like the findById incident in the companion article, just one layer up the stack.

3. Everything else — runInTenantContext directly

src/plugins/tenantPlugin.ts
export const tenantContext = new AsyncLocalStorage<{ tenantId: string }>();

export async function runInTenantContext<T>(
  tenantId: string,
  fn: () => Promise<T>,
): Promise<T> {
  return tenantContext.run({ tenantId }, fn);
}

This is the one primitive everything else is built from. setTenantContext (used by the HTTP middleware) and the raw tenantContext.run() calls in the socket middleware are really the same operation wearing different clothes — a request-shaped wrapper versus a direct call — but underneath, it's always the same AsyncLocalStorage.run().

4. How the eight models actually read from it

This part is refreshingly uncomplicated: the reading logic exists in exactly one file, src/plugins/tenantPlugin.ts, and every tenant-scoped model opts in with a single line: 

channelSchema.plugin(tenantIsolationPlugin);

tenant.model.ts is correctly excluded: a Tenant document doesn't have a tenantId of its own to be scoped by — it is the thing everything else is scoped around. So this is eight tenant-scoped models sharing one plugin function, not nine models each reimplementing the same logic. Mongoose calls the plugin function once per schema it's applied to, and each call independently attaches the same set of pre(...) hooks — shared code, applied repeatedly, rather than one global hook watching every model at once. Here's the plugin in full, for reference: 

export function tenantIsolationPlugin(schema: Schema<any>) {
  const queryMiddleware = function (
    this: Query<any, any>,
    next: (err?: any) => void,
  ) {
    const context = tenantContext.getStore();
    const filter = this.getFilter();

    if (!filter.tenantId) {
      if (!context?.tenantId) {
        throw new Error(
          "🚨 SECURITY: Query attempted without tenant context! " +
          "All queries must have tenantId.",
        );
      }
      this.where({ tenantId: context.tenantId });
    }
    next();
  };

  schema.pre(
    [
      "find", "findOne", "findOneAndUpdate", "findOneAndDelete",
      "findOneAndReplace", "findById", "count", "create", "insert",
      "insertMany", "countDocuments", "deleteOne", "deleteMany",
      "updateOne", "updateMany",
    ] as any,
    queryMiddleware,
  );

  schema.pre("validate", function (next) {
    const context = tenantContext.getStore();
    if (this.isNew) {
      if (!context?.tenantId) {
        return next(new Error("🚨 SECURITY: Cannot create document without tenant context!"));
      }
      this.tenantId = context.tenantId;
    }
    next();
  });

  schema.pre("save", function (next) {
    if (!this.isNew && this.isModified("tenantId")) {
      return next(new Error("🚨 SECURITY: Cannot modify tenantId! This is immutable."));
    }
    next();
  });

  schema.pre("aggregate", function (next) {
    const context = tenantContext.getStore();
    if (!context?.tenantId) {
      throw new Error("🚨 SECURITY: Aggregate query attempted without tenant context!");
    }
    this.pipeline().unshift({ $match: { tenantId: context.tenantId } });
    next();
  });
}

Four separate hooks, four separate concerns: queryMiddleware for reads and writes routed through named query methods, "validate" for stamping new documents, "save" for preventing tenant reassignment, and "aggregate" for pipelines. All four ask the same question of the same box — tenantContext.getStore() — they just ask it at different points in a document or query's lifecycle.

Fail closed or fail open? Both — depending which gap you hit

Read the query hook again with this specific question in mind: what happens if tenantContext.getStore() returns nothing?

Method IS hooked
e.g. findOne, no context
→
Check runs
context?.tenantId is undefined
→
🚨 Thrown
loud, safe — fails closed
Method NOT hooked
(historically: findById)
→
Check never runs
there's no code to ask the question
→
Query executes unfiltered
silent, wrong answer — fails open

The mechanism is designed to fail closed — when it fires, it either finds a tenant to filter by or it throws, loudly, before touching the database. But its coverage is an enumerated list of method names, not a structural guarantee that covers every possible query shape. Anything outside that list doesn't fail at all, in either direction — it just runs, as if the plugin didn't exist. There's no deliberate fallback, no catch swallowing the security error, no feature flag disabling the check. The fail-open behavior is a side effect of omission, not a designed escape hatch — which is exactly why it went unnoticed for as long as it did: nothing about the code at the call site looks unusual when it silently skips the check.

Worth auditing, not yet confirmed
While tracing this, one more call site with the same shape as the original incident turned up: src/services/message.service.ts, getMessageByIdOrThrowError (around line 51): 
async getMessageByIdOrThrowError(messageId: string): Promise<MessageInterface> {
  const message = await messageRepository.findById(messageId);
  if (!message) {
    throw new NotFoundError("message");
  }
  return message;
}
No runInTenantContext wrapper around a raw findById call — the same pattern that caused the original leak. Whether this is actually exploitable depends on whether tenantContext is already open higher up the call stack every time this runs (likely for HTTP paths that went through authMiddleware; less certain for any socket-originated call path that reaches this method without its own runInTenantContext wrapper). This wasn't traced end-to-end in this session, so treat it as an audit item, not a confirmed second incident.

Improvements: turning "remembered" into "structural"

The companion article's Improvements section covers the enforcement side in depth — replacing the plugin's method-name array with a regex hook or an exec()-level interception, and making tenant scoping a compile-time requirement via a branded TenantScope type. Both apply here too, since the getMessageByIdOrThrowError case above is the same class of bug. What's specific to this article is the socket-layer plumbing, which has its own version of the same underlying problem: correctness depends on every handler author remembering to do the right thing, rather than the framework making the wrong thing impossible to write.

1. Make socket handlers open context by construction, not by convention

Right now, every socket event handler independently writes runInTenantContext(socket.data.tenantId, ...) around its own body. That's five-plus files repeating the same pattern by hand — which is precisely the "remembered convention" shape that caused the original array bug, just at a different layer. A small wrapper applied at registration time removes the possibility of forgetting: 

function withSocketTenant<A extends any[]>(
  socket: Socket,
  handler: (...args: A) => Promise<void>,
) {
  return (...args: A) =>
    runInTenantContext(socket.data.tenantId, () => handler(...args));
}

// usage — the context-wrapping is now guaranteed by the registration
// helper, not by whether the handler author remembered to add it:
socket.on("send_message", withSocketTenant(socket, sendMessageHandler));
socket.on("join_channel", withSocketTenant(socket, joinChannelHandler));

This doesn't change behavior for handlers that already wrap themselves correctly — it just moves the guarantee from "every author remembers" to "every handler registered through this helper is covered, full stop," which is the same shift in kind as replacing an enumerated method-name array with a regex match.

2. Apply the same regex-hook fix from the companion article

Briefly, for continuity: replacing the enumerated method list with a regex-based hook removes the need to remember every method name individually, and would have caught findById (and would catch getMessageByIdOrThrowError's call today) without anyone needing to anticipate it specifically: 

schema.pre(/^find/, queryMiddleware);              // find, findOne, findById, findOneAnd*
schema.pre(/^(count|update|delete)/, queryMiddleware); // count*, updateOne/Many, deleteOne/Many

3. Close the getMessageByIdOrThrowError gap with a required scope parameter

The structural fix proposed in the companion article — a branded TenantScope type that can only be constructed from inside an active tenant context — applies directly here too. Adapted to this call site: 

async findById(id: string, scope: TenantScope): Promise<T | null> {
  return this.model.findOne({ _id: id, tenantId: scope.tenantId });
}

// getMessageByIdOrThrowError now cannot compile without a scope:
async getMessageByIdOrThrowError(
  messageId: string,
  scope: TenantScope,
): Promise<MessageInterface> {
  const message = await messageRepository.findById(messageId, scope);
  if (!message) throw new NotFoundError("message");
  return message;
}
The throughline connecting both articles
Every version of this bug — the original findById array gap, the socket handlers' repeated manual wrapping, and the newly-spotted getMessageByIdOrThrowError pattern — is the same failure mode wearing different clothes: a safety property that depends on a human remembering to invoke it correctly, at every call site, forever. The fixes that actually hold up are the ones that make the unsafe version impossible to write — a regex that matches by shape instead of name, a wrapper that opens context by construction instead of convention, a type that can't compile without proof a scope exists — rather than the ones that just add one more place to remember to check.
