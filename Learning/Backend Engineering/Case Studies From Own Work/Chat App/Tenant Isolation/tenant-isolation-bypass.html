The findById That Slipped Past the Tenant Guard

Background: how the tenant plugin works

This backend is a Mongoose/MongoDB service supporting multiple tenants (separate customer organizations) sharing the same database and the same collections. That's a common and economical design — one users collection, one channels collection, and so on, with every document carrying a tenantId field that says which customer it belongs to. The danger, of course, is that a single missed filter can let one tenant's code accidentally read or write another tenant's data. If you've never worked with a shared-database multi-tenant system before, that's the entire risk in one sentence: every single query, everywhere in the codebase, forever, must remember to filter by tenant — and "must remember" is a fragile place to put a security boundary.

To make that less fragile, this codebase centralizes the enforcement in one place: a Mongoose schema plugin called tenantIsolationPlugin, defined in src/plugins/tenantPlugin.ts. A schema plugin in Mongoose is just a function that gets applied to every model's schema and can attach hooks — code that runs automatically before or after certain operations, without the call site needing to remember to invoke anything. Think of it as an interceptor that sits between "a service calls User.find(...)" and "MongoDB actually runs the query."

The second piece of background you need is AsyncLocalStorage — a Node.js built-in that lets you stash a value (here, the current tenant ID) at the start of handling a request, and have that value be transparently available anywhere later in that request's call stack, without threading it through every function argument. This codebase calls that stashed value the tenant context. An Express middleware, setTenantContext, establishes it once per request (right after authenticating the user); a helper, runInTenantContext, does the same thing for code paths that aren't a plain HTTP request — WebSocket handlers, background jobs, and so on.

If you're already comfortable with Mongoose middleware and AsyncLocalStorage, skip ahead — the part that matters for this story is narrower: which specific Mongoose operations the plugin actually intercepts.

Reader vs. writer: queryMiddleware and runInTenantContext are not the same job

It's easy to conflate these two pieces because they both mention "tenant context," but they sit on opposite sides of the same box. queryMiddleware — the function registered via schema.pre(...) — is a reader. It never determines the tenant itself; all it can do is ask tenantContext.getStore(), "is there anything in the box right now?" If the box is empty, it throws. It has no mechanism for figuring out the tenant from the query alone — a User.findOne({...}) call carries no tenant information on its own.

runInTenantContext(tenantId, fn) is the writer. It's a thin wrapper around AsyncLocalStorage.run({tenantId}, fn): for as long as fn is executing — including every await inside it, and every function it calls, transitively — tenantContext.getStore() will return {tenantId}. The moment fn returns, the box empties again. setTenantContext (the Express middleware) is just runInTenantContext wearing an Express-shaped hat, wired up once in the middleware chain right after authentication.

Put differently: the plugin hook is a smoke detector, and runInTenantContext is the thing that has to actually be in the room for the detector to have anything to detect. A smoke detector with nothing burning doesn't malfunction when it stays silent — it's working correctly. The question is always upstream: did anyone strike a match (call runInTenantContext) before this code path ran?

1. Auth middleware

2. setTenantContext(tenantId)

3. service calls User.findOne(...)

reads the box → finds tenantId → injects filter

For anything outside a normal HTTP request — a WebSocket event handler, a background job, a cron task — there is no Express middleware chain to auto-open the box in step 2. Whoever kicks off that work has to call runInTenantContext(tenantId, () => { ... }) by hand before any query runs inside it. Skip that call, and step 4's reader finds an empty box — which is precisely the shape of the bug this article is about: getUserById called userRepository.findById(id) with no runInTenantContext anywhere in its call chain, so even once findById was added to the hooked-methods list, the fix required also adding the missing runInTenantContext(tenantId, ...) wrapper around it. Neither change alone was sufficient — a reader with nothing to read is a no-op, and a writer whose value nothing reads is unenforced.

The narrow background: the hooked-methods list

tenantIsolationPlugin attaches one hook, queryMiddleware, to a hand-written list of Mongoose query methods via schema.pre([...], queryMiddleware). For every method in that list, before the query actually runs, the hook does two things:

  1. Looks at the query's existing filter. If it already has a tenantId, nothing to do.
  2. Otherwise, it reads the tenant ID out of the AsyncLocalStorage context. If one is present, it silently adds { tenantId } to the filter. If no context is present — meaning some code somewhere queried the database without ever entering a tenant context — it throws: "🚨 SECURITY: Query attempted without tenant context!"

There are sibling hooks too: one on "validate" that stamps a new document with the current tenant ID before it's allowed to save, one on "save" that refuses to let an existing document's tenantId be changed, and one on "aggregate" that injects a $match: { tenantId } stage at the front of any aggregation pipeline. All of them lean on the same idea: read the tenant out of context, and fail loudly if there isn't one.

That "fail loudly" design is exactly what makes this bug interesting — the safety net was designed to be noisy when triggered. So how did a cross-tenant leak happen silently?

The detail to hold onto
The list of methods passed to schema.pre([...]) — find, findOne, findOneAndUpdate, findOneAndDelete, findOneAndReplace, count, create, insert, insertMany, countDocuments, deleteOne, deleteMany, updateOne, updateMany — is a manually typed-out array, not something Mongoose derives automatically from "all query methods." Whatever isn't on that list gets no interception at all: no auto-filter, and — this is the sting — no loud failure either. It's invisible to the plugin entirely.

Intuition: an allow-list with one door left unlocked

Picture the tenant plugin as a security guard standing at a set of named doors into the database — one door labeled find, one labeled findOne, one labeled updateOne, and so on. At each named door, the guard checks your badge (the tenant context) before letting you through, and slams the door in your face with an alarm if you don't have one.

But there was a door with no label on the guard's clipboard at all: findById. Not because anyone decided it should be exempt — it just wasn't written down. Walk up to that door, and there's no guard there. No badge check, no alarm. You just... walk into the building.

Concretely, with toy data: suppose tenant acme has a user with ID u_501, and tenant globex has a user with ID u_777. A request authenticated as someone in globex — whose tenant context correctly says tenantId: "globex" — calls a function that does User.findById("u_501"). If findById were on the guarded list, the plugin would inject tenantId: "globex" into the filter, the ID wouldn't match (because u_501 belongs to acme), and Mongoose would correctly return null. Instead, because findById had no guard at all, the query ran as plain { _id: "u_501" } with no tenant filter whatsoever — and returned acme's user record to code running in a globex request.

The bypassing call: UserService.getUserById

The unlabeled door wouldn't have mattered if nothing ever walked through it. Something did: UserService.getUserById in src/services/user.service.ts. Before the fix, its entire body was this:

src/services/user.service.ts — before commit 37d7930
public async getUserById(id: string): Promise<User> {
  const user = await userRepository.findById(id);
  if (!user) {
    throw new NotFoundError("user");
  }
  return user;
}

userRepository.findById traces down to the base repository's thinnest possible wrapper — src/repositories/base.repository.ts's findById(id) { return this.model.findById(id); } — which is just Mongoose's raw Model.findById. Two things are notably absent from this method, compared to its siblings:

  • No runInTenantContext(...) wrapper — it doesn't even try to establish a tenant scope.
  • It routes through findById, the one query method the plugin doesn't watch.

Either flaw alone might have been caught. If it had gone through findOne instead without a tenant context, the plugin's SECURITY check would have thrown immediately — annoying, but safe, and it would have surfaced in testing or logs right away. Instead, the two gaps stacked: no context, and no guard to notice the missing context. The failure mode wasn't a crash — it was silence, plus a wrong answer.

Why this one was quiet, not loud
Every other query path in this codebase that skips its tenant context fails noisily — that's the plugin doing its job. This one path failed quietly, because it used the one method name the guard's clipboard didn't mention. A loud bug gets found in minutes. A quiet one gets found whenever someone happens to compare notes across tenants.

Code walkthrough of the fix

The fix landed in a single commit, 37d7930 ("feat(fix): tenant content was wrongly applied", 2025-10-17), and it made two changes that only work together.

1. Add the missing method to the guard's list

src/plugins/tenantPlugin.ts
   "findOneAndUpdate",
   "findOneAndDelete",
   "findOneAndReplace",
+  "findById",
   "count",
   "create",

One line. From this commit onward, findById calls are intercepted exactly like findOne and the rest: filtered by tenant if a context exists, or thrown loudly if it doesn't.

2. Give getUserById an actual tenant context to be checked against

Adding the method to the list alone would have just converted the silent bug into a loud crash — getUserById still wasn't establishing any tenant context before calling findById. So the method itself was rewritten to resolve the real tenant and wrap the call:

src/services/user.service.ts — after commit 37d7930
public async getUserById(id: string): Promise<User> {
+  const tenantId = await this.getTenantIdForUser();
+  return runInTenantContext(tenantId, async () => {
+    const user = await userRepository.findById(id);
+    if (!user) {
+      throw new NotFoundError("user");
+    }
+    return user;
+  });
-  const user = await userRepository.findById(id);
-  if (!user) {
-    throw new NotFoundError("user");
-  }
-  return user;
}

Now the shape matches every other correctly-written query in the codebase: establish tenant context, then query, with the plugin able to double-check the filter either way.

A nuance worth flagging (not the main bug)
The same commit touches sibling methods like createUser, and an intermediate version of this fix wrapped some of them in runInTenantContext("default", ...) — a hardcoded tenant string, rather than a tenant resolved from the actual request. That's a different, smaller correctness smell: a hardcoded "default" tenant technically satisfies the plugin's "is there a context?" check, but it defeats the entire point of tenant isolation if it's used anywhere a real tenant should be threaded through instead. It's adjacent to this story, not the headline bug — but if you're auditing this pattern, it's the kind of thing worth grepping for.

Did this get fixed for good, or just fixed once?

This is the part worth being honest about in an interview answer, because the interesting engineering judgment isn't "did you fix the bug" — it's "did you fix the class of bug." Here, the evidence says: no, this was a one-off fix. The two broken call sites were repaired, and the missing method was added to the array — but the underlying fragility that produced the bug in the first place is still sitting in the codebase today.

Residual risk
The enforcement mechanism for tenant isolation is still, today, a single hand-typed array of method-name strings inside tenantPlugin.ts. If a future feature reaches for Model.distinct(...), Model.estimatedDocumentCount(...), Model.bulkWrite(...), or any other Mongoose query method not currently on that list, the exact same failure mode reproduces: no auto-filter, no thrown error, just a silent cross-tenant read or write. Nothing in the codebase — no type, no test, no lint rule — would catch it before it shipped. The findById incident wasn't really about findById specifically; it was the first time this particular kind of gap in a manually maintained allow-list got exercised. It's unlikely to be the last time that class of gap exists, unless the enforcement moves from "remember to update this array" to something the type system or CI can verify on its own.

Improvements: closing the class, not the instance

Everything so far explains what actually happened. This section is different — it's a proposal for what would need to change to make this entire category of bug structurally impossible, rather than merely patched wherever it's been noticed so far. The guiding principle: an allow-list that a human has to remember to update is not a security boundary, it's a to-do list. The fixes below are ordered by leverage — how much of the underlying fragility each one actually removes, versus how much it just adds another layer of hoping someone remembers.

1. Replace the method allow-list with a single choke point (highest leverage)

The core defect in the current design is that tenantIsolationPlugin hooks named methods — find, findOne, findById, and so on — one string at a time, in an array a human has to keep up to date. Mongoose actually gives you two verified ways to stop enumerating and instead intercept by shape. Both are documented, real Mongoose behavior — not invented for this article.

Option A — a regex hook, staying inside Mongoose's own middleware system

schema.pre() accepts a RegExp in place of a method name, matched against the operation name. Mongoose's own docs give exactly this example: schema.pre(/^find/, fn) to strip soft-deleted documents from every find-style query. The important detail for this story: because findById is implemented internally as a call to findOne, a regex hook on /^find/ already covers findById — nobody has to think to list it by name. That reframes the original incident: it wasn't that someone forgot to type "findById" into an array; it's that the array was the wrong data structure to encode "every find-shaped query" in the first place.

src/plugins/tenantPlugin.ts — Option A: regex-based hooks
export function tenantIsolationPlugin(schema: Schema<any>) {
-  schema.pre(
-    [
-      "find", "findOne", "findOneAndUpdate", "findOneAndDelete",
-      "findOneAndReplace", "findById", "count", "create", "insert",
-      "insertMany", "countDocuments", "deleteOne", "deleteMany",
-      "updateOne", "updateMany",
-    ] as any,
-    queryMiddleware,
-  );
+  // Matches find, findOne, findById, findOneAndUpdate,
+  // findOneAndDelete, findOneAndReplace — findById is covered
+  // because Mongoose implements it as a call to findOne internally.
+  schema.pre(/^find/, queryMiddleware);
+
+  // Matches count, countDocuments, updateOne, updateMany,
+  // deleteOne, deleteMany — these don't start with "find", so
+  // they still need their own regex/name, but it's one line
+  // covering a whole family instead of one line per method.
+  schema.pre(/^(count|update|delete)/, queryMiddleware);
  ...
}

This isn't a perfect wildcard — create, insert, and insertMany are document-creation operations, not query operations, so they stay on the existing pre("validate")/pre("save") hooks, which is correct as-is. But two regexes now do the work of thirteen enumerated strings, and — critically — a brand-new method matching an existing pattern (say, a future findOneAndBulkUpdate) is covered automatically, with nothing to remember to add.

Option B — intercept at the actual choke point, Query.prototype.exec()

Every query-based Mongoose method — regardless of name, present or future — ultimately calls Query.prototype.exec() before it reaches MongoDB. This is a documented pattern: caching libraries like top-cache monkey-patch exactly this method to add a cache layer in front of every query, globally, with no per-method registration at all.

src/plugins/tenantPlugin.ts — Option B: override the common terminus
+import { Query } from "mongoose";
+
+const originalExec = Query.prototype.exec;
+
+Query.prototype.exec = function (this: Query<any, any>, ...args: any[]) {
+  const filter = this.getFilter();
+  if (!filter.tenantId) {
+    const ctx = tenantContext.getStore();
+    if (!ctx?.tenantId) {
+      throw new Error(
+        "🚨 SECURITY: Query attempted without tenant context!",
+      );
+    }
+    this.where({ tenantId: ctx.tenantId });
+  }
+  return originalExec.apply(this, args as any);
+};

This is the more complete of the two: literally every Query-based operation funnels through exec() by construction, so there is no method name left to forget. It's also blunter — it patches a shared prototype for the whole process rather than opting in per schema, so it needs a guard (e.g. skip schemas that don't declare a tenantId path) to avoid breaking models that are deliberately tenant-agnostic. aggregate is a separate Aggregate class with its own exec, so the existing pre("aggregate") hook still needs to stay for pipelines.

Why either option matters more than the original fix
Both replace "did we remember to list this method" with "is it structurally possible to reach the database without going through the check." The regex option (A) is the lower-risk, more idiomatic change — it stays inside Mongoose's existing middleware system and is scoped per schema, the same way the plugin already works today. The exec-override (B) is more complete but more invasive, and would want careful rollout given it touches a shared prototype. Either one — unlike the original array — would have caught the findById gap without anyone needing to anticipate findById specifically in advance.

2. Make tenant scoping a compile-time requirement

Right now, base.repository.ts's findById(id: string) compiles perfectly with no tenant awareness at all — TypeScript has no opinion on whether a tenant context exists. A branded-type approach closes that gap by making it impossible to construct the thing a query needs without having gone through tenant context first:

src/repositories/base.repository.ts — proposed rewrite
-export class BaseRepository<T> {
-  async findById(id: string): Promise<T | null> {
-    return this.model.findById(id);
-  }
-}
+// A TenantScope can only be minted from inside runInTenantContext,
+// so its mere existence as a parameter is proof a context was set up.
+export type TenantScope = { readonly tenantId: string; readonly __brand: "TenantScope" };
+
+export function currentTenantScope(): TenantScope {
+  const ctx = tenantContext.getStore();
+  if (!ctx?.tenantId) {
+    throw new Error("🚨 No tenant context — cannot mint TenantScope");
+  }
+  return { tenantId: ctx.tenantId, __brand: "TenantScope" };
+}
+
+export class BaseRepository<T> {
+  // `scope` is required — there is no overload that omits it.
+  async findById(id: string, scope: TenantScope): Promise<T | null> {
+    return this.model.findOne({ _id: id, tenantId: scope.tenantId });
+  }
+}

With this shape, userRepository.findById(id) — the exact call that caused the incident — simply fails to compile. There is no runtime path where the mistake can ship, because the mistake is now a type error, not a code review miss.

3. A CI guard as defense in depth, not as the primary fix

Even with #1 and #2 in place, a cheap belt-and-suspenders check is worth adding: a lint rule (or a grep-based CI step, which is nearly as effective and far less work) that fails the build if any file outside src/repositories/ or src/plugins/ calls Model.<anything> directly on an imported Mongoose model. This wouldn't have been enough on its own — the original bug went through the repository layer, which this rule would have allowed — but it closes a different, related gap: someone bypassing the repository layer entirely and calling User.findById(...) straight from a service.

4. Replace the single regression test with a coverage-parity check

The natural instinct after this incident is "add a test that asserts getUserById rejects cross-tenant IDs." That's necessary but not sufficient — it only proves this one call site stays fixed. The more useful test is one that asserts parity between reality and the plugin's coverage: scan the codebase for every Mongoose query method actually invoked (via a source grep or a runtime spy), and fail CI if any of them isn't provably intercepted by the plugin. That test would have failed on day one of the original findById gap — before a single line of service code ever called it.

Priority if only one of these ships: #1. It's the only change that removes the actual mechanism of failure (an enumerable, forgettable list) rather than adding another layer of checks around it. #2 is the next highest value — it moves the failure from production to the editor. #3 and #4 are good hygiene, but neither would have stopped this specific incident on its own.

Reading the left diagram top to bottom: the request carries a valid tenant context all the way down to the Mongoose query layer — that part was never broken. The break is a single box: the plugin's hooked-methods array has no entry for findById, so the query executes with the context sitting right there, unused, and MongoDB returns whichever document matches the ID regardless of tenant. Everything upstream of that box did its job correctly; the leak is entirely local to one missing string in one array.

The right diagram shows the same path after the fix discussed earlier: a regex hook (/^find/) matches on the shape of the operation name rather than a literal list, so findById is caught as a side effect of matching "anything that starts with find" — the same fix that also covers whatever future method Mongoose adds that happens to start with "find." The query never reaches MongoDB without the tenant filter injected.
