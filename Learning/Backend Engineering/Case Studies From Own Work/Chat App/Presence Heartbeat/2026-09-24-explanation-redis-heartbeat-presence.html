1. Background

The small green dot next to a colleague's name makes a promise: this person is here now. Keeping that promise is harder than it looks, because the one event you most want to detect, someone leaving, is the one the network is least likely to report.

Presence, in general

Beginner background: skip if you already know why presence needs heartbeats

A presence system answers one question for every user: are they reachable right now, and if not, when were they last seen? Two facts about networks make this tricky.

  • Clean departures are optional. When a user clicks "log out," the browser can tell the server. When the laptop lid closes, the Wi-Fi drops, or the process is killed, nothing is sent. The server just stops hearing from the client.
  • Silence is ambiguous. A client that hasn't spoken for ten seconds might be idle, slow, or gone. The server can't tell the difference by waiting passively.

The standard answer is a heartbeat: the client proves it is alive by sending a small message on a fixed schedule. The server treats presence as a lease that each heartbeat renews. If the lease runs out, the user is considered gone. This turns an unknowable question ("did they leave?") into a checkable one ("has the lease expired?").

Key idea: lease with TTLA lease is a claim that is valid only for a fixed time-to-live (TTL). Renewing it before it expires keeps it alive, and missing a renewal makes it lapse automatically. You don't need to detect death. You only need to stop renewing.

Why Redis? Presence data is small, read constantly, written every few seconds per user, and it is fine to lose on a restart because clients will re-announce themselves. Redis fits this well: it lives in memory, and SETEX key seconds value writes a value and its expiry in one atomic command. When the TTL runs out, Redis deletes the key itself.

Why Socket.IO? Heartbeats and presence changes flow in both directions and should arrive instantly. A persistent WebSocket connection (which Socket.IO wraps) lets the client send heartbeat cheaply and lets the server push user_online to everyone else without polling. Socket.IO's rooms are named groups of sockets. io.to("presence:u42").emit(...) reaches every socket that has joined that room.

The pieces this chat app already had

Before presence existed, the backend was an Express + Socket.IO server with MongoDB for durable data and a Redis client already in use (for example, UnreadMessagesService kept unread counts there). Every authenticated socket already carried a userId and, later, a tenantId, because the app is multi-tenant: several organisations share one deployment, and their data must not mix.

On the frontend, a Next.js app had a SocketProvider that owned the socket connection, a Zustand auth-store with the logged-in user, and React Query for REST calls. Presence was built on all of these without replacing any.

2. Intuition

Now that the setting is clear, the design fits in one sentence: the browser renews a 60-second lease every 30 seconds, and anyone who misses two renewals is marked offline. Everything else serves this rule. Some parts make it fast (socket events), some make it visible (UI dots), and some make it durable (Mongo history).

A lease that must be renewed

Picture Alice in tenant acme. Her presence is a single Redis key:

key:   presence:acme:alice
value: {"userId":"alice","tenantId":"acme","status":"online",
        "lastSeen":"2026-09-24T10:00:30Z",
        "deviceInfo":{"type":"web","socketId":"k3Jx..."}}
TTL:   60 seconds

Each heartbeat overwrites the key and resets the TTL to 60. With a 30-second interval there is always one spare beat of slack, so a single dropped packet doesn't make Alice flicker offline.

Alice's laptop sleeps just after the 60 s beat. No more beats arrive, and 60 s later (t = 120 s) her lease lapses. Blue ticks are heartbeats.

Two clocks, not oneThe server actually runs two expiry mechanisms side by side. Redis TTL makes the key disappear. An in-process setTimeout of 60 s, reset on every beat, actively calls setUserOffline(), which writes an "offline" record and broadcasts it. The Redis TTL alone would be silent: the key would vanish, but no client would be told.

Three ways to go offline

Detecting arrival is easy, and the system has three separate paths for detecting departure:

PathTriggerLatencyWhat runs
Clean disconnectTab closed, logout, socket disconnect eventImmediatesetUserOffline() → offline record (24 h TTL) + user_offline broadcast + history session closed
Missed heartbeatsNo beat for 60 s (sleep, network loss)≤ 60 sIn-memory setTimeout fires → setUserOffline()
Lease lapseRedis TTL reaches 060 sKey deleted silently. Readers treat a missing key as offline
Why keep an "offline" record at all?If going offline just deleted the key, "last seen 12 minutes ago" would be impossible. The system writes status:"offline", lastSeen:now with a 24-hour TTL instead, so the fact that a user was online recently outlives the session.

3. Code walkthrough

The intuition maps closely onto the code. The walkthrough follows the order a heartbeat travels through it: the core state machine first, then the socket layer, the Mongo side, and finally the React side.

3.1 PresenceManager: the state machine

chat-app-backend/src/presence/presence-manager.ts

A single PresenceManager is created at boot in server.ts with the shared Redis client and registered in the ServiceLocator. It extends EventEmitter. It decides what happened and emits an event, and the socket layer decides who to tell. This separation keeps Socket.IO out of the manager.

export class PresenceManager extends EventEmitter {
  private heartbeatInterval = 30000; // 30 seconds
  private timeoutWindow = 60000;     // 60 seconds
  private heartbeatTimers: Map<string, NodeJS.Timeout> = new Map();

  async processHeartbeat(userId, tenantId, status, deviceInfo) {
    const presenceKey = `presence:${tenantId}:${userId}`;
    const currentPresence = await this.getUserPresence(userId, tenantId);
    const wasOffline = !currentPresence || currentPresence.status === "offline";

    await this.redis.setEx(presenceKey, Math.ceil(this.timeoutWindow / 1000),
                           JSON.stringify({ userId, tenantId, status, lastSeen: now, deviceInfo }));

    if (wasOffline) {
      this.emit("userOnline", { userId, status, timestamp: now });
      await this.broadcastPresenceChange(userId, tenantId, "online", status);
    } else if (currentPresence.status !== status) {
      this.emit("statusChanged", { userId, oldStatus: currentPresence.status, newStatus: status, ... });
      await this.broadcastPresenceChange(userId, this.tenantId, "online", status);
    }
    this.resetOfflineTimer(userId, this.tenantId);
  }

Notice that status changes also go through processHeartbeat. Picking "busy" in the UI is simply a heartbeat with a different status, and the "status changed?" branch detects it. There is one write path for everything.

The remaining methods are small:

  • resetOfflineTimer / clearOfflineTimer keep one setTimeout per user in a Map. Every beat cancels the old timer and starts a new 60 s one that calls setUserOffline.
  • setUserOffline rewrites the key as offline with an 86 400 s TTL, emits userOffline, and broadcasts it. It checks status !== "offline" first, so calling it twice is harmless.
  • getBulkPresence batches GETs in a MULTI so a sidebar of 30 DMs costs one round trip.
  • getOnlineUsers uses SCAN MATCH presence:{tenant}:* with a cursor (non-blocking, unlike KEYS) and filters out offline records.
  • A 60 s cleanupInterval scans every presence:*:* key and gives any key without a TTL a 24 h expiry. This catches keys written by older code or by hand.

So there are two broadcast styles: a targeted presence_update to each contact's personal room, and a global io.emit to everyone.

3.3 Mongo side: connections and history

Redis holds the current state. Mongo holds two slower-moving things:

  • UserConnection (+ ConnectionService) stores directed edges userId → connectionId, typed direct_message or channel_member. broadcastPresenceChange reads them to decide which rooms receive presence_update. Compound unique indexes (including tenantId) prevent duplicate edges, and inserts use ordered:false and ignore error 11000 so re-adding is idempotent.
  • PresenceHistory (+ PresenceHistoryService) stores one document per session with sessionStart, sessionEnd and duration. Background jobs in server.ts delete history older than 90 days (daily) and close sessions left open by crashed sockets (hourly). This feeds the /presence/history and /presence/analytics endpoints.

The REST routes in presence.routes.ts (/me, /me/status, /bulk, /online, /connections, /history, /analytics, /admin/*) call the same manager. They exist so the UI still works before the socket connects or after it fails.

3.4 Frontend: provider, hooks and UI

Chat-App-Frontend/providers/presence-provider.tsx

PresenceProvider wraps the app in app/layout.tsx inside the socket provider. A useReducer holds currentStatus, isAuthenticated, lastHeartbeat, a userPresence map, and onlineUsers. Three effects do the work:

// 1. Authenticate once socket + user are ready
useEffect(() => {
  if (socketConnected && user && isAuthenticated && !state.isAuthenticated)
    authenticatePresence();          // emits authenticate_presence {status}
}, [...]);

// 2. The heartbeat loop
useEffect(() => {
  if (!state.isAuthenticated) return;
  const interval = setInterval(sendHeartbeat, 30000);  // emits heartbeat {status}
  return () => clearInterval(interval);
}, [state.isAuthenticated, sendHeartbeat]);

// 3. Listen for others' changes
socket.on("presence_update", ...); socket.on("user_online", ...);
socket.on("user_offline", ...);    socket.on("status_changed", ...);

When the socket drops, effect 1's partner resets isAuthenticated to false. That stops the heartbeat loop, and on reconnect the provider authenticates again automatically. Every action (changeStatus, getBulkPresence, getOnlineUsers) uses the socket when authenticated and presenceApi (REST) otherwise.

Chat-App-Frontend/hooks/use-presence.ts, use-presence-indicator.ts, components/presence/*

  • useUserPresence(ids) merges React Query REST data (refetched every 60 s) with the real-time context map. Real-time wins: {...apiPresence, ...realtimePresence}.
  • useOnlineUsers calls get_online_users again whenever user_online, user_offline or status_changed arrives.
  • useMyPresence powers StatusSelector. usePresenceIndicator turns a status into colours and "last seen" text for PresenceIndicator, PresenceAwareAvatar, ChatWindow, ChatSidebar and ConversationList.

The key design decision (d4d5dfa)The first version ran a heartbeat on the server: setInterval(processHeartbeat(userId, ONLINE), 30000) for each socket. That defeats the purpose. The server was vouching for a client it couldn't see, and it always re-sent ONLINE, which overwrote any "away" or "busy" the user had picked. After the change, the client must prove it is alive and says which status it is in. A heartbeat only means something if it comes from the party whose liveness is in question.

3.6 Loose ends worth knowing

Bug: this.tenantId is undefined since 4be4784The constructor stopped setting this.tenantId, but processHeartbeat still passes it to resetOfflineTimer and to the status-change broadcast. When the 60 s timer fires, it calls setUserOffline(userId, undefined), which reads presence:undefined:alice, finds nothing, and does nothing. As a result, path 2 (missed heartbeats) is broken. Silently disconnected users fall back to path 3, where the Redis key lapses with no user_offline broadcast. Other clients keep a green dot until their 60 s REST refetch. The fix is to use the tenantId argument in both places.
  • Global broadcasts cross tenants. io.emit("user_online") reaches every socket in every tenant. A per-tenant room (io.to("tenant:"+tenantId)) would scope it.
  • Multiple tabs. Presence is keyed per user, not per socket. Closing one of two tabs sends disconnect → offline, even though the other tab is still open. The next heartbeat (≤ 30 s later) brings the user back online. A per-user socket count, or a Redis set of socket ids, would fix this.
  • Timers live in one process. The heartbeatTimers map lives in one Node process. With several backend instances, a user's beats may land on different instances. Redis keyspace notifications or a sorted set of lastSeen scores would move expiry into Redis.
  • UserConnection is mostly empty. Only POST /presence/connections writes to it, and DM and channel creation don't call ConnectionService. The targeted presence_update therefore rarely reaches anyone, and the UI depends on the global events.
  • Enum drift. The backend PRESENCE_STATUS includes WORK, but the frontend's doesn't.
