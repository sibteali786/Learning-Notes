Redirect URLs in mobile apps

One thing unique to mobile security in OAuth is how iOS and Android handle redirect URLs. The redirect is where the authorization server sends the user back after login and approval, and on mobile that handoff is much easier to attack.

1. Web vs mobile: where the redirect happens

Web browser

Interaction stays in one browser tab. The browser checks DNS and validates HTTPS, so this is generally considered relatively secure.

Mobile

Many of those browser protections are lost. The app launches an in-app browser to the authorization server (fine), but then the server's redirect back to the app may be intercepted, depending on how it is handled.

2. Two ways to handle redirects on mobile

Older A. Custom URL schemes

How it works
  • The app defines a custom scheme (for example todo://, or a reverse-DNS style name).
  • Whenever anything on the phone launches a URL matching that scheme, that app launches.
  • It used to be much more common.
Why it is weak
  • No registry. Any app can claim any scheme.
  • If someone discovers your scheme, they can build a competing app claiming the same one.
  • The two then fight to catch the redirect, and in most cases the platforms have no well-defined behavior for which app wins.
  • A malicious app can steal the authorization code in the redirect step.
Real-life scenario

Picture a street with no house numbers where anyone can paint "To Do" on their door. A courier delivering a parcel marked "To Do" just picks a door. If a scammer painted the same sign, your parcel (the authorization code) may end up on their doorstep.

Modern B. Claimed URL patterns (deep linking)

How it works
  • The app claims a URL pattern, including a full domain name or even a path.
  • Once registered, whenever such a URL is visited from another app or even a mobile browser, your app launches instead.
  • This is how a link to Amazon opens the Amazon app on that product, or an Instagram photo link drops you into the Instagram app rather than the website.
Why it is more secure
  • To claim a URL pattern, the developer must prove they control that domain name.
  • So other apps cannot simply claim yours.
  • The platform can verify the claim, and there is much less risk of others stealing or clobbering your redirect handling.
My addition (not in the lecture): on Apple's platform this feature is called Universal Links and on Android it is App Links. Searching those names in the platform docs is the way to set it up.

Real-life scenario

You tap a link to a product on a shopping site in a chat message. Because the shopping app proved it owns that domain, the phone opens the app on that product page. A fake app cannot register the same domain, so it cannot intercept the link.

3. Still not perfect: why PKCE matters

Even claimed URL patterns can fail, so redirect URLs in mobile apps are not trusted as much as in a browser.

Imagine you are the OAuth server about to generate an authorization code and redirect to the app. You do not know whether the redirect will make it back to the right app. There are many ways it can fail. You "kind of just hope it does", with no real guarantees.

That is why PKCE is so important: even if a code is intercepted, the party that did not start the flow cannot redeem it (see the PKCE and authorization code injection notes).

4. Key takeaways

  • On the web, the redirect stays inside the browser, which checks DNS and HTTPS. On mobile, the redirect returns to the app from an in-app browser, losing many protections.
  • Custom URL schemes have no registry: any app can claim any scheme, platform behavior on conflicts is generally undefined, and a malicious app can steal the authorization code.
  • Claimed URL patterns (deep linking) require proof of domain control, so they are verified by the platform and much safer.
  • Even so, the server cannot be certain the redirect reaches the right app, so use PKCE.
  • Recommendation: for a mobile app, prefer app-claimed URL patterns over custom schemes.
