How mobile apps launch the browser for OAuth

How the app opens the authorization server to start the flow is one of the most important security decisions on mobile. There are three approaches, and the lecture's verdict is that the platform's in-app secure browser is the best balance of security and user experience.

1. The three approaches at a glance

1. External browser

Safari / Chrome launched from the app.

Secure, but clunky.

2. Embedded web view

A page framed inside the app.

Convenient, but insecure.

3. Secure in-app browser

SFSafariViewController (iOS), Chrome Custom Tabs (Android).

Best balance.

2. Approach 1: the native browser (the old secure way)

It used to be the most secure option, but the experience was poor.

Pros
  • Real browser with address bar.
  • The app cannot touch the password.
  • Shares the existing session, so users already logged in to Safari are not asked again.
Cons
  • Arguably not the best experience: leaving the app.
  • More fragile, since the user leaves the app's context.

3. Approach 2: the embedded web view (avoid)

Popular back when the native browser was the only alternative: the user never leaves the app. The lecture lists several serious problems.

Problem 1 No address bar, no verification

It is not a real browser. The user just sees the page framed in the app and cannot check that it is really the authorization server. It could be an attacker's clone, and the user would type their password into it. There is no way to verify.

Problem 2 No shared cookies, so worse UX

Because the app fully controls the web view, platforms isolate it in its own container (otherwise data would link between apps). If you are logged in to the authorization server in Safari, you are not logged in inside the app's web view, so users retype their password every time.

Problem 3 The app can steal the password

Even if the real OAuth server is shown, the app has full control and can reach into the web view and extract the password. That is exactly what OAuth was meant to prevent: apps should never touch a user's password.

Problem 4 No modern system authentication

Mechanisms like WebAuthn or built-in TouchID, now being built into browsers, are not available in a web view because it is not a real browser. This compounds the password-exposure problem.

Real-life scenario

A shopping app shows a "Sign in with Google" page in an embedded web view. It looks right, but there is no address bar, so you cannot tell if it is genuinely Google. Even if it is, the shopping app is the one drawing the window and could quietly read what you type. It is like handing your house key to a stranger to "just hold it while the lock is opened".

4. Approach 3: platform secure in-app browsers (best)

As OAuth matured, mobile platforms built special APIs to launch a browser securely within the app.

Why it is the best of both worlds
  • The user never leaves the app.
  • The app has no access to the browser and cannot inspect its contents, so it cannot touch the password.
  • Because the app cannot inspect it, it is safe to share cookies with the system: if the user is already logged in in Safari, they are already logged in in the pop-up, so no password retyping.
  • Security benefit of the external browser plus the smoothness of a web view.

Real-life scenario

You open a food-delivery app and tap "Log in with Google". A Google sheet slides up over the app and you are already signed in, so you just confirm. The sheet closes and you are back in the app. The delivery app never saw your password or the contents of that sheet.

My addition (not in the lecture), please verify in current Apple docs:

On iOS, Apple's more recent dedicated API for OAuth sign-in is ASWebAuthenticationSession, and current OAuth guidance for native apps points to it. Also, I believe newer iOS versions no longer let SFSafariViewController share cookies with Safari, so the single-sign-on benefit described above applies to ASWebAuthenticationSession rather than to SFSafariViewController. The lecture's principle is unchanged: use the system-provided secure browser, not a web view. Android Custom Tabs remains the recommended Android option.

5. Key takeaways

  • How the app launches the browser to the OAuth server is one of the most important parts of mobile OAuth security.
  • External browser: secure, but the user leaves the app and the experience is fragile.
  • Embedded web view: avoid. No address bar to verify the server, no shared cookies (repeated logins), the app can extract the password, and no WebAuthn or TouchID.
  • Platform secure in-app browser (iOS, Android Chrome Custom Tabs): the user stays in the app, the app cannot inspect the browser, cookies can be shared so existing logins carry over.
  • It gives the best balance of security and user experience, and it is the recommended way to start OAuth from a mobile app.
