Authorization Code Flow for web apps

A full walkthrough for a server-side (confidential) web app: the roles, the eight steps, the exact parameters in each request, refresh tokens, and why PKCE is now recommended even when you have a client secret.

Front channel (browser address bar) Back channel (server to server, HTTPS)

1. The big picture

The end goal is an access token delivered to the app's server through the back channel, so the browser never sees it. Before starting, you need an application registered with the OAuth server, giving you a client ID and client secret.

Real-life scenario

You click "Log in with Google" on a photo-printing website. The site generates a one-off secret, sends you to Google carrying only a fingerprint of it, you log in and tap Allow, and Google sends you back with a short-lived code. The site's server then trades that code (plus the original secret and its own credentials) directly with Google for a token. You never touch the token.

2. Step by step (concept view)

1
User clicks the login button

This means: "I would like to use this application."

2
App generates a per-flow secret: the PKCE code verifier

A random string, different every time a flow starts. It is not the client secret. The app keeps it on its server and computes a one-way hash of it, the code challenge. Because a hash cannot be reversed, knowing it does not reveal the secret.

3
Front channel #1App redirects the user to the authorization server

The query string carries the hash (code challenge), client ID, redirect URI and scope. The app is really asking the server for something, but it hands the request to the user to deliver. Since the front channel can be snooped, only the hash is sent, never the secret.

4
User logs in at the OAuth server

Including any multifactor auth, then confirms they really want to log in to the app.

5
Front channel #2Server redirects back with a temporary, one-time authorization code

It takes the app's redirect URI, adds the code to the query string, and sends the browser there. This is not really two steps; it is one delivery routed through the browser. The server cannot know for sure the code was received.

The code is valid for one use and must be redeemed within a short time, typically under a minute.

6
Back channelApp's server exchanges the code for a token

Sent from the app's server to the OAuth server, so it never goes through the browser. It includes the code, client ID, client secret, and the plaintext code verifier.

The server checks: I issued this code, it is unused, it was meant for this client, the secret matches, and the hash of the verifier equals the challenge I saw at the start. If all match, the redeemer is the same thing that started the flow.

7
Server returns the access token

Flow done. The app can now make API requests with it.

3. Parameters in detail

3.1 Generate the code verifier and code challenge

Code verifier (secret)

A random string, 43 to 128 characters long.

Slide example: 4A6hBupTkAtgbaQs39RSELUEqtSWTDTcRzVh1PpxD5YVKl1U

Code challenge (public hash)

base64url(sha256(code_verifier))

Slide example: ipSBt30y48l401NGbLjo026cqwsRQzR5KI40AuLAdZ8

Base64-URL encoding is just Base64 with a slightly different character set, so any language with a base64 function can do it. Example (Node.js, illustrative; the lecture does not show code):

import crypto from "node:crypto";

const codeVerifier  = crypto.randomBytes(32).toString("base64url"); // 43 chars
const codeChallenge = crypto.createHash("sha256")
                            .update(codeVerifier)
                            .digest("base64url");

3.2 Authorization request Front channel

Find the authorization endpoint in the server's docs, or programmatically via the server's metadata URL.

https://authorization-server.com/auth?
  response_type=code&
  client_id=CLIENT_ID&
  redirect_uri=REDIRECT_URI&
  scope=photos&
  state=XXXXXXX&
  code_challenge=XXXXXXXXXXXXX&
  code_challenge_method=S256
ParameterMeaning
response_type=codeTells the server you are doing the authorization code flow
client_idWhich app is making the request
redirect_uriWhere to send the user back. Must match one of the redirect URIs registered for the app
scopePermissions you need, based on the API you will call (example: photos)
stateOriginally for CSRF protection. With PKCE it can store app-specific state instead, such as which page to return to (cart, checkout)
code_challengeThe hash of the code verifier
code_challenge_method=S256The hash method used (SHA256)
State caveat: only use state for app data if you are sure the server supports PKCE. If it does not, state must be a random value to protect against CSRF.

3.3 Redirect back to the app Front channel

https://example-app.com/redirect?
  code=AUTH_CODE_HERE&
  state=XXXXXXX
  • Check that state matches the value you sent (CSRF protection).
  • On failure, the server redirects back with an error code in the URL instead of a code.
  • Your app does not see the user again until they land on this redirect URL.

3.4 Exchange the code for a token Back channel

A backchannel HTTPS POST from your server to the server's token endpoint (a separate endpoint to look up), with a traditional form-encoded body.

POST https://authorization-server.com/token
  grant_type=authorization_code&
  code=AUTH_CODE_HERE&
  redirect_uri=REDIRECT_URI&
  code_verifier=VERIFIER_STRING&
  client_id=CLIENT_ID&
  client_secret=CLIENT_SECRET
ParameterMeaning
grant_type=authorization_codeTells the server you are doing the authorization code grant
codeThe code from the query string
redirect_uriSame redirect URI used in the authorization request
code_verifierThe plaintext secret the app made up at the beginning
client_id + client_secretThe app's credentials. Some servers want them in the POST body, others in a Basic auth header: check the docs

3.5 Token response Back channel

{
  "token_type": "Bearer",
  "access_token": "RsT5OjbQz0zqLgV3Ia",
  "expires_in": 3600,
  "scope": "photos",
  "refresh_token": "H4HSMMV2409INW"
}

You get the access token, its expiration time (seconds), and possibly a refresh token.

4. Refresh tokens

When the access token expires, use the refresh token to get a new one without repeating the whole flow. It works like redeeming an authorization code.

POST https://authorization-server.com/token
  grant_type=refresh_token&
  refresh_token=REFRESH_TOKEN&
  client_id=CLIENT_ID&
  client_secret=CLIENT_SECRET

Back channel from your web server. Client credentials are still required so the server knows it is really this app.

What comes back
  • A new access token, and possibly a new refresh token (same JSON shape as before).
  • If you do not get a new refresh token, the one you have should probably keep working.
  • Behavior differs between OAuth servers.
A refresh token is never guaranteed to work. It can fail because the user was deleted, the user revoked permissions, an admin deleted the application, or other expiry reasons. If it fails, the only option is to start a new flow from the beginning.
Real-life scenario

A web app syncing your calendar gets a one-hour access token. After an hour, instead of asking you to log in again, its server quietly trades the refresh token for a new access token. If you revoked the app from your Google account settings last week, that trade fails and the app must send you through login again.

5. Why PKCE for confidential clients too?

History

PKCE was originally developed for mobile apps. The lecture's flow is for server-side apps, yet the OAuth working group guidance is now to recommend PKCE for all kinds of applications, even with a client secret.

The reason: the authorization code injection attack

Even with a client secret, a subtle attack lets someone swap authorization codes so you end up logged into somebody else's account in the real application. It is not the same as stealing a token, but potentially worse, since neither the application nor the server would know it happened. PKCE solves it.

The lecture does not explain the attack. See the separate file oauth-pkce-code-injection-attack.html.

Where this guidance lives
  • Security Best Current Practice
  • OAuth 2.1
If the server does not support PKCE yet
  • Recommend that they add it.
  • Meanwhile use a random state to protect against CSRF.
  • You can still send PKCE parameters: servers must ignore parameters they do not recognize.
  • Code your clients with PKCE today; no rebuild needed when the server adds support.

6. Key takeaways

  • Two front channel messages (request, then code) and one back channel exchange (code for token). The access token never touches the browser.
  • The code verifier is a fresh per-flow secret (43 to 128 chars). The code challenge is base64url(sha256(verifier)), sent with code_challenge_method=S256.
  • The authorization code is single-use and short-lived (typically under a minute).
  • The token request proves identity two ways: client secret (who the app is) and code verifier (same flow that started it).
  • Always verify the state on return, and use only registered redirect URIs.
  • Responses may or may not include a refresh token; refresh can always fail, so be ready to restart the flow.
  • Use PKCE for all clients, including confidential ones, to stop authorization code injection.
  • Server quirks: credentials in body vs Basic header, whether a new refresh token is returned, PKCE support. Read the server docs.
