How PKCE stops authorization code injection

The lecture says PKCE defeats a subtle attack even for apps that have a client secret, but does not explain it. This page fills that gap.

Source note: this explanation is not from the lecture. It is based on the general OAuth security guidance (the Security Best Current Practice and OAuth 2.1 background), simplified for learning. The lecture only states that the attack exists, lets someone "swap authorization codes", leaves you logged in to another person's account, and that PKCE solves it.

1. First, the key insight

A client secret proves which app is redeeming a code. It says nothing about which user session the code belongs to.

What the client secret protects

"An imposter app cannot redeem this code, because it does not know the secret."

What it does NOT protect

In injection, the real, legitimate app redeems the code with its real secret. The attacker is not trying to be the app. They are tricking the app into redeeming the wrong code.

Real-life scenario

A coat check gives out numbered tickets. The attendant (the app) is honest and checks the ID of the staff window (the secret). But a prankster slips their ticket into your hand just before you reach the counter. The honest attendant gladly hands you the prankster's coat. Nobody was fooled about who the attendant is; the mix-up was about whose ticket it is.

2. The attack, step by step

One common variant: the attacker logs the victim into the attacker's account at the real app.

1
Attacker starts their own flow

They use the real app, are sent to the authorization server, and log in with their own account. The server issues an authorization code for the attacker's account. The attacker stops here, never redeeming the code, and keeps it.

2
Attacker plants that code in the victim's browser

For example, by getting the victim to click a crafted link to the app's redirect URI: https://example-app.com/redirect?code=ATTACKERS_CODE.

3
Victim's browser delivers the code to the real app

The app sees a request on its redirect URI with a code. It looks normal. The app redeems it over the back channel with its genuine client secret.

4
Without PKCE: it works

The code is valid, unused, for this client, and the secret is right. The server issues a token for the attacker's account, and the app logs the victim's session into it.

Result: the victim keeps using the app while it is tied to the attacker's account. They may upload photos, documents or payment details that the attacker can then read. Neither the app nor the server noticed anything wrong.

A second variant: the attacker steals the victim's code (from logs, a leaked referrer, a malicious app on the device) and injects it into the attacker's own session with the app, ending up logged in as the victim. Same root cause: the app cannot tell the code was not produced by the flow its own session started.

3. How PKCE breaks it

PKCE binds the code to the specific flow that requested it.

Why it works
  • The verifier is generated per flow and kept in the app's session for that user.
  • The server stores the challenge alongside the code when issuing it.
  • At redemption it hashes the submitted verifier and compares. A code only redeems for whoever holds the matching verifier.
The stolen-code variant
  • A code stolen from the victim is bound to challenge(V), where verifier V sits in the victim's app session.
  • The attacker's session holds a different verifier, so redemption fails.
  • The attacker would need V, which never travels in the front channel (only its hash does).
Real-life scenario

Back to the coat check: now each ticket also has a unique stamp, and when you hand in your coat you write a private word on a card that stays at the counter. To collect it you must say that word. The prankster's ticket belongs to a stamp-and-word pair you never saw, so the attendant refuses, and the swap fails even though the attendant is perfectly honest.

4. Why the other defenses are not enough

DefenseDoes it stop injection?Why
Client secretNoThe real app redeems with the real secret. The secret authenticates the app, not the session.
Registered redirect URINoThe code is injected at the legitimate redirect URI.
Short-lived, single-use codeNoThe attacker plants it while still valid, and it is used only once, by the victim's session.
Random state checked by the clientPartlyAn injected code carries the wrong state for the victim's session, so a correct client rejects it. But this relies on every client implementing the check properly and cannot be enforced by the server.
PKCEYesThe server enforces the binding at redemption, so it works even if the client is sloppy. This is why the lecture says state can now carry app data when PKCE is supported.
Caveat on enforcement: PKCE only protects you if the server checks it. Clients that send PKCE parameters to a server that ignores them are safe to ship (as the lecture notes) but not yet protected, which is why a random state is still needed in that case.

5. Quick recap

  • Injection attack: an attacker gets the legitimate app to redeem the wrong authorization code, tying a session to the wrong account. No token theft is needed and nobody sees an error.
  • Client secret is irrelevant here, since the legitimate app is the one redeeming.
  • PKCE fix: the code is cryptographically bound to the flow that requested it (verifier → challenge → verifier check at the token endpoint).
  • Result: an injected or stolen code fails because the redeeming session cannot present the matching verifier.
  • Practice: use PKCE for every client type; still use a random state when the server does not enforce PKCE.
