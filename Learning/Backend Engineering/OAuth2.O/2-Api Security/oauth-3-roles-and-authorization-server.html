Roles & the Authorization Server

Recap: earlier lessons covered pre-OAuth API authentication. Now we introduce the role that makes OAuth work — the authorization server — and the vocabulary used throughout the spec.

The Four Original Rolesin a typical "user accesses data" scenario
1

User

The person with the account.

2

Device

Phone or browser the user is using. It either runs the app (mobile) or accesses it over the internet (browser).

3

Application

The software the user interacts with, making requests to the API.

4

API

Where the data lives; the thing the application makes requests to.

Don't stress: it's fine to use the casual and spec terms interchangeably in conversation.
Watch out for "application": people call mobile apps and APIs "applications". In the OAuth spec, "application" means only the client — the thing in the middle that accesses data at the API.
Previous Methods: Data Moves Directly Between Rolesthe limitation

Cookie-based authentication example: the user types the password into their device → the device sends it to the web application → the application returns a session cookie → the device holds the cookie and sends it on future requests.

That's better than the application keeping the password and sending it on every request — but we can do even better.

The goal: OAuth was meant to let third-party apps access a user's data. We don't want to hand passwords to random apps, so we need a way for the app to get "something like a session cookie" without ever receiving the password.
Enter the Authorization Serverthe fifth role

Job: manage access to the API it protects. It does this by:

  • getting the user to log in at the authorization server
  • creating an access token
  • giving that access token to the app

The app uses the access token to make API requests, so the API needs a way to validate the token — far better than APIs validating passwords directly.

The key rule: the user types their password only at the authorization server. The application never sees it — it sends the user over to log in and gets back an access token to use at the resource server.
Roles ≠ Componentsarchitecture varies

In OAuth these are roles, not necessarily distinct deployed pieces. Your real architecture may look different from the diagram.

Small system

All-in-one

An API with a built-in OAuth server: one codebase, one server. Still two roles — it plays both Authorization Server and Resource Server.

Microservices

External auth server

A separate authorization server plus many microservices. All the microservices together make up the Resource Server role.

API Gateway

Gateway in front

Easier to picture: with a gateway out front, everything behind the gateway is clearly a Resource Server.

// Mapping real components → OAuth roles
Small app      : [ monolith API + auth module ]  →  Authorization Server + Resource Server
Microservices  : [ Auth0 / Keycloak ]             →  Authorization Server
                 [ orders-svc, users-svc, ... ]   →  Resource Server (all of them)
Mobile app     : [ the app on the phone ]        →  OAuth Client (+ phone = User Agent)
Debugging tip: if you're unsure how a token should move, or whether "this thing" may do "that thing", reframe the question in terms of OAuth roles — the answer usually becomes much clearer.
The Complete Picturefive roles
Role
What it does
Resource Owner (user)
Owns the account and the data; logs in at the authorization server
User Agent (device)
Browser/phone used to reach the client and get redirected to log in
OAuth Client (app)
Sends the user to log in; receives the access token; calls the API
Authorization Server
Authenticates the user, issues access tokens
Resource Server (API)
Holds the data; validates the access token on each request
Real-world scenario: You open "PixelPro" (the client) on your phone (user agent) to save a photo to your Dropbox (resource server). PixelPro redirects you to Dropbox's login page (authorization server) where you type your password. Dropbox hands PixelPro an access token; PixelPro uploads the photo to the Dropbox API with that token — never having seen your password.
Key Takeawaysinterview-ready

Remember

  • Five roles: Resource Owner, User Agent, Client, Authorization Server, Resource Server.
  • Password only ever goes to the authorization server.
  • Client gets an access token; the API validates the token rather than a password.
  • Roles are logical; one piece of software can play several.
  • In OAuth, "application" = the client only.

Interview one-liner

"The authorization server authenticates the user and issues access tokens to the client, so the client can call the resource server without ever seeing the user's password. These are logical roles — one deployment can play more than one."
