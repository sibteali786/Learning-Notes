Confidential vs Public Clients

A client type is shorthand for several security properties of an application. OAuth 2.0 defines exactly two, based on one question: can the client hold credentials to authenticate itself during the OAuth flow?

The Two Client Typesdefined by credentials
Confidential Client

Has credentials

Typically a client secret, which is not visible to users of the app. Normal for apps running on a web server (Java, .NET, PHP…).

You already trust server-side secrets: API keys in config or environment variables stay secret because users can't access your app's source code.

Public Client

No credentials

Can't ship a secret because users could see it. Applies to mobile apps and single-page apps (SPAs), and any app running on a device the user controls.

How to Decide Which Type You Havethe rule of thumb
SPA

Most obvious case

The user can click View Source and poke through the code. There's no way to ship a secret and keep it secret.

Mobile

Less obvious, same result

No view-source button, but plenty of tools exist to extract strings from the binary files.

Any user device

Same rule

Apple TV, IoT devices — any time the app runs on a device the user controls, you can't include a secret.

Why It Matters in OAuthclient authentication

The app talks to the authorization server. If the app has credentials, it can authenticate its requests with them — so the server knows only the real application could have made them.

Without credentials, the server never really knows whether it's the real app or something pretending to be it.

Authorization Server Policies Depend on Client Typewhy the distinction matters
Consent screen

Skip it?

A confidential + first-party client might skip the consent screen — the server is sure only the real app can end up with the access token.

Refresh tokens

Issue or not

The server may decide whether to include refresh tokens depending on client type.

Token lifetime

Shorter for public

May change token lifetimes to mitigate risk for clients it can't authenticate.

Attack scenario (first-party public client): an attacker copies the real app's client ID and starts a flow. If they can control the redirect URL, they end up with the access tokens the server thought it issued to the real app. This is why consent can't safely be skipped for public clients.

Real-world scenarios:
• Laravel/PHP dashboard that logs users in with Google → confidential; secret lives in server .env.
• React SPA calling an API → public; anything in the bundle is readable by anyone with DevTools.
• Flutter mobile app → public; hard-coding a secret in the app just means a determined user can extract it from the APK/IPA.
Key Takeaways & Tipsinterview-ready

Remember

  • Client type = can it keep a secret?
  • Runs on a server → confidential. Runs on user's device → public.
  • Never put a client secret in a mobile app or SPA — it's no longer secret.
  • Use client authentication whenever possible.
  • Pick the correct type when registering the app at the OAuth server, and safeguard credentials if you have them.

Interview one-liner

"Confidential clients can authenticate to the authorization server with a secret or key because they run on a server; public clients like SPAs and mobile apps can't hold secrets, so the server can't be sure the caller is the real app and applies stricter policies."
