User Consent & the Password Grant

One goal of OAuth is to protect user data and make sure it's shared only with parties the user wants. The consent screen is how the authorization server proves it's doing that job — and the password grant shows what goes wrong without it.

What Is the Consent Screen?the interrupt in the flow

Think of the last time you clicked "Sign in with Twitter" and got a screen asking if you're sure you want to share your information. That screen, which interrupts the authorization flow to ask the user for permission, is the consent screen.

It's critical because it lets the authorization server know the user actually agrees to what the app is asking for.

What Happens Without It: the Password Grantaka Resource Owner Password flow

The spec still contains the password grant: the app shows a password prompt in the app itself, collects the user's password, sends it to the authorization server, and gets back an access token. The whole thing is one POST request to the token endpoint, with username, password, client ID and (optionally) client secret.

POST https://authz-server/token
  grant_type=password&
  username=USERNAME&
  password=PASSWORD&
  client_id=CLIENT_ID
// optionally also: client_secret=... (confidential clients)
Problems with the Password Grant3rd party and 1st party
Third-party apps

The obvious problem

The user hands their password to an app under another developer's control (recall the apps asking for your Gmail password). The spec has always advised against letting third-party apps use the password grant.

First-party apps

The subtle problems

Even if you trust your own app, look from the authorization server's view. Its job: protect resources and ensure only authorized apps and users get access. A password grant request only shows the app presenting credentials.

Is the user present?

Can't tell

The request looks identical whether the user is actively using the app or the app is replaying a stored password from last time.

Real agreement?

No consent

Even trusting the app not to replay passwords, you can't be sure the user agrees to the access requested.

Scope abuse

Asks for more

The app might tell the user it will only read photos, but with the password it can request a token that can modify photos too.

What's missing: confirmation that the user is actually at the computer and has initiated and agreed to this request right now.
The Fix: Put the Authorization Server in the Flowredirect + consent

The app first directs the user to the authorization server. The user types their password there, sees the consent screen and approves, then is taken back to the app.

  • The password is only ever typed into the authorization server.
  • The server knows the user is actually trying to use that app — the app can't do anything without the user in front of the keyboard.
  • The app can ask for specific kinds of access, and the server shows that request to the user, so it knows the user agrees.
The MFA Advantagesecond huge problem it solves

Multifactor authentication has exploded in use and is a huge step up for security. But the password grant just exchanges a password for a token — it wasn't designed to hold MFA.

To bolt MFA onto it you'd have to invent your own approach and build it into every application from scratch.

Real-world scenario: A company has 40 internal apps across 6 teams. Security mandates passkeys/hardware keys. With the password grant: 6 teams × a release cycle each. With a redirect-based flow: the auth team enables it once and all 40 apps are covered the same day.
When Consent Can Be Skippedfirst-party confidential clients

Typically the consent prompt is skipped for first-party confidential clients:

  • First-party: logging into your own service's web app where you have an account — no need to ask permission to log in.
  • Confidential: no app-impersonation risk, since the app can authenticate with a secret.

So it's safe to redirect back immediately. The redirect step still matters — that's where you get the security benefits and MFA support — you just skip the prompt.

But consider keeping consent ON for your own first-party mobile or single-page apps (public clients) if you worry about attackers tricking users into logging into a fake app impersonating yours. The prompt makes that attack harder.

Key Takeaways & Tipsinterview-ready

Remember

  • Consent screen = user explicitly approves what the app requests.
  • Password grant = one POST with username + password; no consent, no MFA room, no proof the user is present.
  • Spec advises against it for third-party apps.
  • Redirect flow proves the user is at the keyboard, enables scoped approval and central MFA.
  • Skip consent only for first-party confidential clients; keep the redirect regardless.

Interview one-liner

"The password grant sends credentials straight to the token endpoint, so the server can't confirm the user is present, consents to the requested access, or completes MFA. A redirect to the authorization server fixes all three, and lets MFA be added centrally for every app."
