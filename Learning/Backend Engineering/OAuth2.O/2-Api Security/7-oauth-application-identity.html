Application identity in OAuth

How an authorization server knows which app is asking, how far it can trust that claim, and what each piece (client ID, client secret, PKCE, redirect URI) actually proves.

1. Applications are their own entity

In OAuth terms, applications are called clients.

What you see as a user

The authorization screen: "this application would like to access your account." Which application? This one.

You might grant one application different access than another.

What the system uses

Each application has an identifier called a client ID, used to identify itself throughout the OAuth flow.

The client secret is just another name for the application's password. Without it, nothing assures that whoever uses the client ID really is that application.

Real-life scenario

A calendar app and a photo-printing app both ask to connect to your Google account. Google shows each one separately, and you may let the calendar read events while the printer only gets photo access. That separation only works because each has its own client ID.

2. Authorization Code flow, summarized

An improvement over the Implicit flow because the access token is delivered in the back channel.

1
App builds a URL and redirects the browser to the authorization server (front channel)

Parameters describe the request: scope, redirect URI (where to send the user back), and client ID (which app is asking).

2
User logs in and approves the request at the authorization server
3
Server redirects back to the app with an authorization code (front channel)

Redirects are front channel, so ideally it should not matter if something intercepts or modifies them. Sending the access token here would be like mailing it, which opens it up to many attacks.

Instead the server sends a one-time-use coupon with a short expiration: the authorization code.

4
App redeems the code over the back channel, authenticating with its client secret

The code can be exchanged for an access token only once and only within a short time. Authenticating with the secret proves the redeemer is the real app and the code was not stolen.

Real-life scenario

Think of a coat-check ticket that works once and expires in a few minutes. Someone could see the ticket, but to collect the coat they must also show the staff your membership card (the client secret). Without the card, the ticket is useless to a thief.

3. The problem: apps without a client secret

Gap

Mobile apps and single page apps cannot be deployed with a client secret (they are public clients). If they used the plain authorization code flow, the OAuth server would effectively let any application that steals the code get an access token.

The fix: PKCE (Proof Key for Code Exchange)

Details come in the next sections. High-level idea:

  • Before the first request, the app makes up a unique secret for each request.
  • It uses that secret to start the flow, and again when it redeems the code.
  • The server learns that the redeemer is the same thing that started the flow, so a stolen code cannot be used.
What PKCE does NOT do
  • It does not prove the app's identity or authenticate the app.
  • It only ensures the code is used by the same app that started the flow.
  • The flow runs on entirely public information. An attacker can start a flow using another app's public client ID, and if they then steal the code, they can get a token.
Real-life scenario

PKCE is like writing a random number inside your own sealed envelope when you place an order, and quoting it again at pickup. It proves the person collecting is the one who ordered. It does not prove you are who you say you are, so a scammer can place their own order pretending to be your company.

Real-life scenario

A custom scheme is like a nickname: two people can both call themselves "Sam" and the post office cannot tell them apart. An HTTPS domain is like a registered street address: only the owner can receive mail there, and the app stores check you own it.

Honest limitation
  • For mobile apps and single page apps without a secret, the HTTPS redirect URI is the only part of identity we can rely on.
  • It is nowhere near as reliable as a client secret: "better than nothing, but still potentially problematic."
  • There is no proper solution today. This may change if mobile platforms add APIs to authenticate apps from their app stores.

5. What this means in practice

If you build a public client

Be aware of the identity limitation when setting policies such as:

  • Token lifetimes
  • Whether to skip the consent screen

Register redirect URIs

Because the redirect URI is the only hint of identity without a secret, redirect URIs must be registered at the server. Then the server only redirects to registered URLs for a given client ID. (Registration is covered in the next section.)

Real-life scenario

A mobile banking-style app cannot prove who it is, so you might issue it short-lived tokens and always show the consent screen. A server-side web app with a client secret could reasonably get longer-lived tokens, and a trusted first-party app might skip consent.

The lecture names these policy areas without prescribing values; the examples above are illustrative.

6. Key takeaways

  • Each client has its own client ID, used throughout the flow. The client ID alone proves nothing.
  • The client secret is the app's password and is the strongest proof of identity, but only confidential clients can hold one.
  • In the authorization code flow, a short-lived, one-time code travels via the front channel and is redeemed over the back channel for the token.
  • PKCE ties code redemption to the app that started the flow. It does not authenticate the app.
  • HTTPS redirect URIs are globally unique and are a partial identity signal. Custom schemes are not an identity at all.
  • Public clients have no proper identity solution today, so set token and consent policies carefully and register redirect URIs.
