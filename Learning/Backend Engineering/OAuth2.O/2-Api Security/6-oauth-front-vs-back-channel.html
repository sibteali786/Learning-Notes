Front channel vs back channel in OAuth

Two ways data moves between systems. Understanding their security properties is the key to judging every OAuth flow, and it explains why the Implicit flow is being retired.

1. The two channels at a glance

Same goal (move data from A to B), very different trust properties.

Back channel

The "normal" secure way

  • A client-to-server connection.
  • Over HTTPS, so you can validate the server's certificate and know who you are talking to.
  • Data is encrypted in transit, so nobody can modify it.
  • The response is trustworthy: you know where it came from and that it was not tampered with.
  • Use it whenever you can.
Front channel

Using the browser's address bar

  • Literally moves data between two systems via URLs in the user's browser.
  • No direct link between the application and the OAuth server.
  • Like handing a package to a delivery company instead of delivering it yourself.
  • More opportunities for things to fail or be intercepted.

2. Why the front channel is risky

The package analogy makes the problems obvious, on both the sending and receiving end.

Sender's problems
  • You trust the courier because it is their job, but you never really know the package arrived. Tracking only shows what the courier claims.
  • Even if it arrives, it may have been opened in transit and the contents copied or stolen.
  • In OAuth terms: you can never be sure about the browser.
Receiver's problems
  • A return address on the package can be faked too easily.
  • So you cannot be sure the sender is who the label says.
  • Therefore you cannot be sure the thing you received is legitimate.
Real-life scenario

You order a new phone and the courier leaves it on your porch. You cannot tell if the box was swapped or opened on the way, and a scammer could just as easily have mailed you a fake box with a convincing return label. A hand delivery with ID checked at the door has neither problem. The back channel is that hand delivery.

3. Then why use the front channel at all?

The end goal is the application receiving an access token. The most secure delivery would be the back channel, but there is a catch.

Consent. The authorization server must be sure the user is present and has given permission for a token to be issued to the app.

  • The password grant uses the back channel, but cannot confirm the user consented to that request. So it is not an option.
  • The front channel is the way to insert the user into the negotiation between client and authorization server.
  • Bonus: it makes multi-factor authentication easy, since only the authorization server needs to handle it.
Real-life scenario

A photo-printing app wants access to your Google Photos. With the password grant you would type your Google password into the printing app, and Google has no proof you agreed to anything. With the front channel, the app sends you to Google, you log in there (including your 2FA prompt) and click "Allow". Google now knows you personally consented.

4. Building a flow with the front channel

Step through what happens if we try to use the front channel for everything.

1
App tells the authorization server what it wants (front channel, first "package")

The app redirects the user to the authorization server, with details in the URL query string: the application's identifier, the requested scope, and similar info.

Fine Nothing in this request is particularly sensitive, so the front channel is acceptable here.

2
User logs in and approves the request

The authorization server now knows the user is present and consented.

3
Authorization server wants to send the access token back

If it sends the token in the redirect, that is like mailing an access token:

  • The authorization server has no guarantee it was delivered to the application.
  • The application has no guarantee the token really came from the authorization server.

Not a good option

Real-life scenario

Think of a bank sending your new debit card PIN on a postcard. The bank cannot confirm you got it, you cannot confirm the bank sent it, and anyone handling the postcard can read it. The sensitive part (the token) should never travel that way.

5. The Implicit flow: the cautionary tale

What it is

The Implicit flow uses the front channel for both the app's request and the delivery of the access token. There is no back channel.

Current status

  • Latest OAuth working group guidance: do not use it.
  • The latest Security BCP (Best Current Practice) says so explicitly.
  • A future update of the OAuth spec will remove it.

Why was it ever included?

Then

Browsers had no other option. Pure JavaScript apps could not make cross-origin requests.

Change

Browsers added CORS (Cross Origin Resource Sharing). JavaScript can now POST to the OAuth server.

Now

CORS is everyday life. A more secure flow that keeps tokens out of the front channel is perfectly practical.

Real-life scenario

Old single-page apps (circa the early 2010s) had to use the Implicit flow because the browser would block a call from myapp.com to auth.example.com. Today the same app can simply fetch() the token endpoint over HTTPS, as shown in the snippet below, so the old workaround is no longer needed.

// Back channel from JavaScript: a plain HTTPS request
const res = await fetch("https://auth.example.com/token", {
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
  body: new URLSearchParams({ /* grant parameters */ })
});

Illustrative only: the lecture does not detail the parameters. They are covered in the later flows.

6. Common misconception

"Back channel" does not mean "back end server".

It means a client-to-server connection. A JavaScript app can absolutely use the back channel by making an AJAX or Fetch request from its own code.

  • A back channel request from JavaScript has the same security properties as one from a backend server.
  • You still get certificate verification and an encrypted connection.
  • That is very different from the front channel, which moves data via the address bar with more chances to fail or be intercepted.

7. Key takeaways

  • Back channel = direct, HTTPS, verified, encrypted. Trustworthy. Does not require a backend server.
  • Front channel = browser address bar. Convenient for involving the user, but neither side can fully trust it.
  • The front channel exists in OAuth so the user can consent (and use MFA). The password grant fails this need.
  • Non-sensitive requests (client ID, scope) are OK in the front channel. Access tokens are not.
  • The Implicit flow sends the token via the front channel. It existed only because browsers lacked CORS. It is now discouraged by the Security BCP and will be dropped from the spec.
  • The secure approach (next sections of the course): front channel to get the user's consent, back channel to deliver the token.
