Life Before OAuth

How apps used to handle authentication, why handing passwords to apps is risky, and the problem OAuth was built to solve.

The Problem Statementwhy this lesson matters

The most common pre-OAuth approach: the app shows a username + password form, the user types credentials, and the app exchanges them for something like a session cookie.

For a simple, self-contained web app with its own built-in auth, this works fine (assuming you hash passwords properly and never log them accidentally). It breaks down when you need:

  • a mobile app alongside the web app
  • multiple apps sharing one user database (Single Sign-On)
  • apps from different companies sharing the same user base — e.g. Sign in with Apple, or a third-party app that manages files in your Google Drive
Core issue: without OAuth, every one of those apps must collect the user's password and forward it to the API. That's bad for third-party apps (user trust) — and still a bad idea for first-party apps (API control).

Problems the User Cares Abouttrust & control
Trust

Can I trust this app?

You can never really be sure what an app does with your password. You hope it swaps it for a session cookie and forgets it — but it could accidentally log it, or intentionally store it.

Note: legitimate apps never ask for your Google password — not even Google's own apps (revisited in the mobile apps lesson).

Over-privilege

Password = keys to the kingdom

A photo-editor only wants to upload a photo to Dropbox. But with your password it can also read any file and even change your password.

The app gets far more power than the task needs.

Revocation

No clean way to revoke

Want to cut one app off? The only option is changing your password — which also kills access for every other app and forces you to log in everywhere again.

Real-world scenario: You use "PixelPro" to edit a photo and it asks for your Dropbox password so it can save the result. Handing it over means PixelPro can now browse your tax documents, download everything, or lock you out. Later, to remove PixelPro's access, you must reset your Dropbox password — and re-login on your phone, laptop, and every other connected app.
Problems the API Cares About"but my apps are first-party!"

True: with first-party apps the user-trust issue mostly disappears (the Twitter app asking for your Twitter password isn't suspicious). But look from the API owner's side — you must ensure the API is accessed only by real users and real applications.

Identity

Can't tell apps apart

If the API takes username + password and returns a session/token, the request looks identical from every app. You can't distinguish which app is calling.

Attacks

Is it even your app?

An attacker can take a password dump from another service and start trying those credentials directly against your API (credential stuffing). You can't be sure the caller is the real user — or your app.

Scaling MFA

MFA rollout is painful

Add MFA (email, SMS, push, hardware key…) and every app team must update their login UI. Each new MFA type = repeat the whole process. It slows the dev lifecycle and doesn't scale.

Real-world scenario: A company has a web app, an iOS app, an Android app and an admin portal — each built by a different team. Security wants to add a hardware-key MFA step. Without OAuth: 4 teams, 4 releases, 4 sets of bugs, and any team that lags leaves a weaker door open.
How OAuth Solves Ithigh-level preview

OAuth requires every application to send the user out to the OAuth server to log in, then redirect them back to the app so the app can receive tokens. The key is the redirect: the user leaves the app and types their password at the OAuth server — the app never sees it.

User clicks Log in

App doesn't show a password form.

Redirect out

Browser is sent to the OAuth server.

Authenticate there

Password / MFA entered at the OAuth server only.

Redirect back

App receives tokens, not a password.

Key Distinctions & Practical Tipsremember these

Third-party vs first-party

3rd party Main issue = user trust & over-privilege.

1st party Main issue = API control, app identity, and MFA flexibility.

OAuth helps both.

Mental model

Giving an app your password = giving it your house keys.

OAuth = a valet key: limited, revocable, and issued by the owner without handing over the master key.

Practical tips

  • Never ask users for a password for another service.
  • Centralise login (and MFA) in one place.
  • Treat "which app is calling?" as a first-class API question.

Interview one-liner

"OAuth removes the need for apps to ever see user passwords by redirecting users to a central authorization server, which then issues tokens back to the app — improving security, revocability, and letting MFA be changed in one place."
