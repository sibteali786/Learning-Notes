P50 vs P99

Latency percentiles — what they mean, why they diverge, and how it was proven live against Postgres
The Problem
Saying "check the database" when asked to find a bottleneck is a component guess. P50/P99 is a diagnostic lens — it tells you which kind of problem you're looking for before you go looking.
Averages hide the tail
How It Works
Definition: out of 100 requests, P99 is the latency below which 99 of them fall — the slowest 1% is worse than this.
MetricMeaning
P50 (median)Typical experience
P95Most users, including some friction
P99The tail — GC pauses, lock contention, cold cache, slow disk I/O, retries, noisy neighbor
P999Worst case — often one flaky node/shard
fast requests (P0–P97)tail (P99+)
Example: 9,900 requests at 20ms, 100 requests at 5000ms.
Average ≈ 68ms (looks fine!) — P99 = 5000ms (users are furious). At millions of requests, that 1% is thousands of real angry users.
Key Distinctions — Reading the Shape
Uniform badness → P50 bad too
Cause typeStructural / code path
Examplesmissing index, bad query plan, N+1
SignatureP99 − P50 spread stays small
FixEXPLAIN ANALYZE, add index
Tail-only badness → P99 bad, P50 fine
Cause typeOccasional / contention
ExamplesGC pause, pool exhaustion, cold cache, slow shard, retry
Signaturetail % ≈ % of unlucky requests
Fixtracing, per-node metrics
CauseWhy it hits P99 only
GC pauseRuns occasionally — only requests coinciding with it suffer
Connection pool exhaustionPool has N connections; under a burst, requests wait — only burst traffic suffers
Cold cache miss99% hit rate → the 1% miss rate ≈ your tail, almost mathematically
Slow shard / noisy neighborOnly requests routed to that one bad replica are slow
Network retryOnly the small % hitting a transient blip pay the extra RTT
Uniform badness across the whole distribution → look at the code path itself (query plan, index, algorithm).
Badness only in the tail → look at what happens occasionally (contention, cache miss, GC, retries, one bad node).
Real-World Proof — Postgres Experiment
Setup: feed_engine DB, article table (millions of rows), only indexes present were the primary keys. 
EXPLAIN ANALYZE
SELECT a.id, a.title, a.url, p.name AS "publisherName",
       a.category, a.region, a.published_at AS "publishedAt"
FROM article a
JOIN publisher p ON p.id = a.publisher_id
WHERE a.region = 'US' AND a.id < 500000
ORDER BY a.id DESC
LIMIT 20;
Inconclusive — first attempt

Composite index (region, id DESC) was created, but the planner ignored it — kept using article_pkey both times. Why: ORDER BY id DESC LIMIT 20 lets Postgres walk the pkey backward and stop after only 20 matches (skipped just 39 non-US rows) — cheaper than switching indexes. The 1.14ms → 0.09ms drop between runs was buffer-pool caching (cold vs warm), not the index — a live demonstration of the "cold cache" P99 mechanism, just at the DB buffer level.

Corrected test: removed LIMIT and ORDER BY id so the index actually has to compete on its own merit. 
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM article WHERE region = 'US';

Interview & Practical Tips
Never say "check the database" alone — name whether it's a P50 (structural) or P99 (tail) problem first.
P50 bad → pull EXPLAIN ANALYZE, look for Seq Scan vs Index Scan, missing composite indexes, N+1 queries.
P99 bad, P50 fine → pull distributed tracing on slow requests specifically, correlate spike timestamps with GC logs / connection pool metrics / per-replica dashboards.
Tail % should roughly match the % of requests on the "unlucky path" — a 99% cache hit rate almost mathematically predicts a P99 bump.
An index existing ≠ an index being used — the planner picks based on cost, and LIMIT + a sorted PK can beat a "smarter" index for small result sets.
Ties back to the News Aggregator design: this is why the accepted answer for category feeds was in-memory filtering on Redis, not WHERE category=... on Postgres — measured seq-scan cost (1.9s) makes the DB non-viable at 50M req scale.
