🧭 Resource check — is it CPU at all?

Before reaching for a profiler, confirm which resource is actually saturated.

hostcore count
docker exec -it feed_api nproc

Confirms how many CPUs the container actually has to work with — the number you compare load average against.

containerlive per-process CPU
docker exec -it feed_api top

Run this while k6 is hammering the API. Key columns:

FieldWhat to read
%Cpu(s) idIdle CPU. 0.0 across the whole run ⇒ CPU-bound, not I/O-bound.
%Cpu(s) waI/O wait. Near-zero here ruled out disk/network blocking.
load averageCompare to nproc. Went 3.32 → 8.41 against 4 cores — real queuing, not just busy.
per-PID %CPUConfirmed all 4 Gunicorn workers evenly loaded — earlier docker stats snapshot showing "only 2 workers" was a stale single-sample misread.

🔬 py-spy — live sampling profiler

Attaches to a running process and shows which Python functions are actually on-CPU, without needing to modify or restart anything.

hostfind the PIDs first
docker top feed_api

Lists every process inside the container with its PID/PPID — this is how the Gunicorn master was told apart from its 4 worker children. The master's children (matching PPID) are the ones handling requests; the master itself never touches an HTTP request.

hostlive top-style view, all subprocesses
sudo /home/sibteali-baqar/.local/bin/py-spy top --pid 307782 --subprocesses

--subprocesses follows the master PID and samples all its child workers at once instead of picking a single worker to guess at.

Needs SYS_PTRACE py-spy reads another process's memory directly, so it needs elevated privilege (sudo, or the container needs --cap-add SYS_PTRACE) to attach.
hostlive view, one worker only
sudo /home/sibteali-baqar/.local/bin/py-spy top --pid 307847

No --subprocesses here — sampling a single worker PID keeps Gunicorn's own internal (non-request) threads out of the picture.

🔥 py-spy record — flamegraph

Same sampling, but written out as an SVG flamegraph instead of a live scrolling table — much easier to eyeball the widest (= most cumulative time) branch across a whole run.

hostrecord a flamegraph
sudo /home/sibteali-baqar/.local/bin/py-spy record --pid 370147

Produces a timestamped .svg next to wherever the command was run. Open it in a browser — width of a bar = proportion of total sampled time, click to zoom into a branch.

hostsingle worker, no subprocess noise
sudo /home/sibteali-baqar/.local/bin/py-spy record --pid 337266

The one that actually produced a usable request-path flamegraph — recording against a single worker PID (skip --subprocesses) avoided mixing in the master's own bookkeeping threads.

🧩 What the numbers actually meant

False lead: _worker (concurrent/futures/thread.py) Dominated every --subprocesses snapshot (~1200% own time, growing linearly with wall time). Looked alarming, but the flamegraph showed it branching off as a sibling of Gunicorn's own arbiter loop — straight from _bootstrap_inner, not nested under any request-handling code. Confirmed as an artifact of profiling all subprocesses together (including the master's own internal threads) rather than a real cost of serving requests.
Real finding: solve_dependencies Re-profiling a single worker in isolation showed solve_dependencies → request_params_to_args → three _get_multidict_value calls (one per query param: region, limit, cursor) as a branch comparable in width to the actual Postgres fetch/execute branch. FastAPI's own per-request parameter-resolution machinery was costing roughly as much CPU as the database round-trip itself — despite EXPLAIN ANALYZE showing the query at ~2ms.
Falsification test Removed response_model/Pydantic response validation, returned a raw JSONResponse instead → no change in p99 (~1.5s, same as before). Correctly predicted by the profiling data: the response-side cost (dump_json/validate_python) was small; the untouched solve_dependencies branch was the large one. A clean confirm-or-falsify test, not a guess.
