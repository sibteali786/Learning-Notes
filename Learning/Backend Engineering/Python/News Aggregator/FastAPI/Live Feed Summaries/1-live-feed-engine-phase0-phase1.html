Live Feed Engine · Learning Report

From First Query to a 5x Faster API

How a simple GET /feed endpoint over Postgres went from serving ~205 requests/second with a 10.9-second worst-case wait, to ~1,114 requests/second with a 1.42-second worst case — and what each step of that journey actually taught us about where web applications get slow.

1.Background

Skip ahead to Intuition if you're already comfortable with connection pools, WSGI/ASGI workers, and Postgres query plans.

What this project is

The Live Feed Engine is a small news aggregator: a background poller pulls articles from real RSS feeds (BBC, TechCrunch, Hacker News) into a Postgres database, and a FastAPI service exposes a single endpoint, GET /feed, that returns a page of articles for a given region. It's deliberately simple — the interesting part isn't the feature, it's what happens when you point real load at it.

For beginners: the pieces in play

A web API like this one has several layers, and slowness can hide in any of them. It's worth having names for each before we go further:

  • The web server process. Something has to accept incoming HTTP connections and hand them to your application code. Here that's uvicorn, an ASGI server — the modern, asynchronous counterpart to older WSGI servers like Gunicorn's classic sync workers. "ASGI" just means it can juggle many in-flight requests on one thread using async/await, rather than blocking one thread per request.
  • The application framework. FastAPI sits on top of the ASGI server. It turns a Python function into an HTTP route, validates query parameters against type hints, and serializes return values into JSON via Pydantic models.
  • The database driver and connection pool. Every query to Postgres needs an open TCP connection to it. Opening a new one per request is slow, so applications keep a pool of already-open connections and borrow one for the duration of a query. asyncpg is the async Postgres driver used here; its create_pool() takes a min_size/max_size that bounds how many real Postgres connections ever exist at once.
  • The database itself. Postgres has its own hard limit on total concurrent connections (max_connections, default 100) — regardless of what your application-level pool allows, Postgres will refuse connections beyond this.
  • The operating system. Every open socket or file — including every open database connection and every open HTTP connection — consumes a file descriptor, and the OS (or, inside a container, Docker) caps how many a process may hold open at once (the ulimit).

Directly relevant to this change: how the project started

Phase 0 of the project built exactly the chain above, by hand, so its concepts could be learned rather than taken for granted:

  • Postgres running via docker-compose.yml, schema with article and publisher tables.
  • A tiny RSS poller (rss_poller.py) inserting real articles.
  • A FastAPI app (main.py) with one route, GET /feed?region=&limit=&cursor=, using cursor-based pagination — paging by the strictly-increasing article.id rather than a numeric offset, so that pages never drift or overlap even as new rows are inserted concurrently.
  • A connection pool created once at startup via FastAPI's lifespan context manager, and reused for every request — the standard pattern, since opening a fresh Postgres connection per request would be far too slow to survive real traffic.
  • A Dockerfile and a matching api service in docker-compose.yml, so the whole thing runs as two containers talking over Docker's internal network.

That's the system as it stood at the end of Phase 0: correct, and confirmed working against real RSS data. What it had never done was face concurrent load. That's where Phase 1 — and this report — begins.

2.Intuition

The core idea: a system with zero errors can still be "broken" — and the fix isn't always where you first suspect.

The setup: proving you need to worry, before you worry

A tempting habit when building something like this is to add caching (Redis), message queues (Kafka), and other heavyweight infrastructure speculatively, because "that's what real systems have." The more disciplined — and more instructive — approach is to prove you need it first. So Phase 1 seeded the article table with one million synthetic rows, using Postgres's COPY ... FROM STDIN rather than a million individual INSERT statements (which would have taken drastically longer — each INSERT is its own network round trip, while COPY streams the whole batch in one go), and then hit the running /feed endpoint with k6, a load-testing tool that simulates many concurrent users ("virtual users," or VUs) hitting an endpoint at once, ramping from 0 up to 1,000 VUs over five 30-second stages.

What is k6, really?
It's a standalone command-line tool (not a Python or JS library your project depends on) — you install it once via your OS package manager, and it runs test scripts written in JavaScript purely as its own configuration language. It sits outside your stack entirely, generating real HTTP requests against your already-running server, the same way a browser or curl would.

Act 1 — the first surprise: it's not crashing, it's queuing

The first run's result looked, at first glance, like total collapse: a 99th-percentile (p99) latency of 10.93 seconds against a target of 200ms, with some requests taking over 32 seconds. But the crucial detail was that 0% of requests failed — every single one eventually returned a correct 200 OK. That distinction matters enormously: a system returning errors under load is rejecting work it can't do; a system where every request eventually succeeds, just slowly, is queuing — work is piling up faster than it can be drained, like a single toll booth trying to process a thousand cars arriving at once. Nobody gets turned away, but the line grows without bound.

Sure enough, the pool was configured with max_size=10 — meaning only 10 requests could ever be actively talking to Postgres at once, no matter how many thousands were waiting. Raising it to max_size=50 cut the median latency roughly 5x (914ms → ~180ms) and nearly doubled throughput. Progress — but the tail (p99, max) barely moved, and a new symptom appeared: hundreds of requests were now getting cut off by k6's own graceful-shutdown timer because they still hadn't finished. Fixing one bottleneck had simply exposed the next one underneath it.

Act 2 — ruling out the "obvious" suspect

The project's own plan document predicted that at large row counts, pagination would start doing expensive full-table scans, especially for offset-style pagination reading deep pages. This is a very real and common failure mode — but it's worth learning to check rather than assume, using Postgres's EXPLAIN ANALYZE, which runs a query for real and reports exactly what plan it used and how long each step took.

Running it against the actual /feed query — at the full 1 million rows — showed an Index Scan Backward on the primary key, executing in under 2 milliseconds. Because this project used cursor-based pagination (WHERE id < $cursor ORDER BY id DESC LIMIT 20) rather than an offset (OFFSET 500000 LIMIT 20), Postgres could jump directly to the right position using the primary key index, rather than scanning and discarding 500,000 rows to get there. The predicted bottleneck simply wasn't present — a valuable negative result, and a good illustration of why cursor pagination is the standard recommendation for large, growing tables.

Lesson
A slow system under load doesn't mean the database query is slow. Measure before you assume — EXPLAIN ANALYZE turned a suspicion into a two-millisecond fact, and pointed the search elsewhere.

Act 3 — watching the container itself

With the query cleared, the next question was: if it's not the database, what is eating the time? Running docker stats alongside a k6 test — which shows live CPU%, memory, and network I/O per container — revealed the API container's CPU pinned at ~92-95% for the entire run. That number needs a bit of interpretation: docker stats reports CPU usage as a percentage of a single core, so 95% means "fully saturating one core," not "using most of the machine." And that's exactly the problem: the container was running plain uvicorn with no --workers flag, meaning one Python process, one event loop, one core — no matter how many CPU cores the host machine actually had sitting idle.

At the same time, the container logs showed a second, previously-invisible failure: OSError: [Errno 24] Too many open files. Every open connection — HTTP or Postgres — consumes a file descriptor, and the container's default limit was too low for the connection volume 1,000 concurrent VUs was generating.

Act 4 — parallelism, not just bigger numbers

The fix here wasn't "make the pool even bigger" — it was to let the application actually use more than one CPU core. Gunicorn is a process manager that can run several independent worker processes behind one bound port; pairing it with Uvicorn's own worker class (UvicornWorker) gives you several full ASGI event loops, each pinned to its own core, all accepting connections on the same port.

This is the subtlety worth sitting with: each Gunicorn worker is a separate process, so each one independently runs the app's lifespan startup code and creates its own connection pool. Four workers each allowed up to 20 connections means up to 80 real Postgres connections in total — which is why the pool size had to come down (from 50 to 20) at the same time the worker count went up (from 1 to 4): the two numbers multiply together, and the product has to stay under Postgres's max_connections=100. Alongside this, raising the container's file-descriptor ulimit to 65,536 addressed the "too many open files" crash directly.

Note that the target threshold (p99 under 200ms) still wasn't met — this is a genuinely CPU-bound, single-machine ceiling now, which is precisely the kind of measured, honest breaking point that motivates adding a cache like Redis in the project's next phase, rather than reaching for one on faith.

3.Code Walkthrough

The changes, grouped by what problem each one solves rather than by file.

1. Fix: the connection pool was too small

main.py — first pass, widening the pool:

main.py
-    app.state.pool = await asyncpg.create_pool(DB_DSN, min_size=10, max_size=50)

(This was the very first fix tried, going from an original max_size=10 up to 50 in a single-worker setup — it's the value shown as "before" in step 2 below, once the worker count changed.)

2. Fix: only one CPU core was ever in use

Dockerfile — replacing bare Uvicorn with Gunicorn managing four Uvicorn workers:

Dockerfile
-CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
+CMD ["gunicorn", "main:app", "-k", "uvicorn.workers.UvicornWorker", "--workers", "4", "--bind", "0.0.0.0:8000"]

requirements.txt — Gunicorn added as a dependency:

requirements.txt
+gunicorn==23.0.0

3. Fix: rebalancing the pool now that there are 4 processes, not 1

Because each of the four Gunicorn workers creates its own independent pool, the per-worker max_size had to shrink so the total (workers × max_size) stayed under Postgres's max_connections=100:

main.py
-    app.state.pool = await asyncpg.create_pool(DB_DSN, min_size=10, max_size=50)
+    app.state.pool = await asyncpg.create_pool(DB_DSN, min_size=5, max_size=20)

4 workers × 20 connections = 80 total, leaving roughly 20 connections of headroom under the 100 limit for Postgres's own internal use (autovacuum, direct psql sessions, etc.) — the kind of safety margin worth deliberately reserving rather than maxing out.

4. Fix: the container was running out of file descriptors

docker-compose.yml — raising the open-files limit for the API container:

docker-compose.yml
  api:
    build: .
+    ulimits:
+      nofile:
+        soft: 65536
+        hard: 65536
    container_name: feed_api
    restart: unless-stopped

Diagnostic tools used along the way (not code changes, but essential steps)

  • k6 run --env BASE_URL=http://localhost:8000 k6/load_test.js — a ramping-vus scenario stepping 0 → 1,000 virtual users across five 30-second stages, with a threshold asserting p(99)<200ms, run after every change to get an apples-to-apples before/after comparison.
  • EXPLAIN ANALYZE, run directly in psql against both the cursor and non-cursor forms of the /feed query — the tool that ruled out query cost as the bottleneck, by actually executing the query and reporting its real plan and timing rather than guessing.
  • docker stats feed_api, watched live during a k6 run — the tool that revealed single-core CPU saturation, by making visible what percentage of a core the container was actually consuming.

Together, these three tools tell a small story about debugging performance in general: reach for the load generator to reproduce the problem, the query planner to rule out the database as the cause, and the container/process monitor to locate which resource is actually saturated — rather than guessing and applying fixes at random.
