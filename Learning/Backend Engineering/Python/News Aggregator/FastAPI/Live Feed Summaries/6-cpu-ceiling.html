🧭 Reasoning before touching anything

Before profiling, worked through why PgBouncer and Redis solve different problems than the one actually observed.

PgBouncer vs. Redis vs. "what's actually saturated right now"

PgBouncer addresses connection exhaustion between app and Postgres; Redis addresses expensive-to-fetch data. Since the worker/ulimit fix already ruled out connection queuing (p99 1.42s, not connection-starved), and EXPLAIN ANALYZE already showed the query at ~2ms, neither tool's usual justification applied yet. The real open question was: what's consuming CPU right now, if not the query?

This reframing — "which resource is actually saturated" instead of "which tool is popular for this kind of problem" — is what shaped every step that followed.

🔬 CPU diagnosis: top → py-spy → flamegraph

Confirmed CPU-bound, then caught a profiling artifact before it wasted the rest of the session.

top inside the containeridle 0.0%

docker exec -it feed_api top during a k6 run: all 4 Gunicorn workers evenly loaded (35–80% CPU each — ruling out an earlier stale docker stats misread of "only 2 workers used"). %Cpu(s) id = 0.0 and wa = 0.0 across every snapshot, load average climbing 3.32 → 8.41 against nproc=4 — genuinely CPU-bound, with real queuing by the end of the run.

py-spy — the false lead~1200% OwnTime

Caught, not fixed py-spy top --pid <master> --subprocesses showed _worker (concurrent/futures/thread.py) dominating every snapshot. Diagnosed via the flamegraph that this branches off as a sibling of Gunicorn's own arbiter loop, straight from _bootstrap_inner — and critically, it showed up even on the master process (PID 307782), which never touches an HTTP request. An artifact of profiling all subprocesses together, not real request cost.

Clean re-profilesingle worker only

py-spy record --pid <single-worker> (no --subprocesses) — a clean flamegraph of just request handling, with the master's bookkeeping threads excluded. This is the run that surfaced the real finding below.

🧩 The real finding: solve_dependencies

FastAPI's own overhead ≈ the database round-trip Zooming progressively into the flamegraph: routing.py → solve_dependencies (comparable in width to the DB fetch/execute/write branch) → request_params_to_args → three roughly-equal _get_multidict_value calls, one per query parameter (region, limit, cursor). A comparable share of per-request CPU time was spent just extracting three query parameters as was spent on the actual Postgres round-trip — despite the query itself costing ~2ms per EXPLAIN ANALYZE.
Why this ruled out Redis before testing it

Postgres's shared_buffers/OS page cache already serves hot rows from memory, consistent with the ~2ms result — so for this access pattern, Redis and Postgres both resolve to an in-memory lookup. Redis's usual win (avoiding disk I/O) wasn't available to claim here. Correctly reasoned this before spending time building a cache layer.

🧪 Experiments — one falsified, one real

Attempt 1: drop response_modelp99 1.53s — no change

Falsified Removed response_model=list[FeedItem], returned a raw JSONResponse([dict(r) for r in rows]). p99 stayed ~1.53s. Correct prediction from the profiling data: the route's parameters (region: str, limit: int = Query(...), cursor) were untouched, so solve_dependencies — the actual largest branch — kept running unchanged. Only the smaller response-side cost was removed.

Attempt 2: raw Request.query_paramsp99 ~1.34-1.38s — real, modest win

Confirmed Rewrote get_feed to accept the raw Starlette Request and read region/limit/cursor from request.query_params directly, bypassing FastAPI's Query() dependency injection entirely. Re-profiling confirmed the fastapi/dependencies/utils.py branch shrank/disappeared for this path. Cost: manual type coercion/bounds-checking that Query(ge=1, le=100) gave for free — judged not worth keeping once it stopped moving the needle further (see next).

New discovery: access-log writescomparably sized

A branch previously unnoticed: app (routing.py:145) → sender → send → Python's logging module (info → _log → makeRecord → emit) — Gunicorn's --access-logfile writing a line per request, comparably sized to the other three costs (dependency resolution, DB round-trip, response validation).

Pool max_size: 20 → 22 per worker88/97 conns — small, noisy effect

Checked SHOW max_connections (100) and SHOW superuser_reserved_connections (3) → 97 available to non-superuser roles → chose 22 × 4 workers = 88, leaving real headroom (not the naive 25 × 4 = 100, which would have left zero room for an admin psql session). Effect present but small and within run-to-run noise (throughput varied ~860–1120 req/s across otherwise-similar runs) — correctly reasoned that any real gain here is capped by CPU saturation, not connection availability.

🏁 Verdict

4 physical cores, fully saturated, no dominant cost left By this point, the remaining per-request costs (dependency resolution, DB round-trip, response serialization, access logging) are all roughly comparable in size — no single fix left with outsized leverage. Since the host has only 4 physical cores (confirmed via nproc), adding replicas or Gunicorn workers on the same machine would just divide the same saturated cores further, not add real capacity. Real horizontal scaling — more replicas behind a load balancer — only pays off with additional hardware, which wasn't available to test locally. Correctly identified this as the honest stopping point for code-level tuning, rather than continuing to chase diminishing returns.

💡 Lessons worth keeping

  • Process model Gunicorn's master/arbiter spawns and monitors workers but never handles a request. Always profile a worker PID for request-path questions; --subprocesses is for the aggregate picture only, and can quietly mix in the master's own internal threads as if they were request cost.
  • Falsification > guessing The response-model removal test cost nothing and definitively ruled out one hypothesis (response serialization) rather than leaving it as an untested assumption.
  • Reasoning before reaching for tools Redis was ruled out by reasoning about Postgres's own buffer cache before writing any caching code — cheaper than building and then discovering it wouldn't help.
  • Watch for noise Throughput swung ~20% (860–1120 req/s) between runs meant to test the same variable — a reminder to be skeptical of small deltas without repeated runs.
  • Know the hardware ceiling "Add more replicas" only helps if there's spare CPU somewhere to give them — on a 4-core host already at 0% idle, more processes on the same machine just divides the same saturated cores further.
