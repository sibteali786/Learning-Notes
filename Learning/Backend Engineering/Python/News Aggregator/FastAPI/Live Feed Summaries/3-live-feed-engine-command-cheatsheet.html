🐍Local dev / venv

Running the API directly on the host, outside Docker — fastest loop for iterating on main.py.

Run the API with auto-reloaddev
.venv/bin/uvicorn main:app --reload --port 8000

Interactive docs at http://localhost:8000/docs. Talks to Postgres via the DATABASE_URL env var, falling back to localhost:5432 if unset.

Install/verify project deps into .venv
.venv/bin/pip install -r requirements.txt

Only needed on the host if running outside Docker. Do not run this against the system Python — it's externally managed on this machine (Debian/Ubuntu PEP 668) and will refuse with externally-managed-environment.

🐳Docker & Compose

Running the full stack (Postgres + API) as containers, matching how it actually deploys.

Start everything, rebuilding the API imagemost common
docker compose up --build

--build is required any time Dockerfile or requirements.txt changed — otherwise Compose reuses the stale cached image and your code changes silently don't take effect.

Start everything without rebuilding
docker compose up

Fine when only docker-compose.yml itself changed (ports, env vars, ulimits) — nothing that gets COPY'd into the image.

Stop and remove containers
docker compose down

Add -v only if you intentionally want to wipe the Postgres data volume (pgdata) too — that deletes all seeded/ingested rows.

Watch live resource usage of the API containerdiagnosis
docker stats feed_api

CPU% is reported per single core — 95% means one core fully saturated, not "the whole machine." Run this in a second terminal while a k6 test is active in another.

Tail container logs
docker compose logs -f feed_api
# or, while `docker compose up` is already attached in the foreground,
# just watch its own terminal output

This is where the OSError: Too many open files and Gunicorn worker-boot messages showed up during diagnosis.

Open a shell / one-off command inside a running container
docker exec -it feed_api sh

python:3.12-slim based images don't ship bash by default — use sh.

🐘Database / psql

Talking to Postgres directly, bypassing the API — for schema checks, EXPLAIN ANALYZE, and manual queries.

Open an interactive psql session in the Postgres containermost common
docker exec -it feed_postgres psql -U feed_admin -d feed_engine
Check Postgres's connection ceilingbefore tuning pools
SHOW max_connections;

Always check this before raising workers × pool max_size — the product must stay comfortably under it.

Inspect a table's columns and indexes
\d article
Run a query plan against the real /feed querydiagnosis
EXPLAIN ANALYZE
SELECT a.id, a.title, a.url, p.name AS "publisherName",
       a.category, a.region, a.published_at AS "publishedAt"
FROM article a JOIN publisher p ON p.id = a.publisher_id
WHERE a.region = 'US' AND a.id < 500000
ORDER BY a.id DESC
LIMIT 20;

Look for Index Scan (good) vs Seq Scan (bad at scale), and read the actual time=... on the outermost node for real execution time.

One-off row count sanity check
SELECT count(*) FROM article;
Exit psql
\q

🌱Seeding data

Generating synthetic load-test volume without waiting on real RSS ingestion.

Seed N synthetic articles via COPYmost common
.venv/bin/python seed.py 1000000

Defaults to 100,000 if no argument is given. Uses COPY ... FROM STDIN rather than row-by-row INSERT — the only approach fast enough at six-figure-plus row counts.

Run the RSS poller manually, one-shot
.venv/bin/python rss_poller.py

Pulls real articles from BBC/TechCrunch/HN into Postgres. Not yet running continuously/containerized — still a manual, on-demand step.

📈k6 load testing

A standalone binary — not a project dependency — that generates real concurrent HTTP traffic against the running API.

Install k6
sudo apt install k6

If the apt repo isn't already configured, see k6's own install docs for the repo/key setup step first.

Run the load testmost common
k6 run --env BASE_URL=http://localhost:8000 k6/load_test.js

Ramps 0→1000 virtual users across five 30-second stages, asserting a p(99)<200ms threshold. Run this after any pool/worker/config change for a clean before/after comparison.

0 VUs→ 50→ 200→ 500→ 800→ 1000
Run and save raw results to a file
k6 run --out json=results.json --env BASE_URL=http://localhost:8000 k6/load_test.js

Useful if you want to diff two runs programmatically instead of eyeballing the terminal summary.

Reading the output: check http_req_failed / checks_failed are 0% first — a run with real failures makes the latency percentiles below it unreliable. Then read http_req_duration's med / p(95) together with http_reqs' rate (req/s) as your throughput number.

🔬Typical diagnosis sequence

The actual order these commands get reached for when something's slow — not a fixed rule, but the pattern that held up across Phase 1.

Reproduce → rule out the DB → locate the resource
k6 run ...→ docker stats feed_api→ EXPLAIN ANALYZE (psql)→ fix→ docker compose up --build→ k6 run ... (again)

Run k6 and docker stats side by side in two terminals — docker stats updates live for the whole duration of the k6 run.
