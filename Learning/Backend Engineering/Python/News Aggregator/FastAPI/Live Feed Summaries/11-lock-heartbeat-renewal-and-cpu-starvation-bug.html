The problem heartbeat renewal solves

The fixed-TTL lock commits to one static guess for how long the winning request's work will take, decided the moment the lock is acquired — before anyone knows how long the work will actually take.

Guess too short → lock expires mid-computation, a second request piles on. Guess too long → a genuinely crashed process's lock lingers, slowing everyone else's recovery. Heartbeat renewal replaces the single guess with small, repeated extensions while real work is still happening — the lock lives almost exactly as long as work is happening, no longer.

Concepts learned

asyncio.Event

A flag one coroutine can .set() and another can await .wait() on. Not polling — a real wake-up signal. The moment .set() fires, every waiter's .wait() returns immediately, no matter how long they'd been sitting there.

asyncio.wait_for(awaitable, timeout)

Races an awaitable against a clock. Two outcomes: the awaitable finishes first → returns its result normally. The timeout elapses first → cancels the awaitable, raises asyncio.TimeoutError. Wrapping event.wait() (which alone would block forever) in wait_for(..., timeout=interval) gives "wake up early if signaled, otherwise wake up after N seconds regardless" — exactly the shape a heartbeat loop needs.

asyncio.TaskGroup (Python 3.11+)

Structured concurrency: every task created inside the async with block must finish before the block exits. If any task raises, every sibling task is cancelled and the exception re-raises at the async with itself — wrapped in an ExceptionGroup, caught with the new except* syntax, not plain except. A task's own return value isn't handed back by the block; you hold the Task object from tg.create_task(...) and call .result() on it afterward.

Cooperative scheduling — the rule that broke everything

asyncio can only switch which coroutine is running at await points. A stretch of plain synchronous Python with zero await in it — no matter how long it runs — freezes the entire event loop, including every other task's timers and callbacks. This is the root of the big bug below.

asyncio.to_thread + the GIL

CPython's GIL lets only one thread execute Python bytecode at a time — so moving CPU-bound pure-Python work into a thread via to_thread doesn't make it faster. But the GIL is released and re-acquired on a timer (~5ms default switch interval), even without I/O — so a thread running that work still periodically hands control back. Critically, await asyncio.to_thread(...) is a real await point on the main thread, so the event loop stays free to run other coroutines while the worker thread grinds through the computation. Goal here wasn't speed — it was keeping the loop responsive.

Design & build

Built end-to-end via one-question-at-a-time Socratic walkthrough — every line hand-written, corrections found by tracing logic rather than being handed fixes.

1. Renewal Lua script — same shape as the existing release script

-- scripts/renewLock.py
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("expire", KEYS[1], ARGV[2])
else
    return 0
end

Mirrors the compare-and-delete release script already in place — extending someone else's lock (after yours expired and a new one took over the key) would be just as wrong as blindly deleting theirs.

2. The renew loop

async def renew_loop(event, key, token, ttl=10, interval=5):
    while True:
        try:
            await asyncio.wait_for(event.wait(), timeout=interval)
            break  # event fired -> winner is done, stop renewing
        except asyncio.TimeoutError:
            try:
                await app.state.lockRenewScript(keys=[key], args=[token, ttl])
            except Exception as e:
                print("Error in redis script for renewal: ", e)

3. Wiring it into the winner branch via TaskGroup

event = asyncio.Event()

async def fetch_and_signal():
    try:
        rows = await fetchFromDb(query, args)
        return rows
    finally:
        event.set()   # fires on success AND failure

try:
    async with asyncio.TaskGroup() as tg:
        fetch = tg.create_task(fetch_and_signal())
        tg.create_task(renew_loop(event, lock_key, token))
except* Exception as eg:
    await release_lock(lock_key, token)
    print(f"Request failed for database: {eg.exceptions}")
    raise

json_serialized = fetch.result()

release_lock(lock_key, token) was extracted as its own helper (wrapping the Lua call in its own try/except) to flatten what was becoming a try/except pyramid across two call sites — the success path and the new failure path.

Bug hunt: three small bugs, one big one

Bug 1
off-by-oneLua arrays are 1-indexed — KEYS[0] in renewLock.py should have been KEYS[1] (both occurrences).
Bug 2
typo / mismatchrenew_loop called app.state.renewLockLuaScript, but the script was registered under app.state.lockRenewScript in lifespan — would have raised AttributeError on the very first renewal attempt.
Bug 3
swallowed exceptionAn early version added a bare except Exception: print(...) in fetch_and_signal with no re-raise. fetch.result() would then silently return None on a real DB failure — which then got cached and served as the response to everyone until TTL expiry. Worse than the original unhandled-crash behavior. Fixed by dropping back to plain try/finally and letting TaskGroup propagate the exception naturally.

The real find: CPU-bound event-loop starvation

Serious

Manual k6 runs showed 0% failures — looked clean. But a direct Redis TTL watch during a real request told a different story: the lock's TTL just counted straight down to expiry, with no renewal ever firing, even though the fetch clearly ran past the 5-second renewal interval.

Live evidence — before the fix

t=0.00renew_loop iteration start
t=8.14fetch_and_signal completed → event set → loop breaks (no renewal ever attempted)

Root cause: after rows = await conn.fetch(...) — a genuine, non-blocking await — the rest of fetchFromDb was plain synchronous Python: a dict-comprehension building rows_modified, then json.dumps(...). Zero await points. Since asyncio can only switch coroutines at await points, that multi-second block froze the entire event loop — including renew_loop's own timer, the very thing built to protect against exactly this kind of stall.

Bonus bug Debug prints (and, silently, all along, the app's own error-logging prints) weren't showing up in docker logs at all — same root cause as the earlier rss_poller.py stdout-buffering gotcha, this time on a Gunicorn-managed process. Fixed with ENV PYTHONUNBUFFERED=1 in the Dockerfile — an environment variable the interpreter reads at startup regardless of what actually invokes it, unlike the CLI-only python -u flag.

The fix

def processArticleResponse(rows) -> str:
    rows_modified = [
        dict(r) | {"publishedAt": r["publishedAt"].isoformat()} for r in rows
    ]
    return json.dumps(rows_modified)

async def fetchFromDb(query, args):
    async with app.state.pool.acquire() as conn:
        rows = await conn.fetch(query, args)
    return await asyncio.to_thread(processArticleResponse, rows)

Along the way, a piece of pasted research correctly noted to_thread can't speed up pure-Python CPU-bound work under the GIL — and proposed run_in_executor as an alternative, not realizing to_thread is run_in_executor with the default thread pool. The actual fix needed wasn't speed — it was keeping the main thread's event loop free to keep servicing renew_loop while the worker thread did the (still GIL-bound, still not-faster) computation.

Why memory dropped: before the fix, every multi-second CPU-bound freeze stalled every coroutine in that worker — new fetches, polling, renewals, all of it. Once the freeze ended, that backed-up work got a chance to run all at once, in a burst — several large row-lists/JSON blobs alive in memory simultaneously. With to_thread, the loop never freezes, so work gets serviced roughly as it arrives instead of piling into bursts. Same "queuing/burstiness beats raw compute cost" lesson as the original Phase 1 diagnosis — surfacing again in a completely different part of the system.

Takeaways

  • Heartbeat renewal is a reliability win, not a throughput one — replacing one hand-guessed worst-case TTL with a small, self-correcting one. Throughput numbers were a wash; recovery-time-from-failure is the actual promised benefit (still to be directly demonstrated — see below).
  • 0% failures in a load test doesn't prove a concurrency mechanism actually works — the CPU-starvation bug never caused a real stampede in any k6 run purely because no second request happened to arrive during the ~5–8s unprotected gap. Direct instrumentation (a live TTL watch) was needed to catch it.
  • The CPU-bound-event-loop-starvation pattern is now a repeat offender in this project — first found via py-spy/docker stats against raw request throughput (Phase 1), now found again defeating a concurrency-based correctness mechanism (this session). Worth remembering as a first suspect whenever async code "should" be concurrent but isn't behaving that way.
  • Correcting your own research in real time is normal and good — a pasted explanation of to_thread vs. the GIL was factually accurate but answered the wrong question ("does this add parallelism?" vs. "does this keep the loop responsive?").

Verifying the two promised wins

The heartbeat design made two claims that hadn't actually been tested yet — only reasoned through. Both were verified directly this session.

1. Crash recovery — measured, not asserted

Simulated a genuine crash: kill -9 on one specific Gunicorn worker process mid-request (not the whole container — a real crash means the process disappears with zero chance to run any cleanup, fundamentally different from a caught fetchFromDb exception, which was already handled correctly).

Tooling gotchas hit along the way: the slim base image has no kill/ps binaries (sent the signal via docker exec ... python -c "os.kill(...)" instead); docker top reports host-side PIDs but docker exec runs in the container's own PID namespace, so the two don't match — resolved by reading /proc/*/cmdline from inside the container to get its own view of PIDs (1=master, 7,8,9,10=workers, matching Gunicorn's own boot-order logs).

t=0.00worker acquires lock, TTL=10s
t≈1.5sworker killed via SIGKILL — no cleanup runs
t≈8.3–9.4s after killlive TTL watch shows lock naturally expiring — matches the 10s TTL exactly
first probe afterimmediately reclaims lock, does the real fetch, populates cache
Worst-case reasoning, confirmed correct on the first try: no matter when in the renewal cycle a crash happens, recovery is always bounded by the TTL itself (10s) — never TTL+interval. Crash right after a fresh renewal → full 10s must elapse (worst case). Crash right before a renewal was due → recovery is nearly immediate. 10s is a hard ceiling — a direct, measured improvement over the old scheme's up-to-45s hand-guessed worst case.

2. The small throughput cost — explained, not dismissed

Four k6 runs post-to_thread-fix, same 10-VU weighted scenario:

All four sit consistently below the old fixed-45s-TTL baseline (135–141 iterations, avg ~6.8s) — in the same direction, every time. Four independent samples agreeing is signal, not noise.

First hypothesis, corrected: "the periodic renewal Redis calls add overhead" — but renewals only fire on requests running past 5s, while the slowdown shows up across the entire run, including fast sub-5s requests that never trigger a single renewal. Actual cause: the fixed per-request setup cost of asyncio.TaskGroup + asyncio.Event + scheduling two concurrent tasks, present on every request regardless of whether a renewal ever fires — versus the old scheme's single bare await fetchFromDb(...) with none of that machinery.

Verdict: a real, understood, accepted trade-off — a hard 10s crash-recovery ceiling in exchange for a small, constant per-request concurrency-setup cost. Not a regression to chase; a deliberate reliability-for-throughput trade confirmed by evidence.
