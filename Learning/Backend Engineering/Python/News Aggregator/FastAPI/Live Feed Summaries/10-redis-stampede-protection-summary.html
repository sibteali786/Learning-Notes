1. The setup

/feed/full-scan?limit= is a deliberately expensive endpoint: it fetches up to a million rows, joins them, and serializes the result into a JSON blob that can be over 200MB. It was made cacheable in Redis — key fullscan:limit:{limit}, value = the final serialized JSON string, TTL 20 seconds.

It was load-tested with k6 at 10 concurrent virtual users, each picking a random limit from a weighted distribution — 800000 dominant at 70%, the rest much rarer — so the cache would have a real "popular key" to demonstrate a benefit on.

2. The bug: caching made things worse

The surprising result
Adding a cache to a struggling endpoint is supposed to help. Here it didn't — it made things measurably worse than having no cache at all.

38.70%

Average request duration rose from 30.27s (uncached) to 41.8s (cached), and the API container hit an actual kernel SIGKILL out-of-memory event — something that hadn't happened at that severity even without a cache.

3. Why: a cache stampede

The cache's 20-second TTL was far shorter than how long a request actually took to complete under load (avg 41.8s). That mismatch is the whole story:

Every VU checks fullscan:limit:800000 at roughly the same instant, sees nothing cached, and all of them independently fetch from Postgres, serialize ~200MB of JSON, and write their own redundant copy into Redis — simultaneously.

Why memory got worse, not better
Without a cache: N duplicate ~200MB blobs live briefly in the API's own memory.
With an unprotected cache: N duplicate blobs in the API's memory plus N duplicate ~200MB copies written into Redis. Adding the cache added a second place for the same duplicated memory to pile up.

4. The fix: a Redis distributed lock (single-flight)

The goal: when a key is uncached, exactly one request should do the expensive work while everyone else waits for it — "request coalescing."

data key
→
Miss →

→
Lost?

Three design decisions

A separate lock key. fullscan:lock:limit:{limit}, distinct from the data key fullscan:limit:{limit} — so a "someone's working on this" marker can never be mistaken for real cached data by an unrelated reader.

SET lock_key token NX EX ttl as the mutex. NX means "only set if it doesn't already exist" — whichever request's SET succeeds is the winner. token is a fresh uuid.uuid4() per request, held as a plain local variable (each HTTP request is its own isolated async call — no shared state needed).

Safe release — compare-and-delete, not a blind DELETE. This is the part worth dwelling on:

The bug a blind DELETE would cause
If Winner A's lock outlives its own TTL (because A is just slow, not dead) and Winner B legitimately acquires a fresh lock in the gap — then A finally finishes and calls a blind DELETE on the lock key. That deletes B's lock, not A's. A third request can now pile on too. One unprotected delete cascades into exactly the stampede this whole lock was built to prevent.

The fix, straight from Redis's own "Distributed locks with Redis" documentation, run as an atomic Lua script so the check-and-delete can't be split by another operation in between:

local current = redis.call("get", KEYS[1])
if current == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

Only delete the lock if it still holds my own token. (Redis 8.4 added a native DELEX key IFEQ for exactly this — but this project runs redis:7-alpine, so the Lua-script version was required.)

Losers poll the data key, not the lock key, at a fixed interval — and fall back to computing it themselves (unprotected) if they wait too long without success.

5. Real bugs caught along the way

Dockerfile only copied main.py
The new scripts/ directory (holding the Lua script) never made it into the image. Every Gunicorn worker crashed on boot with ModuleNotFoundError: No module named 'scripts'. Fixed with COPY scripts/ ./scripts/. No __init__.py was needed — Python 3.3+ treats a plain directory as an implicit namespace package.
Two missing awaits
fetchFromDb(...) and the registered Lua script call are both async — calling either without await silently returns an unresolved coroutine/Script object instead of the real value. No crash, just wrong behavior. Same recurring bug class as the original redis.get/redis.set await bugs earlier this project.

6. Tuning the lock — two iterations, both tested

The lock alone wasn't enough on the first try. The TTL and the waiter's poll budget had to actually match how long real work takes under contention — not a guess.

Iteration 1 — TTL 18s, wait budget 10s

Real improvement over the unprotected stampede, but still degraded: two consecutive runs showed 11.36% then 0% failed, avg duration 21.98s then 11.38s.

Root cause (self-diagnosed)
Requests under 10-VU contention took up to ~42s to finish — far longer than the 18s lock TTL. The lock could expire while the winner was still legitimately working, letting a second request grab a fresh lock and start a smaller duplicate stampede. And even fixing the TTL alone wouldn't help: a waiter that gives up after only 10s of polling would still duplicate work against a winner who's merely slow, not dead. Both numbers needed to move together.

Iteration 2 — TTL 45s, wait budget 40s

Comfortable margin above the observed ~42s worst case, and the waiter's patience extended to match.

The clean win
Zero failures across two consecutive 10-VU runs, average duration cut roughly in half again from the tighter-window attempt, memory contained under 2GB (down from OOM), and nearly double the completed iterations in the same wall-clock time — more useful work done, not just fewer errors.

The remaining gap to the 2-VU numbers (~6.8s vs 2.87s avg) is structural, not a bug: at 10 VUs spread across 5 different limit keys, with 800000 dominating (88–100 of ~135–141 total requests per run), only one request per key can be the active winner at a time — real queuing on the hottest key is expected, even with a perfectly correct lock.

8. What's next — two upgrades, deliberately deferred

Two further improvements were designed in detail but not built this round — the goal was a working, understandable first version, not a fully production-hardened one.

Fixed-interval polling Pub/Sub or BLPOP
Fixed TTL ← built this session upgrade #2
Lease renewal (heartbeat) upgrade #1 most production-correct

These two axes are independent — either can be upgraded without touching the other.

Lease renewal (heartbeat)

Instead of guessing one fixed TTL up front (the exact problem iteration 1 hit), the winner would periodically extend its own lock's TTL while genuinely still working, and simply stop renewing once done or crashed. The lock then lives exactly as long as real work is happening — no more guessing a worst case.

Pub/Sub or BLPOP notification

Replaces the 500ms polling loop with a push notification — the winner announces "done" once, and waiters wake up immediately instead of discovering it on their next poll tick. BLPOP avoids a real pub/sub race (a message published before anyone's subscribed can be missed entirely; a list item just sits there until popped).

Suggested order: lease renewal first (smaller, self-contained change to the existing lock code), verified under the same 10-VU test — then Pub/Sub or BLPOP as the larger structural change, tested against an already-correct lock lifetime.
