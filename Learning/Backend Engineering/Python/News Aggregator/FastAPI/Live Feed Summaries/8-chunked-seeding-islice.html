Concepts covered

generator functions

generate_rows() uses yield, so calling it doesn't run the body — it returns a generator object that's already an iterator. No iter() wrapping needed.

itertools.islice(iterator, n)

Pulls the next n items off any iterator, lazily, then stops — even if the source is infinite (like itertools.count()). This is what turns one long row-stream into fixed-size batches.

the walrus while-loop

while batch := list(islice(rows, batch_size)): re-slices the next chunk each pass. When rows is exhausted, islice returns nothing, the list is empty, and the loop ends — no manual counter required.

StringIO as a scratch buffer

calleffect
writer.writerow(row)appends CSV text, cursor moves to the end
buf.seek(0)rewinds cursor to start — for reading, doesn't delete data
buf.truncate(0)deletes from the cursor onward — only clears if cursor is already at 0

Per chunk: write all rows → seek(0) → copy_expert reads it whole → seek(0) + truncate(0) to empty it for the next chunk.

Bugs caught along the way

  • fixed iter(count) on an int — ints aren't iterable; needed the generator object instead.
  • fixed outer loop variable was a whole chunk, not a row — needed a nested loop before writerow.
  • fixed buffer was reset every row instead of once per chunk — collapsed batching back to one COPY per row.
Still open: uq_url unique constraint collides with prior seed runs (URLs like article/0 already exist from ~10M earlier rows). Options discussed: shift the id offset, stage + ON CONFLICT DO NOTHING, or truncate article before reseeding. Decision: truncate/delete first for a clean run.
Also noted: conn.commit() only fires once, after all 50 chunks — so row count stays frozen in another psql session until the whole run finishes. Not a bug; just transaction visibility.
