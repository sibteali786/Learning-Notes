1. Containerizing rss_poller

Reasoned first The poller's main() already had a while True: poll_once(); sleep(300) loop from earlier work — "run manually" only meant poll_once() had been called directly, not that the loop structure was missing. Containerizing was mostly plumbing, not new logic.

Decision: no asyncpg pool

api.py juggles hundreds of concurrent HTTP requests → needed a pool. rss_poller is one sequential process, one connection, no concurrency → pooling solves a problem this process doesn't have.

Decision: separate Dockerfile

Different CMD, different dependency set (no fastapi/gunicorn/uvicorn needed). One shared Dockerfile handling two images invites confusion for future readers → Dockerfile.poller + requirements-poller.txt.

Gotcha Empty docker logs despite the poller clearly working

Rows were inserting (confirmed via SELECT count(*) climbing), but docker logs rss_poller showed nothing. Cause: Python buffers stdout differently depending on whether it's a TTY. In a container, stdout is piped — not a terminal — so CPython switches from line-buffered to block-buffered, and print() output sits in a buffer instead of flushing.

# fix — either works
CMD ["python", "-u", "rss_poller.py"]
# or: ENV PYTHONUNBUFFERED=1

2. Duplicate-Row Bug

Every 5-minute cycle re-fetches the same live feed entries. With a plain INSERT and no identity check on url, that means every cycle re-inserts every still-live article as a brand new row.

poll_once()
every 5 min
→
same feed entries
re-fetched
→
plain INSERT,
no url check
→
duplicate rows
pile up forever

Diagnosis: ROW_NUMBER() OVER (PARTITION BY url)

SELECT id, url, ROW_NUMBER() OVER (PARTITION BY url ORDER BY id) AS row_num
FROM article;

Ranks every row within its own url group, ordered by id — the first-inserted copy gets row_num = 1, every re-fetch after that gets 2, 3, 4...

idurlrow_num
10000124blinkenlights.de1
10000187blinkenlights.de2
10000250blinkenlights.de3
10000315blinkenlights.de4
......(6 copies total)...

Confirmed the synthetic seed data (example.com/article/N) was all unique — every duplicate traced back to the poller's own re-fetch pattern, nothing to do with the seed.

Why DB constraint, not app-level check-then-insert

Reasoned

Rejected "SELECT to check, then INSERT if absent" from the app — it has a TOCTOU (time-of-check-to-time-of-use) gap between the check and the write where a duplicate could still slip through, plus it costs two round trips per row instead of one. A DB-level UNIQUE constraint + ON CONFLICT enforces it atomically, in a single round trip.

The fix, in order

Added to init.sql so any fresh volume starts clean:

CREATE TABLE article (
    id            BIGSERIAL PRIMARY KEY,
    title         TEXT NOT NULL,
    url           TEXT NOT NULL UNIQUE,
    ...
);

The live table already had duplicates, so a straight ALTER TABLE failed first:

ERROR:  could not create unique index "uq_url"
DETAIL:  Key (url)=(...) is duplicated.

Fixed by deleting all but the earliest copy of each duplicated url, using a CTE (a window function like ROW_NUMBER() can't be referenced directly in a WHERE clause, and DELETE must target a real table — so the CTE computes the ids to delete, and the outer DELETE matches against them):

WITH duplicate_rows AS (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY url ORDER BY id) AS row_num
    FROM article
)
DELETE FROM article
WHERE id IN (SELECT id FROM duplicate_rows WHERE row_num > 1);
-- DELETE 418

ALTER TABLE article ADD CONSTRAINT uq_url UNIQUE (url);
-- ALTER TABLE ✓

Updated insert_article so a re-seen url on a future poll silently no-ops instead of crashing on UniqueViolation:

cur.execute(
    """
    INSERT INTO article (title, url, publisher_id, category, region, published_at)
        VALUES (%s, %s, %s, %s, %s, %s)
        ON CONFLICT (url) DO NOTHING
    """,
    (title, url, publisher_id, category, region, published_at),
)
