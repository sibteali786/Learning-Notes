Hot Keys, Buffer Pools, and the Cache You Don't Need Yet

How a weighted-random k6 scenario proved, with numbers instead of assumptions, that Redis wouldn't help the Live Feed Engine's /feed endpoint — and why that's a genuine engineering result, not a wasted afternoon.

Background

For readers new to this project

The Live Feed Engine is a small news-aggregation service: a FastAPI app (main.py) serves GET /feed?region=&limit=&cursor= over a Postgres table of articles, paginated by cursor (WHERE id < cursor ORDER BY id DESC LIMIT n) rather than by offset, so pagination stays cheap even as the table grows. A separate poller ingests real RSS feeds every five minutes, and a synthetic seeder (seed.py) can pad the table with millions of fake rows on demand, to simulate scale the real feeds would take years to produce.

Earlier work (an entire previous phase, not covered here) chased the system's raw throughput ceiling: profiling with py-spy, moving from a single Uvicorn process to four Gunicorn workers, tuning the asyncpg connection pool, and bypassing FastAPI's automatic query-parameter parsing. That took the endpoint's p99 latency at 1000 concurrent virtual users from 10.93 seconds down to roughly 1.3–1.4 seconds — and then it stopped improving. Profiling showed why: all four CPU cores sat at 0% idle under load. The bottleneck had moved from "one thread doing everything" to "four threads, still all busy," which is a ceiling that adding more application-level cleverness can't push past. That's the state the project was in walking into today's session.

What's directly relevant here

The project's plan (borrowed from a system-design case study assuming ~100 million daily active users) calls for adding Redis as a read-through cache — ZADD feed:US <timestamp> <articleId> per region — specifically to handle hot keys: a small number of regions or feeds receiving a disproportionate share of traffic, the classic shape of real-world news consumption (everyone reads the top headlines; almost nobody reads yesterday's regional business digest).

But the project's own stated philosophy, written into its plan document, is blunt about sequencing: "Don't add Redis speculatively — prove you need it first." Today's session took that seriously. Two questions needed answering before touching Redis at all:

  1. Does raw data volume alone (going from 1 million rows to 50 million) move the needle?
  2. Does skewing traffic toward a hot key — the exact pattern Redis is meant to solve — actually break anything, given everything already known about where this system's bottleneck lives?

Answering question 2 required teaching the load-testing tool, k6, to simulate realistic hot-key traffic instead of its original uniform-random region picks — and that's the code change this document walks through.

Why this matters beyond one file
A one-line uniform Math.random() pick is easy to write and easy to trust. But if your entire argument for adding a piece of infrastructure rests on "traffic isn't evenly spread," your load test had better not spread traffic evenly. Today's work is really about closing that gap between the test and the real-world assumption it's supposed to validate.

Intuition

From "any region, equally likely" to "usually the same region"

The original k6/load_test.js picked a region like rolling a fair four-sided die: each of US, EU, APAC, and LATAM had exactly a 25% chance on every request. That's a fine test of raw throughput, but it can never produce a hot key — by construction, no region is "hot," they're all identically warm.

To simulate a hot key, you need a weighted random choice: say 70% of requests should land on US, 20% on EU, 7% on APAC, and 3% on LATAM. JavaScript has no built-in equivalent of Python's random.choices(options, weights=...), so the weighting has to be built by hand — and the cleanest way to do that is to think of the interval from 0 to 1 as a number line, sliced into four pieces sized by each region's weight.

Weighted regions as slices of a 0–1 number line
US — 70% [0, 0.7)
EU — 20% [0.7, 0.9)
A [0.9, 0.97)
L [0.97, 1)

A single call to Math.random() produces a random point on that line. Wherever it lands determines the region. The mechanism for finding "where it lands" is a running total: walk through the regions in order, adding up their weights as you go, and stop at the first region where that running total exceeds your random draw.

Traced by hand, with r = 0.75 and weights US: 0.7, EU: 0.2, APAC: 0.07, LATAM: 0.03:

StepRegion examinedRunning totalRunning total > 0.75?
1US (0.7)0 + 0.7 = 0.7No — keep going
2EU (0.2)0.7 + 0.2 = 0.9Yes — stop, pick EU

That's the whole algorithm: no libraries, no lookup tables, just a running sum and a comparison.

Why the hot key didn't break anything

Here's where the story gets more interesting than "we simulated hot keys, the end." The hot-key scenario was built, verified to actually produce a 70/20/7/3 split, and run against the 50-million-row table — and latency barely moved. To understand why, it helps to see the request's actual path:

Two of those five boxes barely care which region was requested. solve_dependencies and the Pydantic validation/serialization step run identically whether the query says region=US or region=LATAM — their cost is driven by "a request arrived," full stop, not by which rows it touches. And the database step, even though it's the box people usually suspect first, was already shown (by EXPLAIN ANALYZE) to take about 0.09 milliseconds regardless of region or table size, because it's an index scan on a primary key with a LIMIT 20 — the query only ever touches the newest 20 rows for whichever region it's asked about. Postgres's own buffer pool keeps that tiny "top of the feed" slice in memory permanently; hammering it harder doesn't make it any less already-cached.

The bottleneck that skewing traffic can't touch
Earlier profiling (in the prior phase of this project) found the real ceiling: with four Gunicorn workers spread across four CPU cores, all four cores sit at 0% idle under load. That's a bottleneck shaped by how many requests per second arrive, not by which data those requests ask for. Skewing 1000 virtual users toward one region changes nothing about total request volume or per-request CPU cost — so the same four saturated cores stay exactly as saturated.

Put differently: a cache is a trade — pay an expensive cost once, then serve repeats for free. That trade only pays off when two things are both true: the underlying work is genuinely expensive, and many requests overlap on the same result so the cache actually gets reused. This endpoint fails the first condition outright. Its query is already cheap and already effectively cached by Postgres. No amount of "make the traffic lopsided" can manufacture expense that was never there. Repeating a cheap operation just keeps it cheap.

The actual result
p99 latency went from 1.67–1.68 seconds (uniform-random, 50M rows) to 1.83 seconds (70/20/7/3 hot-key, 50M rows) — a small, unremarkable bump, nowhere close to the dramatic "Postgres collapses under a hot key" outcome the ~100M-DAU case study assumes. That's not a failed experiment. It's a successful one: it proved, with a real measurement instead of an assumption, that Redis would not move this specific endpoint's numbers today.

The Code

k6/load_test.js evolved through several small, hand-written iterations over the course of the session, each one catching a real bug before the final version worked. There's no git diff to walk — this is a learning-mode project where the code is written by hand, iteration by iteration — but the "before" and "after" states of the file tell the story clearly enough.

1. Uniform pick → weighted pick

The starting point was a flat, equally-likely pick among four regions:

const REGIONS = ["US", "EU", "APAC", "LATAM"]; export default function () { const region = REGIONS[Math.floor(Math.random() * REGIONS.length)]; const res = http.get(`${BASE_URL}/feed?region=${region}&limit=20`);

It was replaced with a list of {region, value} weight pairs and a running-total walk:

const REGIONS = [ { region: "US", value: 0.7 }, { region: "EU", value: 0.2 }, { region: "APAC", value: 0.07 }, { region: "LATAM", value: 0.03 }, ]; export default function () { const randomNo = Math.random(); let chosenRegion = ""; let runningTotal = 0; for (const region of REGIONS) { runningTotal += region.value; if (runningTotal > randomNo) { chosenRegion = region.region; break; } } const res = http.get(`${BASE_URL}/feed?region=${chosenRegion}&limit=20`);

2. Two bugs, caught before they could quietly break the result

The first attempt at the weighted logic shipped with two mistakes that would have silently produced garbage data — worth dwelling on because they're both classic JavaScript traps, not exotic ones.

BugWhat it actually didFix
Math.floor(Math.random()) Math.random() always returns a value in [0, 1) — never reaching 1. Math.floor() of anything in that range is always 0. Every single "random" draw was identical: zero. That would have made every request land in whichever region owns the [0, x) slice starting at zero — US, unconditionally, every time. Drop the Math.floor — use the raw float from Math.random() directly.
for (const region in REGIONS) for...in over an array yields the indices as strings ("0", "1", "2", "3"), not the array's actual elements. So region was the string "0", not {region: "US", value: 0.7} — and region.value was undefined, which would have poisoned the running total with NaN. Use for...of, which iterates over an array's actual elements.
Why this mattered
Neither bug would have thrown an error. The script would have run to completion, printed a normal-looking k6 summary, and quietly produced a meaningless or 100%-US distribution — the exact kind of silent failure that makes "trust but verify" essential before drawing conclusions from a load test.

3. Proving the weights actually worked

Writing the weighting logic correctly is one thing; trusting that it worked under real load is another. A k6 Counter metric, tagged per region, was added to measure the actual distribution rather than assume it:

import { Counter } from "k6/metrics"; const counterPerRegion = new Counter("region_counter"); // ...inside the region-selection loop, right where a region is chosen: counterPerRegion.add(1, { region: region.region });

There was one more wrinkle: k6's default terminal summary doesn't automatically break a tagged custom metric down by tag value — it just shows one aggregate total. The workaround is to add a deliberately unfailable threshold for each region's submetric, whose only job is to force k6 to print that submetric's line:

thresholds: { http_req_duration: ["p(99)<200"], "region_counter{region:US}": ["count>=0"], "region_counter{region:EU}": ["count>=0"], "region_counter{region:APAC}": ["count>=0"], "region_counter{region:LATAM}": ["count>=0"], },

EXPLAIN ANALYZE on the hot-key query at 50M rows still showed an Index Scan Backward on article_pkey with execution time of roughly 0.086 milliseconds — the query didn't get more expensive with fifty times more data, and it didn't get more expensive when hammered on one region. Both results point the same direction: the CPU-bound framework overhead identified in the earlier phase is still the ceiling, and neither more data nor skewed access changes that.

What's next
Redis stays deprioritized — correctly, and now backed by a measurement rather than a hunch. If a cache is revisited later, it'll need to be justified by a genuinely expensive per-request cost (a complex ranking query, a slow downstream call, or a dataset too large to fit in Postgres's buffer pool) — conditions this endpoint doesn't currently meet.
