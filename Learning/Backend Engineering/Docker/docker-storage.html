Docker · Storage Model

Where does your container's data actually live?

Docker storage splits into two unrelated ideas people conflate: how the daemon stores image layers (storage drivers), and how your app's data survives past a container's death (volumes, binds, tmpfs). This is about the second one.

The problem

By default, everything a container writes dies with the container. Every file created inside runs against a thin writable layer sitting on top of the read-only image layers. Delete the container → delete the layer → data gone. There's no clean way to reach into that layer from the host or another container.

How the layers stack

The five mount types

Volume

managed

Persistent storage the Docker daemon owns fully. Lives on the host filesystem but you never touch it directly — only through a mounted container.

Use it forPerformance-critical, long-term data: databases, uploaded files, anything that must survive container removal.

Bind mount

host path

A direct link between a specific host path and the container. Not isolated by Docker — the host and the container can edit the same files simultaneously.

Use it forLocal dev — mounting your source code so edits on the host show up live inside the container.

tmpfs mount

in-memory

Stored directly in host RAM. Never written to disk, and wiped when the container stops or the host reboots. Truly ephemeral.

Use it forSecrets, credentials, caches — anything sensitive or throwaway that shouldn't hit disk.

Image mount

read-only

Mounts the contents of another image into a path in your container, read-only. Requires the containerd image store.

Use it forPulling a debug toolset into a minimal container, or sharing read-only assets across images.

Named pipe

IPC

A communication channel between host and container — not really "storage" at all, but grouped here since it's another host↔container bridge.

Use it forConnecting a containerized tool to the Docker Engine API on the host.

Real-world scenarios

DB

Postgres in production — mount a volume at /var/lib/postgresql/data. Redeploy the container for an image update all you want; the data survives because it never lived in the writable layer.

DEV

Next.js hot reload — bind mount your project folder into /app. You edit in your editor on the host, the dev server inside the container picks up the change instantly.

SEC

Short-lived JWT signing key — tmpfs mount at /run/secrets. Never persisted to disk, wiped the moment the container stops — nothing left behind to leak.

DBG

Debugging a distroless image — image mount a busybox image into the minimal production container so you get a shell and coreutils without rebuilding the image itself.

Quick syntax

# volume — Docker manages the host location
docker run -d -v pgdata:/var/lib/postgresql/data postgres

# bind mount — you name the exact host path
docker run -d -v $(pwd):/app -p 3000:3000 my-next-app

# tmpfs — in-memory only, size-capped
docker run -d --tmpfs /run/secrets:rw,size=64m my-service
Interview / practical tip — if asked "how does Docker persist data?", the answer isn't "volumes" alone — it's volumes for daemon-managed persistent data, bind mounts for host-editable data, tmpfs for ephemeral/sensitive data. Naming all three and when each applies is the signal that you understand the model, not just the flag.
