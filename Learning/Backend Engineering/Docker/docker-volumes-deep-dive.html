Volumes, one level deeper

Follow-up to the storage overview — this is everything specific to volumes: named vs. anonymous, what happens when you mount over existing files, lifecycle with Compose, backup/restore, and read-only mounts.

Named vs. anonymous

Named volume

persists

You give it an explicit name (pgdata). Docker keeps it around forever — surviving container removal, docker-compose down, everything — until you explicitly docker volume rm it.

Example-v pgdata:/var/lib/postgresql/data

Anonymous volume

random name

No name given — Docker generates a random hash-like ID. Still persists after the container is removed unless the container was started with --rm, in which case it's cleaned up automatically.

Example-v /app/node_modules (no source before the colon)
Why this matters — the /app/node_modules trick from your compose file is an anonymous volume. It shadows the bind-mounted host folder so the container's own node_modules (built for its OS/arch) isn't overwritten by your host's copy.

What happens when you mount over existing data

No undo — there's no flag to "unmount and reveal" the obscured files. Your only way back is recreating the container without the mount. Use volume-nocopy if you specifically don't want the auto-copy-on-empty behavior.

--mount vs -v syntax

Need-v--mount
Basic named volume-v pgdata:/data--mount type=volume,src=pgdata,dst=/data
Read-only-v pgdata:/data:ro--mount ...,readonly
Volume driver optionsnot supported--mount ...,volume-opt=...
Mount a subdirectorynot supported--mount ...,volume-subpath=app1
Swarm service mountnot supportedrequired

--mount is the more explicit, more capable flag — Docker's own docs recommend it in general, and it's required once you need driver options, subpaths, or Swarm services.

Lifecycle with Compose

services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:  # declared here so compose tracks it
1st

docker compose up first time — volume doesn't exist, Compose creates it empty.

2nd+

docker compose up again — same volume is reused, data intact.

-v

docker compose down -v — this is the one that actually deletes the volume + your data.

Backup & restore pattern

Volumes aren't host paths, so you can't just cp them. The trick: spin up a throwaway container that mounts both the volume and a host backup folder, then run tar inside it.

# back up: tar the volume's contents to a host folder
docker run --rm --volumes-from dbstore -v $(pwd):/backup ubuntu \
  tar cvf /backup/backup.tar /dbdata

# restore: untar into a fresh volume
docker run --rm --volumes-from dbstore2 -v $(pwd):/backup ubuntu \
  bash -c "cd /dbdata && tar xvf /backup/backup.tar --strip 1"

Interview / practical tip — "volumes are managed by Docker, bind mounts are managed by you" is the one-line distinction, but the sharper follow-up is why volumes win for prod: no dependency on host directory structure/OS, safer multi-container sharing, and pluggable drivers (NFS, S3-backed, etc.) let you move storage off-box without touching application code.
