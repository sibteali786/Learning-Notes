Docker Compose · Environment Variables

Two different jobs wear the same ${VAR} syntax

The single biggest source of confusion here: interpolation (filling placeholders in your YAML file, on your host) and passing env vars into the container (what the app inside actually sees) are separate mechanisms that happen to look alike. This page keeps them apart.

Two mechanisms, two moments

1. Interpolation syntax

FormMeaning
${VAR} / $VARDirect substitution — braces optional but recommended
${VAR:-default}Use default if VAR is unset or empty
${VAR-default}Use default only if VAR is unset (empty string counts as set)
${VAR:?error msg}Exit with error if VAR is unset or empty
${VAR?error msg}Exit with error only if VAR is unset
${VAR:+replacement}Use replacement only if VAR is set and non-empty (inverse of default)

Applies to

Unquoted values and double-quoted values in compose.yaml and in .env files.

Does NOT apply to

Single-quoted values — those stay completely literal, no substitution happens inside '...'.

Precedence — who wins when the same var is set twice

1st
Shell environment variable — e.g. export TAG=2.4 before running compose
↓ overridden by nothing above ↓
2nd
--env-file CLI flag — explicit path passed to docker compose
↓
3rd
.env in project root — auto-loaded, lowest priority of the three
Verify before deploying — run docker compose config --environment to see exactly what Compose resolved, instead of guessing.

2. Getting vars into the container

environment:

inline

Defined directly in compose.yaml. Visible at a glance, good for a handful of values.

Two equivalent syntaxes mapping: DEBUG: "true"
list: - DEBUG=true

env_file:

external file

Points at one or more files of KEY=value lines. Keeps config out of the compose file, reusable across services.

Multiple filesEvaluated in order — later files override earlier ones for the same key.

CLI override

one-off

Set a variable for a single run without touching any file — good for a quick test.

Syntaxdocker compose run -e DEBUG=1 web ...
services:
  web:
    environment:
      - DEBUG=true
      - API_KEY  # no value = inherit from shell env
    env_file:
      - common.env
      - web.env        # overrides matching keys from common.env
      - path: optional.env
        required: false  # 2.24.0+ — don't error if file missing

File syntax rules (.env / env_file)

#

Lines starting with # are comments.

=

Key-value pairs use = or : as delimiter.

""

Double-quoted values support interpolation and escape sequences like \n, \t.

''

Single-quoted values are literal — no interpolation, no escapes.

Different from docker run — interpolation inside .env is a Compose CLI feature only. It is not supported by plain docker run --env-file.

Best practices

✕
Never put secrets in environment: or env_file:
Passwords, API keys, tokens — use Docker Secrets instead. Env vars are visible via docker inspect, process listings, and often get logged.
✓
Keep separate .env files per environment
dev / staging / prod — swap with --env-file rather than editing one shared file.
✓
Know your precedence before debugging "wrong" values
Shell env → --env-file → project .env. A stray export in your shell silently wins over the file.
✓
Verify resolved config before deploying
docker compose config --environment shows what actually got substituted.
✓
Use env_file: for reuse, environment: for visibility
A handful of service-specific flags → inline. Shared config across services → external file.
Interview / practical tip — the trap question is "how do I pass a variable into my container?" — the honest answer is it depends which of the two mechanisms you mean. If the interviewer says "the app can't see my env var," the real bug 9 times out of 10 is confusing YAML-level interpolation (host-side, build-time) with environment:/env_file: (container-side, runtime).
