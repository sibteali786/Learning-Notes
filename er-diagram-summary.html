① What Is an E-R Diagram?

Definition

Graphical representation of entities (tables) and their relationships. Describes data structure, not data itself — a table with 10M rows is still one box.

Components

Boxes = entities (tables)
Lines = relationships
Crow's Foot symbols = cardinality (how many)

Notation Used

Information Engineering / Crow's Foot notation. Industry standard for relational DB design. Other types: Chen, UML, IDEF1X.

Purpose

Not just visual — it's a contract between designers, developers, and stakeholders. Errors caught here cost 10× less to fix than in code.

⑦ Real-World Analogies

Many-to-Many → Bridge Table

Amazon: 1 order can have 10 products; 1 product can appear in 1M orders. The order_item table bridges them — just like purchase_product here.

Stakeholder Discovery

Like the payment_method→purchase link, Uber Eats discovered during review that every order needs a linked wallet/card — added after initial draft, before a single line of SQL was written.

1:M — User & Payment Methods

Netflix: you can save multiple cards but each card belongs to only your account. One user → many payment methods.

E-R as a Contract

WhatsNextPlease: defining the task↔user↔tenant schema upfront prevents FK constraint bugs in Prisma migrations mid-sprint.

⑧ Interview / Practical Tips
🎯Always start with plain English sentences (Subject → Verb → Object) before drawing any lines.
🔗Many-to-many relationships always need a bridge/junction table in relational DBs (e.g., purchase_product).
🧪Test every relationship with sample data — if you can't find a row that violates the rule, the cardinality is likely correct.
👥Stakeholder walk-throughs are mandatory — they'll always catch something (like the billing→purchase link).
🗃️Skip attributes in draft diagrams. Only add them once entity relationships are confirmed — it reduces noise during iteration.
⚠️Crow's Foot notation reads both directions: "A user can make zero or many purchases; a purchase is made by one and only one user."
